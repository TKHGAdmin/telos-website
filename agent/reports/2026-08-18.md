## P1 — Homepage "About" section ships ~2.4 MB of unoptimized, eager-loaded imagery

### Files

- `index.html:252` — `<img src="images/thomas.jpeg" ...>`
- `index.html:258` — `<img src="images/thomas-speaking-wide.jpeg" ...>`
- `index.html:261` — `<img src="images/thomas-speaking-close.jpeg" ...>`
- `chs.html:946`, `chs.html:950`, `chs.html:953` — same three images, same pattern
- `images/thomas.jpeg` — **1,897,318 bytes (1.9 MB)**, 1206×2136 JPEG
- `images/thomas-speaking-wide.jpeg` — 251,297 bytes (245 KB), 712×1104
- `images/thomas-speaking-close.jpeg` — 215,899 bytes (211 KB), 725×1086

### Evidence

```
$ du -h images/thomas.jpeg images/thomas-speaking-close.jpeg images/thomas-speaking-wide.jpeg
1.9M    images/thomas.jpeg
212K    images/thomas-speaking-close.jpeg
248K    images/thomas-speaking-wide.jpeg
```

- All three live inside the `#about` section, which sits well below the fold on both `index.html` (about section starts at line 245) and `chs.html`.
- **None** have `loading="lazy"`, so the browser fetches all three during initial page load, blocking the network for above-the-fold content and eating LCP budget on slow connections.
- **None** have `width`/`height` attributes, so the layout reflows when they arrive — a CLS hit on every visit.
- `thomas.jpeg` in particular is 1206×2136 (portrait). Its CSS render slot in `.about-photo` is at most ~600 px wide on desktop and ~350 px on mobile, so the browser downloads roughly **4× more pixels than it displays** on desktop and **~12× more on mobile**. A properly sized JPEG in that slot would be ~150–250 KB.

Grep confirmation that lazy-loading is essentially absent from marketing pages:

```
$ grep -c 'loading="lazy"' *.html
client-dashboard.html:1   # (dynamic module thumbnail, injected by JS)
```

Not a single `<img>` on `index.html`, `chs.html`, `pricing.html`, `resources.html`, `shop.html`, or `product.html` uses `loading="lazy"`.

### User impact

- Every homepage and every Charleston landing page visit pays for ~2.4 MB of imagery that is not needed for first render. On a typical 4G connection (~5 Mbps effective), that is 4+ seconds of extra transfer before the browser is done fetching non-critical content, which competes with critical requests.
- The Charleston page (`chs.html`) is application-gated and a primary paid conversion path. Any delay directly costs applications.
- CLS on the About section will affect Lighthouse / Core Web Vitals scoring, which Google now surfaces in mobile search.

### Repro

1. `npx serve -l 3000 .`
2. Open Chrome DevTools → Network tab → throttle to "Fast 3G".
3. Load `http://localhost:3000/`. Observe `thomas.jpeg` (1.9 MB) fetched during initial load even though the About section is off-screen.
4. Load `http://localhost:3000/chs`. Same behavior.

### Recommendation (author will implement — do not modify code from this agent)

- Add `loading="lazy" decoding="async" width="<intrinsic>" height="<intrinsic>"` to all three `<img>` tags on both `index.html` and `chs.html`.
- Re-export `thomas.jpeg` at ~800 px on the long edge, quality 80 — should land near 120–180 KB. Consider a `.webp` sibling and use `<picture>` if easy.
- The two `thomas-speaking-*.jpeg` files are already reasonable sizes but still benefit from lazy-loading + intrinsic dimensions.

### Confidence

High. Sizes, dimensions, absence of `loading=` attribute, and location below the fold are all verifiable from the repo — no live-site probing needed. No stylistic judgment involved.
