## Bugs

### [P1] Weekly summary email shows streak = 0 for every active client every Monday

**File**: `api/cron/weekly-summary.js:86-90`

**What**: The cron schedule is `0 14 * * 1` (Monday 14:00 UTC = 9:00 AM ET). The streak counter walks back from `d=0` (today, i.e. Monday itself):

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

At 9 AM ET on Monday, almost no client has logged their daily check-in for Monday yet, so `weekData[0][0].result` is null → `break` on the first iteration → streak = 0.

Result: every active client with `portalEnabled` and `emailEnabled !== false` receives a "Your Weekly Telos Recap" email with `Current Streak: 0 days` regardless of actual behavior. A client who logged Sun, Sat, Fri, Thu, Wed, Tue still sees "0 days".

**Repro**: Trigger the cron manually with a curl POST including `Authorization: Bearer $CRON_SECRET` before any of the active clients logs in for the current Monday. Inspect the rendered HTML for any client - `Current Streak` line shows `0 days`.

**Suggested fix**: Start the streak walk at `d = 1` (yesterday) and treat today as a "do not penalize" day. Alternatively, only break on a *gap* after the first non-empty hit:

```js
var startedCounting = false;
for (var d = 0; d < 7; d++) {
  var has = weekData[0][d] && weekData[0][d].result;
  if (!startedCounting && !has) continue;   // ignore leading empties (today)
  if (has) { streak++; startedCounting = true; }
  else break;
}
```

**Why this matters**: This is the public-facing weekly engagement touchpoint. Sending an inaccurate "0 day streak" misrepresents the client's behavior and undermines the email's purpose (positive reinforcement).

### [P2] Engagement-check cron sends daily reminder emails with no per-client cooldown

**File**: `api/cron/engagement-check.js:60-94`

**What**: Cron runs daily at 15:00 UTC. For any client whose most-recent daily log is 3+ days old (or absent in the last 5 days), it unconditionally sends a "We miss you at Telos" email. No state is recorded for "already nagged today / this week", so:

- Client inactive 3 days → email day 3.
- Client inactive 4 days → email day 4 (second consecutive day).
- Client inactive 5+ days → email day 5 (third consecutive day, then capped at "5+").

A client who goes on a 2-week vacation receives ~12 identical reminder emails in a row. This is borderline-spam, harmful to deliverability (Resend reputation, future cron emails going to spam folder), and likely to trigger unsubscribes.

**Repro**: With at least one active client that has not logged in 3+ days, manually invoke the cron 3 days in a row. The same client receives an email each day.

**Suggested fix**: Before sending, set a Redis key like `engagement_emailed:{clientId}:{YYYY-MM-DD}` with a 6-day TTL, and skip if any such key has been set in the last 5 days. Alternative: only send on `lastLogDaysAgo === 3` (first crossing), not every subsequent day.

**Why this matters**: Whether this is "intentional" or not, the current behavior almost certainly conflicts with what a coach would expect ("one reminder, not five"), and it's a sender-reputation risk.

### [P2] Login endpoints have no rate limiting - admin password and client passwords brute-forceable

**File**: `api/dashboard/login.js` and `api/client/login.js`

**What**: Public form endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) implement IP-based rate limiting (`ratelimit:*` Redis keys, `INCR` + `EXPIRE`). The two login endpoints implement none. An attacker can submit unlimited POSTs to either login endpoint.

Admin login is the higher-risk surface: a single `DASHBOARD_PASSWORD` env var protects the entire `/thomas` dashboard (full lead/client/revenue data). The `verifyPassword` helper is timing-safe for the comparison but bails early on length mismatch, so password *length* is observable - that further narrows the brute-force search space.

Client login is lower risk per-account (PBKDF2-100k slows offline attacks if a hash leaked, and online attacks would have to enumerate emails too) but still allows credential-stuffing at scale.

**Repro**: `for i in $(seq 1 10000); do curl -X POST https://www.telosathleticclub.com/api/dashboard/login -H 'Content-Type: application/json' -d "{\"password\":\"guess_$i\"}"; done` - all 10,000 receive 401 (or 200 if guessed). No 429.

**Suggested fix**: Mirror the existing form-submission pattern - per-IP `ratelimit:login_admin:{ip}` with `EXPIRE 3600` and cutoff at ~10/hr. Optionally also a per-account counter for client login (`ratelimit:login_client:{email}`). Today's focus is Functional - flagging here because failed-login flood is also a functional denial-of-service risk for legitimate users via Redis credit burn, not just a security item.

**Note**: Today's focus is Functional, not Security. This finding lives at the boundary - I'm including it because the same code path (the rate-limit primitive) is already implemented for every other public POST handler, so it reads as an oversight on the login endpoints rather than a deliberate security tradeoff. If the user prefers to defer security-flavored findings to the Security focus day, deny this one and the agent will re-evaluate scope.
