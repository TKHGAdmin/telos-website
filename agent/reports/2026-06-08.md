# Telos Bug Hunt — 2026-06-08

**Focus:** Functional
**Findings:** 3
**Run notes:** First run. Bootstrapped agent memory + schema. All 3 findings concentrated in the new shop/product flow and asset cache versioning.

---

## Summary

Three small but real defects, all introduced by recent commits. The most notable is a cache-version mismatch on `shop.js` between `shop.html` (`?v=1`) and `product.html` (`?v=2`), which means returning visitors can serve a stale build of the shop grid even after the product detail update shipped. `product.html` is also missing canonical / Open Graph / Schema.org metadata, so every product shares one generic preview when shared on social. Finally, `chs.html` loads `main.js` with no cache-busting query at all while every other page uses `?v=2`.

None are P0 / P1. Two are P2 (worth fixing this week), one is P3.

---

## Findings

### Finding TLS-20260608-01: P2 — `shop.js` cache version mismatch between `shop.html` (v=1) and `product.html` (v=2)

- **Location:** `shop.html:841`, `product.html:822`
- **Confidence:** high
- **Category:** functional

**Description**

The two pages that load `js/shop.js` reference different cache-busting versions. `product.html` was bumped to `?v=2` in the recent "image gallery with thumbnails" commit (`f5cb8c4`), but `shop.html` is still pinned at `?v=1`. Because the browser keys its cache by full URL including the query string, a returning visitor who already cached `js/shop.js?v=1` will keep receiving the old script on the shop grid, while getting the fresh script on the product detail page. The two pages then execute different builds of the same file in the same session.

In this specific commit the user-visible impact is limited (the new thumbnail-gallery code only runs on the product page via `loadProductDetail()`), but the rule the codebase relies on - "bump `?v=N` on every page when the file changes" - is broken, so the next change to `shop.js` will silently regress for cached shop-page visitors.

**Reproduction / Evidence**

```bash
$ grep -n "shop.js" *.html
product.html:822:  <script src="js/shop.js?v=2"></script>
shop.html:841:    <script src="js/shop.js?v=1"></script>
```

CLAUDE.md "Important Conventions" explicitly calls this out: *"CSS cache busting: Stylesheet references use `?v=N` query param. Bump the version on all pages when changing style.css."* The same convention applies to script tags.

**Suggested fix**

In `shop.html` line 841, change `js/shop.js?v=1` to `js/shop.js?v=2`. Going forward, when bumping `shop.js`, grep all files that reference it (`grep -rn 'shop.js' *.html`) and bump in lockstep.

### Finding TLS-20260608-02: P2 — `product.html` is missing canonical URL, Open Graph tags, and Schema.org markup

- **Location:** `product.html:1-20` (the `<head>` block)
- **Confidence:** high
- **Category:** seo

**Description**

Every product detail page is served from the single `product.html` file with the handle in the query string (e.g. `/product?p=hyrox-guide`). The page's `<head>` only declares `<title>Product - Telos Athletic Club</title>` and a generic `meta name="description"`. It has none of:

- `<link rel="canonical">`
- `<meta property="og:title|description|url|image|type">`
- `<meta name="twitter:card">`
- Schema.org `Product` JSON-LD

Compare with `shop.html` (lines 9-42), which has all of the above for the storefront.

Consequences:

1. **Social sharing is broken.** When anyone shares a product URL on iMessage, Slack, Twitter, Facebook, or LinkedIn, the link preview reads "Product - Telos Athletic Club" with no product name, price, or image. This is the first impression for every paid social campaign that drives traffic to a specific product.
2. **SEO duplicate-content risk.** Without a canonical, search engines may treat `/product?p=a` and `/product?p=b` as the same page or arbitrarily merge them. The title is also identical for every product when the JS title rewrite doesn't run for the crawler.
3. **No structured-data eligibility** for Google product rich results (price, availability, ratings in SERP).

The JS does update `document.title` at line 158 of `shop.js`, but social scrapers (Facebook, LinkedIn, iMessage) and many crawlers do not execute JS, and even those that do read the static head first.

**Reproduction / Evidence**

```bash
$ grep -n "canonical\|og:url\|og:title" product.html
# (no output - none present)
```

vs. `shop.html` head block (lines 9-42) which has `og:title`, `og:description`, `og:type`, `og:url`, canonical link, and Schema.org `Store`.

**Suggested fix**

Add a placeholder set of meta tags in `product.html` head that the existing `loadProductDetail()` in `shop.js` then populates dynamically. Minimal static defaults plus JS hydration:

```html
<link rel="canonical" id="canonicalLink" href="https://www.telosathleticclub.com/shop">
<meta property="og:type" content="product">
<meta property="og:title" id="ogTitle" content="Telos Athletic Club">
<meta property="og:description" id="ogDescription" content="Premium training guides and performance resources.">
<meta property="og:url" id="ogUrl" content="https://www.telosathleticclub.com/shop">
<meta property="og:image" id="ogImage" content="">
<meta name="twitter:card" content="summary_large_image">
```

Then in `shop.js`'s `loadProductDetail()` after `document.title = ...`, update each tag's `content` (or `href` for the canonical) with the product's title, description, handle URL, and first image. Static crawlers still see *something* better than "Product"; client-rendered crawlers (and the title-tag rewrite for browsers) get the full thing.

For Schema.org, append a `<script type="application/ld+json">` block with a `Product` schema once the Shopify response is in.

### Finding TLS-20260608-03: P3 — `chs.html` loads `js/main.js` with no cache-busting query

- **Location:** `chs.html:1050`
- **Confidence:** high
- **Category:** tech-debt

**Description**

Every other public page loads `main.js` as `js/main.js?v=2`. `chs.html` loads it as plain `js/main.js`. That means:

- Returning visitors who previously cached `js/main.js` from `chs.html` will keep serving that cached copy indefinitely, even after the site bumps `main.js` to `v=3` everywhere else.
- The page is currently functional (the cached copy still runs the nav/hamburger/scroll code), so this is dormant tech debt rather than a live bug - but the next change to `main.js` will leak through for repeat visitors of `chs.html` while every other page picks it up immediately.

`chs.html` was added in commit `3d87367` after the site had already standardized on `?v=2`, so this looks like a one-line oversight in that PR.

**Reproduction / Evidence**

```bash
$ grep -n "main.js" *.html
chs.html:1050:                <script src="js/main.js"></script>
index.html:844:               <script src="js/main.js?v=2"></script>
pricing.html:894:             <script src="js/main.js?v=2"></script>
product.html:820:             <script src="js/main.js?v=2"></script>
resources.html:610:           <script src="js/main.js?v=2"></script>
shop.html:837:                <script src="js/main.js?v=2"></script>
```

(Note: `hyrox-predictor.html` and `protein-calculator.html` are absent from this list because they don't load `main.js` at all - that's a separate, already-tracked backlog item per CLAUDE.md.)

**Suggested fix**

Change `chs.html:1050` from `<script src="js/main.js"></script>` to `<script src="js/main.js?v=2"></script>` so it stays in lockstep with every other public page on the next bump.
