## Details

### BUG-2026-07-31-01 — P1 — Quiz submits empty, unlocks pricing gate

- **Where:** `js/quiz.js:225-275`, `index.html:580`, `pricing.html` (same `type="button"` for `.quiz-see-score-btn`)
- **Repro:**
  1. Visit `/pricing`, take the 8-question quiz.
  2. On the lead-capture screen, leave name/email blank.
  3. Click "See Your Score".
  4. Results render, `localStorage.telosQuizCompleted = "true"` is set, and on next visit the pricing content is unlocked. Backend POST 400s, silently discarded.
- **Root cause:** The button is `type="button"` (line 580 in `index.html`) — the browser's native `required` validation never runs. `quiz.js:226` calls `e.preventDefault()` immediately and reads `nameInput.value` without any null/length check.
- **Impact:** Pricing gate defeats itself, and the lead is never captured. Both the "get the lead" and "gate the price" product goals fail simultaneously.
- **Fix sketch:** Either change to `type="submit"` and let the form fire `submit`, or guard in JS: `if (!nameInput.value.trim() || !emailInput.value.includes('@')) { show inline error; return; }` before setting localStorage.

### BUG-2026-07-31-02 — P1 — Retake stacks duplicate submit handlers

- **Where:** `js/quiz.js:225` (`submitBtn.addEventListener`) and `js/quiz.js:415-442` (`resetQuiz`)
- **Repro:**
  1. Take quiz, submit lead capture (1 POST, 1 localStorage write).
  2. Click "Retake Assessment".
  3. Take quiz again, submit. Now the click handler fires twice → 2 POSTs, 2 localStorage writes.
  4. After N retakes: N+1 POSTs per click. Trivially burns the 10/hr IP rate limit set in `api/submit-quiz.js:26-32`.
- **Root cause:** `setupLeadCapture()` is called every time the lead-capture screen shows (`quiz.js:215`), and it unconditionally `addEventListener`s on the same button node. `resetQuiz()` only calls `form.reset()`, never removes listeners.
- **Impact:** Duplicate submissions inflate the `quiz_submissions` ZSET; a single user can trigger the 10/hr rate limit for their own IP and get locked out of future legitimate submits. Also mis-inflates analytics.
- **Fix sketch:** Move the listener attachment out of `setupLeadCapture()` and bind once at DOMContentLoaded, OR clone the button before re-binding, OR track a `boundListener` flag.

### BUG-2026-07-31-03 — P1 — Silent fetch swallows every backend error

- **Where:** `js/quiz.js:258-269`
- **Repro:**
  1. Trigger any error from `api/submit-quiz.js` — easiest: submit 11 times from same IP (429), or block network in DevTools.
  2. User sees the exact same "your score" screen as a successful submit.
  3. `localStorage.telosQuizCompleted = "true"` still set. The lead is never captured; the user has no way to know.
- **Root cause:** `fetch(...).catch(function(){})` swallows network errors and never inspects `res.ok`. Combined with `localStorage.setItem(...)` happening BEFORE the POST, success state is committed unconditionally.
- **Impact:** Systemic silent lead loss. Every rate-limit hit, every 5xx, every offline user disappears without a trace. This is the biggest "leaky funnel" defect in the codebase.
- **Fix sketch:** `await` the fetch, check `res.ok`, and gate the localStorage + results render on success. Show a retry state on failure.

### BUG-2026-07-31-04 — P2 — Disabled clients keep access for up to 7 days

- **Where:** `api/client/me.js`, and every other file in `api/client/*` — only `login.js:36-41` checks `portalEnabled` / `status`.
- **Repro:**
  1. Client logs in successfully; browser holds `telos_client_session` cookie (7-day TTL, `client-auth.js:6`).
  2. Coach disables the portal (`client-portal.js` POST with `enabled:false`) or sets client `status: 'inactive'`.
  3. Client can still call `/api/client/daily-log`, `/api/client/nutrition-log`, etc. for up to 7 days until the cookie naturally expires. There is no server-side revocation store.
- **Impact:** A churned/refunded client keeps writing to their portal for a week. Data-integrity risk (stale logs) and support risk ("why can this account still log in?").
- **Fix sketch:** In `verifyClientSession`, re-fetch `client:{id}` and hard-fail if `!portalEnabled` or `status !== 'active'`. Or bump the cookie TTL down and add a `client_session_rev:{clientId}` counter that's checked on every request.

### BUG-2026-07-31-05 — P2 — Weekly summary streak is always 0

- **Where:** `api/cron/weekly-summary.js:86-90`
- **Repro:**
  1. Cron fires Monday 14:00 UTC (09:00 ET).
  2. Loop starts at `d = 0` (today, Monday) — `weekData[0][0]` is Monday morning's daily log, which for essentially every client is missing at 9am ET.
  3. `else break;` fires immediately → `streak = 0`.
  4. Every email says "Current Streak: 0" regardless of the client's actual behavior last week.
- **Impact:** The Monday recap's core motivational metric is broken for every recipient — undermines the whole email.
- **Fix sketch:** Start the loop at `d = 1` (yesterday) so today's absence doesn't zero the streak, OR only break if two consecutive days are missing.

### BUG-2026-07-31-06 — P2 — Client DELETE leaves orphans, breaks re-create with same email

- **Where:** `api/dashboard/clients.js:143-153`
- **Repro:**
  1. Create client with email `x@y.com` — writes `client:{id}`, `clients_index`, `client_email:x@y.com`.
  2. Delete that client via admin. `client:{id}` + `clients_index` removed; `client_email:x@y.com` and all `client_nutrition_plan:*`, `client_mindset:*`, `client_training_program:*`, `client_sidemenu:*`, `client_supplement_plan:*`, and all daily/training/nutrition/545 logs remain.
  3. Try to create a new client with `x@y.com` → uniqueness check at line 71 fails, admin gets an error even though from their UI the old client no longer exists.
- **Impact:** Admin cannot reonboard clients who churned and returned without manual Redis cleanup. Also leaks the ex-client's data indefinitely.
- **Fix sketch:** On DELETE, also `DEL client_email:{normalizedEmail}` and either `DEL` the per-client side-tables or `SCAN` and clean up prefixes.

### BUG-2026-07-31-07 — P2 — Push subscription single-key kills multi-device notifications

- **Where:** `api/client/push-subscribe.js:21` — uses fixed key `client_push_sub:{clientId}`.
- **Repro:**
  1. Client enables push on iPhone Safari — endpoint A stored.
  2. Client enables push on desktop Chrome — endpoint B overwrites endpoint A.
  3. Any subsequent notification sent to that client only hits desktop. Also every browser endpoint rotation silently drops the prior device.
- **Impact:** Silent notification loss on all-but-latest device. Users think push is broken; there's no UI signal.
- **Fix sketch:** Store as a hash keyed by endpoint URL hash, e.g. `client_push_subs:{clientId}` as a Redis hash of `{endpointHash: subJson}`. On send, iterate all entries.

### BUG-2026-07-31-08 — P2 — Double-tap during quiz auto-advance crashes results

- **Where:** `js/quiz.js:197-218` (no button disable during `setTimeout(..., 400)`) + `quiz.js:284-286` (`getResultTier` returns `undefined` for score > 40) + `quiz.js:325` (`tierName.textContent = tier.name` throws when `tier` is undefined).
- **Repro:**
  1. On a question, tap one option, then immediately tap a second option before the 400ms fade-out fires.
  2. Both click handlers run — `quiz.scores[pillar] += option.points` twice per question.
  3. Over 8 questions, total can exceed 40. `getResultTier(41)` returns `undefined`.
  4. `renderResults()` throws `TypeError: Cannot read properties of undefined (reading 'name')` — results page half-renders (score ring populated, tier/description blank, pillar bars never animate, retake button never bound).
- **Impact:** Frozen results screen on mobile-users who mistap. No way forward without reload. Also invalidates the lead's score in the DB (`totalScore > 40` is nonsensical).
- **Fix sketch:** In `handleAnswerSelect`, set `pointerEvents: 'none'` on `.quiz-options` immediately, or clear/disable siblings.

### BUG-2026-07-31-09 — P3 — Cron `sent++` inflates delivery success counts

- **Where:** `api/cron/weekly-summary.js:97-114`, `api/cron/engagement-check.js:76-90` (same pattern), and `api/client/send-email.js:80-94`.
- **Repro:** Any Resend 4xx (e.g. invalid recipient, missing domain verification) responds successfully to `fetch()` — the `try` block does not throw. `sent++` runs anyway. Only network failures increment the catch counter.
- **Impact:** Cron log line `{ ok: true, sent: N }` overstates delivery. Admin has no way to know the real send rate without checking Resend dashboard directly.
- **Fix sketch:** `if (resp.ok) sent++; else console.error('resend failed', await resp.text());`

### BUG-2026-07-31-10 — P3 — Hyrox weight `min` doesn't switch on unit change

- **Where:** `hyrox-predictor.html:540-541` — weight input `min="80" max="400"`, unit dropdown offers `lbs`/`kg` but the numeric bounds stay in lbs.
- **Repro:** Select `kg`, enter `60` (a 132 lb athlete) → HTML5 validator blocks submit with "Value must be 80 or more."
- **Impact:** Metric-unit users under ~180 lb can't use the predictor at all.
- **Fix sketch:** On unit change, JS-set `min`/`max` to `{lbs: [80,400], kg: [36,180]}`.

### BUG-2026-07-31-11 — P3 — Password reset token single-use is not atomic

- **Where:** `api/client/reset-password.js:76-93`
- **Repro:** Race two POSTs against the same reset token within ~100ms (PBKDF2 hash window). Both `GET password_reset:{token}` return the same clientId, both hash their password, both `SET`, then both `DEL` the token. The "single use" property is broken for that window.
- **Impact:** In practice: mostly benign (last write wins, both writes are for the same client). Theoretical: if a token were intercepted, both attacker and legitimate client could set passwords in the same window; whoever loses the race is locked out until the next reset. Real risk is low, but the guarantee is worth having.
- **Fix sketch:** Use `GETDEL` (Upstash supports it) or a small Lua script to atomically consume the token before any hashing.
