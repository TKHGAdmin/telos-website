## BUG-2026-10-25-01 — Client dashboard writes daily logs under UTC date, not local date

- **Severity**: P1
- **Area**: Client dashboard (daily check-in, 545 Method, nutrition,
  training, supplements, activity logging)
- **File**: `client-dashboard.html:1840`
- **Status**: Still unresolved (previously noted in `CLAUDE.md:241` as
  part of the April 2026 bug-crawl P1-P3 backlog; no prior agent report
  exists because this is the first run)

### What's wrong

```js
function todayStr() {
  return new Date().toISOString().split('T')[0];
}
```

`toISOString()` returns the UTC date. Every daily-indexed feature in the
client dashboard keys its Redis read/write off this value:

- Daily check-in logs — `client_dailylog:{id}:{todayStr()}`
- Nutrition logs — `client_nutrition_log:{id}:{todayStr()}`
- 545 daily tasks + routine — `client_545_daily:{id}:{todayStr()}`
- Training logs — `client_training_log:{id}:{todayStr()}`
- Supplement completion — `client_supplement_log:{id}:{todayStr()}`
- Activity logs — `client_activity_log:{id}:{todayStr()}`

Call sites verified via `grep todayStr\\(`: 30+ in
`client-dashboard.html`, including state init (1794-1800), log save bodies
(2513, 2589, 3029, 3156, 3502, 3682), home-tab "today" checks (2784, 2939,
4033), and GET-request date query strings (2294, 3743-3749).

### Failure scenario

- Target user: Thomas / Charleston clients (EST/EDT, UTC-5 or UTC-4).
- At 7:30 PM local time on Saturday Oct 25, a client taps "Complete
  check-in" in the Home tab.
- Browser local time: Sat Oct 25 19:30 EDT. UTC: Sat Oct 25 23:30.
- `todayStr()` → `"2026-10-25"` ✓ correct.

- Second scenario (**the breaking one**): at 9:00 PM local Saturday Oct 25:
- UTC: Sun Oct 26 01:00. `todayStr()` → `"2026-10-26"`.
- The log is written to `client_dailylog:{id}:2026-10-26`.
- On Sunday morning when the client opens the app:
  - UTC: Sun Oct 26 13:00. `todayStr()` → `"2026-10-26"`.
  - The Home tab fetches the "today" log, finds Saturday-night's entry,
    and shows the day as **already completed**.
  - If the client submits a real Sunday check-in, it overwrites Saturday's
    data (the key collides).

Same mechanism breaks the 7-day streak heatmap (3-hour window per night
where "today" is wrong), the "last trained X days ago" display, and the
weekly-summary email (crons use the local date in `api/cron/*`, but the
client-written data is keyed to UTC, so the server queries can miss or
double-count logs).

### Fix sketch (for context, not to apply)

Replace with a local-date formatter:

```js
function todayStr() {
  var d = new Date();
  var y = d.getFullYear();
  var m = String(d.getMonth() + 1).padStart(2, '0');
  var dd = String(d.getDate()).padStart(2, '0');
  return y + '-' + m + '-' + dd;
}
```

That matches the pattern already used elsewhere in the file for display
(`formatDate` uses `T12:00:00` to pin to local noon). The write key must
match the display key, otherwise the Home tab, history view, and heatmap
disagree with the server-side crons.

Shipped data under UTC keys will not auto-migrate; a one-shot migration
script that scans `client_dailylogs_index:{id}` ZSETs and rewrites keys
dated inside the UTC-shift window may be worth doing after the client fix
lands.

### Confidence

**High.** Code is read directly; the UTC behavior of `toISOString()` is
specified; the key-collision scenario reproduces trivially by running
`node -e "d=new Date('2026-10-25T23:30:00-04:00'); console.log(d.toISOString().split('T')[0])"`
(returns `2026-10-26`). CLAUDE.md itself flags this as known-unresolved.
