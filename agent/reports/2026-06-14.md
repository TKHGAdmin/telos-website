### BUG-2026-06-14-01 | P1 | Rate limits on all public POST endpoints are bypassable via spoofed X-Forwarded-For

**Where:** api/submit-quiz.js:23, api/submit-email.js:28, api/submit-chs-application.js:40
**Repro:**
- Send `POST /api/submit-quiz` with header `X-Forwarded-For: 1.1.1.1` and a valid body. Observe rate-limit bucket key becomes `ratelimit:quiz:1.1.1.1`.
- Repeat the request 11 times rotating the `X-Forwarded-For` value each time (`1.1.1.1`, `1.1.1.2`, ...). Each request lands in a new bucket and none are blocked.
- Same pattern reproduces on `/api/submit-email` (10/hr cap) and `/api/submit-chs-application` (5/hr cap).

**What's wrong:** All three handlers do `const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown'` and use the resulting string verbatim as the rate-limit key. `X-Forwarded-For` is client-supplied and Vercel appends to it rather than overwrites, so the leftmost value is attacker-controlled. The fallback `x-real-ip` (which Vercel sets to the actual peer IP and clients cannot spoof) is only consulted when XFF is empty, which it never is in production. Net effect: an attacker can flood the Resend/Redis-backed lead funnel and CHS application table without ever hitting the cap.

**Suggested fix:** Trust `x-real-ip` first, or parse the rightmost comma-separated value of XFF (the IP Vercel observed). E.g.
```js
function clientIp(req) {
  const xff = (req.headers['x-forwarded-for'] || '').split(',').map(s => s.trim()).filter(Boolean);
  return req.headers['x-real-ip'] || xff[xff.length - 1] || 'unknown';
}
```
Apply to all three submit endpoints (and reuse in `chs-application` so the persisted `ip` field on each application is also the trustworthy value).

### BUG-2026-06-14-02 | P2 | Deleting a portal-enabled client orphans the email-to-id lookup and blocks re-use of that email

**Where:** api/dashboard/clients.js:143-154
**Repro:**
- In `/thomas` create client X with email `foo@example.com`, enable portal access (writes `client_email:foo@example.com -> {id}` via client-portal POST).
- Delete client X from the Clients tab. DELETE handler runs `DEL client:{id}` and `ZREM clients_index {id}` but does not touch `client_email:foo@example.com`.
- Attempt to create a new client with email `foo@example.com`. clients.js:70 finds the stale lookup and returns 400 "Email already in use by another client", even though no live client owns it.
- Bonus side effect: until the orphan key is manually deleted in Redis, a stale password-reset link (issued before the deletion) could still resolve `password_reset:{token} -> {oldClientId}`, though login is correctly blocked by the missing `client:{id}` GET.

**What's wrong:** The DELETE handler removes the primary `client:{id}` record and the `clients_index` membership but never cleans the `client_email:{normalizedEmail}` lookup that client-portal.js writes when portal is enabled. The duplicate-email check on POST/PUT then fires against a tombstone, blocking legitimate re-creation.

**Suggested fix:** Read the client record before deletion, normalize the email, and `DEL client_email:{normalizedEmail}` if portal was ever enabled. Same pattern already lives at client-portal.js:121-123 - factor it out or inline:
```js
var raw = await redis('GET', 'client:' + id);
if (raw) {
  var existing = JSON.parse(raw);
  if (existing.email) {
    var { normalizeEmail } = require('../lib/client-auth');
    await redis('DEL', 'client_email:' + normalizeEmail(existing.email));
  }
}
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

**Confidence:** high

### BUG-2026-06-14-03 | P2 | Weekly summary email reports "Current Streak: 0" for any client who hasn't checked in yet on Monday morning

**Where:** api/cron/weekly-summary.js:87-90
**Repro:**
- Set up a portal-enabled client and POST a daily log every day for the prior 30 days (skipping today).
- Trigger `api/cron/weekly-summary` with the proper `CRON_SECRET`. (Cron runs Monday 2pm UTC = 9am ET per CLAUDE.md.)
- Inspect the rendered email. `Current Streak` shows `0 days` regardless of the 30-day run, because today's log doesn't exist yet at cron time.

**What's wrong:** The streak loop iterates `d = 0..6` over `weekData[0]` (daily logs) starting at today and breaks at the first empty slot. Since the cron fires Monday 9am ET - before most clients have logged for the day - the very first check at `d=0` fails and `streak` stays at 0. A user with a real streak gets a demoralizing zero number in the recap, which directly undermines the point of the recap email (re-engagement).

**Suggested fix:** Allow today to be empty before counting:
```js
var start = (weekData[0][0] && weekData[0][0].result) ? 0 : 1;
for (var d = start; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```
Better long-term: count the streak from the persisted `client_dailylogs_index:{id}` ZSET so it isn't capped at 7 (currently the email can never display a streak longer than a week even though clients can reach much longer). The header literally says "Current Streak" - it should reflect the lifetime number, not just this calendar week.

**Confidence:** high

### BUG-2026-06-14-04 | P2 | Homepage header Instagram link points to a different (likely non-existent) account than every other page

**Where:** index.html:34
**Repro:**
- Open `index.html` in a browser. In the top nav, click the small Instagram-story icon to the left of `TELOS FITNESS`.
- It opens `https://www.instagram.com/telosathleticclub`.
- From the same page, scroll to the footer and click the Instagram link. It opens `https://instagram.com/telos_fitness`.
- The same is true for every other page (pricing, shop, resources, product, all 23 blog posts) - they all use `telos_fitness`. CLAUDE.md confirms the canonical handle is `@telos_fitness`.

**What's wrong:** A single link, only on the homepage header, sends users to `instagram.com/telosathleticclub` while the rest of the site routes to `instagram.com/telos_fitness`. Either the handle was renamed at some point and one link wasn't updated, or this is a typo from the `telosathleticclub.com` domain. Best case: users land on a profile inconsistent with the rest of the funnel. Worst case (if `telosathleticclub` doesn't exist on IG): the header link is a 404 from the highest-traffic entry point.

**Suggested fix:** Decide which handle is canonical and align. If `@telos_fitness` is correct per CLAUDE.md, replace the homepage header href:
```html
<a href="https://www.instagram.com/telos_fitness" target="_blank" rel="noopener" class="nav-ig-story" title="@telos_fitness">
```
(also adds `rel="noopener"` for tabnabbing hygiene, missing on this link).

**Confidence:** high
