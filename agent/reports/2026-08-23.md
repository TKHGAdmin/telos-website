# Telos Bug Report - 2026-08-23

**Focus:** Functional
**Findings:** 7 (P0: 0, P1: 4, P2: 3, P3: 0)
**Approval-rate context:** First run - no prior decisions in `decisions.jsonl`.

## Summary

First pass over the API surface (`api/**`) and the client PWA
(`client-dashboard.html`, `js/quiz.js`). Zero P0s: no auth bypass, no exposed
secrets, no unauthenticated writes to client data, cron endpoints properly
gated. Four P1s are real user-facing regressions worth fixing this week - the
strongest is a silent account-lockout when two clients share an email
(`api/dashboard/client-portal.js`). Two entire subsystems (push notifications,
engagement emails) are shipping but not working the way admins believe they
are; both are P1. Known items already documented in CLAUDE.md's "Known
Limitations" (UTC `todayStr()`, SW cache version, tool-page `main.js`) are
intentionally excluded to keep the signal high.

## Findings

### 20260823-01 - P1 - Silent client-account hijack when two clients share an email

- **File:** `api/dashboard/clients.js:70-73` (missing lookup write) and `api/dashboard/client-portal.js:114-118` (overwrites without owner check).
- **Symptom:** Enabling portal access for a second client whose email matches an existing portal-enabled client silently overwrites `client_email:<email>` in Redis. The first client's login now resolves to the wrong record; because password hashes differ, they see "Invalid email or password" and are permanently locked out with no admin-visible warning.
- **Repro:**
  1. Create client A with email `alex@example.com`, tier `growth`, portal enabled, password set. Confirm login works.
  2. Create client B via the admin table with the same email `alex@example.com` (any tier). The uniqueness check at `clients.js:70` passes because `clients.js` POST never writes the reverse lookup, so the key doesn't exist.
  3. On the Client Portal tab, enable portal on client B and set a password. `client-portal.js:117` runs `SET client_email:alex@example.com <B.id>` with no owner check.
  4. Log out and try to sign in as A - fails. Try as B - succeeds.
- **Impact:** Any coach flow that reuses an email (spouse, family plan, re-onboarded former client) can silently lock an active client out of their portal. No error visible to admin. Recovery requires manual Redis inspection.
- **Fix sketch:**
  - In `clients.js` POST, after `INCR id:clients`, also write `SET client_email:<normalized> <id>` so the uniqueness check on subsequent creates actually finds the existing row.
  - In `client-portal.js` POST, before the `SET` on line 117, `GET client_email:<email>` and refuse (400) if the existing owner is a different client id. Only write when the lookup is empty or already points at `client.id`.
  - Bonus: on `clients.js` DELETE, also remove `client_email:<normalized>` to avoid leaving dangling lookups for the next reuse.

### 20260823-02 - P1 - Push notifications silently fail delivery (admin sees "sent", client sees nothing)

- **File:** `api/client/notify.js:47-76`.
- **Symptom:** When `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` are configured, the handler POSTs the payload directly to the push endpoint with no VAPID JWT `Authorization` header and no RFC 8291 payload encryption. Every mainstream push service (FCM, Mozilla autopush, Apple, Edge) rejects the request. When the rejection returns, `notify.js:75` still returns HTTP 200 with `{ok: true, warning: 'Push delivery uncertain'}`, so the dashboard reports success.
- **Repro:** Set VAPID env vars, register a push subscription from a client browser, then POST to `/api/client/notify.js` from the admin dashboard. The endpoint returns 200; the client never sees the notification. Confirm in Vercel logs: `Push failed: 401` (or 403) from the push endpoint.
- **Impact:** Any admin who trusts the "sent" indicator will send messages that never arrive. This affects any workflow that assumes push works (reminders, coach nudges). The code itself acknowledges the gap - see comments at lines 60-61: `// Full RFC 8291 Web Push encryption would go here / // Placeholder: attempt direct POST`.
- **Fix sketch:** Either (a) add the `web-push` npm dependency and use `webpush.sendNotification(subscription, payload, {vapidDetails})`, or (b) surface the current state honestly by returning `{ok: false, error: 'Web Push not yet implemented'}` when VAPID keys are set but the placeholder path is used, so the admin UI stops falsely claiming delivery. Recommend (a); (b) is the interim safety fix.

### 20260823-03 - P1 - Daily engagement cron re-emails the same inactive client every 24h with no dedupe

- **File:** `api/cron/engagement-check.js:36-94`.
- **Symptom:** The daily cron loops every active portal client and emails "We miss you at Telos" to any client whose latest daily log is 3+ days old, with no last-sent tracking or backoff. A client who stops logging (vacation, injury, churning) receives the same email every single day indefinitely.
- **Repro:** Any client with `status:'active'`, `portalEnabled:true`, `emailEnabled !== false`, and no daily log rows for the last 5 days. On each cron tick they hit the branch at line 61 and Resend delivers another copy of the same email.
- **Impact:** Spam risk to real paying clients (Rebuild $1,497 - Lifestyle+ $6,997 tier). High probability of unsubscribes and Resend abuse flags against `noreply@telosathleticclub.com`. Reputational damage disproportionate to the number of affected accounts.
- **Fix sketch:** Before the Resend call, `GET client_engagement_sent:<id>` (or store `client.lastEngagementEmailAt` on the client record). Skip if less than 7 days ago. After a successful send, `SET client_engagement_sent:<id> <today> EX 604800` (7-day TTL). This preserves the reminder cadence without daily repetition.

### 20260823-04 - P1 - Training rest-timer interval leaks on tab switch, logout, and session expiry

- **File:** `client-dashboard.html:3428-3452` (definitions) plus `client-dashboard.html:2057` (`switchTab`), `:2044` (`handleLogout`), and `:1891` (401 handler).
- **Symptom:** `startRestTimer` sets `S.restTimerInterval = setInterval(..., 1000)`. The interval is only cleared inside `dismissRestTimer`, which is called from `loadTraining` (:3160), unchecking a set (:3414), the explicit skip button, and natural expiry. None of the other exit paths call it, so the timer keeps ticking every second and writing to hidden DOM (`$('restTimerValue').textContent`, `ring.style.strokeDashoffset`) after the user leaves.
- **Repro:**
  1. On the Train tab, tap a set checkbox with a rest value (e.g. "90s"). Confirm the circular overlay starts counting.
  2. Tap the Home bottom tab. Overlay hides visually, but open devtools performance: `setInterval` firing every 1000ms continues.
  3. Alternatively: while the timer is running, tap Logout - `handleLogout` clears session but the interval survives until the tab is closed, still trying to write to now-detached DOM.
  4. Alternatively: while the timer is running, let a background fetch return 401 - the auth handler at :1891 shows the login screen; the interval survives across screens.
- **Impact:** Wasted CPU/battery on mobile PWA in the background (real for a fitness app used mid-workout). More concerning: on session expiry, the interval continues to reference DOM that no longer represents the user's state - a set that ticks over to 0 during a login screen may fire follow-up UI actions on the wrong context.
- **Fix sketch:** Add `if (S.restTimerInterval) dismissRestTimer();` at the top of `switchTab` (or, cleaner, inside `handleLogout` and after the 401 branch too). One line each in three places. Alternatively, wrap the interval callback with a guard: `if (!S.restTimerActive) { clearInterval(S.restTimerInterval); return; }`.

### 20260823-05 - P2 - Learning modules with empty or missing `tierAccess` return 403 to every tier

- **File:** `api/client/module.js:48-60` (and the same pattern in `api/client/modules.js:61-69`).
- **Symptom:** `minTier` is initialized to `999`. If `mod.tierAccess` is undefined or `[]`, the forEach at line 51 never runs, `minTier` stays 999, and the check `clientTierLevel < minTier` is true for every real tier (levels 0-3). Response: `403 {error: 'Upgrade required', requiredTier: 'lifestyle_plus'}`. Even a `lifestyle_plus` client sees an impossible-to-satisfy upgrade prompt.
- **Repro:** In the admin dashboard, create or edit a module and either leave `tierAccess` empty or explicitly clear it. `api/dashboard/modules.js` accepts `if (body.tierAccess !== undefined) mod.tierAccess = body.tierAccess`. Any client, including `lifestyle_plus`, hitting `/api/client/module?id=<id>` now gets 403.
- **Impact:** A published-but-unrestricted module is invisible to every client - the exact opposite of what "no tier restriction" implies. Likely to bite the coach the first time they forget to check tier boxes.
- **Fix sketch:** Change the check to explicitly treat empty/absent `tierAccess` as "no restriction":
  ```js
  var allowedTiers = mod.tierAccess || [];
  if (allowedTiers.length > 0) {
    var minTier = Math.min.apply(null, allowedTiers.map(tierLevel));
    if (clientTierLevel < minTier) return res.status(403).json(...);
  }
  ```
  Apply the same fix to `modules.js`.

### 20260823-06 - P2 - Password reset tokens are not single-use and are not rate-limited

- **File:** `api/client/reset-password.js:20-68`.
- **Symptom:** Two issues in one endpoint.
  1. Requesting a reset (`?mode=request` or POST without a token) mints a new `password_reset:<token>` with 1h TTL but never deletes previously-issued tokens for the same client. If an old reset link leaked earlier (or was intercepted), it stays valid for its remaining hour even after the victim requests a fresh reset.
  2. Consuming a token (`?mode=confirm`) doesn't `DEL password_reset:<token>` after use, so the same token can be replayed until it expires.
  3. No IP or per-email rate limiting anywhere in the file, so this endpoint is a free email-relay: any attacker who knows a client's email can send them one reset email per request.
- **Repro:**
  - Replay: request reset, use the token to set a new password, then within the hour re-POST the same token with a different `newPassword`. Second call succeeds.
  - Old-link survival: request reset (link A, expires 15:00). At 14:30, request another reset (link B, expires 15:30). Link A still works until 15:00.
- **Impact:** Not a direct account takeover on its own but weakens defense-in-depth on the client portal. Rate limiting is the more urgent piece - unattended it's an email-abuse vector against Telos's Resend deliverability.
- **Fix sketch:**
  - On confirm: `redis('DEL', 'password_reset:' + token)` right after the password hash is written.
  - On request: track the current token id on the client record, and `DEL` the previous one before minting the new one.
  - Add a Redis-based rate limit: `INCR ratelimit:reset:<ip>` with 1h EXPIRE, cap at ~5. Same pattern as the CHS submission endpoint.

### 20260823-07 - P2 - Quiz "Retake" races the count-up animation and accumulates a fresh "View Pricing" handler each time

- **File:** `js/quiz.js:316-323` (`countUp` interval), `:401-411` (`viewPricingBtn` listener), and `:416` onward (`resetQuiz`).
- **Symptom:** Two overlapping issues in the results-screen render.
  1. `renderResults` starts `const countUp = setInterval(...)` that increments `scoreNumber.textContent`. The interval only clears when `currentCount >= totalScore`. If the user clicks Retake before it finishes (~1.2s), the old interval keeps writing to the same DOM node while `resetQuiz` clears it and the next `renderResults` runs its own count-up. Visual result: score number jitters and can land on the wrong value.
  2. Each `renderResults` call re-runs `viewPricingBtn.addEventListener('click', function() {...})` with a fresh anonymous function. `addEventListener` does not deduplicate, so after N retakes the button fires N stacked handlers - each hides the overlay, sets scroll-lock, scrolls to top, and calls `revealPricing()` N times.
- **Repro:**
  1. On `/pricing`, complete the quiz. Immediately click "Retake" while the score is still animating up. Watch the number oscillate.
  2. Complete + retake three times, then click "View Pricing". Devtools: three handlers on the click. Visible symptom: `revealPricing()` animation replays overlapping.
- **Impact:** Public-facing quiz overlay - polish issue but visible on the primary conversion surface. Users who retake to try different answers see a broken UI on a page that gates pricing.
- **Fix sketch:**
  - Save the interval id on the module scope (e.g. `quiz.countUpInterval`) and `clearInterval(quiz.countUpInterval)` at the top of both `renderResults` and `resetQuiz`.
  - Move the `viewPricingBtn` listener out of `renderResults` - bind it once during quiz init. Or track the last handler with `viewPricingBtn.__handler` and `removeEventListener` before re-binding.

## Not-bugs (verified negative, this run)

- `sw.js`: uses network-first on same-origin, so stale HTML risk is small even without a cache-name bump. Still worth bumping on asset changes, but not a live bug today.
- FAB show/hide (`client-dashboard.html:1924`, `:2067`): correctly uses `display:'block'` and `'none'` per the CLAUDE.md convention. No regression.
- Public `submit-*` endpoints: rate-limited per IP, method-checked, and input-validated. Nothing to flag.
- All cron endpoints: correctly gate on `CRON_SECRET`. `weekly-summary.js` idempotency was fine (runs once weekly).
- Admin session (`api/lib/auth.js`): HMAC compare uses raw `!==` rather than `timingSafeEqual` (client-side uses timing-safe), but at 256-bit HMAC over the network the exploit surface is negligible. Not worth a report entry above P3, noted in learnings for future runs.
