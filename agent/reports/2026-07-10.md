## BUG-2026-07-10-01 — Client DELETE leaks the `client_email` login lookup

- **Severity:** P2
- **File:** `api/dashboard/clients.js:143-153`
- **Focus area:** Functional

### What's wrong
`DELETE /api/dashboard/clients` only removes `client:{id}` and the `clients_index` ZSET entry. It never removes the `client_email:{normalizedEmail}` lookup key that `POST` (`clients.js:70`) and `PUT` (`clients.js:121-132`) both maintain when the portal is enabled.

Consequences:
1. The email address stays reserved forever. If Thomas later tries to re-add the same client (or a different client with the same email), `POST /api/dashboard/clients` at `clients.js:70-73` returns `Email already in use by another client` — but the "other client" no longer exists.
2. Downstream client data (`client_nutrition_plan`, `client_training_program`, `client_dailylog:*`, `client_..._logs_index`, `client_supplement_plan`, `client_sidemenu`, `client_545_*`, etc.) is also orphaned. If the numeric `INCR id:clients` counter ever wraps around to a reused ID (unlikely in practice), a new client could inherit a deleted client's portal data. Lower risk, but worth noting.

### Reproduction
1. In `/thomas`, create a client with email `test@example.com` and enable the portal (this writes `client_email:test@example.com` → new client's id).
2. Delete that client from the Clients tab.
3. Try to re-add another client with `test@example.com`. The API rejects it with 400 `Email already in use by another client` even though no client exists.

### Suggested fix
In the DELETE handler, load the client record first, then delete the email lookup if `portalEnabled && email`:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });
  var existing = await redis('GET', 'client:' + id);
  if (existing) {
    try {
      var client = JSON.parse(existing);
      if (client.email) {
        var { normalizeEmail } = require('../lib/client-auth');
        await redis('DEL', 'client_email:' + normalizeEmail(client.email));
      }
    } catch(e) {}
  }
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

Optional follow-up: also DEL the orphaned per-client keys (`client_nutrition_plan`, `client_training_program`, `client_mindset`, `client_resources`, `client_sidemenu`, `client_supplement_plan`, `client_545_goals`, `client_545_routine`) and the per-day log ZSETs. If Thomas prefers soft-delete for audit reasons, the email cleanup alone unblocks the practical bug.

## BUG-2026-07-10-02 — Weekly summary email always reports "Streak: 0 days"

- **Severity:** P2
- **File:** `api/cron/weekly-summary.js:86-90`
- **Focus area:** Functional

### What's wrong
The streak counter starts at `d=0` (today) and `break`s the first time a daily log is missing:

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

The cron is scheduled `0 14 * * 1` (Monday 14:00 UTC ≈ 9–10am ET). At that time, essentially no client has logged Monday's daily check-in yet. So `d=0` misses, the loop breaks immediately, and the email says `Current Streak: 0 days` — regardless of whether the client actually strung together six consecutive days Tue–Sun.

Because this fires the same way every Monday, **every weekly summary email shows Streak: 0** unless a client happens to log before the cron runs.

### Reproduction (code trace)
1. A client logs `client_dailylog:{id}:2026-07-05` (Sun), `2026-07-04` (Sat), and `2026-07-03` (Fri).
2. Cron runs Monday 2026-07-06 at 14:00 UTC. `now = Date.now()`.
3. `weekData[0][0]` = today's log (Monday) — `null`.
4. Loop iteration `d=0`: `weekData[0][0].result` is falsy → `break`. `streak = 0`.
5. Email renders `Current Streak: <strong>0 days</strong>` (`weekly-summary.js:131`) even though the real streak going into Monday is 3.

### Suggested fix
Skip today when computing the current streak going into the new week. Two easy options:

```js
// Option A: start at d=1 (yesterday) if today isn't logged
var startD = (weekData[0][0] && weekData[0][0].result) ? 0 : 1;
for (var d = startD; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

```js
// Option B: report streak ending yesterday, always
for (var d = 1; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

Option A is more forgiving to early-bird clients; option B is simpler and always reflects "last week's momentum."

Note: the same "day 0 = today" pattern is fine in `api/cron/engagement-check.js` — that logic *wants* to react to today being unlogged. This bug is specific to the streak calculation in the weekly recap.
