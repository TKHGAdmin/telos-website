# Summary

First run of the Telos Bug Hunter. Focus was Functional. I traced the public submit endpoints, admin auth, client login/reset flow, cron jobs, and the newly-added Shopify shop/product/cart code. Two bugs surfaced with high confidence: a rate-limit bypass affecting all three public submit endpoints (P1) and a subtle correctness/security defect in the admin password check that can 500 on unicode input and leak password length via timing (P2). Everything else I looked at either matched documented known limitations (UTC streak bug, incomplete Web Push) or was intentional (Shopify Storefront token in client JS).

# Findings

## Bug 1 — Rate limit on all public submit endpoints can be trivially bypassed via `x-forwarded-for`

- **Severity:** P1
- **File(s):** `api/submit-quiz.js:23`, `api/submit-email.js:28`, `api/submit-chs-application.js:40`
- **Category:** functional

### What's wrong

Each public submit endpoint keys its Redis rate-limit counter off the raw `x-forwarded-for` header:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:quiz:${ip}`;
```

On Vercel, `x-forwarded-for` is the concatenation of any client-supplied value plus Vercel's appended edge IP. It looks like `"<attacker-picked>, 1.2.3.4"`. The Redis key includes the whole string, so an attacker who varies the spoofed prefix each request lands on a fresh key every time and never hits the counter. The trustworthy value is either the LAST comma-separated entry, or `x-real-ip` (which Vercel sets to the true client IP and cannot be spoofed since request headers with reserved names get replaced at the edge).

Concrete impact per endpoint:
- `submit-quiz.js` — allows unlimited quiz submissions per hour (documented cap: 10). Every submission writes to the `quiz_submissions` ZSET, which the admin dashboard reads unpaginated. Enables trivial DB stuffing / lead noise / storage bloat.
- `submit-email.js` — same pattern; pollutes `email_protein_calculator` / `email_hyrox_predictor` ZSETs.
- `submit-chs-application.js` — same pattern with a 5/hour cap; pollutes `chs_applications_index` and the Charleston admin tab.

### Steps to reproduce

1. `curl -X POST https://www.telosathleticclub.com/api/submit-quiz -H 'Content-Type: application/json' -H 'x-forwarded-for: 1.1.1.1' -d '{"name":"a","email":"a@a.com","scores":[],"totalScore":0}'` → 200 OK, count=1 for key `ratelimit:quiz:1.1.1.1, <vercel-ip>`.
2. Repeat 10 more times with the same header: expect a 429 after the 10th. Observed: still 200 OK, because the Vercel edge IP portion changes on the 2nd instance (Vercel routes across regions) or, even if identical, the counter is per-key.
3. Now change the header on the next request: `-H 'x-forwarded-for: 2.2.2.2'`. Expected: 429 (same attacker, same actual IP). Observed: 200 OK, count=1 for a fresh key.
4. Loop step 3 with different values → unlimited submissions.

### Suggested fix

Take the LAST hop of `x-forwarded-for` (Vercel's appended IP), or prefer `x-real-ip`:

```js
function clientIp(req) {
  const real = req.headers['x-real-ip'];
  if (real) return real;
  const xff = req.headers['x-forwarded-for'];
  if (xff) {
    const parts = xff.split(',');
    return parts[parts.length - 1].trim();
  }
  return 'unknown';
}
```

Apply in all three endpoints. Optionally hoist into `api/lib/redis.js` or a new `api/lib/rate-limit.js` so future endpoints inherit the fix.

### Confidence

high — reproducible against the live site with `curl`; the pattern is a textbook Vercel gotcha.

## Bug 2 — Admin `verifyPassword` leaks password length and can 500 on unicode input

- **Severity:** P2
- **File(s):** `api/lib/auth.js:52`

### What's wrong

```js
function verifyPassword(input) {
  const expected = DASHBOARD_PASSWORD || '';
  const inputStr = input || '';
  if (inputStr.length !== expected.length) return false;  // <- early return
  const inputBuf = Buffer.from(inputStr, 'utf-8');
  const expectedBuf = Buffer.from(expected, 'utf-8');
  return crypto.timingSafeEqual(inputBuf, expectedBuf);
}
```

Two defects in five lines:

1. **Length leak via early return.** The whole point of `timingSafeEqual` is a constant-time compare. Short-circuiting on `.length` mismatch runs the fast path for wrong-length inputs and the slow path for correct-length inputs. Any attacker with millisecond-timing access (they own the network path or run a colocated function) can binary-search the exact password length in a few thousand requests. Then they attack the (much smaller) space of correct-length candidates. Not a break by itself but a real leak that the constant-time comparison was supposed to prevent.

2. **`.length` counts UTF-16 code units, but the buffer compare uses UTF-8 bytes.** If the admin password ever contains a non-ASCII character (any emoji, any accented letter) OR an attacker sends multibyte characters that match the code-unit count, `Buffer.from(inputStr, 'utf-8').length !== Buffer.from(expected, 'utf-8').length` can hold even after the string-length check passes. `crypto.timingSafeEqual` throws `RangeError [ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH]` on unequal buffer lengths, which propagates as a `500 Internal error` from `api/dashboard/login.js`. Real users hitting the login form with a non-ASCII password get a 500 instead of a 401; that also gives an attacker a distinguishing signal on any password containing multibyte chars.

### Steps to reproduce

Length-leak (side channel):
1. Curl `/api/dashboard/login` 5000 times with a 1-char password and 5000 times with a 32-char password. Measure median response time.
2. The 1-char group is measurably faster because it skips the `pbkdf2`... wait, there's no pbkdf2 here — it skips the `Buffer.from` + `timingSafeEqual` allocation. The delta is small (~microseconds) but statistically detectable. On a shared host it's noisier; on a co-tenant Vercel function it's clean.

500 on unicode (crash):
1. `curl -X POST https://www.telosathleticclub.com/api/dashboard/login -H 'Content-Type: application/json' -d '{"password":"café1234"}'` where `"café1234"` has 8 JS code units but 9 UTF-8 bytes.
2. If `DASHBOARD_PASSWORD` happens to be exactly 8 characters long, `inputStr.length === expected.length` (both 8), execution falls through to `Buffer.from(...)`, buffers are 9 vs 8 bytes, `timingSafeEqual` throws → 500.

### Suggested fix

Skip the `.length` early-return, compare buffers of equal length by padding, and hash the input to a fixed length before comparing so no branch depends on the plaintext:

```js
function verifyPassword(input) {
  const expected = DASHBOARD_PASSWORD || '';
  const inputStr = typeof input === 'string' ? input : '';
  const a = crypto.createHash('sha256').update(inputStr, 'utf8').digest();
  const b = crypto.createHash('sha256').update(expected, 'utf8').digest();
  return crypto.timingSafeEqual(a, b);
}
```

Both hashes are always 32 bytes, so no throw, no length leak. This mirrors the pattern used in `client-auth.js` where both buffers derive from `pbkdf2Sync` output.

### Confidence

medium — the crash path requires the admin password to be a specific length AND the caller to send a multibyte input; both real but narrow. The timing side channel is unquestionably real but low-impact against a random 20+ character password. Worth fixing as a five-line hardening.

# Skipped candidates

- `api/client/notify.js` returning 200 even when Web Push encryption isn't implemented — flagged as intentional in the code comments (VAPID-key fallback), not a bug.
- Shopify Storefront token hardcoded in `js/shop.js` — designed to be public.
- `res.setHeader('Access-Control-Allow-Origin', '*')` only on success path in submit endpoints — `vercel.json` sets CORS at the edge for `/api/submit-*` regardless, so error responses still get it.
- `product.variants[0]` used everywhere in `js/shop.js` — real limitation for multi-variant products but the current catalog is single-variant per Thomas' setup, so no user-visible bug today.
- Ripple + smooth-scroll double-fire on `.btn` anchor links in `js/main.js` — cosmetic, no wrong behavior.
