## P1 — Weekly summary email reports "Current Streak: 0 days" for every client, every Monday

- **File**: `api/cron/weekly-summary.js:87-90`
- **Trigger**: Cron fires Monday 14:00 UTC (9am ET, per `vercel.json`). The 7-day window is built with `d=0` as today's UTC date (Monday). The streak loop iterates `d` from 0 upward and `break`s on the first day with no `client_dailylog` entry.
- **Why**: At 9am ET on Monday, the client has not logged Monday yet, so `weekData[0][0].result` is empty, the loop breaks at `d=0`, and `streak` stays `0`. The email then shows `Current Streak: 0 days` even for a client with a 20-day streak ending Sunday. This is both wrong and demoralizing — streak is the headline number in the email body (line 131).
- **Fix**: Skip leading unlogged entries before counting. Replace lines 87-90 with:
  ```js
  var start = 0;
  while (start < 7 && !(weekData[0][start] && weekData[0][start].result)) start++;
  for (var d = start; d < 7; d++) {
    if (weekData[0][d] && weekData[0][d].result) streak++;
    else break;
  }
  ```
- **Confidence**: high

## P1 — Deleting a client orphans the `client_email` lookup and blocks re-adding the same email

- **Files**: `api/dashboard/clients.js:143-154` (DELETE), `api/dashboard/client-portal.js:115-117` (writes the pointer), `api/dashboard/clients.js:70-73` (where the stale pointer blocks re-add)
- **Trigger**:
  1. Thomas creates client A, enables portal → `client-portal.js` writes `client_email:{email} → A.id`.
  2. Thomas deletes client A via the Clients tab → DELETE at `clients.js:147-148` removes `client:{A.id}` and `clients_index` but never touches `client_email:{email}`.
  3. Thomas tries to add a new client with that same email → POST at `clients.js:70-73` finds the orphan pointer and returns `400 "Email already in use by another client"`.
- **Why**: The orphan pointer references a non-existent client record, so the duplicate check is a false positive. There is no admin-side button to clear it — Thomas would have to open Redis directly. Login and password-reset for that email also silently fail (both are read-only against the stale pointer, so no security impact — just a dead end).
- **Fix**: In the DELETE handler, load the client record before deletion, then `DEL client_email:{normalizeEmail(client.email)}` alongside the existing `DEL client:{id}` and `ZREM clients_index`. While there, consider also cleaning the per-client log keys (`client_dailylog:*`, `client_training_log:*`, `client_nutrition_log:*`, `client_supplement_log:*`, `client_activity_log:*`, `client_545_daily:*`, and their `*_index` ZSETs) — not reported as a separate bug because none of them block functionality today, but worth noting.
- **Confidence**: high

## Summary

Two real P1 functional bugs found on the bootstrap run, both in admin/cron paths that run invisibly: a cron-side off-by-one that silently zeroes every client's weekly-summary streak, and an admin-side cascade miss that leaves a stale email pointer and blocks re-adding a deleted client's email. Both are small, isolated fixes. No P0s. No app-breaking issues.

## Patterns observed

- **Delete handlers don't cascade.** `clients.js` DELETE leaves `client_email`, every per-day log key, and the `*_index` ZSETs behind. Only `client_email` is a functional bug today; the rest is data debt but worth watching if a GDPR-style "forget me" ever lands.
- **UTC date arithmetic in cron jobs.** `new Date(now - d * 86400000).toISOString().split('T')[0]` is used in `weekly-summary.js`, `engagement-check.js`, `daily-log.js`, `activity-log.js`, `five-four-five.js`. Clients experience days in local time, so expect off-by-one edge cases around midnight ET — same shape as the streak bug above.
- **Non-atomic GET-modify-SET** on daily logs (`activity-log.js:60-77`, `five-four-five.js:92-124`, `daily-log.js:64-88`). Two parallel requests for the same date can drop writes. Low real-world probability with one user per client, but a latent concurrency hazard.
- **Admin list endpoints have no pagination and no cap.** `clients.js:19` and `pipeline.js:14` do `ZREVRANGE 0 -1` + a full pipeline of GETs on every page load. Fine today, will fail at scale.
- **Mixed signature-compare primitives.** `api/lib/auth.js:27` admin HMAC check uses `!==` while `api/lib/client-auth.js:49` uses `timingSafeEqual`. Not a practical attack today, but worth harmonizing on timing-safe compares the next time either file is touched. Not reported as a finding.
