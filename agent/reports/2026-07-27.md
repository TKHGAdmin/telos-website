## Bug 1 — P1 — Cart icon and badge hidden inside the collapsed hamburger on mobile (shop + product pages)

- **Severity**: P1
- **Area**: `shop.html`, `product.html` (and `css/style.css`)
- **Repro**:
  1. Resize a browser to ≤ 768 px width (or open on any phone) and load
     `/shop` or `/product?p=<handle>`.
  2. Add any item to cart via the product card / detail button.
  3. Try to see the cart badge or open the cart drawer without opening
     the hamburger.
  4. The desktop cart button lives inside `<ul class="nav-links">`
     (shop.html:682, product.html:681). CSS at `css/style.css:557` sets
     `.nav-links { display: none; }` at `@media (max-width: 768px)`.
  5. The mobile cart button lives inside `<div class="mobile-menu">`
     (shop.html:711, product.html:702), which starts collapsed
     (`max-height: 0; overflow: hidden;` at `css/style.css:2772`) until
     `.mobile-menu.active` is set by the hamburger toggle in
     `js/main.js:30-34`.
- **Impact**: Every mobile visitor to `/shop` or `/product` who taps
  "Add to Cart" gets no visible confirmation (badge invisible), no
  discoverable path to checkout, and has to figure out that the
  hamburger contains the cart. Given phones dominate traffic for
  ecommerce, this is the difference between "sale" and "abandoned".
- **Suggested fix**: Hoist the cart button (or a mirror of it) out of
  `.nav-links` / `.mobile-menu` and into the always-visible
  `.nav-container` on mobile — e.g., render it as a sibling of the
  hamburger so both are visible in the top bar. Test that the badge
  visibility toggle in `js/shop.js:384` still finds it via
  `document.querySelectorAll('.cart-badge')`.

## Bug 2 — P1 — Duplicate-email guard on client creation is bypassable and can misroute portal logins

- **Severity**: P1
- **Area**: `api/dashboard/clients.js`, `api/dashboard/client-portal.js`
- **Repro** (code trace):
  1. `POST /api/dashboard/clients` at `api/dashboard/clients.js:70`
     checks for duplicates with
     `redis('GET', 'client_email:' + normalized)`.
  2. But the `client_email:<email>` key is *only ever written* in
     `api/dashboard/client-portal.js:117`, inside the branch that runs
     when portal is being enabled. The client-creation POST never sets
     it (see `api/dashboard/clients.js:76-91` — no `client_email` write).
  3. Consequence A: create Client A with `alice@x.com`, portal
     disabled. Now create Client B with `alice@x.com` — the duplicate
     check at line 70 finds nothing, and both records are stored with
     the same email.
  4. Consequence B: later, enable portal for Client B →
     `client_email:alice@x.com = B`. Then enable portal for Client A →
     the same key at `client-portal.js:117` is `SET` unconditionally
     (no duplicate check on this path either), silently overwriting to
     `= A`. Client B's portal login now attempts to verify B's password
     against A's hash and always fails; more subtly, if the two
     records ever diverge in stored profile data, whoever logs in with
     `alice@x.com` gets A's data even though they thought they were
     accessing B.
- **Impact**: Coach can create duplicate-email clients without warning,
  and the "who owns this login" mapping silently changes when either
  duplicate has its portal toggled — up to and including a client
  seeing the wrong person's nutrition/training/logs.
- **Suggested fix**: In `client-portal.js` POST, before writing
  `client_email:<email> = <clientId>` on portal-enable, `GET` the key
  first and reject if it's owned by a different clientId (mirror the
  existing check on the PUT path in `clients.js:124`). Separately, make
  `clients.js` POST reject duplicates for any client whose email
  already appears in *any* stored `client:*` record (or maintain a
  separate `client_email_all:<email>` index written on every create).

## Bug 3 — P2 — Deleting a client leaves an orphaned `client_email:` lookup

- **Severity**: P2
- **Area**: `api/dashboard/clients.js`
- **Repro** (code trace):
  1. Enable portal for a client, then delete them via
     `DELETE /api/dashboard/clients?id=<id>`
     (`api/dashboard/clients.js:143-154`).
  2. The handler only runs `DEL client:<id>` and
     `ZREM clients_index <id>`. The `client_email:<email>` mapping
     (written by `client-portal.js:117`) is never cleaned up.
  3. Attempted re-create with the same email now hits the (broken)
     duplicate check in Bug 2, so the interaction depends on which
     bug you fix first. If Bug 2 is fixed but Bug 3 isn't, the
     coach can no longer reuse that email for a real new client
     until the orphaned key is manually deleted from Redis.
- **Impact**: Silent data leftover after a deletion; blocks legit
  email reuse; leaves a Redis pointer to a phantom `clientId`.
- **Suggested fix**: In the DELETE branch, first `GET client:<id>`,
  parse the JSON, and if `portalEnabled && email`, also
  `DEL client_email:<normalizeEmail(email)>`. Same pattern as the
  email-change branch already implements.

## Bug 4 — P3 — `js/shop.js` cache-busting version drifts between shop and product pages

- **Severity**: P3
- **Area**: `shop.html`, `product.html`
- **Repro**:
  1. `shop.html:841` loads `<script src="js/shop.js?v=1">`.
  2. `product.html:822` loads `<script src="js/shop.js?v=2">`.
  3. A returning visitor who caches `?v=1` from `/shop` then navigates
     to `/product` fetches a *fresh* copy under `?v=2`, and vice
     versa — both files are the same on disk, but the cache-buster's
     purpose is defeated: the next time `shop.js` is actually edited,
     bumping only one page's version leaves the other page serving a
     stale cached copy.
- **Impact**: Low today (no active drift), but a real footgun on the
  next `shop.js` edit — the version-bump convention documented in
  `CLAUDE.md` ("bump the version on all pages when changing style.css")
  applies here too and is silently violated.
- **Suggested fix**: Bring both pages to the same version — `?v=2` is
  fine — and add `js/shop.js` alongside `css/style.css` in the
  "bump on every change" convention in `CLAUDE.md`.
