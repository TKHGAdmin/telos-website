First run of the bug hunter. Focus: functional (defaulted from an empty rotation state on the assumption that Thomas cares most about broken user flows on day one). Scope was the entire `api/` layer plus the client login / password-reset flow in `client-dashboard.html`. Four findings, all traceable to specific lines. Two are latent identity-management bugs in `api/dashboard/clients.js` that can silently lock a real client out of their portal. One is a rate-limit bypass across all three public POST endpoints. One is a security-hygiene nit in the admin session code.

I deliberately did not report: (a) style-only inconsistencies between the two auth libraries, (b) the cron endpoints' `skipped: true` on missing `RESEND_API_KEY` (that's an intentional graceful degrade), (c) `notify.js` and `send-email.js` living under `api/client/` but using admin auth (also intentional), (d) the `client-dashboard.html?reset=<token>` flow (it is handled; my first grep was too narrow before I widened it). Notes on each are in `agent/memory/learnings.md` so the next run doesn't re-chase them.

## P1: Deleting a client leaves an orphan email lookup and every log entry the client ever wrote

- **File**: `api/dashboard/clients.js:143-153`
- **Category**: functional
- **Reproducing**:
  1. Admin creates client `alice@x.com`, enables portal → `client_email:alice@x.com = <id_A>` gets written by `client-portal.js:117`.
  2. Admin deletes the client via `DELETE /api/dashboard/clients?id=<id_A>`. Only `client:<id_A>` and the `clients_index` ZSET entry are removed.
  3. Admin later creates a new client with the same email `alice@x.com`. `POST /api/dashboard/clients` runs the duplicate check at line 70, finds the orphan `client_email:alice@x.com → <id_A>`, and returns `400 "Email already in use by another client"` — even though no such client exists.
- **Impact**: Onboarding a returning client (or fixing a mistyped record and recreating it) is silently blocked with a misleading error. Independently, every per-client key (`client_dailylog:<id>:*`, `client_training_log:<id>:*`, `client_nutrition_log:<id>:*`, `client_545_*:<id>*`, `client_supplement_*:<id>*`, `client_activity_log:<id>:*`, plus their ZSET indexes, plus `client_push_sub:<id>`) is leaked into Redis forever. Storage bloat scales with client churn.
- **Evidence**:
  ```js
  // api/dashboard/clients.js:143-154
  if (req.method === 'DELETE') {
    try {
      var id = req.query.id || (req.body && req.body.id);
      if (!id) return res.status(400).json({ error: 'ID required' });
      await redis('DEL', 'client:' + id);
      await redis('ZREM', 'clients_index', String(id));
      return res.status(200).json({ ok: true });
    } ...
  }
  ```
  Compare to `client-portal.js:117` and `client-portal.js:123` where the email index is written / cleared — the DELETE handler doesn't invoke either code path.
- **Suggested fix**: Before `DEL client:<id>`, load the client, normalize the email, and `DEL client_email:<normalized>`. Then walk each namespace's ZSET index (`client_dailylogs_index:<id>` etc.) to build a pipeline of DELs for every dated key, and delete the ZSETs themselves. If cleaning the log fanout feels risky in one pass, the P1 half is just the email lookup; the log cleanup is separately worthwhile as a follow-up.
- **Confidence**: high

## P1: Two clients can be created with the same email; enabling portal for the second one silently hijacks the first's login mapping

- **File**: `api/dashboard/clients.js:59-97` and `api/dashboard/client-portal.js:114-118`
- **Category**: functional
- **Reproducing**:
  1. Admin creates client A with email `x@y.com`; does not enable portal yet. The duplicate check at `clients.js:70` reads `client_email:x@y.com` → nothing (index only gets written when portal is enabled), so creation succeeds.
  2. Admin creates client B with the same email `x@y.com`, also without enabling portal. Same check, same "nothing", same success. Two `client:{id}` records now exist with the same email.
  3. Admin enables portal on A → `client-portal.js:117` writes `client_email:x@y.com = <id_A>`. A can log in normally.
  4. Admin enables portal on B → `client-portal.js:117` uses plain `SET`, silently overwriting the mapping to `<id_B>`.
  5. A tries to log in: `login.js:24` resolves the email to `<id_B>`, then `verifyPassword(A's_password, B's_hash, B's_salt)` fails on line 46. A gets "Invalid email or password" and has no way to recover — password reset also resolves to B and mails B's inbox.
- **Impact**: Real coaching client silently locked out of their portal, with the reset flow pointing at the wrong person's email. Data corruption if the second creation was a typo the admin didn't notice.
- **Evidence**:
  ```js
  // api/dashboard/clients.js:70-73  -- the uniqueness check
  var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
  if (existingEmailOwner) {
    return res.status(400).json({ error: 'Email already in use by another client' });
  }
  // but the SET that populates that key is HERE, in a different endpoint, only when portal is toggled on:
  // api/dashboard/client-portal.js:115-118
  if (client.portalEnabled && client.email) {
    var email = normalizeEmail(client.email);
    await redis('SET', 'client_email:' + email, String(client.id));
  }
  ```
- **Suggested fix**: In `clients.js` POST, additionally maintain a separate `client_email_reserved:<normalized> = <id>` index (or reuse `client_email:` and treat portal-enable as a no-op if the mapping already resolves to the same client). In `client-portal.js:117`, either use `SETNX` and 400 on conflict, or reject enabling portal when a different client already owns the email. The `clients.js` PUT path at line 121-132 has the right pattern (checks `emailOwner && String(emailOwner) !== String(client.id)`); mirror it in POST and in the portal-enable step.
- **Confidence**: high

## P2: Rate-limit key uses the full `x-forwarded-for` header, trivially bypassable

- **File**: `api/submit-quiz.js:23`, `api/submit-email.js:28`, `api/submit-chs-application.js:40`
- **Category**: functional (also security-adjacent)
- **Reproducing**:
  1. Send `POST /api/submit-quiz` with `X-Forwarded-For: 1.1.1.1`. Vercel's edge appends the real client IP: the header the function sees is `1.1.1.1, <real-ip>`. Rate-limit key becomes `ratelimit:quiz:1.1.1.1, <real-ip>` → count 1.
  2. Send again with `X-Forwarded-For: 1.1.1.2`. New key `ratelimit:quiz:1.1.1.2, <real-ip>` → count 1.
  3. Rotate the client-supplied portion on every request; each is a fresh bucket. The advertised "10 per IP per hour" (5 per hour for CHS) becomes effectively unlimited.
- **Impact**: An attacker can flood quiz submissions, email captures, or Charleston applications into Redis. Each write also grows a ZSET (`quiz_submissions`, `email_protein_calculator`, `email_hyrox_predictor`, `chs_applications_index`) unboundedly, which shows up in the admin dashboard as spam and eats Upstash storage. No auth is bypassed; only the intended abuse ceiling is.
- **Evidence**:
  ```js
  // api/submit-quiz.js:23-29 (same shape in submit-email and submit-chs-application)
  const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
  const rateLimitKey = `ratelimit:quiz:${ip}`;
  const count = await redis('INCR', rateLimitKey);
  if (count === 1) await redis('EXPIRE', rateLimitKey, 3600);
  if (count > 10) return res.status(429).json({ error: 'Too many requests' });
  ```
- **Suggested fix**: Trust `x-real-ip` first (Vercel sets it to the actual client IP, and the client cannot override it via the edge). Failing that, take the LAST comma-delimited segment of `x-forwarded-for` (Vercel appends the real IP), not the whole string. Something like:
  ```js
  const xff = (req.headers['x-forwarded-for'] || '').split(',').map(s => s.trim()).filter(Boolean);
  const ip = req.headers['x-real-ip'] || xff[xff.length - 1] || 'unknown';
  ```
- **Confidence**: high

## P2: Admin session cookie verification uses a non-timing-safe HMAC comparison

- **File**: `api/lib/auth.js:27`
- **Category**: security
- **Reproducing**: Static code review. The admin cookie is `<expires>.<hmac>` and verification runs `if (signature !== expected) return false;`. This is a plain string compare; each byte position that matches costs measurable time. The client-side counterpart at `api/lib/client-auth.js:46-49` correctly wraps the same check in `crypto.timingSafeEqual` — so the concern is documented as important elsewhere in this codebase, just not applied here.
- **Impact**: A remote attacker who can measure request latency precisely against the admin login could, in principle, forge an admin session cookie by learning the HMAC byte-by-byte. In practice this is extremely hard over the public internet and the more likely exploit is a colocated attacker. The fix is one line and closes the gap.
- **Evidence**:
  ```js
  // api/lib/auth.js:22-30
  const [payload, signature] = parts;
  const expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
  if (signature !== expected) return false;   // ← should be timingSafeEqual
  const expires = parseInt(payload, 10);
  if (Date.now() > expires) return false;
  return true;
  ```
- **Suggested fix**: Mirror `client-auth.js:46-49`:
  ```js
  const a = Buffer.from(signature, 'hex');
  const b = Buffer.from(expected, 'hex');
  if (a.length !== b.length) return false;
  if (!crypto.timingSafeEqual(a, b)) return false;
  ```
  Same treatment optional for `verifyPassword` at line 55, which early-returns on length mismatch and leaks the exact admin-password length via timing — arguably even more sensitive, but out of scope for this finding.
- **Confidence**: high
