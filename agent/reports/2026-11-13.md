## P2-001 — DELETE client orphans portal lookup, content, logs, and push subscription

**File:** `api/dashboard/clients.js:142-154`
**Severity:** P2
**Category:** Data integrity / cleanup

### Observation

The `DELETE /api/dashboard/clients?id=N` handler removes exactly two keys:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

Everything else that was created for that client stays in Redis:

- `client_email:{normalizedEmail}` — the email → ID lookup used by `api/client/login.js:24` and `api/client/reset-password.js:22`. Only ever set when portal is enabled (`api/dashboard/client-portal.js:117`), and never cleaned up on client delete.
- Portal content: `client_nutrition_plan:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_545_goals:{id}`, `client_545_routine:{id}`, `client_training_program:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`.
- Daily per-date records: `client_dailylog:{id}:*`, `client_training_log:{id}:*`, `client_nutrition_log:{id}:*`, `client_545_daily:{id}:*`, `client_supplement_log:{id}:*`, `client_activity_log:{id}:*`.
- ZSET indexes of those: `client_dailylogs_index:{id}`, `client_training_logs_index:{id}`, `client_nutrition_logs_index:{id}`, `client_545_index:{id}`, `client_supplement_logs_index:{id}`, `client_activity_logs_index:{id}`.
- `client_push_sub:{id}` push subscription.

For comparison, `api/dashboard/modules.js:160-186` (DELETE module) correctly removes the main record **and** its series/pillar ZSET entries.

### Reproduction

1. Create a client via `POST /api/dashboard/clients` with email `x@example.com` → id=42.
2. Enable portal via `POST /api/dashboard/client-portal` with `{clientId:42, enabled:true, password:"pw12345678"}`. This writes `client_email:x@example.com = 42`.
3. Delete via `DELETE /api/dashboard/clients?id=42`. The 2-key cleanup runs.
4. `POST /api/dashboard/clients` again with email `x@example.com` → returns 400 `{"error":"Email already in use by another client"}` because the orphaned `client_email:x@example.com` still points at the now-deleted id=42. There is no UI path to clear it.

### Impact

- Admin cannot re-create a client at the same email after deletion. In practice this will look like "the system is broken" when the same person signs up again, moves tiers after a churn-and-return, or when a test client is deleted and the real one is added.
- Every deleted client's full history (daily logs, training logs, nutrition logs, etc.) stays in Redis forever. On a paid Upstash plan this is slow bloat; on a free plan it will eventually hit storage limits.
- If `INCR id:clients` is ever reset (Redis restore, migration to a new instance) a new client could inherit an old client's portal content, logs, and push subscription endpoint. Low probability, but the data is there waiting.

### Suggested fix

Before `DEL client:{id}`, read the record, scan the two log ZSETs that enumerate per-date keys, and clean up every related key. The log ZSETs mean you don't need `KEYS` or `SCAN` — the dates are already indexed:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });

  var existing = await redis('GET', 'client:' + id);
  if (existing) {
    var client = JSON.parse(existing);
    var deletes = [];

    if (client.email) {
      var { normalizeEmail } = require('../lib/client-auth');
      deletes.push(['DEL', 'client_email:' + normalizeEmail(client.email)]);
    }

    var portalKeys = [
      'client_nutrition_plan', 'client_mindset', 'client_resources',
      'client_545_goals', 'client_545_routine', 'client_training_program',
      'client_sidemenu', 'client_supplement_plan', 'client_push_sub'
    ];
    portalKeys.forEach(function (k) { deletes.push(['DEL', k + ':' + id]); });

    var indexes = [
      'client_dailylogs_index', 'client_training_logs_index',
      'client_nutrition_logs_index', 'client_545_index',
      'client_supplement_logs_index', 'client_activity_logs_index'
    ];
    var logPrefixes = {
      'client_dailylogs_index': 'client_dailylog',
      'client_training_logs_index': 'client_training_log',
      'client_nutrition_logs_index': 'client_nutrition_log',
      'client_545_index': 'client_545_daily',
      'client_supplement_logs_index': 'client_supplement_log',
      'client_activity_logs_index': 'client_activity_log'
    };
    for (var i = 0; i < indexes.length; i++) {
      var idxKey = indexes[i] + ':' + id;
      var dates = await redis('ZRANGE', idxKey, 0, -1);
      if (dates && dates.length) {
        dates.forEach(function (d) {
          deletes.push(['DEL', logPrefixes[indexes[i]] + ':' + id + ':' + d]);
        });
      }
      deletes.push(['DEL', idxKey]);
    }

    if (deletes.length) await redisPipeline(deletes);
  }

  await Promise.all([
    redis('DEL', 'client:' + id),
    redis('ZREM', 'clients_index', String(id))
  ]);
  return res.status(200).json({ ok: true });
}
```

(Pipeline the deletes to keep this cheap. Order doesn't matter because by design the client record itself goes last so partial failures leave the record pointing at something traceable.)

## P2-002 — POST client never writes the `client_email` lookup, allowing duplicate-email clients

**File:** `api/dashboard/clients.js:58-96`
**Severity:** P2
**Category:** Data integrity

### Observation

The POST handler normalizes the submitted email and queries `client_email:{normalizedEmail}` to detect duplicates (line 70):

```js
var normalized = normalizeEmail(body.email);
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

…but after creating the client it only writes `client:{id}` and the ZSET entry — it never writes `client_email:{normalizedEmail} = id`.

`grep -n client_email: api/**/*.js` confirms the only writers are `api/dashboard/client-portal.js:117` (SET when enabling portal) and `api/dashboard/clients.js:131` (SET on PUT, when portal is already enabled). POST does not write; DELETE does not clean (see P2-001).

### Reproduction

1. `POST /api/dashboard/clients` `{name:"A", email:"x@example.com", tier:"rebuild"}` → id=1, succeeds.
2. `POST /api/dashboard/clients` `{name:"B", email:"x@example.com", tier:"rebuild"}` → id=2, **also succeeds** (the dup-check reads `client_email:x@example.com`, which is still missing).
3. Admin enables portal for client 1 via `POST /api/dashboard/client-portal`. `client_email:x@example.com = 1`.
4. Admin enables portal for client 2 via `POST /api/dashboard/client-portal`. `client_email:x@example.com = 2` (silently overwrites). Client 1 can no longer log in with that email.

### Impact

- Data integrity. The UI almost certainly assumes unique emails per client, but the backend doesn't enforce it until portal enable — by which point two records can already exist.
- Silent lockout. When portal is enabled for the second duplicate, client 1's portal login breaks with no visible cause. Their passwordHash, logs, etc. are still there — they just can't reach them.

### Suggested fix

Write the lookup unconditionally at client creation, so the dup check is always meaningful. Keep the SET in client-portal.js as an idempotent safety:

```js
// after: await redis('ZADD', 'clients_index', Date.now(), String(id));
await redis('SET', 'client_email:' + normalized, String(id));
```

Also worth normalizing on store: `email: normalized` (currently `email: body.email` keeps the raw casing, which is cosmetic-only but means the stored email can diverge from the key used for login).

## P2-003 — Public submit endpoints rate-limit on client-controlled `X-Forwarded-For`, trivially bypassable

**Files:**
- `api/submit-chs-application.js:40-46`
- `api/submit-quiz.js:23-29`
- `api/submit-email.js:28-34`

**Severity:** P2
**Category:** Rate-limit bypass

### Observation

All three public submit endpoints build their rate-limit key from the raw `x-forwarded-for` header:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:*:${ip}`;
const count = await redis('INCR', rateLimitKey);
if (count === 1) await redis('EXPIRE', rateLimitKey, 3600);
if (count > N) return res.status(429).json(...);
```

`X-Forwarded-For` is a comma-separated list; on Vercel, client-supplied values appear to the **left** of the Vercel edge's entry. An attacker who sends `X-Forwarded-For: <random>` on every request produces a unique rate-limit key each time (the whole string, including the random prefix, becomes the key). The counter hits 1 on every request, never crossing N.

The intended caps are:
- `submit-chs-application`: 5/hour
- `submit-quiz`: 10/hour
- `submit-email`: 10/hour (per IP, but keyed to the same shared ratelimit prefix for both sources)

All three can be exceeded without limit by varying the header.

### Reproduction

```sh
for i in $(seq 1 100); do
  curl -s -X POST https://www.telosathleticclub.com/api/submit-quiz \
    -H "Content-Type: application/json" \
    -H "X-Forwarded-For: $RANDOM.$RANDOM.$RANDOM.$RANDOM" \
    -d '{"name":"spam","email":"spam'"$i"'@example.com","totalScore":20}'
done
```

All 100 should return `{"ok":true}` (observable in the admin Leads tab as 100 fresh rows), vs. the intended 10.

### Impact

- Admin dashboards fill with junk submissions, drowning real leads.
- For `submit-chs-application`, every real submission currently has a visible impact (status workflow, notes). Spam makes the list useless.
- `submit-email` writes to the same Redis structures the dashboard reads for `Leads` metrics, poisoning counts.
- No direct billing hit from Resend here (these endpoints don't send email) but Redis op volume scales with abuse.

### Suggested fix

Prefer Vercel-set, non-forgeable headers and only fall back to the right-most hop of `X-Forwarded-For`. A tiny helper in `api/lib/`:

```js
// api/lib/client-ip.js
function clientIp(req) {
  var vf = req.headers['x-vercel-forwarded-for'];
  if (vf) return String(vf).split(',')[0].trim();
  var xff = req.headers['x-forwarded-for'];
  if (xff) return String(xff).split(',').pop().trim();
  return req.headers['x-real-ip'] || 'unknown';
}
module.exports = { clientIp };
```

Then replace the three call sites with `const ip = clientIp(req);`. (The exact Vercel header to prefer is a deployment-config question — confirm which one Vercel's current infra provides; `x-vercel-forwarded-for` and `x-real-ip` are both documented.)

Longer term: if a real attacker becomes a concern, cap by `(ip, email)` or require a lightweight proof-of-work / Turnstile on the forms. But the X-Forwarded-For fix is the one that preserves the current threat model.
