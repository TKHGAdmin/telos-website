## BUG-2026-06-03-01
**Severity**: P1
**Title**: Homepage downloads 1.9MB founder photo on every visit (no lazy-load, no resize)
**Location**: `index.html:252` and `chs.html:946` - `<img src="images/thomas.jpeg">`
**Reproduction**:
1. Open `https://www.telosathleticclub.com/` in Chrome DevTools Network tab with cache disabled, throttle to "Fast 3G".
2. Observe `images/thomas.jpeg` downloads 1.9MB (source is 1206x2136 px).
3. Inspect the `<img>` tag - no `loading="lazy"`, no `width`/`height`, no `srcset`.
4. Note the displayed frame is capped at `max-height: 350px` in `css/style.css:2286`, so the rendered size is roughly 400x350.

**Expected**: Image bytes proportional to its rendered size (~50-150KB), with `loading="lazy"` since the about section is below the fold for almost every viewport.
**Actual**: 1.9MB JPEG downloaded eagerly on first paint of the homepage. Same image is also embedded on `chs.html` without lazy-loading.
**Impact**: Mobile users on cellular pay ~1.9MB of data and lose ~3-6s on slow connections before LCP and TTI. Hurts Lighthouse Performance / Core Web Vitals and likely Vercel Analytics CWV scores. This is the largest single asset shipped by the marketing site by an order of magnitude.
**Suggested fix**: Re-encode `thomas.jpeg` at ~800x1400 (still 2x retina for 400x700 max display) at quality 80, target <150KB. Add `loading="lazy"`, `decoding="async"`, and explicit `width`/`height` attributes to the tag in both `index.html` and `chs.html`. If preserving the existing JPEG path, consider also adding `srcset` for 1x/2x.

## BUG-2026-06-03-02
**Severity**: P2
**Title**: quiz.js cache version mismatch between index.html (v=2) and pricing.html (v=3)
**Location**: `index.html:845` (`js/quiz.js?v=2`) vs `pricing.html:895` (`js/quiz.js?v=3`)
**Reproduction**:
1. `grep -rn "quiz.js" --include="*.html"` from repo root.
2. Observe `index.html` references `?v=2`, `pricing.html` references `?v=3`. Both load the same file `js/quiz.js`.

**Expected**: Both pages reference the same `?v=N` so that any quiz.js update invalidates the cache for both entry points.
**Actual**: Versions diverged. A returning visitor who already cached `quiz.js?v=2` from a previous homepage visit will continue serving the cached (stale) copy on the homepage even after a fix was shipped, while a fresh visit to `/pricing` will fetch the new `?v=3`.
**Impact**: Quiz logic and lead-capture behavior can silently differ between the inline homepage quiz and the pricing gate. Quiz fixes shipped this week may not reach repeat homepage visitors. Lead data quality risk.
**Suggested fix**: Align both references to the highest version (`?v=3`) and update the CLAUDE.md convention to grep all references whenever a shared JS file is bumped. A future improvement is to use a single shared constant or generate the version param at build time.

## BUG-2026-06-03-03
**Severity**: P3
**Title**: chs.html loads main.js without cache-busting version param
**Location**: `chs.html:1050` - `<script src="js/main.js"></script>`
**Reproduction**:
1. `grep -rn "main.js" --include="*.html"` from repo root.
2. Every other page references `js/main.js?v=2`. Only `chs.html` has bare `js/main.js`.

**Expected**: Consistent `?v=N` cache-busting per CLAUDE.md convention ("CSS cache busting: Stylesheet references use ?v=N query param. Bump the version on all pages when changing style.css.") - same principle applies to shared JS.
**Actual**: `chs.html` will serve a long-cached copy of `main.js` indefinitely (or whatever Vercel's default static cache TTL is) regardless of bumps on other pages.
**Impact**: When `main.js` is updated (hamburger nav, scroll animations, counters), Charleston landing-page visitors with a cached copy keep the old behavior. Low frequency now but will cause confusion when CHS gets traffic from in-person events.
**Suggested fix**: Change `chs.html:1050` to `<script src="js/main.js?v=2"></script>` to match the rest of the site.

## BUG-2026-06-03-04
**Severity**: P2
**Title**: Below-the-fold images on chs.html (4 photos, ~370KB combined) are not lazy-loaded
**Location**: `chs.html:922-928` (`chs-events-01.jpg`, `chs-events-02.jpg`, `chs-events-03.jpg`) and `chs.html:950-953` (founder secondary photos)
**Reproduction**:
1. Open `chs.html` in DevTools.
2. Hero image at line 824 correctly has `loading="eager"` + `fetchpriority="high"` (good).
3. All five subsequent images further down the page have no `loading` attribute (defaults to `eager`).

**Expected**: Images below the fold use `loading="lazy"`.
**Actual**: ~370KB of additional event photos plus two thomas-speaking images (~500KB combined) are fetched on initial page load even if the user bounces from the hero.
**Impact**: Extra ~870KB of unnecessary bandwidth on the application landing page on first paint. Hurts LCP and time-to-application-form on mobile.
**Suggested fix**: Add `loading="lazy" decoding="async"` to lines 922, 925, 928, 950, 953 in `chs.html`. Same treatment for the secondary photos on `index.html:258` and `index.html:261`.
