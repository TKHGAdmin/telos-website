## Bug 1 — Engagement-check cron emails inactive clients every single day (P1)

**File:** `api/cron/engagement-check.js` (lines 43-94)
**Cron schedule:** daily at 15:00 UTC (`vercel.json`)

**What's wrong**
The cron looks at the most recent 5 days of `client_dailylog` entries for each client. It sends the reminder email when `lastLogDaysAgo === -1` (no log in the 5-day window) **or** `lastLogDaysAgo >= 3`. There is no per-client "already sent today/this week" guard — no Redis flag, no timestamp check, no `client.lastEngagementEmailAt`. So once a client crosses the 3-day-inactive threshold, the daily cron fires the same email **every day** until they log again.

Walkthrough for a client who last logged 3 days ago and stays inactive:

| Day from inactivity | `lastLogDaysAgo` | Branch taken | Email sent? |
|---|---|---|---|
| Day 3 | 3 | `>= 3` | Yes |
| Day 4 | 4 | `>= 3` | Yes |
| Day 5 | 5 (or -1) | `>= 3` or `=== -1` | Yes |
| Day 6 | -1 (out of 5-day window) | `=== -1` | Yes |
| Day 7+ | -1 | `=== -1` | Yes (forever) |

**Why this matters**
- Spam: an inactive client receives the same nudge every single morning.
- Deliverability: Resend will start throttling and inbox providers will flag the sender domain (`noreply@telosathleticclub.com`) as spam, which also pollutes the weekly-summary deliverability.
- Quiet failure mode: there's no admin signal that this is happening — `sent` is returned per run, but the dashboard does not surface it.

**Reproduction**
Read the cron in isolation; no input causes it to early-exit for a previously-emailed client.

**Suggested fix (sketch — do not implement unless asked)**
Track a per-client `lastEngagementEmailAt` timestamp on the client record (or as a separate Redis key with TTL) and skip if it was sent within, say, the last 7 days. Same shape as the weekly cron's intended once-a-week cadence.

## Bug 2 — Weekly summary streak counter starts from "today" and is therefore almost always 0 (P2)

**File:** `api/cron/weekly-summary.js` (lines 47-90)
**Cron schedule:** Mondays at 14:00 UTC = ~9-10am ET (`vercel.json`)

**What's wrong**
The streak loop iterates `d = 0..6` where `d = 0` is **today** (the day the email is sent). It breaks on the first day with no log:

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

Because the email goes out Monday at ~9am ET, the vast majority of clients have not done their Monday check-in yet when the cron runs. `weekData[0][0]` is therefore null, the loop breaks immediately, and the email displays `Current Streak: 0 days` regardless of how consistent the client was the prior week.

A client who logged Sun + Sat + Fri + Thu + Wed + Tue + Mon-prior (7-day streak) sees "Current Streak: 0 days" if they haven't logged Monday morning yet.

**Why this matters**
The Monday recap is supposed to be a positive reinforcement email; the streak number is the most prominent stat in `buildWeeklySummary` (line 131). A near-universal "0 days" undermines the email's purpose and signals to consistent clients that the system isn't tracking them.

**Reproduction**
1. Be a client who logged the previous week consistently but hasn't logged on Monday yet.
2. Receive the Monday recap email at ~9am ET.
3. Observe "Current Streak: 0 days".

**Suggested fix (sketch — do not implement unless asked)**
Start the streak loop at `d = 1` (yesterday) — the streak is "as of last completed day", which is the natural framing for a Monday morning email. Alternatively, walk backwards from the most recent logged day.

## Bug 3 — Admin session HMAC comparison is not constant-time (P2)

**File:** `api/lib/auth.js` (line 27)

**What's wrong**
`verifyToken` compares the expected HMAC and the user-supplied HMAC with `!==` on hex strings:

```js
if (signature !== expected) return false;
```

The project clearly understands the constant-time-compare pattern: it is used correctly in `verifyPassword` (`auth.js:58`) **and** the client-side equivalent uses `timingSafeEqual` on the HMAC signature itself (`client-auth.js:46-49`):

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

The admin path was simply missed. This is the gate for `/thomas` (business dashboard, client records, revenue, ad spend).

**Why this matters**
String `!==` short-circuits on the first mismatched character. In theory this exposes a timing-oracle on the HMAC; in practice, over the public internet, exploiting it on a SHA-256 hex string is hard. The actionable problem is consistency — the project is half secure-by-construction and half not. The fix is one-liner-cheap.

**Reproduction**
Code review. Same pattern as `client-auth.js:46-49` is missing here.

**Suggested fix (sketch — do not implement unless asked)**
Mirror `client-auth.js:46-49` — buffer-wrap and call `crypto.timingSafeEqual`.

## Bug 4 — Deleting a client orphans the `client_email:` lookup, blocking re-add by email (P2)

**File:** `api/dashboard/clients.js` (DELETE handler, lines 143-149)

**What's wrong**
The DELETE handler only removes the client record and the index entry:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

But when the client portal is enabled, a `client_email:{normalizedEmail}` key is also created (see `client-portal.js:117` and `clients.js:131` in the email-change path). DELETE never removes that key.

On the next POST (create-client) for the same email, line 70-73 of `clients.js` reads the orphaned key and rejects:

```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

The orphaned key now points to a nonexistent client ID, so the error message is misleading and there is no admin way to clear it from the UI.

**Why this matters**
Real workflow case: a client churns, admin deletes them, later they return and admin tries to re-add them with the same email — the dashboard refuses with a wrong error message. The only fix without code change is to manually `DEL client_email:...` in Redis.

This also affects the password-reset flow: `reset-password.js:22` resolves the email to the orphaned `clientId`, then reads `client:{clientId}` (returns null at line 30), returns 200 success silently (intentional anti-enumeration), but the user is told to check email and nothing arrives. So a deleted client requesting a password reset gets a confusing silent failure.

**Reproduction**
1. Create a client via `/thomas` Clients tab.
2. Enable portal access (sets the `client_email:` lookup).
3. Delete the client via the trash icon.
4. Try to add a new client with the same email.
5. Observe "Email already in use by another client" — but no such client exists.

**Suggested fix (sketch — do not implement unless asked)**
In the DELETE handler, fetch the client record before deleting, normalize the email, and `DEL client_email:{email}`. Optionally also clean the portal-data fan-out keys (`client_dailylog:*`, `client_545_*`, `client_training_*`, etc.) or leave that to a later GDPR-style purge.
