# Summary

First run of the Bug Hunter. Focus: Functional. Four real bugs identified, all in `api/` serverless endpoints and all reproducible from the code. One is a hard functional break (deleted-client email cannot be reused), two are abuse / rate-limit gaps on authentication endpoints, and one is user enumeration via distinct login error strings. No application code was modified. Infrastructure (`agent/memory/`, `agent/reports/`, `docs/BUG_REPORT_SCHEMA.md`) was initialized because it did not exist.

# Bugs

## BUG-2026-10-03-01 - Deleting a client leaves email lookup orphaned, blocks re-use

- **Severity**: P1
- **Area**: `api/dashboard/clients.js:143-154` (DELETE handler)
- **What's wrong**: The DELETE path removes `client:{id}` and the `clients_index` entry but never removes the `client_email:{normalizedEmail}` key. Create (`clients.js:70-73`) then rejects any new client with that email forever ("Email already in use by another client"), even though no live client owns it.
- **Repro / Evidence**:
  1. In `/thomas` Client Portal tab, create a client with `a@b.com` and enable portal (which writes `client_email:a@b.com → id`).
  2. Delete that client from the Clients tab.
  3. Try to create a new client with `a@b.com`. The POST handler at `clients.js:70-73` returns 400: "Email already in use by another client". The `client_email:a@b.com` key still points at the deleted id.
  Code reference: no `redis('DEL', 'client_email:' + ...)` call in the DELETE branch.
- **Impact**: Admin is permanently blocked from re-using any email they've previously used. Also leaves derived keys orphaned (`client_dailylog:{id}:*`, `client_nutrition_plan:{id}`, `client_training_program:{id}`, push subscriptions, etc.), which quietly bloats Redis.
- **Suggested fix**: In the DELETE branch, load the client record first (same pattern as PUT), then delete `client_email:{normalizeEmail(client.email)}` alongside `client:{id}`. Optionally also clean up the derived keys using the index ZSETs.

## BUG-2026-10-03-02 - No rate limit on `/api/dashboard/login`

- **Severity**: P1
- **Area**: `api/dashboard/login.js:3-17`
- **What's wrong**: The admin login endpoint accepts unlimited POSTs. There is no per-IP counter, no backoff, no lockout. Every public submission endpoint on the same codebase (quiz, email capture, chs application) rate-limits with Redis INCR + EXPIRE, but the single endpoint that gates the entire business dashboard does not.
- **Repro / Evidence**: Open `api/dashboard/login.js`. The whole file is 17 lines. Compare with `api/submit-quiz.js:22-29` which does rate-limit. An attacker can run `for i in {1..100000}; do curl -X POST https://www.telosathleticclub.com/api/dashboard/login -H 'Content-Type: application/json' -d "{\"password\":\"$i\"}"; done` and brute-force `DASHBOARD_PASSWORD`.
- **Impact**: Entire admin dashboard (clients, revenue, pipeline, Charleston apps, PII of every lead) sits behind a single password with no brute-force defense. Risk scales with password entropy.
- **Suggested fix**: Add the same INCR+EXPIRE pattern on `ratelimit:dashlogin:{ip}` keyed to the first entry of `x-forwarded-for.split(',')[0].trim()`, cap at ~10/hr. Return 429 above the threshold. Same pattern needed on `/api/client/login` and `/api/client/reset-password`.

## BUG-2026-10-03-03 - Password reset request has no rate limit; victim can be email-bombed

- **Severity**: P2
- **Area**: `api/client/reset-password.js:19-67`
- **What's wrong**: The "request reset email" branch has no per-IP, per-email, or per-account rate limit. Each request issues a fresh Resend send (line 45) for any email mapped to a portal-enabled client.
- **Repro / Evidence**: POST `{"email":"client@example.com"}` to `/api/client/reset-password` repeatedly; every call that hits a portal-enabled account triggers a Resend send. No counter is incremented, no lockout. See the full function at `api/client/reset-password.js:16-68` - the only guard is "always return 200" for enumeration defense (which is good, but is independent of rate limiting).
- **Impact**: (a) Any attacker who knows or guesses a client email can flood that client's inbox with reset emails; (b) burns Resend send quota / cost; (c) each successful request also writes a fresh `password_reset:{token}` key with a 1hr TTL, so multiple valid tokens exist simultaneously (expanding the window for a token-stealing attack).
- **Suggested fix**: Add `ratelimit:reset:{normalizedEmail}` (e.g. max 3/hr) and `ratelimit:reset:{ip}` (e.g. max 10/hr) using the same INCR+EXPIRE pattern already in use for public endpoints. Return 200 regardless (preserve enumeration defense), but skip the Resend call when over the per-email limit.

## BUG-2026-10-03-04 - Client login error messages leak account state (user enumeration)

- **Severity**: P2
- **Area**: `api/client/login.js:25-47`
- **What's wrong**: Login returns five distinct error strings that let an attacker distinguish "email does not exist" from "email exists but [portal disabled / inactive / no password set / wrong password]":
  - Line 26: `"Invalid email or password"` (email not found)
  - Line 37: `"Portal access not enabled"` (email exists, flag off)
  - Line 40: `"Account is not active"` (email exists, status != active)
  - Line 43: `"Password not set - contact your coach"` (email exists, no hash)
  - Line 47: `"Invalid email or password"` (email exists, password wrong)
- **Repro / Evidence**: Submit `{"email":"<guess>","password":"x"}` to `/api/client/login`. If the response body is `"Portal access not enabled"` or `"Account is not active"` or `"Password not set - contact your coach"`, the email is a confirmed Telos client. If it is `"Invalid email or password"` it may or may not be a client - but the four non-generic strings alone enumerate the live roster.
- **Impact**: Attacker can enumerate the client roster given a candidate email list. Combined with BUG-2026-10-03-02 (no rate limit on admin login) and BUG-2026-10-03-03 (no rate limit on reset), this provides targeting data for the other attacks. Each client's email is also often their business email (visible to attacker).
- **Suggested fix**: Collapse all five branches to the same generic string `"Invalid email or password"` with the same ~200ms synthetic delay. If a legitimate client with portal disabled hits the endpoint, surface the real message only after a successful password verification (so the signal requires knowing the password anyway).
