## BUG-2026-08-25-1 — Deleting a client orphans the email lookup and blocks re-adding the same email

- **Severity**: P1
- **Focus**: functional
- **Files**: `api/dashboard/clients.js:143-153`, `api/dashboard/client-portal.js:114-124`
- **Status**: new

### What's wrong

The `DELETE /api/dashboard/clients` handler removes only the primary record (`client:{id}`) and the sorted-set entry (`clients_index`). It does NOT remove the `client_email:{normalized_email}` lookup that `client-portal.js` writes when the portal is enabled, nor any of the per-client fan-out keys (daily logs, training logs, nutrition logs, 545 goals/routine, push subscription, plans, sidemenu config, supplement plan, activity logs).

Consequence: if a coach ever enabled the portal for a client and then deletes that client, the email lookup key stays in Redis forever, and any future attempt to create a new client with the same email fails at `clients.js:70-73` with `Email already in use by another client`. The coach hits a confusing error and has no dashboard-side way to clear it. Historical training/nutrition/545 logs and the push subscription also remain, permanently orphaned.

### How to reproduce

1. In `/thomas` → Clients tab, create a client with email `test@example.com`.
2. Open the Client Portal sub-tab and enable the portal (sets a password). This causes `POST /api/dashboard/client-portal` to write `client_email:test@example.com → {id}` (line 117).
3. Have the client log in and record any daily log, training log, or push subscription.
4. Delete that client from the Clients tab (`DELETE /api/dashboard/clients?id={id}`).
5. Verify in Redis: `GET client_email:test@example.com` still returns the deleted id; the client's daily/training/nutrition/supplement/545/activity keys still exist.
6. Try to re-create a new client with `test@example.com` → server returns `400 Email already in use by another client`.

### Suggested fix

In the DELETE branch of `api/dashboard/clients.js` (around line 143), load the client first, then delete the fan-out keys in one pipeline. Rough shape:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });

  var raw = await redis('GET', 'client:' + id);
  var client = raw ? JSON.parse(raw) : null;

  var cmds = [
    ['DEL', 'client:' + id],
    ['ZREM', 'clients_index', String(id)],
    ['DEL', 'client_nutrition_plan:' + id],
    ['DEL', 'client_mindset:' + id],
    ['DEL', 'client_resources:' + id],
    ['DEL', 'client_545_goals:' + id],
    ['DEL', 'client_545_routine:' + id],
    ['DEL', 'client_training_program:' + id],
    ['DEL', 'client_sidemenu:' + id],
    ['DEL', 'client_supplement_plan:' + id],
    ['DEL', 'client_push_sub:' + id],
  ];

  if (client && client.email) {
    var { normalizeEmail } = require('../lib/client-auth');
    cmds.push(['DEL', 'client_email:' + normalizeEmail(client.email)]);
  }

  // Sweep dated logs via their ZSET indexes, then drop the indexes.
  var indexes = [
    'client_dailylogs_index',
    'client_training_logs_index',
    'client_nutrition_logs_index',
    'client_supplement_logs_index',
    'client_activity_logs_index',
    'client_545_index',
  ];
  var perDayPrefix = {
    'client_dailylogs_index': 'client_dailylog',
    'client_training_logs_index': 'client_training_log',
    'client_nutrition_logs_index': 'client_nutrition_log',
    'client_supplement_logs_index': 'client_supplement_log',
    'client_activity_logs_index': 'client_activity_log',
    'client_545_index': 'client_545_daily',
  };
  for (var i = 0; i < indexes.length; i++) {
    var idxKey = indexes[i] + ':' + id;
    var dates = await redis('ZRANGE', idxKey, 0, -1);
    (dates || []).forEach(function (d) {
      cmds.push(['DEL', perDayPrefix[indexes[i]] + ':' + id + ':' + d]);
    });
    cmds.push(['DEL', idxKey]);
  }

  await redisPipeline(cmds);
  return res.status(200).json({ ok: true });
}
```

If a purge-all-fan-out delete feels too aggressive (Thomas may want soft-delete for audit), the minimum fix is to at least clear `client_email:{email}` in the DELETE handler so future re-adds aren't blocked.
