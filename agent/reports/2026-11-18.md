## Summary

## Findings

### F1 - [P1] Admin dashboard reads client fields as snake_case but API returns camelCase

- **Severity:** P1
- **File(s):** `thomas.html:1094`, `thomas.html:1096`, `thomas.html:1288`, `thomas.html:1289`, `thomas.html:1330`, `thomas.html:1331`, `thomas.html:1386`, `thomas.html:1387`, `thomas.html:1429`, `thomas.html:2450`
- **Category:** correctness

**What's wrong.** `/api/dashboard/clients` returns clients with `monthlyRate`,
`startDate`, and `createdAt` (camelCase - see `api/dashboard/clients.js:46,83,84,88,113,115,118`).
The admin UI reads/writes the same fields as `monthly_rate`, `start_date`, and
`created_at` throughout `thomas.html`. There is no translation layer in the
`api()` helper (`thomas.html:835`), so every read returns `undefined` and every
write sends unknown keys that the API ignores.

**Reproduction / evidence.**

- Clients table, rate column: `fmtMoney(c.monthly_rate)` -> blank/`$0` (`thomas.html:1288`).
- Clients table, start date column: `fmtDate(c.start_date)` -> blank (`thomas.html:1289`).
- Edit modal pre-fill: `esc(c.monthly_rate || '')` and `esc(c.start_date ? c.start_date.substring(0,10) : '')` -> empty inputs even when values exist server-side (`thomas.html:1330-1331`).
- Save client: body sends `monthly_rate`/`start_date`, but `clients.js` PUT only touches `body.monthlyRate` (`:115`) and `body.startDate` (`:118`), so these edits silently no-op (`thomas.html:1386-1387`).
- CSV export: `c.monthly_rate` and `c.start_date` columns are empty (`thomas.html:1429`).
- Revenue by Tier chart: `tierRevenue[c.tier] += (c.monthly_rate || 0);` sums undefined -> every tier row renders `$0/mo`, even though `api/dashboard/revenue.js:33-35` already computes a correct `tierBreakdown` that the UI never reads (`thomas.html:2450`).
- Activity feed: sort key `b.start_date || b.created_at || 0` is always `0`, so recent-client ordering is random (`thomas.html:1094,1096`).

**Impact.** Admin-only, but affects Thomas every day: the Clients tab hides
monthly rate and start date, the Clients edit form can't update them, the CSV
export loses both columns, and the Revenue tab's tier breakdown is a chart of
zeroes. Any admin workflow that depends on seeing or changing per-tier numbers
is currently broken.

**Suggested fix.** Replace each snake_case reference in `thomas.html` with the
matching camelCase key (`monthly_rate` -> `monthlyRate`, `start_date` ->
`startDate`, `created_at` -> `createdAt`). For the Revenue-by-Tier chart,
consider using `rev.tierBreakdown` from `/api/dashboard/revenue` directly rather
than recomputing on the client. 10 sites in `thomas.html` plus the save-client
body builder.

### F2 - [P2] DELETE client orphans client_email lookup and portal data, blocks re-adding same email

- **Severity:** P2
- **File(s):** `api/dashboard/clients.js:143-154`
- **Category:** correctness

**What's wrong.** `DELETE /api/dashboard/clients?id=X` removes only `client:{id}`
and the `clients_index` membership. It leaves behind:

- `client_email:{normalizedEmail}` -> still points at the deleted id.
- `client_dailylog:*`, `client_nutrition_log:*`, `client_training_log:*`,
  `client_545_*`, `client_supplement_log:*`, `client_activity_log:*` and
  their `*_index` ZSETs.
- `client_nutrition_plan`, `client_mindset`, `client_resources`,
  `client_training_program`, `client_sidemenu`, `client_supplement_plan`.
- `client_push_sub:{id}` and any `password_reset:{token}` pointing at the id.

The orphaned `client_email:` entry is the most user-visible: the create path
checks it on `clients.js:70-73` and returns `400 "Email already in use by
another client"`, so Thomas can't re-add a deleted client with the same email.

**Reproduction / evidence.**

1. Create client with `email: "foo@example.com"` and enable portal via `client-portal.js POST` (`:115-118` writes the email lookup).
2. Delete the client via `clients.js DELETE` (`:143-154`).
3. Try to re-create with `email: "foo@example.com"` -> `clients.js:70-73` finds the stale lookup and rejects with 400.

Admin UI gives no hint why ("Error: Email already in use by another client"
pops from `thomas.html:1422`).

**Impact.** Admin workflow: can't re-add a churned client who later returns on
their original email without manually editing Redis. Also quietly accumulates
orphan log/profile data for every deleted client, which will matter for data
hygiene and for any future "export my data" / deletion request.

**Suggested fix.** In the DELETE handler, first `GET client:{id}`, then:

1. If parsed and `client.email`, `DEL client_email:{normalizeEmail(client.email)}`.
2. `DEL client_push_sub:{id}`.
3. `DEL` the coach-set content keys listed above (static set of key names).
4. For each `*_logs_index:{id}` ZSET, `ZRANGE 0 -1`, then pipeline `DEL` for every log key, then `DEL` the index.

Fail-open per step so a partial delete still removes the main record. Can be
done in one `redisPipeline` call once the log date list is loaded.

### F3 - [P3] Admin session cookie signature compared with `!==` (not timing-safe)

- **Severity:** P3
- **File(s):** `api/lib/auth.js:27`
- **Category:** security

**What's wrong.** `verifyToken()` compares the HMAC-SHA256 signature from the
cookie against the expected signature with a plain string inequality:

```js
if (signature !== expected) return false;
```

V8 short-circuits on the first mismatching byte, which leaks timing
information about how many leading bytes of the signature an attacker guessed
correctly. `api/lib/client-auth.js:46-49` handles the equivalent client token
signature with `crypto.timingSafeEqual` - the admin path is the odd one out.

**Reproduction / evidence.** `api/lib/auth.js:18-31`:

```js
function verifyToken(token) {
  ...
  const [payload, signature] = parts;
  const expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
  if (signature !== expected) return false;
  ...
}
```

Compare to `api/lib/client-auth.js:46-49`:

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

**Impact.** Theoretical over HTTPS: network jitter buries the per-byte timing
signal, and the attacker would also need a chosen payload (any future expiry
works since `verifyToken` only checks it's an integer > now). Low practical
exploitability, but it's a well-known hardening pattern and `client-auth.js`
already demonstrates the correct approach, so the inconsistency is the
clearest signal that it's unintentional.

**Suggested fix.** Mirror `client-auth.js`:

```js
const sigBuf = Buffer.from(signature, 'hex');
const expBuf = Buffer.from(expected, 'hex');
if (sigBuf.length !== expBuf.length) return false;
if (!crypto.timingSafeEqual(sigBuf, expBuf)) return false;
```
