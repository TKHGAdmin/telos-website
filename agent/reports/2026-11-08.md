## P1 — Engagement-check cron emails inactive clients every single day

**File:** `api/cron/engagement-check.js` (lines 42-94)
**Scheduled:** daily at 15:00 UTC (`vercel.json`)

### What happens
For each active client, the cron reads the last 5 days of `client_dailylog:{id}:{date}`. If the client has not logged in 3+ days, it sends the "We miss you at Telos" email via Resend. There is **no record of when the last engagement email was sent**, so once a client crosses the 3-day inactivity threshold, they receive a reminder **every single day** until they check in.

### Reproduction
1. Create a test client with `status=active`, `portalEnabled=true`, `emailEnabled` unset/true, valid `email`.
2. Ensure no `client_dailylog:{id}:{YYYY-MM-DD}` keys exist for the last 5 days.
3. Trigger the cron (`curl -H "Authorization: Bearer $CRON_SECRET" https://.../api/cron/engagement-check`).
4. Observe one email sent.
5. Wait 24 hours (or trigger again). No new daily log exists. Observe a **second** email sent to the same client, same subject, same body.
6. Repeat for N days — N emails delivered to a client who went on vacation.

### User impact
A client who takes a two-week break for travel, illness, or a family event will receive 11+ identical "We miss you at Telos" emails. Beyond being spammy, this reads as automated nagging from a premium coaching service and risks spam-folder markings that hurt deliverability of transactional emails (password resets, weekly summaries) for every client.

### Suggested fix (for the human to review — agent does not modify app code)
Write a Redis key `client_engagement_sent:{clientId}` on send, with a TTL of e.g. 7 days, and skip clients whose key still exists. Alternative: only send at exactly `lastLogDaysAgo === 3` rather than `>= 3`, so the email is a one-shot per inactivity streak.

## P2 — Client login endpoint has no rate limiting

**File:** `api/client/login.js` (whole handler)

### What happens
The client login handler validates `email` + `password`, looks up the account, and calls `verifyPassword` (PBKDF2, 100k iterations). There is no IP-based or email-based attempt counter. Any attacker who learns a client email (several are visible in testimonials, blog bylines, or the Whop community) can submit unlimited password guesses.

### Reproduction
```
for i in $(seq 1 1000); do
  curl -s -X POST https://www.telosathleticclub.com/api/client/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"known-client@example.com","password":"guess'$i'"}'
done
```
All 1,000 requests return `401` without ever being throttled.

### User impact
1. Brute-force path against a known client identity.
2. Each failed attempt still runs PBKDF2 server-side, so the endpoint is also a modest resource-exhaustion vector (Vercel function invocations + CPU).
Mitigation on the password side (PBKDF2 slowness) helps but is not a substitute for a limiter — especially because the `/api/submit-*` endpoints already demonstrate the IP-rate-limit pattern and could be reused here.

### Suggested fix
Reuse the `ratelimit:{scope}:{ip}` pattern used in `submit-quiz.js` / `submit-chs-application.js`. Suggest 10 attempts per IP per 15 minutes and 20 per email per hour (the email-keyed one catches rotating-IP attacks).

## P2 — Password-reset request endpoint has no rate limiting

**File:** `api/client/reset-password.js` (lines 20-68, Case 1)

### What happens
A POST with `{email: "..."}` always returns `200 {ok:true}` (to prevent email enumeration — good) but if the email resolves to a client with `portalEnabled`, it generates a reset token and fires a Resend email. No rate limit is applied, so anyone can trigger unlimited reset emails to a known client address.

### Reproduction
```
for i in $(seq 1 200); do
  curl -s -X POST https://www.telosathleticclub.com/api/client/reset-password \
    -H 'Content-Type: application/json' \
    -d '{"email":"known-client@example.com"}'
done
```
200 reset emails land in the victim's inbox. Resend quota burned.

### User impact
- **Harassment / mailbox flooding** against any client whose email is public.
- **Resend quota exhaustion**: at ~$0.001/email on the paid tier and 100 emails/day on the free tier, an attacker can disable password reset for everyone by exhausting the daily send budget.
- Each successful request also writes `password_reset:{token}` keys to Redis (3600s TTL) — minor storage cost but accumulates.

### Suggested fix
Apply IP rate limit (e.g., 3 reset requests per IP per hour) and also an email-keyed one (`ratelimit:reset:{normalizedEmail}` — 3/hour). Important: still return `200 {ok:true}` on rate-limited requests so the email-enumeration guard is preserved.

## P3 — Admin session HMAC signature compared with `!==` (not timing-safe), inconsistent with client auth

**File:** `api/lib/auth.js` line 27

### What happens
```js
const expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
if (signature !== expected) return false;    // <-- plain string compare
```
Meanwhile `api/lib/client-auth.js` line 46-49 uses `crypto.timingSafeEqual`. The admin path takes a shortcut the client path doesn't.

### Reasoning on severity
In practice, HMAC-SHA256 with a 64-char secret is not realistically recoverable by timing attack, and the admin login is further limited by the password check in `verifyPassword` which already uses `timingSafeEqual`. So this is **defense-in-depth consistency**, not a live exploit. Dropped to P3 because the real risk is zero; the finding is "both files should match" rather than "admin auth is broken".

### Suggested fix
Replace lines 23-27 of `api/lib/auth.js` with a `crypto.timingSafeEqual` on `Buffer.from(signature, 'hex')` vs `Buffer.from(expected, 'hex')`, mirroring the client-auth implementation. Also add a length guard before the compare.
