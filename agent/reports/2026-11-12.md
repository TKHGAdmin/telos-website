## Findings

### [P1] Deleting a portal-enabled client orphans `client_email:{email}` and blocks re-adding the same email — `api/dashboard/clients.js:143`

**Summary.** The DELETE handler clears `client:{id}` and `clients_index` but
not the `client_email:{normalizedEmail}` → id lookup that was written when
the portal was enabled, so a later POST with the same email 400s with
"Email already in use by another client" pointing at an id that no longer
exists.

**Repro / evidence.** `api/dashboard/clients.js:143-154` only runs
`DEL client:{id}` and `ZREM clients_index id`. The portal-enable path at
`api/dashboard/client-portal.js:117` writes
`SET client_email:{normalizedEmail} = {id}` (and the client login reads it
at `api/client/login.js:24`), but the delete path never removes it. The
create path at `api/dashboard/clients.js:70-73` then checks that same key
and refuses the email. Repro: create client A with portal enabled → delete A
→ try to create client B with A's email → 400 with no UI escape hatch.
The client sub-records (`client_dailylog:*`, `client_545_*`, etc.) are also
orphaned, which is storage-only but worth cleaning up in the same fix.

**Suggested fix.** In the DELETE handler, read the client first, if
`portalEnabled` compute `normalizeEmail(client.email)` and `DEL client_email:{norm}`,
and while there delete the known per-client sub-records listed in CLAUDE.md
("Client Dashboard - Redis Keys").

### [P2] Quiz answer options stay clickable during the 400 ms auto-advance; a second tap double-scores and skips a question — `js/quiz.js:183`

**Summary.** Each option gets its own click handler and `handleAnswerSelect`
waits 400 ms before advancing without disabling the other options. A
mis-tap on a second option within that window adds a second score to the
same pillar and queues a second `renderQuestion()`, flashing and skipping
the next question.

**Repro / evidence.** `js/quiz.js:183-188` attaches a click handler per
option; `js/quiz.js:198-218` adds points and uses `setTimeout(…, 400)` to
advance. No `pointer-events`, `disabled`, or removeChild runs before the
timeout fires. On mobile, two taps within ~300 ms are easy. Both handlers
execute → `quiz.scores[pillar] += option.points` twice → two advances.
Because the two handlers resolve against the same current question, the
net effect is an inflated pillar score plus a flash-skipped next question.

**Suggested fix.** At the top of `handleAnswerSelect`, run
`optionsContainer.querySelectorAll('.quiz-option').forEach(b => b.disabled = true)`
(or set `pointer-events: none` on the container) before the setTimeout.

### [P2] Mobile hamburger stays open while cross-page anchor navigations happen on privacy/terms/set-password — `js/main.js:10`

**Summary.** `main.js` wires smooth-scroll and mobile-menu-close only to
`a[href^="#"]`. On non-index pages the nav links target `/#how-it-works`,
`/#about`, `/#quiz`, `/#faq`, so the hamburger overlay stays rendered during
the cross-page jump.

**Repro / evidence.** `js/main.js:10` is
`document.querySelectorAll('a[href^="#"]')` — matches only in-page anchors.
`privacy.html:95-131`, `terms.html:95-131`, and `set-password.html` use
`href="/#how-it-works"` etc. in both the desktop and mobile nav. Repro:
open `/privacy` on a phone → open hamburger → tap "System". The full-screen
mobile menu stays up during the navigation flash to the homepage. Not
catastrophic but visibly janky and reported by users mis-perceiving a frozen
menu.

**Suggested fix.** Broaden the selector to also match `/#…` hrefs — e.g.
`a[href^="#"], a[href^="/#"]` — and in the click handler compute whether
the current page is the same origin+path as the link target; if same, do
smooth-scroll; if different, just close the mobile menu and let the
navigation proceed.

### [P3] `chs.html` loads `js/main.js` with no cache-buster while every other public page uses `?v=2` — `chs.html:1050`

**Summary.** Single-character drift: `<script src="js/main.js"></script>`
on CHS vs `<script src="js/main.js?v=2"></script>` on
index/pricing/privacy/terms/set-password/resources/product/shop. When
main.js is bumped site-wide, CHS visitors keep the stale cached file until
a hard refresh.

**Repro / evidence.** `grep -rn "js/main\.js" *.html` shows CHS is the only
offender among the pages that include main.js.

**Suggested fix.** Change `chs.html:1050` to `src="js/main.js?v=2"` and
remember to bump it everywhere together on future updates.

### [P3] Service worker caches opaque `fonts.gstatic.com` responses, so the offline fallback can return an empty response — `sw.js:48`

**Summary.** The SW fetches cross-origin font files without specifying
`mode: 'no-cors'` handling for the opaque case, caches whatever comes
back, and relies on it for the offline path. In browsers where the opaque
response has `response.ok === false` the cached read returns nothing and
the font fails silently after first load if the network is lost.

**Repro / evidence.** `sw.js:48-54` for the `fonts.gstatic.com` cache
branch. Low impact — fonts degrade to the system stack — but a visible
flash of fallback type on reconnects.

**Suggested fix.** Either skip the SW cache for cross-origin font responses
(let the browser's HTTP cache handle it) or only `cache.put()` when
`response.ok || response.type === 'opaque'` is paired with a valid
`Content-Length > 0` check.
