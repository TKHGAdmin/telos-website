## P1-1 — Login endpoints have no rate limiting (both admin and client portal)

**Severity**: P1
**Area**: Authentication

**Where**
- `api/dashboard/login.js` (full file)
- `api/client/login.js` (full file)

**What**

Both login handlers accept unlimited POST requests with no per-IP, per-email, or global throttle. This is inconsistent with every other public POST in the codebase — `api/submit-quiz.js`, `api/submit-email.js`, and `api/submit-chs-application.js` all implement `INCR`-based per-IP Redis rate limits.

`api/dashboard/login.js:1-17` only does a timing-safe password check and sets a cookie. `api/client/login.js:9-55` does PBKDF2 verification but otherwise the same — no `ratelimit:login:*` key, no lockout.

**Why it matters**

- Admin password is a single shared secret (`DASHBOARD_PASSWORD` env var). Online brute force is the threat model the timing-safe comparison was designed against, but timing-safety alone doesn't stop guessing — it stops side-channel leakage during guessing. A throttled attacker can still try thousands of common passwords per minute.
- Client passwords use PBKDF2 with 100k iterations, which slows each guess to ~50–100ms server-side. Still trivially brute-forceable for weak passwords (`<10⁴` common-password dictionary completes in under an hour).
- Vercel does not provide per-endpoint rate limiting by default; only platform-level DDoS protection.

**Repro**

```
for i in {1..10000}; do
  curl -X POST https://www.telosathleticclub.com/api/dashboard/login \
    -H 'Content-Type: application/json' \
    -d '{"password":"guess'"$i"'"}' &
done
```

No 429s will be returned.

**Suggested fix**

Add the same IP-based Redis rate limit pattern already used in `submit-*.js`. For login, a tight cap is appropriate — e.g. 5 attempts per IP per 15 minutes:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const key = `ratelimit:login:dashboard:${ip}`;
const count = await redis('INCR', key);
if (count === 1) await redis('EXPIRE', key, 900);
if (count > 5) return res.status(429).json({ error: 'Too many attempts' });
```

For the client login, also key on the lowercased email so a single attacker IP can't lock all clients out:
```
ratelimit:login:client:ip:${ip}
ratelimit:login:client:email:${normalizedEmail}
```
Increment both; reject if either exceeds threshold.

## P2-1 — Client login leaks account state via distinct error messages

**Severity**: P2
**Area**: Authentication / privacy

**Where**
- `api/client/login.js:25-47`

**What**

The handler returns five distinguishable 401 responses:

| Condition | Response body |
|---|---|
| Email not registered | `{"error":"Invalid email or password"}` |
| Client record missing | `{"error":"Invalid email or password"}` |
| Portal access disabled | `{"error":"Portal access not enabled"}` |
| Status ≠ active | `{"error":"Account is not active"}` |
| Password not set yet | `{"error":"Password not set - contact your coach"}` |
| Wrong password | `{"error":"Invalid email or password"}` |

The first two correctly use a generic message, but the next three reveal that the email **is** a registered client. An attacker scraping public sources (Instagram tags, podcast guest lists, Charleston applications) can confirm which of those individuals are Telos clients.

For a coaching brand whose clients pay $1,497–$6,997/month, the client list itself is sensitive — competitors, ex-partners, or doxxers can confirm someone's enrollment.

The reset-password endpoint (`api/client/reset-password.js:25-36`) correctly returns `{ok:true}` for all states specifically to "prevent email enumeration" — that intent is undermined here.

**Suggested fix**

Collapse all failure cases to the same generic 401 body and message. Keep the distinct UX states behind a successful auth, e.g. after correct password verification, return 200 with `{ ok:false, reason:'portal_disabled' }` and surface those messages there.

## P2-2 — Transitive undici CVEs via `@vercel/blob ^0.27.0`

**Severity**: P2
**Area**: Dependencies

**Where**
- `package.json` (declares `"@vercel/blob": "^0.27.0"`)
- `api/dashboard/upload-video.js` (only consumer)

**What**

`npm audit` (after generating `package-lock.json`) reports:

| Advisory | Severity | Package | Range |
|---|---|---|---|
| GHSA-vrm6-8vpv-qv8q — Undici WebSocket permessage-deflate unbounded memory | high | undici | <6.24.0 |
| GHSA-2mjp-6q6p-2qxm — Undici HTTP Request/Response Smuggling | moderate | undici | <6.24.0 |
| GHSA-g9mf-h72j-4rw9 — Undici unbounded decompression chain | moderate | undici | <6.23.0 |
| GHSA-v9p9-hfj2-hcw8 — Undici WebSocket unhandled exception | (see audit) | undici | (see audit) |

All reach the runtime via `@vercel/blob → undici`. Fix path is a semver-major bump:

```
npm install @vercel/blob@^2.4.0
```

**Why it matters (real impact, not just audit noise)**

The actual attack surface is narrow — the only `@vercel/blob` consumer is `api/dashboard/upload-video.js`, which is behind admin auth and only ever talks to the Vercel Blob endpoint (a controlled HTTPS host). So the request-smuggling and unbounded-decompression CVEs are not directly reachable by an unauthenticated user. However:

1. An authenticated admin (or anyone who phishes admin credentials — see P1-1) could upload a crafted payload that triggers the memory exhaustion.
2. Vercel's logging/monitoring will start flagging this once their security scanner notices.
3. The fix is one `npm install` and a quick smoke test of the upload flow.

**Suggested fix**

Upgrade `@vercel/blob` to `^2.4.0` and verify `api/dashboard/upload-video.js` still works (the `put()` signature should be backwards-compatible but check the changelog).

## P3-1 — Non-timing-safe HMAC comparison in admin session verifier

**Severity**: P3
**Area**: Authentication / defense-in-depth

**Where**
- `api/lib/auth.js:27` — `if (signature !== expected) return false;`

**What**

Admin session verification uses a raw string `!==` compare against the expected HMAC. The client-auth module (`api/lib/client-auth.js:46-49`) correctly does the same comparison with `crypto.timingSafeEqual`. The inconsistency is documented in the bytes:

```js
// admin (auth.js)
if (signature !== expected) return false;

// client (client-auth.js)
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

**Why it matters**

Timing attacks against HMAC verification over the public internet are practical only in lab conditions (sub-microsecond resolution, low jitter). Real-world exploitability is very low. But:

- The right primitive is already imported in the sibling file.
- The fix is 3 lines.
- The asymmetry will eventually confuse a future reader into making the client side worse instead of the admin side better.

**Suggested fix**

```js
function verifyToken(token) {
  if (!token) return false;
  const parts = token.split('.');
  if (parts.length !== 2) return false;
  const [payload, signature] = parts;
  const expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
  const a = Buffer.from(signature, 'hex');
  const b = Buffer.from(expected, 'hex');
  if (a.length !== b.length) return false;
  if (!crypto.timingSafeEqual(a, b)) return false;
  if (Date.now() > parseInt(payload, 10)) return false;
  return true;
}
```

## Out of scope but worth noting

- `js/shop.js:15` exposes `SHOPIFY_STOREFRONT_TOKEN = 'c18766911a02794c7e00f4b7d98aea1b'`. This is **not** a leak — Shopify Storefront API tokens are designed to be public client-side. Filed in `learnings.md` as a known false-positive trap.
- Admin auth path-traversal via `filename` in `upload-video.js:29` (`put('courses/' + filename, ...)`) — admin-only, and `@vercel/blob`'s path semantics mean traversal stays within the same blob namespace. Not actionable on its own.
- Empty `SESSION_SECRET` would produce deterministic HMACs without crashing. No defensive check, but this is a deployment-config concern; flagging requires deployment-side evidence to be actionable.
