## P1 — Weekly summary email always shows an undercounted (usually 0-day) streak

**File:** `api/cron/weekly-summary.js:87-90`

**Repro / trace:**
- Cron runs Monday 2pm UTC (9am ET) per `vercel.json`.
- Streak is computed by iterating `d = 0..6`, where `d=0` is today (Monday) via `new Date(now - d * 86400000).toISOString().split('T')[0]`, and breaking at the first missing daily log.
- Almost no client will have submitted Monday's daily check-in by 9am ET.
- Therefore `weekData[0][0].result` is falsy, the loop breaks at `d=0`, and `streak = 0` for essentially every recipient.

```javascript
// Count streak (from today backwards)
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

**Impact:** The "Current Streak" line in every weekly recap email (`buildWeeklySummary`, line 131) will read `Current Streak: 0 days` for nearly all active clients, even for clients who logged every day of the previous week. This directly undercuts the motivational purpose of the email and is visible to every paying client.

**Suggested fix:** Start the streak walk at `d = 1` (yesterday) so today's still-unlogged day doesn't zero out the count. Optionally, if today's log DOES exist, include it (start at `d = 0` but don't break on the first miss when `d === 0`).

**Confidence:** High — the code path is unambiguous and this fires on the very next Monday cron.

## P1 — Duplicate-email check on client create is non-functional; enabling portal silently steals another client's login

**Files:**
- `api/dashboard/clients.js:65-73` (POST create)
- `api/dashboard/client-portal.js:115-118` (POST enable portal)

**Repro / trace:**
1. `clients.js` POST checks `redis('GET', 'client_email:' + normalized)` for duplicates, but `client_email:` is populated ONLY by `client-portal.js` when portal is enabled. New client records are never registered into that lookup on create, so the "already in use" check catches nothing for the normal create flow — two clients with identical emails can be created back-to-back with no warning.
2. `client-portal.js` POST does `redis('SET', 'client_email:' + email, String(client.id))` unconditionally when enabling portal, with no "does another client already own this email?" check.
3. If client A has portal enabled and client B (same email, e.g. couple sharing an email, or a typo duplicate) later has portal enabled, client A's `client_email:` entry is silently overwritten. Client A's login now resolves to client B; A can no longer log in with their own credentials.

`clients.js` PUT (line 121-132) does the right check — but only when portal is already enabled AND the email is being changed via PUT. The create + enable flow bypasses it entirely.

**Impact:**
- Silent data-integrity failure: coach has no visibility that they broke an existing client's login.
- Affected client sees "Invalid email or password" with no recourse; if they hit the password-reset flow, the reset email goes to the OTHER client's email inbox (since `client_email:{email}` -> B's ID, `client:B` has B's email address, and Resend sends the reset link to B).
- Low frequency (requires coincidence), but high blast radius per occurrence, and effectively unfixable from the client side.

**Suggested fix:** In `client-portal.js` before `redis('SET', 'client_email:' + email, ...)` on line 117, `GET` the key first; if it exists and doesn't equal `String(client.id)`, return a 400 with a clear "email already in use" error. Mirror the same guard in `clients.js` POST after portal-enable if that flow is ever added.

**Confidence:** High — traced end-to-end across `clients.js`, `client-portal.js`, `login.js`, and `reset-password.js`.
