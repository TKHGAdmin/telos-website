### [P1] quiz-no-validation: Quiz lead capture accepts empty name/email and silently unlocks pricing

- **Severity**: P1
- **File(s)**: `js/quiz.js:225`, `index.html:577`, `index.html:580`, `pricing.html:591`, `pricing.html:594`
- **Category**: functional
- **Discovered**: 2026-10-11

**What's wrong**

The "See Your Score" button is `type="button"`, which skips the browser's native `required` validation on the `name` and `email` inputs. `quiz.js`'s click handler does not re-validate: it reads the raw input values, writes `telosQuizCompleted=true` to localStorage, POSTs to `/api/submit-quiz`, and renders the results — all whether the fields are filled or not. The `.catch(() => {})` on the fetch (quiz.js:269) silently absorbs the 400 that `api/submit-quiz.js:18` returns when name or email is missing.

**How to reproduce / confirm**

1. Load `https://www.telosathleticclub.com/pricing` in a private window (no `telosQuizCompleted` set).
2. Click "Start Assessment" and answer all 8 questions.
3. On the "Your Score Is Ready" lead-capture card, leave both inputs empty and click "See Your Score".
4. Observe: results render, pricing unlocks, `localStorage.telosQuizCompleted === 'true'`.
5. Check `/thomas` → Leads tab — no row for this session, even though pricing was unlocked.

Code path:
- `pricing.html:594` button is `type="button"` → no native form validation
- `quiz.js:225-275` reads `nameInput.value` and `emailInput.value` without a non-empty check
- `quiz.js:258-269` posts to `/api/submit-quiz`; `api/submit-quiz.js:18-20` returns 400 "Name and email required"
- `quiz.js:269` `.catch(function() {})` swallows the failure; flow continues at `quiz.js:271-274`

**User impact**

Marketing leads are lost from the pricing page's gated quiz — the primary purpose of the gate. Returning visitors with `telosQuizCompleted=true` never see the overlay again, so a once-skipped lead is effectively unreachable. The CRM metrics (quiz completions vs. captured leads) also drift apart, making tier-fit reporting unreliable.

**Suggested fix**

In `quiz.js:225`, before setting state or submitting, validate:
```js
if (!nameInput.value.trim() || !emailInput.value.trim() || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(emailInput.value)) {
  // flash a tiny inline error, keep card visible, don't advance
  return;
}
```
No HTML change needed if `quiz.js` enforces it. (Changing the button to `type="submit"` would also need a `form.addEventListener('submit', ...)` wiring; the JS-side check is the smaller edit.)

### [P2] orphan-client-email: Deleting a client with portal enabled leaves `client_email:` lookup, blocking email reuse

- **Severity**: P2
- **File(s)**: `api/dashboard/clients.js:143`, `api/dashboard/client-portal.js:115`
- **Category**: functional
- **Discovered**: 2026-10-11

**What's wrong**

`DELETE /api/dashboard/clients?id=…` removes `client:{id}` and the `clients_index` ZSET entry (clients.js:147-148) but does **not** delete the `client_email:{normalizedEmail}` reverse lookup that `client-portal.js:117` created when the portal was enabled. The orphaned key remains forever, pointing at a deleted client ID.

**How to reproduce / confirm**

1. In `/thomas` → Clients: create a client with email `test@example.com`, then open Client Portal → Credentials → set a password (this calls `client-portal.js` POST with `enabled=true`, which writes `client_email:test@example.com → {id}`).
2. Back in Clients, click Delete on that row.
3. Create a **new** client with the same email `test@example.com`.
4. Server returns 400: `"Email already in use by another client"` (clients.js:71-73, because `GET client_email:test@example.com` still returns the deleted ID).

Client login for the orphaned email also fails cleanly (login.js:30-32 handles the missing `client:{id}`), so no auth bypass — but the email is permanently squatted.

**User impact**

Thomas can't re-onboard a dropped client, re-use an email after a data-entry mistake, or recycle test addresses. Workaround today is to use a `+tag` suffix or to manually DEL the Redis key. On a growing roster this will quietly accumulate dead keys.

**Suggested fix**

In `clients.js` DELETE (around line 147), before `DEL client:{id}`, load the client and clean up the lookup:
```js
var existing = await redis('GET', 'client:' + id);
if (existing) {
  try {
    var c = JSON.parse(existing);
    if (c.portalEnabled && c.email) {
      var { normalizeEmail } = require('../lib/client-auth');
      await redis('DEL', 'client_email:' + normalizeEmail(c.email));
    }
  } catch (e) {}
}
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```
Also worth clearing the per-client daily-log / nutrition / training ZSET indexes while here, but that's a scope expansion — orphaned log keys are harmless.

### [P3] activity-log-no-cap: `activity-log` POST appends unbounded without size check

- **Severity**: P3
- **File(s)**: `api/client/activity-log.js:62`
- **Category**: functional
- **Discovered**: 2026-10-11

**What's wrong**

`activity-log.js:62-69` reads the existing day's activities array, pushes `body.activity` onto it, and writes the merged JSON back — with no cap on array length and no size cap on the appended activity object. A client (or a buggy loop in the dashboard) can call POST repeatedly and grow the Redis value until Upstash's per-key size limit (1 MB on the free tier) is hit; after that, further POSTs fail opaquely with "Internal error" and the user loses that day's log integrity.

**How to reproduce / confirm**

1. Log in as any client.
2. From devtools, run:
   ```js
   for (var i = 0; i < 2000; i++) {
     fetch('/api/client/activity-log', { method:'POST', headers:{'Content-Type':'application/json'}, body: JSON.stringify({ date: '2026-10-11', activity: { type:'walk', durationMin:30, note:'x'.repeat(400) }}) });
   }
   ```
3. Watch the array grow in `client_activity_log:{clientId}:2026-10-11`. Once the serialized JSON exceeds Upstash's limit, subsequent POSTs 500 and GETs may fail to parse.

**User impact**

Low in normal use (a human won't add 2000 activities), but there's no server-side guard, so any client-side bug (double-fire, retry loop, offline-queue replay) can quietly corrupt a day's log. Same shape of unbounded append exists only in this file — `training-log`, `nutrition-log`, `daily-log` all overwrite, not append.

**Suggested fix**

In `activity-log.js` POST, cap the array length (e.g. 50) and the activity string fields (e.g. 500 chars):
```js
if (body.activity) {
  var a = body.activity || {};
  if (typeof a.note === 'string') a.note = a.note.slice(0, 500);
  log.activities.push(a);
  if (log.activities.length > 50) log.activities = log.activities.slice(-50);
}
```
