## P1 - Homepage ships a 1.9 MB portrait rendered at ~480x350

- **ID**: 2026-08-22-01
- **Severity**: P1
- **Focus**: Performance
- **File(s)**: index.html:252, chs.html:946, images/thomas.jpeg, css/style.css:2284
- **Symptom**: Every visitor to the homepage and the Charleston landing page
  downloads a 1,897,318-byte JPEG (1206x2136 px, portrait) that is rendered
  inside `.about-photo` at `max-height: 350px` inside a column whose desktop
  max-width caps at ~480 px. Roughly 95% of the transferred bytes are
  thrown away by the browser on every visit.
- **Evidence**:
  - `ls -l images/thomas.jpeg` -> 1,897,318 bytes.
  - `file images/thomas.jpeg` -> `1206x2136, baseline`.
  - `css/style.css:2284-2290` -> `.about-photo { width: 100%; max-height: 350px; object-fit: cover; }`.
  - `css/style.css:2356-2358` -> mobile `.about-photo-col { max-width: 480px; margin: 0 auto; }`.
  - `<img src="images/thomas.jpeg" ... class="about-photo">` on
    `index.html:252` and (same file, no `about-photo` class) on
    `chs.html:946`. Neither tag has `srcset`, `sizes`, explicit
    `width`/`height`, or `loading="lazy"`.
  - Section is below the fold on both pages (About/Founder block), so the
    weight is entirely deferrable but currently is not.
- **Fix**:
  - Re-encode `images/thomas.jpeg` at the actual max display size (a 960x1712
    JPEG at Q80 lands around 100-150 KB - roughly a 90-95% reduction) and
    replace the file in `/images/`. Optionally ship a `.webp` alongside and
    use `<picture>` with a JPEG fallback.
  - Add `loading="lazy"` and explicit `width`/`height` (or `aspect-ratio`
    in CSS) to prevent CLS on the `<img>` tags at `index.html:252` and
    `chs.html:946`.
  - The Schema.org LD-JSON `"image"` reference on `chs.html:36` points at
    `thomas-speaking-wide.jpeg` (not `thomas.jpeg`), so re-encoding
    `thomas.jpeg` is safe for SEO.
- **Confidence**: high

## P2 - Below-the-fold `<img>` tags site-wide never opt into lazy loading

- **ID**: 2026-08-22-02
- **Severity**: P2
- **Focus**: Performance
- **File(s)**: index.html:252, index.html:258, index.html:261, chs.html:946, chs.html:950, chs.html:953 (representative; whole marketing site + `/blog` follows the same pattern)
- **Symptom**: `grep -c 'loading="lazy"'` across all `.html` files at the
  repo root and in `/blog/` returns effectively zero matches (the only
  `loading=` attribute found in the marketing site is
  `chs.html:824` which correctly uses `loading="eager" fetchpriority="high"`
  for the hero). Every other `<img>` - including the ~215 KB and ~251 KB
  "Thomas speaking" photos in the About section, plus all blog article
  imagery - is downloaded eagerly regardless of viewport position.
- **Evidence**:
  - `grep -rn 'loading="lazy"\|loading="eager"' *.html blog/ | wc -l` -> 2.
  - `grep -rl '<img' *.html blog/ | wc -l` -> 3 files with `<img>` at the
    root (index.html, chs.html, resources.html) plus additional blog pages.
    Only one image (the CHS hero) has any `loading=` hint.
  - Together the two below-the-fold "speaking" photos on `index.html` add
    ~467 KB of eager transfer that no browser will use before scroll.
- **Fix**: Add `loading="lazy"` to every below-the-fold `<img>` on the
  marketing pages. A one-line convention (all `<img>` outside the hero /
  first viewport should be `loading="lazy"`, hero images stay
  `loading="eager" fetchpriority="high"`) is a small, safe pattern to
  standardize. Also add explicit `width`/`height` at the same time to
  prevent layout shift when the lazy image resolves.
- **Confidence**: high

## P3 - `/api/dashboard/emails` loads all rows before slicing when `source` is unset

- **ID**: 2026-08-22-03
- **Severity**: P3
- **Focus**: Performance
- **File(s)**: api/dashboard/emails.js:28-47
- **Symptom**: When the dashboard requests emails without a `source` filter
  (the default view), the handler pulls the entire
  `email_protein_calculator` and `email_hyrox_predictor` ZSETs into memory
  with `ZREVRANGE key 0 -1 WITHSCORES`, merges them, sorts, and only then
  applies the client-requested `limit` / `offset`. Latency and function
  memory both scale with total lead count rather than with page size.
- **Evidence**:
  ```js
  // api/dashboard/emails.js:30-46
  const [rawProtein, rawHyrox] = await Promise.all([
    redis('ZREVRANGE', 'email_protein_calculator', 0, -1, 'WITHSCORES'),
    redis('ZREVRANGE', 'email_hyrox_predictor',     0, -1, 'WITHSCORES'),
  ]);
  // ...build `all`, sort by score, then slice(offset, offset + limit)
  ```
  With ~200 leads today the cost is invisible; at a few thousand it becomes
  a real dashboard hitch and a Vercel serverless memory concern.
- **Fix**: For the merged view, fetch only what's needed - e.g. pull
  `offset + limit` items from each ZSET (`ZREVRANGE key 0 offset+limit-1
  WITHSCORES`), merge, sort, slice; `total` can still come from two cheap
  `ZCARD` calls added to a pipeline. That drops the per-request work from
  O(N_total) to O(offset + limit).
- **Confidence**: high

  Limitations" as needing a bump when cached assets change. Not new.
