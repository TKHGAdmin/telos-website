# Telos Bug Hunter - 2026-09-03

## Summary
First run of the bug hunter. Focus was functional bugs in the API surface (auth, cron jobs, client lifecycle, service worker). Three real bugs found - two in the client lifecycle (orphaned lookup on delete, no rate limit on password reset) and one reliability bug in the service worker install. All three are reproducible from a code trace and would affect real users.

## Findings

### [P1] Deleting a client leaves orphaned `client_email:` lookup and blocks re-adding that email
- **File**: `api/dashboard/clients.js:143`
- **Category**: cleanup-orphan
- **Reproduction**:
  1. In `/thomas` Client Portal, create client with email `x@y.com`, enable portal (this writes `client_email:x@y.com -> {id}`).
  2. Delete the client via the Clients tab. The DELETE handler at `clients.js:143-154` only calls `DEL client:{id}` and `ZREM clients_index`.
  3. Try to create a new client with `x@y.com`. `clients.js:70-73` fails with "Email already in use by another client" because the orphan `client_email:x@y.com` still points to the deleted ID.
- **Impact**:
  Coach cannot re-add a former client (or fix a typo by delete-and-recreate) without manually purging Redis. Also leaves an unbounded set of stale keys (`client_dailylog:*`, `client_nutrition_*`, `client_training_*`, `client_545_*`, `client_supplement_*`, `client_activity_*`, `client_mindset:*`, `client_resources:*`, `client_sidemenu:*`, `client_supplement_plan:*`, `password_reset:*`) that were fine when created but now belong to nobody.
- **Suggested fix**:
  In the DELETE branch, read the client first, then also DEL `client_email:{normalizeEmail(client.email)}` when it exists. The full log cleanup is a larger question (retention policy), but at minimum the email lookup must go.

### [P1] `/api/client/reset-password` has no rate limit - abusable for email spamming
- **File**: `api/client/reset-password.js:20`
- **Category**: abuse-vector
- **Reproduction**:
  1. `POST /api/client/reset-password` with `{ "email": "victim@example.com" }`.
  2. If the email is a portal-enabled client, Resend fires an email. If not, the endpoint still returns `{ok:true}` silently.
  3. Repeat with a script - there is no `ratelimit:reset:{ip}` counter in the handler. Every other public POST in this codebase (`submit-quiz.js:24-29`, `submit-email.js:29-34`, `submit-chs-application.js`) has one; this one was missed.
- **Impact**:
  An attacker can flood a real client's inbox with reset emails (harassment / phishing pretext) or blow through the Resend send quota. Cost is unbounded per IP.
- **Suggested fix**:
  Add the same rate-limit pattern used by `submit-email.js`: `ratelimit:reset:{ip}` with `INCR` + `EXPIRE 3600`, cap at ~5 per hour. Apply it only to Case 1 (email present, no token) so legitimate token submissions aren't affected.

### [P2] Service worker install fails atomically if any static asset 404s
- **File**: `sw.js:5`
- **Category**: reliability
- **Reproduction**:
  1. `sw.js:14-18` calls `cache.addAll(STATIC_ASSETS)` inside the install `waitUntil`.
  2. `cache.addAll` is atomic per the spec - if any one entry rejects (network error, 404, non-2xx), the whole install rejects and the service worker never activates.
  3. `STATIC_ASSETS` includes `/client-dashboard` (route requires `cleanUrls: true` to resolve; a stale CDN edge or a redeploy race can serve a 404 for a few seconds) and `/manifest.json`. If either flakes on the client's first visit, push notifications and offline caching are silently disabled until the user hard-refreshes.
- **Impact**:
  Silent regression - no user-visible error, but push notifications never register and cached-first fetches never work. Clients on flaky connections during a deploy are the most exposed.
- **Suggested fix**:
  Replace `cache.addAll` with a `Promise.allSettled` loop over `cache.add(url)` per asset, so a single failed asset doesn't abort the install. Also bump the cache name to `telos-v2` when this ships (CLAUDE.md flags this as a pending backlog item).

## Notes
- Verified the password-reset frontend flow does handle `?reset=TOKEN` correctly at `client-dashboard.html:5190-5200`, so the link users click from email is functional. Only the abuse vector is a bug.
- The `verifyPassword` in `api/lib/auth.js:52-59` is safe under the current env config (`DASHBOARD_PASSWORD` is set in Vercel). If that env var were ever cleared or blanked, an empty-string password would pass `crypto.timingSafeEqual(Buffer.from(''), Buffer.from(''))` and grant admin access - worth adding a `if (!expected) return false` guard as defense-in-depth, but not raising as a bug today since it requires a misconfig.
- `js/shop.js:199` writes `product.descriptionHtml` directly via `innerHTML`. Shopify admin content is trusted (single-tenant store owned by Thomas), so this is not a live XSS. Flagging in learnings only - do not report unless the trust model changes.
