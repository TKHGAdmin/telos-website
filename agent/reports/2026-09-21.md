# Telos Bug Report 2026-09-21

## Summary

Visual and accessibility pass across the public site and the client dashboard PWA. Nine real bugs verified at the line. Four P1s: three block keyboard-only or screen-reader clients from primary client-dashboard tasks (FAB menu, modal close, "Forgot password?" link), and one is a WCAG non-text contrast failure on the client tab bar. Four P2s are missing or broken form-label associations on every public lead-gen form (protein calculator, hyrox predictor, homepage quiz, pricing quiz, email gates). One P3 on the CHS form label contrast. No P0s.

## Findings

### [P1] 2026-09-21-01 - FAB menu items in client dashboard are non-focusable, keyboard users cannot log check-ins, food, or activity

- **File:** `client-dashboard.html:1750,1754,1758`
- **Severity:** P1
- **Category:** accessibility
- **Reproduction:** On the Home tab of the client dashboard PWA, a keyboard-only user tabs to the FAB button (which is a real `<button>` with aria-label) and presses Enter. The menu opens. Nothing inside is focusable: the three items are `<div class="fab-menu-item" onclick="...">` with no `role`, no `tabindex`, no key handler. Tab moves focus off the menu entirely. The user has no way to reach the Daily Check-in, Log Food, or Add Activity modals, which are the primary logging surface on Home.
- **Suggested fix:** Change each `<div class="fab-menu-item">` to `<button type="button" class="fab-menu-item">` (buttons are focusable and Enter/Space activate onclick by default). Alternatively add `role="menuitem"`, `tabindex="0"`, and a keydown handler for Enter/Space.
- **Confidence:** high

### [P1] 2026-09-21-02 - Client dashboard modal close buttons have no accessible name

- **File:** `client-dashboard.html:1533,1605,1685`
- **Severity:** P1
- **Category:** accessibility
- **Reproduction:** All three `<button class="modal-close">` (Daily Check-in, Food, Activity modals) contain only an SVG X and have no `aria-label`, no visible text, no SVG `<title>`. VoiceOver announces "button" with no purpose; NVDA the same. Screen-reader users can open the modals but cannot identify or intentionally activate the close control other than by trial.
- **Suggested fix:** Add `aria-label="Close"` to each of the three `modal-close` buttons (or a shared class style with the attribute applied per element).
- **Confidence:** high

### [P1] 2026-09-21-03 - Client login "Forgot password?" and "Back to sign in" are non-focusable spans; a keyboard-only client cannot reset a password

- **File:** `client-dashboard.html:1065,1076,1088`
- **Severity:** P1
- **Category:** accessibility
- **Reproduction:** On the client dashboard login screen, the "Forgot password?" element is `<span class="login-link" onclick="showView('forgot')">Forgot password?</span>` with no `role`, no `tabindex`, no key handler. Tabbing through the login form skips it. A user on a keyboard, on a screen reader, or with a mobile switch who has forgotten their password has no way to reach the reset flow. Same shape for the two "Back to sign in" spans on the forgot and reset views.
- **Suggested fix:** Replace each `<span class="login-link" onclick>` with `<button type="button" class="login-link" onclick>`. The visual styling can be preserved with CSS on the class.
- **Confidence:** high

### [P1] 2026-09-21-04 - Client bottom-tab inactive icons fail WCAG 1.4.11 non-text contrast (~2.63:1); tab labels hidden on inactive tabs

- **File:** `client-dashboard.html:120,125`
- **Severity:** P1
- **Category:** accessibility
- **Reproduction:** Inactive `.dash-tab` uses `color: #505058` on the tab bar background `rgba(6,6,8,0.92)` (near-black). Computed contrast ratio is approximately 2.63:1; WCAG 1.4.11 requires 3:1 for non-text UI. On top of that, `.tab-label` for inactive tabs is set to `opacity: 0; max-height: 0`, so a low-vision user sees only faint icons and the ambiguous "Home" and "Train" glyphs are indistinguishable at a glance. Users on a phone at bright ambient light cannot tell 545 from Nutrition from Profile.
- **Suggested fix:** Raise inactive tab color to at least `#8a8a94` (var(--text-dim), which crosses 3:1) or keep the label always visible with just an opacity or color shift for inactive.
- **Confidence:** high

### [P2] 2026-09-21-05 - Protein calculator form labels are not programmatically associated with inputs

- **File:** `protein-calculator.html:545` (weight, height, age, sex, body fat, activity, goal)
- **Severity:** P2
- **Category:** accessibility
- **Reproduction:** Every `<label>` in the calculator is written as `<label>Body Weight (lbs)</label>` (or `<label id="weightLabel">`) with no `for=` attribute and does not wrap its input. Sighted users see the label, but screen readers announce the input as "spin button" or read only the placeholder. Applies to weight, height, age, sex select, body fat, activity select, and goal select - the entire form.
- **Suggested fix:** Add `for="weight"` (etc.) to each `<label>` matching the corresponding input `id`, or wrap the input inside the label.
- **Confidence:** high

### [P2] 2026-09-21-06 - Hyrox predictor labels reference IDs that do not exist

- **File:** `hyrox-predictor.html:565,582`
- **Severity:** P2
- **Category:** accessibility
- **Reproduction:** `<label for="fiveKTime">5K Run Time</label>` is followed by two inputs `id="fiveKMin"` and `id="fiveKSec"`; no element with id `fiveKTime` exists in the file (grep confirmed). Same pattern for `<label for="rowPace">` above `rowMin` and `rowSec`. Neither the minutes nor the seconds input has a programmatic label; both announce as unlabeled spin buttons.
- **Suggested fix:** Wrap each pair in a `<fieldset><legend>5K Run Time</legend>...</fieldset>` and add `aria-label="Minutes"` / `aria-label="Seconds"` to each input, or split into two labeled inputs.
- **Confidence:** high

### [P2] 2026-09-21-07 - Quiz lead-capture inputs on homepage and pricing page use placeholder-as-label

- **File:** `index.html:577` and `pricing.html:591`
- **Severity:** P2
- **Category:** accessibility
- **Reproduction:** The "Your Score Is Ready" capture form has three inputs (first name, email, phone) with no `<label>` and no `aria-label`. Once a user starts typing or an autofill fires, the placeholder disappears and the visible label goes with it. Screen reader coverage of `placeholder` is inconsistent across NVDA/JAWS/VoiceOver. This form gates every quiz-driven lead on both pages, so it hits every quiz completer.
- **Suggested fix:** Add a visible `<label>` above each input, or at minimum `aria-label="First name"`, `aria-label="Email address"`, `aria-label="Phone number"` on each input.
- **Confidence:** high

### [P2] 2026-09-21-08 - Tool-page email gates have no label on the email input

- **File:** `protein-calculator.html:646` and `hyrox-predictor.html:670`
- **Severity:** P2
- **Category:** accessibility
- **Reproduction:** `<input type="email" id="gateEmail" placeholder="Your email address" required>` (and the hyrox equivalent) has no `<label>` and no `aria-label`. The email gate unlocks the calculated result, so every screen-reader user submitting an email hits an unlabeled control at the highest-intent step of the funnel.
- **Suggested fix:** Add `aria-label="Email address"` to the `#gateEmail` input on both pages, or a visible label above it.
- **Confidence:** high

### [P3] 2026-09-21-09 - CHS application form labels and placeholders fail 4.5:1 text contrast

- **File:** `chs.html:617`
- **Severity:** P3
- **Category:** accessibility
- **Reproduction:** `.chs-field label` uses `color: var(--chs-text-dim)` = `#6b6660` on background `#080608`. Computed contrast is approximately 3.77:1 on 10px `Space Mono` uppercase text; WCAG AA requires 4.5:1 for text this small. Placeholders on the same fields use the identical color and are italicized, so the placeholder does not compensate. Low-vision users cannot read what any field asks for.
- **Suggested fix:** Raise `--chs-text-dim` for labels to at least `#8a8a8a`, or apply a brighter label color only to `.chs-field label`.
- **Confidence:** high
