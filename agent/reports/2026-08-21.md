# Telos Bug Hunter — 2026-08-21

## Summary

First run. Focus: **functional**. Reviewed the full `api/**` surface, the two dashboards' auth/module flows, and the Shopify integration. Found **3 real bugs**, one of them P0: learning modules created via the admin UI cause the client-facing module API to throw and return 500 across the board. The other two are lower-severity but concrete: deleting a client silently orphans their email lookup (blocking email reuse), and the daily-log endpoint mangles legitimate zero-values and empty inputs.

## Findings

### P0 — learning modules crash the client API (schema mismatch on `tierAccess`)

**File** — `api/client/module.js:51-54` and `api/client/modules.js:63-66`

**Failure scenario** — Admin creates or edits a module through `/thomas` → `Learning Modules`. The UI (`thomas.html:2365-2370`) submits `tierAccess` as an **object**: `{ rebuild: true, growth: true, lifestyle: true, lifestyle_plus: true }`. `api/dashboard/modules.js` stores it verbatim (POST line 78, PUT line 124). When any client then calls `GET /api/client/module?id=<id>` or `GET /api/client/modules`, the handler runs `(mod.tierAccess || []).forEach(...)`. `.forEach` does not exist on a plain object, a `TypeError` is thrown, the outer `try/catch` swallows it, and the response is HTTP `500 {"error":"Internal error"}`. Every module in the current schema is affected — the learning-modules feature is end-to-end broken for clients.

**Why it matters** — The Learning Modules feature is a tier-gated deliverable (visible from the client hamburger menu, tracked with progress and completion). Right now every client who opens Growth / Community / Resources content hits a 500 immediately. Silent 500s also mean this bug has probably been in production undetected.

**Suggested fix** — Normalize `tierAccess` to a single shape on read, then fix the write path. Minimal patch in both client handlers:

```js
// api/client/module.js and api/client/modules.js
function tiersFromAccess(ta) {
  if (Array.isArray(ta)) return ta;
  if (ta && typeof ta === 'object') {
    return Object.keys(ta).filter(function (k) { return ta[k]; });
  }
  return TIER_ORDER.slice(); // undefined/null → all tiers (matches POST default)
}
// then:
var tiers = tiersFromAccess(mod.tierAccess);
var minTier = tiers.length
  ? Math.min.apply(null, tiers.map(tierLevel))
  : 0;
```

Follow-up: change `api/dashboard/modules.js` to canonicalize on write (`body.tierAccess = tiersFromAccess(body.tierAccess)`) so old records auto-heal on next admin edit. The admin filter at `api/dashboard/modules.js:39` (`m.tierAccess.indexOf(tier)`) is the same latent bug and gets fixed for free.

### P1 — deleting a client orphans the `client_email:` lookup, blocking email reuse

**File** — `api/dashboard/clients.js:143-154`

**Failure scenario** — Coach creates a client, enables the portal (which writes `client_email:{normalizedEmail} → {id}` in `api/dashboard/client-portal.js:117`), then deletes the client via `DELETE /api/dashboard/clients?id=<id>`. The delete handler only removes `client:{id}` and the `clients_index` ZSET entry — it never touches `client_email:{email}`. Next time the coach tries to add another client with that same email (test cleanup, re-signup, name change, etc.), `POST /api/dashboard/clients` line 70 sees the stale lookup and rejects with `400 "Email already in use by another client"` — pointing at a client that no longer exists. All other per-client data (`client_dailylog:*`, `client_nutrition_plan:*`, `client_training_program:*`, `client_545_*`, `client_sidemenu:*`, push subscriptions, etc.) is also left as orphaned Redis keys.

**Why it matters** — Silent data corruption. The coach cannot fix this from the UI — the only remedy is direct Redis surgery. Real triggers: onboarding a test client and re-adding the real one; a client bouncing off and rejoining; correcting a typo in the original email.

**Suggested fix** — Fetch the client before deleting, then clean up the lookups it owns. Sketch:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });

  var raw = await redis('GET', 'client:' + id);
  var promises = [
    redis('DEL', 'client:' + id),
    redis('ZREM', 'clients_index', String(id)),
  ];
  if (raw) {
    try {
      var c = JSON.parse(raw);
      if (c.email) {
        var { normalizeEmail } = require('../lib/client-auth');
        promises.push(redis('DEL', 'client_email:' + normalizeEmail(c.email)));
      }
    } catch (e) {}
  }
  await Promise.all(promises);
  return res.status(200).json({ ok: true });
}
```

Optional follow-up: also delete `client_push_sub:{id}`, `client_sidemenu:{id}`, and the plan keys — or leave a comment noting they are intentionally retained for auditing. Deleting the two ZSET indexes (`client_dailylogs_index:{id}`, `client_training_logs_index:{id}`, …) can be batched here or handled by a periodic cleanup.

### P2 — `daily-log` POST drops legitimate zero-values and silently rewrites empty inputs to 1

**File** — `api/client/daily-log.js:70-76`

**Failure scenario** — The handler runs three coercions that collapse distinct inputs into the wrong value:

1. `log.steps = parseInt(body.steps, 10) || null;` — a genuine `0` steps entry becomes `null` (treated by the dashboard as "not logged"). Client sees "steps: 0" saved successfully, then reopens the log and sees the field empty.
2. `log.water = parseFloat(body.water) || null;` — same story: `0` glasses of water is not the same as "not tracked."
3. `log.sleep = Math.max(1, Math.min(5, parseInt(body.sleep, 10) || 0));` and the parallel lines for `energy`, `stress`, `mood`. If the client submits with the field cleared (empty string), `parseInt('', 10)` → `NaN` → `|| 0` → `0` → clamped up to `1`. The client sees a "1/5 sleep" score they never chose.

**Why it matters** — This corrupts the very metric the daily check-in exists to capture, and it's silent. It also feeds the streak/execution-score calculations in the weekly-summary cron, so the harm cascades into email content and the Home-tab activity feed.

**Suggested fix** — Distinguish "not provided" from "zero":

```js
function toInt(v)  { var n = parseInt(v, 10);   return Number.isFinite(n) ? n : null; }
function toNum(v)  { var n = parseFloat(v);      return Number.isFinite(n) ? n : null; }
function toRating(v) {
  var n = parseInt(v, 10);
  if (!Number.isFinite(n)) return null;
  return Math.max(1, Math.min(5, n));
}

if (body.sleep  !== undefined) log.sleep  = toRating(body.sleep);
if (body.energy !== undefined) log.energy = toRating(body.energy);
if (body.stress !== undefined) log.stress = toRating(body.stress);
if (body.mood   !== undefined) log.mood   = toRating(body.mood);
if (body.weight !== undefined) log.weight = toNum(body.weight);
if (body.water  !== undefined) log.water  = toNum(body.water);
if (body.steps  !== undefined) log.steps  = toInt(body.steps);
```

`null` here means "explicitly cleared" and `undefined` means "field not sent" — both are handled correctly downstream. If the dashboard's charts assume numeric zero, coerce there instead of in the writer.
