# Telos Bug Hunter Report - 2026-06-29

## Summary

First scheduled run, focus Functional. Three bugs found, all server-side: the engagement-check cron has no throttling and will spam inactive clients with the same reminder email every single day (P1), the admin client DELETE leaks Redis state in two ways (P2), and the public password-reset endpoint has no rate limit (P2).

## Bugs

### Bug 1: Engagement-check cron emails inactive clients every day

- **Severity:** P1
- **Area:** Cron / Client emails
- **File:** `api/cron/engagement-check.js`:60-94, `vercel.json`:23-25
- **Status:** new

**What's wrong**
The engagement-check cron runs daily (`0 15 * * *`) and, for every active client whose most recent `client_dailylog` is 3+ days old, fires a "We miss you at Telos" email. Nothing on the client record tracks "engagement email last sent" and nothing in the cron filters on it, so the same client receives the same email every day they stay inactive.

**Why it matters**
A client who skips a week gets 5 identical "we miss you" emails - quickest way to train clients to mark Telos as spam or unsubscribe entirely. The email contains no escalation, no varying subject line, and no new content day over day, so this is pure noise from the recipient's perspective.

**Repro / evidence**
- `api/cron/engagement-check.js`:60-61: condition is `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`; the only gate is the inactivity window, not whether an email was already sent.
- Lines 76-90: `fetch` to Resend fires unconditionally inside the matched branch; `sent++` is the only state change after.
- Compare to `api/cron/weekly-summary.js`, which is naturally throttled to once a week by its `0 14 * * 1` schedule. The daily cron has no equivalent throttle.

**Suggested fix**
Stamp `client.engagementEmailSentAt` on the client record after a successful send, and skip clients whose previous send is less than ~7 days old. Persist via the same `SET client:{id}` write used elsewhere. Optionally, also skip if `emailEnabled === false` is changed mid-week.

### Bug 2: Admin client DELETE leaks email lookup and orphans all per-client data

- **Severity:** P2
- **Area:** Admin dashboard / Client CRUD
- **File:** `api/dashboard/clients.js`:142-154
- **Status:** new

**What's wrong**
The DELETE handler removes only `client:{id}` and the entry in `clients_index`. It does not delete:
1. The `client_email:{normalizedEmail}` reverse lookup created on POST/PUT for portal-enabled clients.
2. Any of the per-client data the client portal writes - `client_dailylog`, `client_dailylogs_index`, `client_nutrition_*`, `client_545_*`, `client_training_*`, `client_supplement_*`, `client_activity_*`, `client_mindset`, `client_resources`, `client_sidemenu`, `client_supplement_plan`, etc.

**Why it matters**
Two real consequences:
1. **Re-creation blocked.** If an admin deletes a client and then tries to recreate them with the same email (very common during onboarding cleanup), POST `/api/dashboard/clients` returns "Email already in use by another client" because `client_email:{email}` still points at the deleted ID (`api/dashboard/clients.js`:70-73). The error message is misleading because no other client actually exists with that email.
2. **Data leak / quota waste.** All per-client log keys remain in Redis indefinitely. Numeric client IDs come from `INCR id:clients` and never repeat, so this data is unreachable but still billed against the Upstash quota.

**Repro / evidence**
- `api/dashboard/clients.js`:147-148: only two ops on delete.
- `api/dashboard/client-portal.js` (and the client endpoints under `api/client/`) write the additional keys listed above; none are cleaned up here.
- Compare to `api/dashboard/chs-applications.js`:71-77 - cleaner because the schema is simpler, but it does correctly remove both the record and the index entry.

**Suggested fix**
Before deleting, GET the client, normalize the email, and `DEL client_email:{normalized}`. Then sweep the known per-client keys. Easiest: keep a documented list of `client_*` key prefixes in `api/lib/` and loop `DEL` over the per-day keys by pulling dates from each `*_index:{clientId}` ZSET, then `DEL` the index ZSETs and singletons. A pipeline keeps it to one round trip.

### Bug 3: Client password-reset endpoint has no rate limit

- **Severity:** P2
- **Area:** Client auth
- **File:** `api/client/reset-password.js`:19-67
- **Status:** new

**What's wrong**
The "request reset email" branch generates a token and triggers a Resend send on every POST that supplies a known email, with no per-IP or per-email throttle. All three public submit endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) implement `ratelimit:*:{ip}` counters; this one does not.

**Why it matters**
- Abuse vector: anyone who knows a client's email can pound `/api/client/reset-password` and the client will receive an unlimited number of "Reset Your Password" emails. From the client's perspective this looks like an account compromise attempt and erodes trust in Telos's portal.
- Cost / abuse: each request also writes a new `password_reset:{token}` key (1hr TTL) and burns a Resend send. A small loop is enough to drive Resend cost and risk deliverability reputation.
- The endpoint already deliberately returns `200 ok` for unknown emails to prevent enumeration (lines 25-36), so abusers don't even need to know whether an email is valid - the response shape is uniform.

**Repro / evidence**
- `api/client/reset-password.js` has no `INCR ratelimit:*` block anywhere. Walk lines 17-68: validation → email lookup → token gen → unconditional `fetch` to Resend → return.
- `api/submit-email.js`:28-34 is the right shape to copy: per-IP key, EXPIRE on first, cap of N/hour.

**Suggested fix**
Add a per-IP counter (`ratelimit:reset:{ip}`, 5/hour) and a per-email counter (`ratelimit:reset_email:{normalizedEmail}`, 3/hour). Apply both before generating the token / sending the email. Keep returning `200 ok` on limit-exceeded to preserve enumeration-resistance.
