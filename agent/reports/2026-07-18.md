## BUG-20260718-1: Weekly summary email reports streak of 0 for consistently active clients

- **Severity:** P2
- **Area:** api/cron/weekly-summary.js
- **File:** api/cron/weekly-summary.js:86-90

**What's wrong**

The streak counter iterates `d = 0..6` where `d=0` is the current day (today). The cron runs Monday 9am ET, well before most clients would have logged for the day. If today's daily log is missing, the loop immediately breaks and `streak` stays at 0, even if the client logged every one of the previous six days.

**Reproduction**

Trace `api/cron/weekly-summary.js:86-90`:

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

Client Alice logs a daily log Sun, Sat, Fri, Thu, Wed, Tue, Mon (last week). At Monday 9am ET the cron fires. `d=0` looks up today (Monday's) log, finds none, breaks. Alice's weekly recap email says "Current Streak: 0 days" despite a real 7-day streak.

**Impact**

Every active portal-enabled client on the weekly summary list gets a demotivating "streak: 0 days" line every Monday, undermining the recap's stated purpose. The other summary fields (avg score, workouts, days logged) are computed from the same 7-day window and are correct; only the streak is wrong.

**Suggested fix**

Start the streak scan at `d=1` (yesterday) so today's not-yet-logged state doesn't zero it out. Or scan the full 7 days but skip the leading `d=0` gap: `let start = 0; if (!weekData[0][0]?.result) start = 1; for (var d = start; ...)`.

## BUG-20260718-2: Client duplicate-email check silently misses when portal is disabled

- **Severity:** P2
- **Area:** api/dashboard/clients.js + api/dashboard/client-portal.js
- **File:** api/dashboard/clients.js:70-73

**What's wrong**

The duplicate-email guard when creating a client reads the `client_email:{email}` reverse index. That index is only populated by `client-portal.js:115-118` when portal access is enabled on a client. New clients whose portal has never been enabled do not create the reverse mapping, so a second client can be created with the same email address without triggering the guard. When portal is later enabled for both, the second enable overwrites the reverse mapping and the first client can no longer log in by that email.

**Reproduction**

1. Coach creates client A with email `foo@bar.com` (portal not enabled). `client_email:foo@bar.com` is not written.
2. Coach creates client B with the same email `foo@bar.com`. `clients.js:70` checks `client_email:foo@bar.com` → not found → passes the check → B is created.
3. Coach enables portal for A via `client-portal.js` POST → sets `client_email:foo@bar.com` → A.id.
4. Coach enables portal for B → sets `client_email:foo@bar.com` → B.id (overwrites).
5. A tries to log in with foo@bar.com + A's password → `client/login.js:24` resolves the email to B.id, loads B's client record, and verifyPassword fails against B's hash. A is permanently locked out from email login until manually rekeyed.

**Impact**

Data-corruption class: two clients silently share an email until portal enablement collides them, at which point one is orphaned from login. The CLAUDE.md project notes explicitly call out "duplicate email check" as a feature; this bug undermines that contract.

**Suggested fix**

Either (a) write `client_email:{normalizedEmail} → id` at create time in `clients.js:88-91` (and keep it updated in the PUT handler and on email change even when portal is disabled), or (b) maintain a separate always-populated `client_email_any:{email}` index that the dupe guard reads. Option (a) is simpler and mirrors what `client-portal.js` already does.

## BUG-20260718-3: Quiz score can be inflated by rapid multi-clicking within the 400ms advance delay

- **Severity:** P2
- **Area:** js/quiz.js
- **File:** js/quiz.js:183-218

**What's wrong**

`handleAnswerSelect` adds `option.points` to the pillar score and then defers question advance with a 400ms `setTimeout`. During that window, the option buttons remain enabled and unbound event listeners still fire, so a user can click a second (or third) option and stack points on the same question. Each extra click adds another 1-5 points to `quiz.scores[pillar]` before `renderQuestion()` replaces the DOM.

**Reproduction**

Open `/` or `/pricing`, start the quiz, on question 1 click the 5-point option, then within 400ms click the 3-point option. Set a breakpoint on `js/quiz.js:204` or just log `quiz.scores` in the final results: pillar 0 shows 8 points instead of 5 for a single question. Doing this on every question can push the total score from a legitimate ~15 up to the maximum 40.

**Impact**

- Corrupts the analytics stored via `POST /api/submit-quiz` (`totalScore`, per-pillar scores) — Thomas uses these to segment leads.
- Lets prospects on `/pricing` game their execution tier and see the "Executing" result copy even when they'd legitimately land in "System Offline". The pricing gate opens either way, but the tiering messaging is a marketing surface that shouldn't be manipulable.

**Suggested fix**

After the first click in a question, disable all sibling option buttons and set a `handled` flag on the button before scheduling the advance: e.g. inside `handleAnswerSelect`, `optionsContainer.querySelectorAll('.quiz-option').forEach(b => b.disabled = true)` and add an early `return` if already handled. Debouncing via a boolean on `quiz` state (e.g. `quiz.answering`) also works.

## BUG-20260718-4: Client login endpoint leaks account state through error messages

- **Severity:** P3
- **Area:** api/client/login.js
- **File:** api/client/login.js:26-47

**What's wrong**

The login handler returns five distinct error strings for five different failure states: email unknown ("Invalid email or password"), account record missing ("Invalid email or password"), portal disabled ("Portal access not enabled"), status not active ("Account is not active"), password never set ("Password not set - contact your coach"), and wrong password ("Invalid email or password"). An unauthenticated attacker can enumerate which emails belong to Telos clients and infer their portal/account state from the response body alone.

Notably `api/client/reset-password.js:24-36` explicitly returns success for unknown or disabled emails to prevent enumeration, so the intent is already documented in the codebase; the login path just missed it.

**Reproduction**

`curl -X POST https://www.telosathleticclub.com/api/client/login -H 'content-type: application/json' -d '{"email":"probe@example.com","password":"x"}'` returns `{"error":"Invalid email or password"}` for a non-client email but `{"error":"Portal access not enabled"}` for a real client whose portal is off. The status is 401 in every case; only the body differs.

**Impact**

Discloses which people are Telos clients (a private list) and which have active portal access — useful for targeted phishing that name-drops Telos. Small blast radius for a small client roster, but it is a real privacy leak on an unauthenticated endpoint.

**Suggested fix**

Collapse the three "found but not eligible" branches (portalEnabled, status, password-set) into the same generic response used for the not-found and wrong-password cases: `return res.status(401).json({ error: 'Invalid email or password' });`. Keep the granular messages in server logs if the coach wants to debug why a specific login failed.
