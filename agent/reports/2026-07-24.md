### 20260724-01 - Product detail page layout broken on desktop

- Severity: P1
- Area: product.html
- Confidence: high
- Status: new

**What's wrong**

`.product-detail.loaded` is a two-column CSS grid, but the container `#productDetail` has three direct children in this order: `#productImage`, `#productThumbs`, `.product-detail-info`. With default auto-flow the image lands top-left, the thumbnails strip lands top-right (where title/price/Add-to-Cart should be), and the entire info panel wraps to a second row underneath the image. This affects every product, including single-image ones, because the empty thumbs div still consumes a grid cell.

**Reproduction**

1. `npx serve -l 3000 .` and open `http://localhost:3000/product?p=<any-handle>` at desktop width (over 768px).
2. Observe title, price, Add to Cart, and description sitting below the image on the left half; the top-right cell is either blank or occupied by the thumbnail strip.
3. Mobile (under 768px) still renders correctly because the media query collapses to one column.

- product.html:105-108 (CSS - `grid-template-columns: 1fr 1fr`)
- product.html:765-779 (HTML - three direct children)
- js/shop.js:161-177 (JS never removes/hides the thumbs div)

**User impact**

Every product detail page on desktop renders with a broken visual hierarchy. Add to Cart is pushed below the fold; the top of the page looks half-empty. Likely drives shop-page abandonment.

**Suggested fix**

Wrap image and thumbs in one left-column div, or add `#productImage, #productThumbs { grid-column: 1; }` and `.product-detail-info { grid-column: 2; grid-row: 1 / span 2; }`. Also hide `#productThumbs` when it's empty.

### 20260724-02 - Rate limit trivially bypassable via forged X-Forwarded-For

- Severity: P2
- Area: api/submit-email.js, api/submit-quiz.js, api/submit-chs-application.js
- Confidence: high
- Status: new

**What's wrong**

All three public POST endpoints derive the rate-limit key from `req.headers['x-forwarded-for']` verbatim. Vercel appends the true client IP to any client-supplied XFF chain rather than stripping it, so the header the code reads is `<attacker-controlled>, <real-ip>`. An attacker who varies the client-supplied prefix on every request gets a fresh Redis counter each time, defeating the limit entirely. The intended cap (10/hr for email, similar for quiz/CHS) is unenforced.

**Reproduction**

```
for i in $(seq 1 50); do
  curl -sS -X POST https://www.telosathleticclub.com/api/submit-email \
    -H "Content-Type: application/json" \
    -H "X-Forwarded-For: 10.$RANDOM.$RANDOM.$RANDOM" \
    -d '{"email":"a@b.com","source":"protein-calculator"}' &
done
wait
```

All 50 requests succeed with `{"ok":true}` instead of the 41st returning 429.

- api/submit-email.js:28
- api/submit-quiz.js:23
- api/submit-chs-application.js:40

**User impact**

Attacker can flood the leads pipeline with junk quiz submissions and email captures, drowning real leads in Thomas's dashboard. CHS applications get the same treatment (harder to clear since each shows in a separate tab). No user-visible break, but real operational burden.

**Suggested fix**

Parse the header as `header.split(',').map(s => s.trim()).pop()` to take the last hop (Vercel's appended, trusted entry), or switch to `x-real-ip` alone if Vercel guarantees it. Same one-line change in all three files, plus one shared helper.

### 20260724-03 - Enabling portal for a client silently hijacks another client's login mapping

- Severity: P2
- Area: api/dashboard/client-portal.js
- Confidence: high
- Status: new

**What's wrong**

The POST handler unconditionally overwrites `client_email:{normalizedEmail}` with the current client's ID whenever portal is enabled. `api/dashboard/clients.js` POST and PUT both check for a pre-existing owner and return "Email already in use", but the portal-enable path skips that check. If two client records share an email (typo, copy-paste, family address) and admin enables portal for the second one, client A's login credentials silently start authenticating as client B.

**Reproduction**

1. Create client Alice with email `alice@example.com` - portal disabled. No `client_email` mapping is written yet.
2. Create client Bob with the same email `alice@example.com` - portal disabled. Still no mapping. `clients.js` POST allows this because the dup check reads the (still absent) mapping, not the client records.
3. Enable portal for Alice, set a password. `client_email:alice@example.com` now points at Alice's ID.
4. Enable portal for Bob. `client-portal.js` line 117 unconditionally overwrites the mapping to Bob's ID. No warning.
5. Log in with `alice@example.com` + Alice's password: routed to Bob's account, password check fails, Alice sees generic "Invalid email or password". Locked out.

- api/dashboard/client-portal.js:115-118 (unconditional SET, no owner check)
- Compare against api/dashboard/clients.js:70-73 and 124-127 (proper checks)

**User impact**

Admin footgun. Alice's login breaks with a generic "invalid credentials" from `/api/client/login`. No admin-side indicator that Alice was displaced. Support ticket incoming.

**Suggested fix**

Before the SET at line 117, GET the existing mapping. If it exists and points to a different client ID, return 400 with "Email already claimed by another portal user".

### 20260724-04 - Deleting a client leaves orphan Redis mappings

- Severity: P3
- Area: api/dashboard/clients.js
- Confidence: high
- Status: new

**What's wrong**

DELETE only clears `client:{id}` and removes from `clients_index`. Everything else the client accumulated - `client_email:{email}`, `client_dailylog:{id}:*`, `client_training_log:{id}:*`, `client_nutrition_log:*`, `client_545_*`, `client_supplement_*`, `client_activity_log:*`, per-client indices, push subscriptions, unused password-reset tokens - all remain in Redis. The most user-visible consequence: the `client_email` mapping still resolves, so admin cannot recreate a client with the same email (POST returns 400 "Email already in use").

**Reproduction**

1. Create client with email `test@example.com`, enable portal.
2. Delete the client via DELETE /api/dashboard/clients?id={id}.
3. Try to create a new client with the same email. POST returns 400 "Email already in use by another client".
4. Check Redis directly: `client_email:test@example.com` still points at the deleted ID.

- api/dashboard/clients.js:143-153 (two-line cleanup, no mapping purge)
- api/dashboard/client-portal.js:117 (creator of the orphan mapping)

**User impact**

Admin has to know to purge Redis manually or edit the client's email before deletion. Small support-load bug, not a security issue. Also long-term Redis bloat from log keys nobody will ever read.

**Suggested fix**

In DELETE, fetch the client first, then in a pipeline: delete `client_email:{normalizeEmail(email)}` if `portalEnabled`, delete all `client_*:{id}` keys (Upstash lacks `KEYS` in the REST tier - track them via an index set, or extend the DELETE handler to enumerate the known key list). If Redis bloat is not a concern, the minimum fix is just the `client_email` purge - that unblocks the recreate case.
