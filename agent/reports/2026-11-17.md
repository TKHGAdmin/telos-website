## [P2] 2026-11-17-01 — Marketing hamburger button never updates `aria-expanded`

- **ID:** 2026-11-17-01
- **Severity:** P2
- **Area:** visual-ux
- **Location:** `js/main.js:30-34`, `js/main.js:50-58`; the button itself is declared across all public pages (e.g. `index.html:58`, `chs.html:801`, blog articles, etc.).
- **Summary:** The public marketing hamburger toggles only a `.active` class on the button, the mobile menu, and `body.nav-open`. It never sets or updates the `aria-expanded` attribute, so assistive tech cannot tell whether the mobile nav is open or closed.
- **Repro / evidence:**
  - Markup: `<button class="hamburger" aria-label="Toggle menu">` with no initial `aria-expanded`.
  - Handler (`js/main.js:30`):
    ```js
    hamburger?.addEventListener('click', function() {
      body.classList.toggle('nav-open');
      hamburger.classList.toggle('active');
      mobileMenu?.classList.toggle('active');
    });
    ```
  - Compare `client-dashboard.html:1096` where the dashboard hamburger correctly carries `aria-expanded="false"` and the drawer open/close code flips it (`client-dashboard.html:2651, 2661`). The public nav predates that pattern.
- **Impact:** Screen-reader users on every public page (homepage, pricing, chs, product, shop, coaches, blog articles, protein-calculator, hyrox-predictor, privacy, terms, resources, set-password) get no feedback that the menu expanded. WCAG 2.1 SC 4.1.2 (Name, Role, Value) — standard disclosure-widget pattern.
- **Suggested fix:** In `js/main.js`, set the attribute on initial load and toggle it alongside the class — e.g. `hamburger.setAttribute('aria-expanded', hamburger.classList.contains('active'))` inside both the click handler and the link-click close path. No markup change needed.
- **Confidence:** high
- **Decision:** _pending_

## [P2] 2026-11-17-02 — Quiz lead-capture inputs have no accessible label (name / email / phone)

- **ID:** 2026-11-17-02
- **Severity:** P2
- **Area:** visual-ux
- **Location:** `index.html:577-579`, `pricing.html:591-593`.
- **Summary:** The three lead-capture inputs that gate the Execution Score / pricing reveal use `placeholder` as their only label. There is no `<label>`, no `aria-label`, no `aria-labelledby`, and no `autocomplete` attribute. Once the user starts typing, the placeholder disappears and the field loses all textual context.
- **Repro / evidence:**
  - `index.html:577`:
    ```html
    <input type="text" name="name" placeholder="First name" required style="...">
    <input type="email" name="email" placeholder="Email address" required style="...">
    <input type="tel" name="phone" placeholder="Phone number" style="...">
    ```
  - `pricing.html:591` is the same block in the overlay.
  - For contrast, `chs.html:991-1015` wires every field with a real `<label for="...">` + `autocomplete`, which is the correct pattern already in the codebase.
- **Impact:** Screen readers announce these as "edit", "email edit", "phone edit" with no purpose. Browsers also can't autofill cleanly without `autocomplete="given-name" | "email" | "tel"`. WCAG 2.1 SC 1.3.1 (Info and Relationships) and SC 3.3.2 (Labels or Instructions). This form sits at the conversion point — any user who struggles here is a lost lead.
- **Suggested fix:** Either add visually-hidden `<label>`s (`sr-only` style) with `for="..."`, or add `aria-label="First name"` / `aria-label="Email address"` / `aria-label="Phone number"` to each input, and tack on the matching `autocomplete` values. Mirror the `chs-field` pattern from `chs.html`.
- **Confidence:** high
- **Decision:** _pending_
