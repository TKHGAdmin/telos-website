## Bug 1

**ID**: 2026-09-08-01
**Severity**: P1
**Category**: Functional / Layout
**Title**: Product detail page renders broken on desktop - info panel wraps below the image row, thumbs collide with info column

**Files**:
- `product.html:105-108` (CSS: `.product-detail.loaded { display: grid; grid-template-columns: 1fr 1fr; }`)
- `product.html:765-780` (DOM: `.product-detail` has three sibling children)
- `js/shop.js:161-174` (populates `#productImage` and `#productThumbs` at runtime)

**Root cause**: Commit `f5cb8c4` ("feat: add image gallery with thumbnails on product page", 2026-05-20) added `<div class="product-detail-thumbs" id="productThumbs"></div>` as a direct sibling of `#productImage` and `.product-detail-info` inside `.product-detail`. That container is a 2-column CSS grid (`grid-template-columns: 1fr 1fr`). With three children and only two columns, grid auto-placement puts:

- Row 1, col 1 → `#productImage` (the main image)
- Row 1, col 2 → `#productThumbs` (thumbnails, or an empty flex box if the product has only one image)
- Row 2, col 1 → `.product-detail-info` (type, title, price, add-to-cart, description)

The intended layout was clearly image + thumbs stacked in the left column with info in the right column. Instead the info panel now falls to row 2, sitting under the image at half width, while the thumbnails (or an empty div) occupy the space info should have.

The mobile breakpoint (`@media (max-width: 768px)`) sets `grid-template-columns: 1fr`, so all three stack in one column. That happens to look OK on mobile, which is likely why the regression was missed.

**Reproduction**:
1. Open any product detail URL on desktop, viewport ≥ 769px wide: `/product?p=<handle>` for any live Shopify product.
2. Observe: main image is squeezed to left column; add-to-cart / description sit BELOW the image on the next grid row instead of to the right of it.
3. If the product has >1 image, thumbs render to the right of the image where info should be.

**Failure scenario**: Every visitor who clicks a product card on `/shop` (which navigates to `/product?p=<handle>` via `js/shop.js:271`) sees a broken checkout flow: the primary Add to Cart CTA is pushed below the fold on standard desktop viewports, and the visual hierarchy of a premium storefront looks amateur. Directly impacts conversion on the site's newest revenue surface.

**Suggested fix (author to verify)**: Wrap `#productImage` and `#productThumbs` in a single left-column div, so the grid still has exactly two children. Something like:

```html
<div class="product-detail" id="productDetail">
  <div class="product-detail-image-wrap">
    <div class="product-detail-image" id="productImage"></div>
    <div class="product-detail-thumbs" id="productThumbs"></div>
  </div>
  <div class="product-detail-info"> ... </div>
</div>
```

Alternatively, use `grid-template-areas` or move thumbs inside `#productImage` before appendChild-ing them.

**Confidence**: High. Traced from git blame + CSS grid auto-placement rules. No live-site verification available (egress blocked from this environment) - a quick manual load on desktop is warranted before shipping the fix.

## Bug 2

**ID**: 2026-09-08-02
**Severity**: P2
**Category**: Functional / Data integrity
**Title**: Deleting a client leaves orphaned `client_email:` reverse lookup, permanently blocking re-creation of a client with the same email

**Files**:
- `api/dashboard/clients.js:143-154` (DELETE handler - the offender)
- `api/dashboard/clients.js:70-73` (POST handler - the block that fires because of the orphan)
- `api/dashboard/client-portal.js:114-118` (creates the reverse lookup when portal is enabled)

**Root cause**: The DELETE handler removes only two Redis keys:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

It does NOT remove `client_email:{normalizedEmail}`, which is written by `POST /api/dashboard/client-portal` when the coach enables portal access for that client (client-portal.js line 117). After DELETE, that reverse-lookup key still points to the deleted client's ID.

The POST handler in `clients.js` line 70-73 does a pre-flight check:

```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

That check now fires against the orphan and returns 400 to the coach.

**Reproduction**:
1. Coach adds client with `email: jane@example.com`.
2. Coach opens the Client Portal tab and enables portal for Jane. (Now `client_email:jane@example.com` = jane's client id.)
3. Coach deletes Jane from the Clients tab.
4. Coach attempts to create a new client with `email: jane@example.com` (e.g. Jane's second engagement, or she was created in error and needs to be re-added). Result: 400 "Email already in use by another client". There is no UI path to clear the orphan; the coach has to open Upstash and delete the key by hand.

Login flow itself is unaffected (login.js:29-32 handles the "email lookup points to a deleted client" case by returning 401 "Invalid email or password"). Only the coach's re-creation workflow is broken.

Secondary but related: none of the client's per-day log data (`client_dailylog:{id}:{date}`, `client_training_log:{id}:{date}`, etc.) or coach-set plan keys (`client_nutrition_plan:{id}`, `client_training_program:{id}`, side menu, 545 goals/routine, resources, mindset, supplement plan) are cleaned up on delete either. This leaves orphaned data in Redis. Storage cost is negligible; privacy/GDPR could matter if a client asks for deletion.

**Failure scenario**: Concrete sequence in the "Reproduction" section. The coach has no way to recover from the admin UI - only by editing Redis directly or by using a different email for the re-added client.

**Suggested fix**: In the DELETE handler, first read `client:{id}` to recover the email, then also `DEL client_email:{normalizedEmail}`. If a full cleanup is desired, also iterate the daily-log indexes and delete their entries (this is more work; the email-lookup cleanup alone would fully unblock the coach). Sketch:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });
  var raw = await redis('GET', 'client:' + id);
  if (raw) {
    try {
      var client = JSON.parse(raw);
      if (client && client.email) {
        var { normalizeEmail } = require('../lib/client-auth');
        await redis('DEL', 'client_email:' + normalizeEmail(client.email));
      }
    } catch (e) {}
  }
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

**Confidence**: High. Verified against the code paths on both sides (POST guard + DELETE handler + client-portal.js lookup write). Not runtime-verified, but the logic is direct.
