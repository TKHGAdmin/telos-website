## P1-01 - Homepage LCP: 1.9 MB `thomas.jpeg` served at ~350 px rendered height

**Severity:** P1
**Focus area:** Performance
**Files:**
- `images/thomas.jpeg` (source asset)
- `index.html:252`
- `chs.html:946`
- `css/style.css:2284-2296` (`.about-photo { max-height: 350px }`)

### Repro
1. `curl -sI https://www.telosathleticclub.com/images/thomas.jpeg | grep -i content-length` returns ~1.9 MB (1,897,318 bytes locally).
2. `file images/thomas.jpeg` reports intrinsic dimensions of 1206x2136.
3. `index.html:252` and `chs.html:946` both include the image with no `srcset`, no `<picture>`, no `loading="lazy"`, no `decoding="async"`.
4. The image is rendered inside `.about-photo` (see `css/style.css:2284-2296`) with `max-height: 350px; width: 100%; object-fit: cover;` - i.e. capped at ~350 px on the vertical axis. Even at a 2x device pixel ratio, a source of ~1000 x ~700 px would cover the rendered area.

### Impact
- Homepage delivers ~2.4 MB of images before any JS runs; `thomas.jpeg` alone is 1.9 MB of that budget for a photo that is rendered at ~350 px tall.
- On a 4G connection (~5 Mbps), this image adds ~3 s to the About-section paint and competes with the LCP resource for bandwidth.
- Same asset is re-used on `/chs`, doubling the wasted bytes for anyone who visits both pages before the browser cache warms.
- No responsive images (`grep -rn "srcset\|<picture" *.html blog/` returns zero hits site-wide) - so mobile users pay the full desktop weight.

### Fix (suggested)
1. Re-export `thomas.jpeg` at 1000 x ~1770 px (2x DPR for the widest expected column) and save as `thomas.webp` + `thomas.jpeg` fallback. Target < 250 KB.
2. Update `index.html:252` and `chs.html:946` to:
   ```html
   <img src="images/thomas.jpeg" alt="Thomas Kern - Telos Fitness founder"
        class="about-photo" width="1000" height="1770"
        loading="lazy" decoding="async">
   ```
   (or a `<picture>` with `.webp` primary + `.jpeg` fallback).
3. Add explicit `width`/`height` attributes on all About-section images to prevent CLS.

### Confidence
High. Source size, rendered CSS bounds, and lack of `loading`/`srcset` are all directly verifiable from the repo.

## P2-01 - Below-the-fold homepage images render eagerly (~2.4 MB extra above LCP)

**Severity:** P2
**Focus area:** Performance
**Files:**
- `index.html:35` (nav-avatar - small, keep eager)
- `index.html:252` (`thomas.jpeg`, 1.9 MB, About section)
- `index.html:258` (`thomas-speaking-wide.jpeg`, 251 KB, About section)
- `index.html:261` (`thomas-speaking-close.jpeg`, 216 KB, About section)
- `chs.html:945-976` (5 About-section images including `thomas.jpeg` again + `chs-events-01/02/03.jpg`)

### Repro
1. `grep -c '<img ' index.html` returns 4; `grep -n 'loading=' index.html` returns 0. None of the four `<img>` tags declares a `loading` attribute.
2. The About section is roughly 2000 px below the hero on desktop (past the "How It Works", social-proof, and program-tiers sections). None of the three About-section photos are visible on first paint at any common viewport.
3. Same pattern on `/chs`: `chs-hero.jpg` correctly uses `loading="eager" fetchpriority="high"` (chs.html:824), but the four About-section images below have no `loading` attribute.

### Impact
- Every homepage visitor downloads ~2.4 MB of imagery before the browser has finished the LCP resource, even though 100% of the pixels are far below the fold.
- Compounds with P1-01 above: fixing lazy-loading alone eliminates the 1.9 MB thomas.jpeg cost for anyone who bounces before scrolling.

### Fix (suggested)
Add `loading="lazy" decoding="async"` to:
- `index.html:252, 258, 261`
- `chs.html:946` and the analogous `chs-about-image` <img> tags below it (verify `chs-events-01/02/03.jpg` at chs.html:961-976).
Keep the nav avatar (`ig-profile-telos.png`, index.html:35) and `chs-hero.jpg` (chs.html:824) eager as they are.

### Confidence
High. All verifiable via grep and reading the CSS section order.

## P3-01 - Duplicate `.about-photo` and `.about-photo-frame:hover` CSS rules

**Severity:** P3
**Focus area:** Performance (tech debt / cascade clarity)
**Files:**
- `css/style.css:2284-2296` (first definition)
- `css/style.css:3443-3450` (second definition, ~1160 lines later)

### Repro
1. `grep -n "^\.about-photo " css/style.css` returns two hits: line 2284 and line 3443.
2. First block: `.about-photo { ... transition: filter 0.6s ease; }` and `.about-photo-frame:hover .about-photo { filter: grayscale(0%) contrast(1.05); }`.
3. Second block: `.about-photo { transition: filter 0.8s ease, transform 0.8s ease; }` and `.about-photo-frame:hover .about-photo { filter: grayscale(0%) contrast(1.05); transform: scale(1.03); }`.
4. Because both selectors have identical specificity and the second appears later in source order, the second wins - which is presumably the intended effect. But this makes the file harder to reason about and increases the chance of a future edit at line 2284 silently getting overridden.

### Impact
- No runtime user impact today.
- Maintenance risk: a developer editing the first block would not see the override 1100 lines below. On a 3500-line stylesheet with no source map, this is a realistic footgun.
- Marginal bytes over the wire (< 200 B).

### Fix (suggested)
Consolidate both rule blocks into a single `.about-photo { ... }` and `.about-photo-frame:hover .about-photo { ... }` around line 2284, then delete the duplicate at 3443. Preserve the final resolved values: `transition: filter 0.8s ease, transform 0.8s ease;` and the `transform: scale(1.03)` on hover.

### Confidence
Medium. The duplication is real; whether Thomas prefers keeping "layered override" style rules is a judgment call. Marking P3 accordingly - safe to deny if intentional.
