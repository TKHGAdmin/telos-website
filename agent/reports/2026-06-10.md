## Summary

The admin dashboard (`thomas.html`) and its backing API (`api/dashboard/*.js`) disagree on field naming. The UI reads and writes **snake_case** (`monthly_rate`, `start_date`, `follow_up_date`, `created_at`, `score`); the API stores **camelCase** (`monthlyRate`, `startDate`, `followUpDate`, `createdAt`, `quizScore`/`totalScore`, `submittedAt`).

The dashboard's TypeScript-style discipline never caught this because there is no build step. Five user-visible bugs all root-cause to this mismatch. None were obvious from a casual click-through because the broken paths silently fall through to defaults (today's date, tier base price, `null`, `'-'`), not errors.

A sixth bug (client session revalidation) is unrelated.

## 2026-06-10-001 - Client monthly rate, start date, and createdAt timestamps silently dropped on save and blank in display

- **Severity:** P0
- **Focus:** Functional
- **Location:**
  - `thomas.html:1386-1387` (POST/PUT body uses `monthly_rate`, `start_date`)
  - `thomas.html:1288-1289` (display reads `c.monthly_rate`, `c.start_date`)
  - `thomas.html:1330-1331` (edit form prefills from snake_case fields)
  - `thomas.html:1429` (CSV export reads snake_case)
  - `thomas.html:2450` (Overview "Revenue by Tier" reads `c.monthly_rate`)
  - `api/dashboard/clients.js:83-84, 115, 118` (API uses camelCase `monthlyRate`, `startDate`)
- **Reproduction:**
  1. Log into `/thomas`, go to Clients tab, click **+ Add Client**.
  2. Fill name + email + tier, set **Monthly Rate** to something other than the tier default (e.g. $1,800 on a Growth client whose tier default is $1,997), set **Start Date** to a past date.
  3. Save. Reopen the client. The Monthly Rate field is empty; Start Date is empty.
  4. Look at the Clients table - the Monthly Rate column shows empty/N/A; Start Date is blank.
  5. Open the Overview tab - "Revenue by Tier" chart bars all read $0/mo despite active clients.
- **Why this is real:** The API never receives `monthlyRate`/`startDate` keys, so `clients.js:83` falls through to `tierInfo.rate` (tier default) and line 84 falls through to today's date. Every client created via the dashboard has its custom rate silently overwritten with the tier base price, and every start date is forced to today. The stored client object is then read in the UI under the wrong key, so the displayed value is `undefined` -> `fmtMoney(undefined)` -> "N/A".
- **Blast radius:**
  - Custom client rates impossible to set through the UI (sales discounts, promotional rates, grandfathered pricing all silently lost).
  - All Start Dates incorrect (always = creation date); breaks tenure tracking.
  - Overview Revenue-by-Tier chart shows $0 for every tier; coach cannot see tier-level revenue split.
  - Clients table date/rate columns blank; CSV export ditto.
  - Activity feed "Client added" timestamp uses `c.start_date || c.created_at` - both undefined - so all client-added events sort/render as epoch 0.
- **Suggested fix:** Pick a side. Easiest is to change `thomas.html` to use camelCase everywhere (one file, mechanical rename of `monthly_rate` -> `monthlyRate`, `start_date` -> `startDate`, `created_at` -> `createdAt` in all client/lead/submission/email/module render code). Alternative: add an alias layer in the API responses.

## 2026-06-10-002 - Pipeline lead follow-up date and quiz score silently dropped on save; "Due Follow-ups" widget never fires

- **Severity:** P1
- **Focus:** Functional
- **Location:**
  - `thomas.html:1204` (`score:` sent instead of `quizScore`)
  - `thomas.html:1208` (`follow_up_date:` sent instead of `followUpDate`)
  - `thomas.html:994` ("Due Follow-ups" reads `l.follow_up_date`)
  - `thomas.html:1042, 1147, 1155, 1185` (display + days-since logic uses `l.follow_up_date`)
  - `api/dashboard/pipeline.js:53-55` (expects `quizScore`, `followUpDate`)
- **Reproduction:**
  1. Open `/thomas` -> Pipeline tab -> **+ Add Lead**.
  2. Fill in name + email, set **Follow-up Date** to tomorrow, set **Quiz Score** to 22.
  3. Save. Reopen the lead - Follow-up Date is blank; Quiz Score is blank.
  4. Wait until the follow-up date passes; the Overview "Due Follow-ups" section never lists this lead (line 994 filter `l.follow_up_date && ...` always falses).
  5. Also: click "+ Pipeline" on any quiz submission row. The pipeline modal prefills `pl-score` from `s.score`, which is undefined (API stores `totalScore`), so the score field is blank even when the submission has a score.
- **Why this is real:** The PUT/POST body sends `score`/`follow_up_date`. `pipeline.js:53-55` only reads `body.quizScore` and `body.followUpDate`. Both default to `null`/`""`. The whole follow-up-reminder system in the Overview is dead.
- **Blast radius:** Sales operations workflow - coach cannot schedule or be reminded of lead follow-ups via the dashboard. Manual follow-up tracking required.
- **Suggested fix:** Rename `score:` -> `quizScore:` and `follow_up_date:` -> `followUpDate:` in `savePipeline` (thomas.html:1198-1210). Also fix `s.score` -> `s.totalScore` in `addLeadFromQuiz` (thomas.html:2554).

## 2026-06-10-003 - Quiz submission and email-capture tables show empty Date columns; CSV export omits dates

- **Severity:** P1
- **Focus:** Functional
- **Location:**
  - `api/submit-quiz.js:38` stores `submittedAt`
  - `api/submit-email.js:39` stores `submittedAt`
  - `thomas.html:2527` displays `s.created_at` (undefined)
  - `thomas.html:2574` displays `em.created_at` (undefined)
  - `thomas.html:2619` CSV writes `s.created_at` (undefined)
  - `thomas.html:2526` displays `s.score` (undefined - stored as `totalScore`)
- **Reproduction:**
  1. Visit `/` as a logged-out user, take the quiz, submit with email.
  2. Visit `/protein-calculator`, fill it out, submit your email at the gate.
  3. Log into `/thomas` -> Leads tab -> Quiz Submissions sub-view. The Date column is blank for every row. The Score column also blank (because `s.score` should be `s.totalScore`).
  4. Switch to Email Captures sub-view - Date column blank for every row.
  5. Export CSV - date and score columns are empty strings.
- **Why this is real:** Confirmed by reading both endpoints. `submit-quiz.js` and `submit-email.js` each write a `submittedAt` ISO timestamp. The dashboard table renders `fmtDate(s.created_at)` and `fmtDate(em.created_at)`. There is no key called `created_at` on these objects.
- **Suggested fix:** Change `s.created_at` -> `s.submittedAt` (also in CSV export), `em.created_at` -> `em.submittedAt`, and `s.score` -> `s.totalScore` in the renderer at `thomas.html:2526-2527, 2574, 2619`.

## 2026-06-10-004 - Client sessions remain valid after coach disables portal or marks client inactive

- **Severity:** P2
- **Focus:** Functional / Auth
- **Location:**
  - `api/client/login.js:36-41` correctly checks `portalEnabled` and `status === 'active'` at login.
  - `api/client/me.js`, `daily-log.js`, `nutrition-log.js`, `training-log.js`, `five-four-five.js`, `activity-log.js`, `supplement-log.js`, etc. only call `verifyClientSession(req)` which validates the cookie signature - they never reload the client record to recheck `portalEnabled` or `status`.
  - Session cookie lifetime: 7 days (`api/lib/client-auth.js:6`).
- **Reproduction:**
  1. Create a client, enable their portal, log in as that client in a browser.
  2. As admin in `/thomas` -> Client Portal -> set the same client's portal to **Disabled** (or set their status to inactive in the Clients tab).
  3. In the client's browser, click any tab in `/client-dashboard`. Daily logs, nutrition entries, 545 task updates, etc. all continue to succeed. The session works for up to 7 days after disable until the cookie expires.
- **Why this is real:** Verified by `grep -n 'portalEnabled\|client.status' api/client/` - only `login.js`, `reset-password.js`, and `send-email.js` (admin-side cron) check these flags. None of the data-access endpoints do.
- **Suggested fix:** Add a centralized helper in `client-auth.js` like `verifyActiveClient(req)` that returns the parsed client record only if the session is valid AND the client is `active` AND `portalEnabled === true`. Use it in all client endpoints. Alternative (cheaper): invalidate sessions globally by rotating `SESSION_SECRET` when disabling - but that's a sledgehammer.

## 2026-06-10-005 - Duplicate-email check on client creation is effectively a no-op

- **Severity:** P2
- **Focus:** Functional
- **Location:**
  - `api/dashboard/clients.js:68-73` (POST checks `client_email:{normalized}` but never sets it)
  - `api/dashboard/client-portal.js:115-118` (only place where the index is set, gated on `portalEnabled`)
- **Reproduction:**
  1. Open `/thomas` -> Clients -> + Add Client. Create client A with email `foo@example.com`. Do not enable portal.
  2. + Add Client again with the same email `foo@example.com` for client B. The dashboard accepts it - no "Email already in use" error. The dup check at `clients.js:70` reads `client_email:foo@example.com` -> `null` (never written), so the check passes.
  3. Later: enable the portal for client A, then enable it for client B. `client-portal.js:117` does a plain `SET` on `client_email:foo@example.com`. B's `SET` overwrites A's.
  4. Client A tries to log in with their password. `login.js:24` returns B's clientId. `verifyPassword(A's pw, B's hash, B's salt)` fails - A locked out of their own data.
- **Why this is real:** The guard rail is fake. The dup check at creation only works once a client with that email already has portal enabled. For coaches in onboarding flows where clients are added in bulk before portal setup, duplicates can slip through.
- **Suggested fix:** Either (a) write the `client_email:{normalized}` index at client creation time regardless of portal state (and clean it up on delete), or (b) at portal-enable time, check whether the lookup already points at a *different* client ID and refuse. Option (a) is more defensible.
