## BUG-2026-06-07-001 — Product detail page layout breaks because thumbs div is placed in the second grid column

- **Severity:** P1
- **File(s):** `product.html:765-779`, `product.html:106-108`
- **Category:** functional

### What's wrong
The product detail page uses CSS Grid (`grid-template-columns: 1fr 1fr`) on `.product-detail`. The latest commit (`f5cb8c4` — "feat: add image gallery with thumbnails on product page") added `<div class="product-detail-thumbs" id="productThumbs"></div>` as a direct sibling of `.product-detail-image` and `.product-detail-info`. That gives the grid three children, not two. Auto-flow places them as: row 1 col 1 = image, row 1 col 2 = thumbs, row 2 col 1 = info. The product title/price/Add to Cart/description column gets shoved BELOW the image instead of beside it, and the empty thumbs div occupies the right column on every product (even single-image ones, because `shop.js:168` only fills `thumbsEl.innerHTML` when `allImages.length > 1`). Every product detail page is currently rendering the info block in the wrong location.

### How to reproduce
1. Visit `/product?p=<any-handle>` on a wide viewport (>768px).
2. Observe that the title, price, Add to Cart button, and description appear stacked below the main image rather than to its right.
3. Open DevTools and inspect `#productDetail` — confirm it has three direct children and `display: grid; grid-template-columns: 1fr 1fr;`.
4. Even on a product with only one image, `#productThumbs` is empty but still claims grid cell (row 1, col 2).

### Suggested fix
Wrap `#productImage` and `#productThumbs` in a single `<div class="product-detail-gallery">` so the grid sees only two children again. Alternatively, set `#productThumbs { grid-column: 1; }` so it stacks under the image and `#productImage`/`#productThumbs` stay in column 1 while info stays in column 2 — but the wrapper approach is cleaner because the CSS for `.product-detail-thumbs` already has `margin-top: 12px`, which expects it to sit directly under the image.

## BUG-2026-06-07-002 — Weekly summary email always reports "Current Streak: 0 days" when the cron runs on Monday morning

- **Severity:** P1
- **File(s):** `api/cron/weekly-summary.js:86-90`, `api/cron/weekly-summary.js:124-141`
- **Category:** functional

### What's wrong
The weekly summary cron runs at `0 14 * * 1` (Monday 14:00 UTC = 09:00 ET, per `vercel.json:21`). The streak calculation iterates `d = 0..6` starting at today (Monday) and breaks the moment a day has no log:

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

At 9 AM on a Monday, virtually no client has logged today's daily check-in yet, so `d=0` returns no result and the loop breaks immediately → `streak = 0`. The email then renders `<strong>0 days</strong>` for "Current Streak" even when the client had a 6-day streak through Sunday. Worse: `daysLogged` (which is just a tally, not a consecutive run) will correctly report e.g. "6 / 7", producing the contradictory line pair:

```
Current Streak: 0 days
Days Logged: 6 / 7
```

This is the very first content most active clients see in their week — it undermines the whole point of the summary.

### How to reproduce
1. In Redis, create logs for a test client for the last 6 days excluding "today" (Monday).
2. Invoke `/api/cron/weekly-summary` with the proper `Authorization: Bearer $CRON_SECRET` header.
3. Inspect the generated HTML in the Resend dashboard (or by logging `emailHtml`) — confirm `<strong>0 days</strong>` next to "Current Streak" and `<strong>6 / 7</strong>` next to "Days Logged".

### Suggested fix
Either (a) skip today in the streak count — start the loop at `d = 1` so the streak measures consecutive logged days up to **yesterday**, or (b) compute the streak from the full `client_dailylogs_index` ZSET rather than the 7-day window so it reflects the client's actual current streak (this is what the in-app UI shows). Option (b) matches user expectation better and avoids the "looks reset" feeling on Monday mornings.

## BUG-2026-06-07-003 — Engagement-check cron re-emails the same inactive client every day with no de-duplication

- **Severity:** P2
- **File(s):** `api/cron/engagement-check.js:42-94`, `vercel.json:23-25`
- **Category:** functional

### What's wrong
The engagement-check cron runs daily (`0 15 * * *`) and emails any client whose most-recent daily log is 3+ days old. There is no record of when (or whether) we last sent that client an engagement email — every active client with `portalEnabled` and `emailEnabled !== false` who hasn't logged in 3 days gets a "We miss you at Telos" email **every single day** they remain inactive. A client who goes on a 10-day vacation receives 8 identical emails. There is no field check on `client.lastEngagementEmailAt` or anything similar, and no per-day key like `engagement_sent:{clientId}:{date}` is being written.

### How to reproduce
1. Pick a test client; ensure no `client_dailylog:*` exists for the last 5 days.
2. Invoke `/api/cron/engagement-check` twice on the same day (or two days in a row).
3. Confirm two reminder emails arrive — code path runs the Resend POST unconditionally each time the inactivity check passes.

### Suggested fix
Before sending, check or write a small lock key like `engagement_sent:{clientId}:{YYYY-MM-DD}` with a ~30-hour TTL (or just gate on `client.lastEngagementEmailAt > now - 6 days`). Skip the send if the lock exists. Alternatively, only send when `lastLogDaysAgo` is exactly 3 — that turns the email from a "daily nag" into a single nudge at the moment a client crosses the inactivity threshold, which matches how most engagement systems work.
