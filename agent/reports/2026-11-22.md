## Findings

### 1. [P2] `/coaches` page is a navigation dead-end

**File**: `coaches.html:292-298` (nav), `coaches.html:472` (footer)
**Category**: Functional / UX
**Introduced**: commits `1ac858d` and `5a75f3d` (recent).

**Problem**
The `coaches.html` page has no link back to the rest of the Telos Athletic Club site. The nav contains only in-page anchor links (`#member`, `#coach`, `#science`, `#compare`, `#pricing`) and the brand logo also points at an in-page anchor (`href="#hero"`). The footer is `<footer><div class="wrap"><span>Telos · by Telos Athletic Club · Charleston, SC</span><span>…</span></div></footer>` — no links at all. The only outbound link on the page is the WhatsApp CTA. `grep "href=\"" coaches.html` outside anchors and externals returns only favicon references.

**Reproduction**
1. Visit `https://www.telosathleticclub.com/coaches` (e.g. from the early-adopter WhatsApp group or an ad).
2. Try to get to online coaching, pricing, Charleston, or the home page.
3. There is no link. Only the browser back button works, and users who arrived cold have nowhere to go.

**Impact**
Visitors who aren't ready to join the WhatsApp group are a bounce. Also prevents organic cross-sell to the coaching tiers for clients who could use the service for themselves.

**Recommendation**
Either (a) add a secondary "Online coaching for athletes" link in the header or footer pointing at `/` (or `/pricing`), or (b) confirm this is intentional for the B2B-coach landing experience and we want it to be a single-exit funnel. If kept, at minimum the TELOS logo should point at `/` rather than `#hero` so homepage traffic behaves predictably.

### 2. [P2] Client login leaks account state via distinct error messages

**File**: `api/client/login.js:33-47`
**Category**: Functional / Security (user enumeration)

**Problem**
The login endpoint returns four different error strings depending on account state:

```js
if (!client.portalEnabled) return res.status(401).json({ error: 'Portal access not enabled' });
if (client.status !== 'active') return res.status(401).json({ error: 'Account is not active' });
if (!client.passwordHash || !client.passwordSalt) return res.status(401).json({ error: 'Password not set - contact your coach' });
…
if (!verifyPassword(...)) return res.status(401).json({ error: 'Invalid email or password' });
```

An attacker who tries an email address can learn whether it belongs to a Telos client, and if so whether the portal is enabled, whether the account is active, and whether a password has been set. The password-reset endpoint (`api/client/reset-password.js:22-35`) handles this correctly — it returns `{ ok: true }` for every case to prevent enumeration. Login does not.

**Reproduction**
```bash
curl -s -X POST https://www.telosathleticclub.com/api/client/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"someone-who-exists@example.com","password":"wrong"}'
# → {"error":"Password not set - contact your coach"}   ← confirms the email exists
```

**Impact**
Low-volume targeted enumeration against the client roster (phishing follow-ups, credential stuffing with known-valid emails). Business impact is bounded because the client base is small, but it's the exact pattern reset-password already defends against.

**Recommendation**
Collapse the four client-state branches into a single `return res.status(401).json({ error: 'Invalid email or password' })`. Keep the internal reasons in `console.error` for debugging. Follow the pattern already used in `api/client/reset-password.js`.

### 3. [P3] Admin session HMAC signature compared with `!==` instead of `crypto.timingSafeEqual`

**File**: `api/lib/auth.js:22-25`
**Category**: Functional / Security (timing-safe consistency)

**Problem**
`verifyToken()` in the admin auth lib compares the HMAC signature with a plain string compare:

```js
const expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
if (signature !== expected) return false;
```

The sibling client-auth lib (`api/lib/client-auth.js:46-50`) uses `crypto.timingSafeEqual` for the same operation:

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

Timing attacks against HMAC verification over the public internet are very hard to execute in practice (network jitter dwarfs the signal), so the real-world risk is low — but the inconsistency between the two libs is noteworthy and `verifyPassword()` in the same file already uses `timingSafeEqual` correctly, so the admin HMAC check is the odd one out.

**Reproduction**
Diff `api/lib/auth.js` against `api/lib/client-auth.js`. The client version is timing-safe; the admin version is not.

**Recommendation**
Replace lines 22-25 with the same timing-safe compare the client lib uses, converting both sides to Buffers of equal length first. Trivial change; brings both auth paths onto the same pattern.
