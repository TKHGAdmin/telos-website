# Telos Bug Hunter — 2026-08-17

**Focus**: Functional (with security-adjacent findings — first run, wide net)

## Summary

This is the first run of the daily bug hunter. I bootstrapped the memory, focus-rotation, and schema files (see `chore(agent): bootstrap bug hunter scaffolding`), then swept the entire `api/` surface: 3 public submit endpoints, 23 client endpoints, 16 admin endpoints, 2 cron jobs, and the two auth libraries. The scan surfaced one meaningful auth-lifecycle bug (revoked clients keep working for up to 7 days), one silent data-corruption bug in the Revenue tab math, one orphaned-record bug that will bite the next time you delete and re-add a client, and three missing-rate-limit gaps (client login, admin login, password-reset email trigger). Every finding was traced back to concrete file lines and verified against the current code — nothing is theoretical.

## Bugs

### Bug: 2026-08-17-01 - Revoked client keeps portal access for up to 7 days after disable

- **Severity**: P1
- **Category**: functional (security-adjacent)
- **File**: `api/lib/client-auth.js:63-66` (and every consumer under `api/client/*.js`)
- **First seen**: 2026-08-17
- **Description**: `verifyClientSession()` only checks the HMAC signature and expiry of the `telos_client_session` cookie. It never re-reads the client record to check `portalEnabled` or `status`. Login (`api/client/login.js:36-41`) correctly rejects a disabled or non-active client, but the token minted at login is valid for **7 days**. Every downstream endpoint (daily-log, training-log, nutrition-log, food-search, activity-log, supplement-log, five-four-five, mindset, resources, module, module-progress, push-subscribe, me, notify, send-email) just does `verifyClientSession(req)` and trusts the client id. Net effect: if a coach revokes a client's portal because a contract ended or credentials were compromised, the client keeps reading and writing their portal until the cookie naturally expires.
- **Failure Scenario**: (1) Client logs in, gets a 7-day cookie. (2) Coach opens `/thomas → Client Portal`, disables the portal (`enabled: false`) or flips `status` to `inactive`. (3) Client continues hitting `/api/client/daily-log`, `/api/client/training-log`, `/api/client/food-search`, etc. All return 200 and mutate Redis for up to 7 days.
- **Evidence**:
  ```js
  // api/lib/client-auth.js
  function verifyClientSession(req) {
    var cookies = parseCookies(req.headers.cookie);
    return verifyClientToken(cookies[COOKIE_NAME]);   // no DB check
  }

  // api/client/daily-log.js (representative of all client endpoints)
  var clientId = verifyClientSession(req);
  if (!clientId) return res.status(401).json({ error: 'Unauthorized' });
  // ...writes to Redis without re-checking portalEnabled/status
  ```
- **Suggested Fix**: Add an async helper `requireActiveClient(req)` in `lib/client-auth.js` that returns the client record (or null) after checking `portalEnabled && status === 'active'`. Have each `api/client/*.js` endpoint use it. Alternative (cheaper): shorten client session duration to 1 day so revocations take effect within 24h.
- **Confidence**: high

### Bug: 2026-08-17-02 - Deleting a client leaves an orphan email lookup, blocking re-creation with the same email

- **Severity**: P2
- **Category**: functional
- **File**: `api/dashboard/clients.js:143-154`
- **First seen**: 2026-08-17
- **Description**: The DELETE handler removes `client:{id}` and the `clients_index` entry, but never deletes the `client_email:{normalizedEmail}` reverse-lookup that the Client Portal creation flow wrote. The next time you try to create a client with that same email, the duplicate check at `clients.js:70-73` finds the stale mapping and returns `Email already in use by another client` — even though no such client exists anymore. Manual Redis surgery is the only way out.
- **Failure Scenario**: (1) Create client Alice with `alice@example.com`, enable her portal (this writes `client_email:alice@example.com → alice.id`). (2) Delete Alice via the admin dashboard. `client:{alice.id}` is gone, but `client_email:alice@example.com` is not. (3) Re-add a client with `alice@example.com` → 400 error, cannot proceed from the UI.
- **Evidence**:
  ```js
  // api/dashboard/clients.js DELETE (143-154)
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
  //     ^^^ client_email:{email} is never deleted
  ```
- **Suggested Fix**: Before the `DEL`, `GET client:{id}` → parse → `DEL client_email:{normalizeEmail(client.email)}`. Same pattern the PUT already uses at line 130.
- **Confidence**: high

### Bug: 2026-08-17-03 - Ad spend PUT does not update the ZSET score, corrupting monthly ad-spend on the Revenue tab

- **Severity**: P2
- **Category**: functional
- **File**: `api/dashboard/adspend.js:84-106`
- **First seen**: 2026-08-17
- **Description**: The PUT handler accepts a new `date` and rewrites the entry blob, but it never re-`ZADD`s the id with the new score into `adspend_index`. `api/dashboard/revenue.js:66` computes "monthly ad spend" via `ZRANGEBYSCORE adspend_index monthStart +inf`, which uses that score. So if you edit an entry's date across a month boundary, the entry silently keeps its old month's score and the Revenue tab's `monthlyAdSpend` (and downstream CPA math) shows the wrong number without any warning.
- **Failure Scenario**: (1) Create an ad-spend entry with `date: 2026-07-30`, `spend: 500`. `adspend_index` score = `ts(2026-07-30)`. (2) Realize it was actually an August spend and PUT with `date: 2026-08-02`. (3) Reload the Revenue tab — August's `monthlyAdSpend` still shows `$0` from this entry, because `ZRANGEBYSCORE(monthStart=Aug 1, +inf)` doesn't return an id whose score is July 30.
- **Evidence**:
  ```js
  // api/dashboard/adspend.js PUT (84-106) — no ZADD in the block
  if (body.date !== undefined) entry.date = body.date;
  ...
  await redis('SET', 'adspend:' + body.id, JSON.stringify(entry));
  return res.status(200).json({ ok: true, entry: entry });

  // compare POST (74-75), which does compute + ZADD:
  var score = new Date(body.date).getTime() || Date.now();
  await redis('ZADD', 'adspend_index', score, String(id));
  ```
- **Suggested Fix**: In the PUT, when `body.date !== undefined`, also `await redis('ZADD', 'adspend_index', new Date(entry.date).getTime() || Date.now(), String(entry.id))`.
- **Confidence**: high

### Bug: 2026-08-17-04 - Admin dashboard login has no rate limiting or lockout

- **Severity**: P2
- **Category**: security
- **File**: `api/dashboard/login.js` (whole file — 17 lines, no throttle)
- **First seen**: 2026-08-17
- **Description**: `POST /api/dashboard/login` compares the supplied password to `DASHBOARD_PASSWORD` (correctly, using `crypto.timingSafeEqual`) but accepts unlimited attempts with no per-IP or global throttle and no lockout. Every other endpoint that accepts user input in this codebase rate-limits (all three `submit-*` handlers). One successful guess yields full access to the CRM: every client's PII, all revenue data, ability to reset any client's portal, and video-blob upload/delete. Blast radius is very high; a smart attacker with a wordlist would run this in the background for days without you noticing.
- **Failure Scenario**: `while true; do curl -s -X POST https://www.telosathleticclub.com/api/dashboard/login -H 'Content-Type: application/json' -d "{\"password\":\"$(shuf -n1 wordlist)\"}" | grep -q '"ok":true' && break; done`. No 429, no ban, no alert.
- **Evidence**:
  ```js
  // api/dashboard/login.js — full file
  if (req.method !== 'POST') return res.status(405)...
  const { password } = req.body;
  if (!password || !verifyPassword(password)) {
    return res.status(401).json({ error: 'Invalid password' });
  }
  // no ratelimit key, no failed-attempt counter, no lockout
  ```
- **Suggested Fix**: Add the same INCR/EXPIRE pattern used in `submit-quiz.js` (line 22-29), keyed on IP: e.g. `ratelimit:adminlogin:{ip}` with a limit of 5 attempts per hour → 429. Optionally add a global counter `ratelimit:adminlogin:global` to defend against distributed attempts (e.g. 50/hour total).
- **Confidence**: high

### Bug: 2026-08-17-05 - Client login has no rate limiting

- **Severity**: P2
- **Category**: security
- **File**: `api/client/login.js` (whole file, 60 lines, no throttle)
- **First seen**: 2026-08-17
- **Description**: `POST /api/client/login` accepts unlimited email+password attempts. PBKDF2-100k adds ~50-100ms of server CPU per guess, which is a mild natural throttle but doesn't stop a wordlist attack against a known client email. Client emails are enumerable (Instagram, Whop community, Charleston applications). The 200-vs-401 response cleanly signals success. Same class as bug 04 but with narrower blast radius (one client's portal, not the CRM).
- **Failure Scenario**: `for pw in wordlist; do curl -s -X POST /api/client/login -H 'Content-Type: application/json' -d "{\"email\":\"victim@x.com\",\"password\":\"$pw\"}"; done`. Every request is served; success returns 200 with the client's name/tier, failure returns 401.
- **Evidence**:
  ```js
  // api/client/login.js — no ratelimit key anywhere
  if (req.method !== 'POST') return res.status(405)...
  var body = req.body;
  if (!body.email || !body.password) return res.status(400)...
  // straight to redis GET + verifyPassword; no throttle, no lockout
  ```
- **Suggested Fix**: `ratelimit:clientlogin:{ip}` = 10/hour → 429. Additionally, add a per-email counter `ratelimit:clientlogin:email:{normalizedEmail}` = 5/hour so a distributed attacker can't sidestep the IP limit.
- **Confidence**: high

### Bug: 2026-08-17-06 - Password reset endpoint has no rate limiting; attacker can flood a client's inbox and burn Resend quota

- **Severity**: P3
- **Category**: security
- **File**: `api/client/reset-password.js:8-68`
- **First seen**: 2026-08-17
- **Description**: The "request a reset email" branch (`body.email && !body.token`) issues a Resend API call for every request that resolves to a portal-enabled client, with no per-IP or per-email throttle. Anyone who knows a client's email address can flood their inbox with real reset emails and rack up Resend API charges on the Telos account. The token-consumption branch is safe (32-byte random token, one-shot).
- **Failure Scenario**: `while true; do curl -s -X POST /api/client/reset-password -H 'Content-Type: application/json' -d '{"email":"victim@x.com"}'; done`. Every iteration where the email is a real portal-enabled client fires a Resend send.
- **Evidence**:
  ```js
  // api/client/reset-password.js — no ratelimit before the Resend fetch
  var token = crypto.randomBytes(32).toString('hex');
  await redis('SETEX', 'password_reset:' + token, 3600, String(clientId));
  if (RESEND_API_KEY) {
    await fetch('https://api.resend.com/emails', { ... });  // unbounded
  }
  ```
- **Suggested Fix**: Two counters before the token/Resend logic: `ratelimit:pwreset:ip:{ip}` (5/hour) and `ratelimit:pwreset:email:{normalizedEmail}` (3/hour). Silently return `{ok:true}` when either limit is hit so enumeration behavior stays consistent.
- **Confidence**: high
