## BUG-20260904-01 - Deleting a client orphans their portal email lock, blocking re-add

**Severity:** P1
**Confidence:** High
**Area:** `api/dashboard/clients.js` DELETE handler
**Status:** New

### What's wrong
When a coach deletes a client via the /thomas dashboard "Delete" button, the DELETE handler removes only `client:{id}` and the `clients_index` sorted-set entry. It does NOT remove the `client_email:{normalizedEmail}` reverse-lookup that was created when the client's portal was enabled. That stale lookup then blocks any later attempt to add a client (any client) with the same email address, because the POST handler at `clients.js:70-73` reads `client_email:{email}`, finds the orphan pointing to a now-dead client id, and returns "Email already in use by another client".

Secondary problem: the DELETE handler also leaves every per-client Redis key untouched - nutrition plan, training program, 545 goals/routine/daily logs, daily check-in logs, nutrition logs, training logs, supplement plan/logs, activity logs, sidemenu config, mindset, resources, push subscription. That data lingers indefinitely in Redis, which is both a slow storage leak and a privacy issue for a deleted client (their health/nutrition data outlives their record).

### Reproduction
1. In /thomas → Clients tab, create a client with email `test@example.com`.
2. Open Client Portal for that client, enable portal, set a password. This writes `client_email:test@example.com → {id}`.
3. Back in the Clients tab, click "Delete" on that client, confirm.
4. Try to create a NEW client with the same email `test@example.com`.
5. **Expected:** the creation succeeds - the old record is gone.
6. **Observed:** a 400 with `{ error: "Email already in use by another client" }`. The coach has no in-UI way to clear this; they'd need Redis CLI access.

Bonus check (privacy): after step 3, GET the Redis keys `client_dailylog:{deletedId}:*`, `client_nutrition_plan:{deletedId}`, etc. They all still exist.

### Suggested fix
In `api/dashboard/clients.js` DELETE, before the `DEL client:{id}`, fetch the client record and, for every per-client key documented in CLAUDE.md's "Client Dashboard - Redis Keys" section, delete it. Include the email index and index sorted-sets. Rough sketch:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });

  // Load client to get email (for the reverse lookup)
  var raw = await redis('GET', 'client:' + id);
  var email = null;
  if (raw) {
    try {
      var { normalizeEmail } = require('../lib/client-auth');
      email = normalizeEmail(JSON.parse(raw).email);
    } catch(e) {}
  }

  // Fetch date-indexed keys to clean up (single-key data is enumerable directly)
  var dateIndexes = [
    'client_dailylogs_index:' + id,
    'client_nutrition_logs_index:' + id,
    'client_training_logs_index:' + id,
    'client_supplement_logs_index:' + id,
    'client_activity_logs_index:' + id,
    'client_545_index:' + id,
  ];
  var dailyKeys = [];
  for (var k = 0; k < dateIndexes.length; k++) {
    var dates = await redis('ZRANGE', dateIndexes[k], 0, -1);
    var prefix = dateIndexes[k].replace('_index', '').replace('_logs', '_log').replace('_dailylog', '_dailylog');
    // pick right per-key prefix per index; simpler to hardcode a table
  }
  // ...then DEL every daily key + every scalar key + email lookup + primary + index
}
```

For safety, this should probably use a small helper that enumerates the exact key patterns from CLAUDE.md. A confirmation prompt in `thomas.html:1414` warning "This permanently deletes all portal data" would also help.

If you'd rather punt on the full cleanup, the minimum fix for the *reported blocker* is two lines: read the email off the client record before deleting, then `DEL client_email:{normalizedEmail}`.

## BUG-20260904-02 - `showEmpty()` on `product.html` init failure leaves the loading spinner spinning forever

**Severity:** P3
**Confidence:** High
**Area:** `js/shop.js` shared init/error path
**Status:** New

### What's wrong
`js/shop.js` is loaded by both `shop.html` and `product.html`. Its top-level init `try { ... } catch (err) { showEmpty(); }` (shop.js:69-72) falls back to `showEmpty()` on any error. `showEmpty()` (shop.js:502-507) only knows about `#shopLoading` and `#shopEmpty`, which are elements in shop.html. On `product.html` those IDs don't exist; the corresponding elements are `#productLoading` and `#productNotFound`. If init throws on the product page (Shopify Buy SDK not loaded, storefront network error, checkout fetch throw, etc.), the product page's loading spinner sits spinning with no user-visible failure and no way to recover other than reload.

Low severity because it fires only on a rare error path, but when it does the page is silently broken.

### Reproduction
1. Open the browser devtools Network panel and block requests to `cdn.shopify.com` (or `*.myshopify.com`).
2. Navigate to `/product?p=any-handle`.
3. **Observed:** the "Loading product" spinner spins indefinitely. No error is shown. Devtools console has the caught error but nothing else surfaces.
4. **Expected:** either a "Product Not Found" / "Couldn't reach the shop" fallback becomes visible, or the loader hides and an error message appears.

### Suggested fix
Make `showEmpty()` context-aware, or add a `showEmptyProduct()` and have the outer init pick the right one based on which page it's on. Smallest patch:

```js
function showEmpty() {
  var loading = document.getElementById('shopLoading') || document.getElementById('productLoading');
  var empty   = document.getElementById('shopEmpty')   || document.getElementById('productNotFound');
  if (loading) loading.style.display = 'none';
  if (empty)   empty.style.display   = 'block';
}
```

### Files
- `js/shop.js:69-72` (outer init catch)
- `js/shop.js:502-507` (`showEmpty` implementation)
- `product.html:752-762` (elements it should be hiding/showing on this page)
- `shop.html:766, 775` (elements it currently targets)
