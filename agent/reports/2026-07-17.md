First run. The `agent/` and `docs/` infrastructure did not exist yet, so I bootstrapped it (memory, focus rotation, this report, and `docs/BUG_REPORT_SCHEMA.md`) before hunting. Focus this run: **security**, targeted at recently-added and undocumented surface area (shop/product pages, auth libs, and public submit endpoints). Three real findings, one P1 and two P2.

### P1 No rate-limiting on admin or client login endpoints

**Severity**: P1
**Category**: security
**File**: api/dashboard/login.js:10, api/client/login.js:46
**Reproduction**: Both endpoints accept unbounded POSTs. `api/dashboard/login.js` gates only on `verifyPassword(password)` with no per-IP or per-account throttling. `api/client/login.js` similarly does one `verifyPassword` per request with no counter. The other public write endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) already use the pattern `redis('INCR', 'ratelimit:<name>:<ip>')` with a 1-hour TTL — login is the outlier.
**Impact**: The admin dashboard has a single shared password (`DASHBOARD_PASSWORD`); an online brute-force run against `/api/dashboard/login` is unbounded. On the client side, once an attacker learns a valid client email (they're used as login IDs and appear in leads/portal flows), they can brute-force that account's password without any lockout. PBKDF2 makes each guess slow client-side but the server never says stop.
**Fix**: Add the same `ratelimit:login:<ip>` (and ideally `ratelimit:login:<email>` on client login) counter used by the submit endpoints — e.g. 10 attempts per hour per IP, plus 5 per hour per email on client login.
**Confidence**: high

### P2 Admin session signature uses non-constant-time string comparison

**Severity**: P2
**Category**: security
**File**: api/lib/auth.js:27
**Reproduction**: `verifyToken` compares the cookie's HMAC signature against the expected value with `if (signature !== expected) return false;` — a JS `!==` string compare that short-circuits on the first differing byte. The sibling file `api/lib/client-auth.js:46-49` handles the identical check with `crypto.timingSafeEqual`, and `verifyPassword` in the same admin file (line 58) also uses `timingSafeEqual`. The admin session verifier is the only place in the auth surface that doesn't.
**Impact**: Practical exploitability is low — the signature space is 256-bit HMAC-SHA256 — but this is a real constant-time-comparison inconsistency in security-critical code, and the fix is one line.
**Fix**: Replace lines 23-27 with an equal-length `Buffer.from` + `crypto.timingSafeEqual` comparison, mirroring `client-auth.js:42-49`.
**Confidence**: high

### P2 submit-quiz.js accepts malformed email addresses

**Severity**: P2
**Category**: security
**File**: api/submit-quiz.js:18
**Reproduction**: The only email check is `if (!email || !name)`. In contrast, `api/submit-email.js:18` requires `email.includes('@')`, and `api/submit-chs-application.js:35` enforces `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`. A POST with `email: "asdf"` succeeds and lands in the `quiz_submissions` ZSET.
**Impact**: Pollutes the leads database — invalid emails clutter the pipeline, hurt outreach conversion, and get counted in stats. Also makes the `email_${source}` and pipeline dedupe logic downstream less reliable.
**Fix**: Reuse the regex from `submit-chs-application.js:35` (or at minimum the `includes('@')` check from `submit-email.js`) in `submit-quiz.js` before the ZADD.
**Confidence**: high
