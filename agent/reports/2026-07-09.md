## BUG-2026-07-09-01 - Deleting a portal-enabled client permanently blocks the email

**Severity**: P2 (functional, affects real admin workflow, not user-facing)

**Location**: `api/dashboard/clients.js:143-154` (DELETE handler)

**Summary**
When you delete a client whose portal was enabled, the delete removes `client:{id}` and `clients_index`, but leaves the `client_email:{normalizedEmail}` → clientId mapping in Redis. Because the create path checks that mapping and refuses on hit, the deleted client's email address is permanently unusable for any future client record.

**Reproduce**
1. In `/thomas`, create a client `Foo` with email `foo@example.com`.
2. Open the Client Portal tab, enable portal for Foo (this writes `client_email:foo@example.com` → Foo's id via `api/dashboard/client-portal.js:117`).
3. In the Clients tab, click Delete on Foo.
4. Try to create a new client with the same email `foo@example.com`.
5. **Actual**: POST `/api/dashboard/clients` returns `400 {"error": "Email already in use by another client"}` (`clients.js:70-73`).
6. **Expected**: Creation succeeds, since Foo no longer exists.

**Root cause**
`clients.js` DELETE only issues:
```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```
It never loads the pre-delete client record, so it can't look up the email to clean up either `client_email:{email}` or the twelve per-client data keys documented in CLAUDE.md (`client_nutrition_plan:{id}`, `client_dailylog:...`, `client_545_*`, etc.).

**Proposed fix**
Before the two DEL/ZREM calls, GET `client:{id}`, and if the record parses and has `portalEnabled && email`, also `DEL client_email:{normalizeEmail(email)}`. Optionally purge the per-client data keys and their index ZSETs while we're at it - CLAUDE.md already lists the full key set.

**Confidence**: High. Traced the create-vs-delete asymmetry directly in code; the email-change path in the same file (`clients.js:130`) already does the cleanup pattern, confirming the intent.
