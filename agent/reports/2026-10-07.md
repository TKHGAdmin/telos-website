## Summary

First run of the Bug Hunter. The `agent/` and `docs/BUG_REPORT_SCHEMA.md` infrastructure didn't exist, so this run bootstrapped them in addition to doing the Security sweep. Focus rotation and memory files are now in place.

Five findings. The headline one is **P1 and functional, not security** — I flagged it anyway because it breaks an owner-critical workflow in `/thomas` every day and I verified it in a real Chromium instance: the "+ Pipeline" button on every quiz submission in the Leads tab is dead on arrival, because the inline `onclick` attribute is malformed. ## Findings

### 1. [P1] "+ Pipeline" button on admin Leads tab is dead — malformed `onclick` attribute

- **ID:** `2026-10-07-1`
- **Severity:** P1
- **Area:** admin (`/thomas`)
- **File(s):** `thomas.html:2528`
- **Reproduction:**
  1. Log in to `/thomas` with the dashboard password.
  2. Open the **Leads** tab (which calls `loadQuizSubmissions`).
  3. On any quiz submission row, click the gold "+ Pipeline" button.
  4. Expected: the Pipeline modal opens with name/email/score prefilled.
  5. Actual: nothing visible happens. DevTools console shows `Uncaught SyntaxError: Unexpected end of input`. The onclick handler never runs.
- **Impact:** The one-click promotion of quiz leads into the pipeline is broken for every submission in production. Thomas has to retype name/email/score by hand every time he wants to move a lead forward.
- **Root cause:** The row template is

  ```js
  html += '<td><button class="btn btn-sm btn-gold" onclick="addLeadFromQuiz(' +
          JSON.stringify(JSON.stringify(s)) + ')">+ Pipeline</button></td>';
  ```

  `JSON.stringify(JSON.stringify(s))` yields a JS source literal like `"{\"name\":\"John\",...}"`. That literal contains raw `"` characters. When the string is pasted into a `onclick="..."` attribute, the first inner `"` (right after `addLeadFromQuiz(`) terminates the HTML attribute, so the browser parses `onclick="addLeadFromQuiz("` and treats the rest as garbage attributes. I reproduced this in headless Chromium: the rendered button's `onclick` attribute is literally `addLeadFromQuiz(`.
- **Suggested fix:** Stop trying to embed JSON in an `onclick` attribute. Attach the handler programmatically after `innerHTML` is assigned, or stash the payload on a `data-*` attribute and read it in a delegated listener:

  ```js
  // In the row template:
  html += '<td><button class="btn btn-sm btn-gold js-add-lead" data-sub=\'' +
          esc(JSON.stringify(s)) + '\'>+ Pipeline</button></td>';

  // After the innerHTML assignment (once):
  $('quiz-table').addEventListener('click', function (e) {
    var btn = e.target.closest('.js-add-lead');
    if (!btn) return;
    addLeadFromQuiz(btn.getAttribute('data-sub'));
  });
  ```

  (`esc()` is safe for a single-quoted attribute because it HTML-encodes `'`.)

### 2. [P2] Password reset does not invalidate existing client sessions

- **ID:** `2026-10-07-2`
- **Severity:** P2
- **Area:** api / auth
- **File(s):** `api/lib/client-auth.js:24-52`, `api/client/reset-password.js:70-96`
- **Reproduction:**
  1. Log in as a client on device A — `telos_client_session` cookie set with a 7-day lifetime.
  2. From device B (or an attacker who stole the cookie), request a password reset for the same email, follow the link, and set a new password via `POST /api/client/reset-password`.
  3. Expected: the device-A cookie no longer works — the client has to re-authenticate everywhere.
  4. Actual: device A continues to make authenticated requests to every `api/client/*` endpoint. The token is `clientId.expires.hmac(SESSION_SECRET, clientId+expires)`; nothing about it depends on the password hash, so changing the password has no effect on token validity.
- **Impact:** The "reset my password because I think my account is compromised" flow doesn't actually log the attacker out. A stolen cookie remains usable for up to 7 days after the reset.
- **Suggested fix:** Bind the token to a password version. On `createClientToken(clientId)`, read the client's `passwordSetAt` (or a short counter `pwVer`) and include it in the signed payload: `clientId.expires.pwVer.hmac(...)`. On verify, re-read the client and reject if the stored `pwVer` has moved past the one in the token. `reset-password.js` already sets `client.passwordSetAt = new Date().toISOString()` — that value, truncated to an integer or hashed to a small token, is enough.

### 3. [P2] No rate limiting on admin login, client login, or password-reset request

- **ID:** `2026-10-07-3`
- **Severity:** P2
- **Area:** api / auth
- **File(s):** `api/dashboard/login.js:1-18`, `api/client/login.js:9-60`, `api/client/reset-password.js:20-68`
- **Reproduction:**
  1. From any IP, send a stream of `POST /api/dashboard/login` requests with `{"password":"guess-N"}`.
  2. Expected: after some low N, requests are rejected with 429 or similar.
  3. Actual: the endpoint responds 401/200 forever at whatever rate the client cares to send. Same for `POST /api/client/login` and `POST /api/client/reset-password` (with just an `email`).
- **Impact:** Three different brute-force surfaces:
  1. Admin password is a single human-chosen secret guarding the whole admin dashboard — unlimited guesses is a real risk.
  2. Client login runs PBKDF2 at 100k iterations per guess (good defense-in-depth) but each attempt bills Thomas's Vercel serverless compute. An attacker can both brute-force and burn money.
  3. Reset-request has no limit, so an attacker who knows a client's email can email-bomb them with reset messages and burn Resend quota.
- **Suggested fix:** Reuse the `INCR ratelimit:<kind>:<key>` pattern that `submit-chs-application.js` already uses, but key it on **the email/username being attempted** (not just IP), with a short lockout window on repeated failures. Example for admin login: `INCR ratelimit:admin-login:global`, set `EXPIRE 300` on first hit, reject above 10. For client login: `ratelimit:client-login:<normalizedEmail>` with similar numbers. For reset: `ratelimit:reset:<normalizedEmail>` capped at 3/hr.

### 4. [P2] Client login error messages enable account enumeration

- **ID:** `2026-10-07-4`
- **Severity:** P2
- **Area:** api / auth
- **File(s):** `api/client/login.js:30-48`
- **Reproduction:**
  1. `POST /api/client/login` with `{"email":"not-a-client@example.com","password":"x"}` → 401 `"Invalid email or password"`.
  2. Same request with a known-client email whose portal is disabled → 401 `"Portal access not enabled"`.
  3. Same request with a known-client email whose status isn't `active` → 401 `"Account is not active"`.
  4. Same request with a client who exists but has no password set → 401 `"Password not set - contact your coach"`.
  5. Expected: all four look the same from the outside.
  6. Actual: each distinct message tells an attacker whether a given email belongs to a client.
- **Impact:** Lets an attacker build a list of real Telos client emails (useful for targeted phishing of a high-value coaching clientele). `api/client/reset-password.js` already does the right thing (always returns `{ ok: true }` regardless of email existence) — login should match that posture.
- **Suggested fix:** Collapse lines 36-48 of `api/client/login.js` into a single generic 401 for every non-successful branch. Example:

  ```js
  function reject() { return res.status(401).json({ error: 'Invalid email or password' }); }
  // ...
  if (!client.portalEnabled || client.status !== 'active' || !client.passwordHash) return reject();
  if (!verifyPassword(body.password, client.passwordHash, client.passwordSalt)) return reject();
  ```

  If Thomas wants clients to know when their portal is disabled or password unset, surface that from the admin side (an email to the client) or in a separate "need help?" flow — not in the login response.

### 5. [P3] Rate-limit key is attacker-controlled via `X-Forwarded-For`

- **ID:** `2026-10-07-5`
- **Severity:** P3
- **Area:** api / infra
- **File(s):** `api/submit-chs-application.js:40`, `api/submit-quiz.js:23`, `api/submit-email.js:28`
- **Reproduction:**
  1. From one real IP, send `POST /api/submit-chs-application` with a valid body and `X-Forwarded-For: 1.1.1.1`. Then again with `X-Forwarded-For: 1.1.1.2`, `1.1.1.3`, …
  2. Expected: after 5 requests per hour from one source, further requests are 429'd.
  3. Actual: Vercel preserves the client-supplied `X-Forwarded-For` prefix and only appends the real edge IP. The handler reads the whole header string as the key. Each spoofed prefix gets its own rate bucket, so the 5/hr cap is trivially bypassed. Same shape on `submit-quiz` (10/hr) and `submit-email` (10/hr).
- **Impact:** The rate limits that exist on public forms are theatre, not enforcement. Low-signal spam, email bombing to the `/chs` and quiz endpoints, and Redis write amplification against the free-tier Upstash quota are all possible from a single host. The payload cap in `chs_application` is also unbounded (no length checks on `goals` / `history` / `availability`), so each spoofed-IP submission can carry a large body.
- **Suggested fix:** Parse `X-Forwarded-For` as a comma-separated chain and use the **last** entry (the one Vercel's edge appended) as the client IP, not the whole header:

  ```js
  function clientIp(req) {
    var xff = req.headers['x-forwarded-for'] || '';
    var parts = xff.split(',').map(function (s) { return s.trim(); }).filter(Boolean);
    return parts.length ? parts[parts.length - 1] : (req.headers['x-real-ip'] || 'unknown');
  }
  ```

  While you're there, add a `.slice(0, 2000)` cap on the long free-text fields in `submit-chs-application.js` so a single POST can't ship megabytes of body.
