## Bug 1 — Product detail page: thumbnails break the two-column layout

**Severity:** P1
**Area:** Shop / Product detail page
**File(s):** `product.html:105-108`, `product.html:765-768`

### What's wrong
The `.product-detail.loaded` grid is defined with `grid-template-columns: 1fr 1fr` but the DOM inside `#productDetail` now has three direct children: `#productImage`, `#productThumbs`, and `.product-detail-info`. On desktop, CSS Grid places them as (image | thumbs) on row 1 and (info | empty) on row 2, so the info column - title, price, add-to-cart, description - drops beneath the image while the entire right half of row 2 sits empty. When a product has multiple images the thumbnail row also lands next to the image instead of directly under it. This regressed in commit `f5cb8c4 feat: add image gallery with thumbnails on product page`, which inserted `#productThumbs` as a sibling of `#productImage` without updating the grid.

The mobile breakpoint (`max-width:768px`) collapses the grid to a single column, so mobile is unaffected; the bug is desktop/tablet only.

### How to reproduce
1. Open `https://www.telosathleticclub.com/product?p=<any-handle>` on a viewport wider than 768px.
2. Wait for the product to load (`.product-detail` gets `loaded` class).
3. Observed: image on left, an empty right column (or thumbnails only for multi-image products), and the title/price/add-to-cart block dropped to a second row on the left.
   Expected: image (with thumbnails under it) on the left, title/price/add-to-cart/description on the right, matching the pre-thumbnail layout.

### Suggested fix
Wrap the image and thumbs in a shared column container so the grid still has two children:

```html
<div class="product-detail-image-col">
  <div class="product-detail-image" id="productImage"></div>
  <div class="product-detail-thumbs" id="productThumbs"></div>
</div>
<div class="product-detail-info">...</div>
```

No CSS change to the grid is needed. Alternatively, add `.product-detail-thumbs { grid-column: 1; }` and `.product-detail-info { grid-column: 2; grid-row: 1 / span 2; }` to explicitly anchor cells.

### Confidence
Read the grid CSS, the DOM, and the git diff that introduced the third child. Grid auto-placement with two columns and three items is deterministic. A single-line CSS/DOM tweak reproduces the intended layout; if the maintainer intentionally wanted the thumbs to displace the info block, that would prove me wrong, but nothing in the commit message or prior product page structure suggests that.

## Bug 2 — Engagement-check cron re-emails the same inactive client every day

**Severity:** P1
**Area:** Cron jobs / Client engagement email
**File(s):** `api/cron/engagement-check.js:61-95`, `vercel.json:24-26`

### What's wrong
`engagement-check` is scheduled daily (`0 15 * * *`) and, for every active client with `portalEnabled` and no daily log in the last 3-5 days, sends a "We miss you at Telos" email via Resend. There is no dedupe key, no per-client cooldown, and no timestamp recorded when a reminder was sent. A client who stops logging on Monday receives one email Thursday, another Friday, another Saturday, and so on until they either check in or the cron stops. A two-week absence produces ~11-12 identical emails.

Beyond user annoyance, repeated identical sends risk Resend spam-flagging the `noreply@telosathleticclub.com` sender and hurting deliverability for the weekly summary and password-reset emails that share the same domain.

### How to reproduce
1. Ensure a client has `status=active`, `portalEnabled=true`, `emailEnabled` not false, and no `client_dailylog:{id}:{today-0..4}` keys in Redis.
2. Trigger `POST /api/cron/engagement-check` with `Authorization: Bearer $CRON_SECRET` two days in a row (or wait for two consecutive Vercel Cron fires).
3. Observed: the client receives the same "We miss you" email on both days. Expected: only one reminder within a reasonable cooldown (e.g. once per 7 days).

### Suggested fix
Add a per-client cooldown key before sending, e.g. inside the `if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3)` block:

```js
var cooldownKey = 'engagement_sent:' + client.id;
var already = await redis('GET', cooldownKey);
if (already) continue;
// ... send email ...
await redis('SETEX', cooldownKey, 7 * 86400, '1'); // 7-day cooldown
```

The cooldown TTL doubles as the automatic reset if the client remains inactive - one nudge per week is a reasonable default; adjust as desired.

### Confidence
Full read of `engagement-check.js` shows no dedupe layer, and `vercel.json` confirms the daily cadence. The failure mode is deterministic every day the cron fires against the same inactive-client set. What would prove me wrong: a dedupe mechanism I missed elsewhere (e.g. Resend's own idempotency, or a marker written by another file that I didn't grep). I grepped the repo for `engagement_sent` and similar - no hits - so I'm confident nothing else guards this.

## Bug 3 — Stale Everfit field still tracked on client records and returned by /api/client/me

**Severity:** P3
**Area:** API / Client + admin endpoints
**File(s):** `api/dashboard/clients.js:119`, `api/client/me.js:28`

### What's wrong
`CLAUDE.md` documents "Everfit removed - Training is now fully in-app (no external Everfit dependency)," but two endpoints still touch it. `api/dashboard/clients.js:119` persists `body.everfitUrl` onto the client record when a coach PUT-updates a client, and `api/client/me.js:28` returns `everfitUrl: process.env.EVERFIT_URL || ''` on every client profile fetch. Because the front-end no longer reads or writes this field, the writes are silently ignored and the reads always return `''`, but the leftover code invites confusion the next time someone touches these files and is stale relative to the documented architecture.

### How to reproduce
1. Grep the repo: `grep -rni everfit api/` returns matches in `dashboard/clients.js` and `client/me.js`.
2. Grep the client and admin HTML for `everfitUrl` - zero references. Confirms the field is dead on the read side but still tracked on the write side.

### Suggested fix
Remove the `body.everfitUrl` assignment in `clients.js` and the `everfitUrl` key from the `me.js` response payload. If a client record already carries a stored `everfitUrl` from historical writes, leaving the field on the JSON blob is harmless; no data migration is required.

### Confidence
Grep confirms the two-file surface. CLAUDE.md is explicit that Everfit is deprecated. What would prove me wrong: a hidden consumer of `everfitUrl` I missed - possible but I searched `everfit` (case-insensitive) across the whole repo and only saw these two writer sites plus doc references.
