# Telos Bug Hunt - 2026-07-25

**Focus:** Functional
**Findings:** 5
**Approval-ready:** yes

## Summary

First run. Verified 5 functional bugs across the recently-shipped shop/product surface, the admin client CRUD, an engagement cron, and the dashboard login endpoint. One P1 (product detail page grid layout is broken for every product on desktop after the image-gallery commit), two P2 (data-hygiene bug on client delete; engagement email cron that sends the same reminder every day forever), two P3 (cache-busting version mismatch between two pages sharing one script, and a request-body destructure that turns bad probes into 500s).

## Findings

### [20260725-1] P1 - Product detail page grid layout broken on desktop

- **File:** `product.html:765-780` (with CSS at `product.html:100-108`)
- **Category:** correctness
- **Failure scenario:** `.product-detail` sets `display:grid; grid-template-columns:1fr 1fr` and has THREE direct children in this order: `#productImage`, `#productThumbs`, `.product-detail-info`. On desktop (>768px) grid auto-flow places `#productThumbs` at row 1 col 2 (where the title / price / add-to-cart should live) and pushes the info block down to row 2 col 1 (below the image). For a single-image product the thumbs div is empty so col 2 row 1 renders as a blank right half; for a multi-image product the thumbnail strip renders in place of the info column. Either way the info block is not beside the image on desktop, which is the intended layout and the reason two columns were defined. Shipped in commit f5cb8c4 ("feat: add image gallery with thumbnails on product page").
- **Suggested fix:** Move `<div id="productThumbs">` inside `.product-detail-image` (thumbnails belong under the main image anyway) so `.product-detail` has exactly two grid children again.
- **Confidence:** high
- **Recurring:** no

### [20260725-2] P2 - Deleting a client leaves an orphan `client_email:` lookup that blocks recreating the client

- **File:** `api/dashboard/clients.js:143-154`
- **Category:** correctness
- **Failure scenario:** The DELETE handler removes `client:{id}` and `clients_index` but never removes `client_email:{normalizedEmail}`, which was written by `api/dashboard/client-portal.js:115-118` when the portal was enabled for that client. Reproduction: (1) admin creates client A with email `foo@bar.com`; (2) admin enables portal for A (writes `client_email:foo@bar.com -> A.id`); (3) admin deletes A; (4) admin now tries to recreate a client with the same email. `clients.js` POST at line 70-73 checks `client_email:{normalized}` first and returns 400 "Email already in use by another client" pointing at an ID that no longer exists. The admin has no UI path to clean this up short of hitting Redis directly.
- **Suggested fix:** In the DELETE branch, GET the client first, and if `client.email` is present call `DEL client_email:{normalizeEmail(client.email)}` alongside the other cleanup.
- **Confidence:** high
- **Recurring:** no

### [20260725-3] P2 - Engagement reminder cron sends the same email every day indefinitely

- **File:** `api/cron/engagement-check.js:36-95`
- **Category:** correctness
- **Failure scenario:** The cron runs daily and stores no "last reminder sent" state anywhere. The moment a client goes 3+ days without a `client_dailylog:*` entry, they receive an identical "We miss you at Telos" email; the next day the same check fires, the client is still inactive, and they get another identical email - forever, until they log back in. A client inactive for 30 days receives ~28 identical reminders. Real risk: Resend deliverability degrades and the sending domain gets flagged, which then breaks the Monday weekly-summary cron that shares the same domain. Secondary issue: `daysSince` is hard-capped at `5` when `lastLogDaysAgo === -1` (line 62), so the email says "5+ days" forever regardless of actual dormancy.
- **Suggested fix:** On send, write `client_last_engagement_email:{clientId}` with a 7-day TTL and short-circuit the loop if it's set; or use explicit backoff (day 3, day 7, day 14, then stop). Same-day dedupe alone is worth doing.
- **Confidence:** high
- **Recurring:** no

### [20260725-4] P3 - `js/shop.js` cache-busting version is out of sync between shop.html and product.html

- **File:** `shop.html:841` (`js/shop.js?v=1`) and `product.html:822` (`js/shop.js?v=2`)
- **Category:** correctness
- **Failure scenario:** Two pages share one script file but pin different `?v=` values. Content is identical today so nothing visibly breaks. The trap fires on the next edit to `js/shop.js`: whichever page's `?v=` is not bumped will keep serving the pre-edit copy from cache to returning users. Given the file was just touched twice in the last week (product-detail work), this is a real foot-gun waiting for the next revision.
- **Suggested fix:** Standardize both to the same version string and always bump the two together. Same pattern is already documented for `style.css` in CLAUDE.md - apply it to `shop.js` too.
- **Confidence:** high
- **Recurring:** no

### [20260725-5] P3 - `api/dashboard/login.js` throws unhandled TypeError on missing body

- **File:** `api/dashboard/login.js:8`
- **Category:** correctness
- **Failure scenario:** `const { password } = req.body;` is not guarded. A POST without a JSON body (missing `Content-Type: application/json`, or empty body) leaves `req.body` undefined; destructuring undefined throws and Vercel returns a bare 500 instead of the intended 401 "Invalid password". Real login form isn't affected because the browser sets the header correctly; this only surfaces from probes/misuse, but it produces noisy 500s in Vercel logs that make real errors harder to spot. Same one-line pattern exists in a few other POST endpoints - worth a sweep once this is fixed.
- **Suggested fix:** `const password = req.body && req.body.password;` (rest of the function already handles falsy password). Or wrap the handler body in try/catch and return 400 on parse failure.
- **Confidence:** high
- **Recurring:** no
