### Summary
First run of the bug hunter. Security sweep across the serverless API, auth libs, and admin dashboard rendering code. Three real findings, two of which are exploitable without any credentials. The headline item is a stored XSS in the admin `/thomas` leads tab that any visitor can plant by submitting a crafted email through `/protein-calculator` or `/hyrox-predictor` - landing JS in the admin's authenticated session when they next open the Leads tab.

Scope: `api/**/*.js`, `thomas.html` JS surface, `vercel.json`, auth libs, public submit endpoints. No application code modified.

### Findings

### B-2026-11-27-1 - Stored XSS: admin Leads tab renders attacker-controlled email into onclick JS
- **Severity:** P1
- **File(s):** `thomas.html:2577`, `api/submit-email.js:18`
- **Area:** Admin dashboard (`/thomas`) Leads > Emails sub-tab
- **What:** `loadEmailCaptures()` builds the Emails table row with `onclick="addLeadFromEmail('" + esc(em.email) + "')"`. The in-file `esc()` helper (`thomas.html:731`) escapes `<`, `>`, `&` only - not single quotes. `em.email` is submitted by anonymous public users through `/api/submit-email`, whose only validation is `email.includes('@')` (no quote filter). An email like `a'); fetch('/api/dashboard/...'); //@example.com` closes the JS string in the `onclick` attribute and executes arbitrary JS inside Thomas's authenticated admin origin on view. Admin cookie is HttpOnly but XSS can still make same-origin authenticated fetches to any `/api/dashboard/*` endpoint - effectively full admin takeover of pipeline, clients, revenue, Charleston applications, module uploads, etc.
- **Repro:**
  1. From anywhere, `curl -X POST https://www.telosathleticclub.com/api/submit-email -H 'Content-Type: application/json' -d '{"email":"a'\''); alert(1); //@evil.com","source":"protein-calculator"}'`
  2. Log in to `/thomas`, go to Leads tab, click Emails sub-tab.
  3. The email list renders; the browser evaluates the injected `alert(1)` (replace with any admin-API-draining payload in a real attack).
  Node verification confirmed: `esc("a'); alert(1); //@example.com")` leaves the single quote intact, producing `<button onclick="addLeadFromEmail('a'); alert(1); //@example.com')">`.
- **Impact:** Anyone on the internet can plant a stored XSS payload that fires as soon as the owner opens the leads tab. Payload can exfiltrate or mutate any admin-only data via same-origin fetch to `/api/dashboard/*`. Also affects `/protein-calculator` and `/hyrox-predictor` since both feed the same table.
- **Fix hint:** Stop building `onclick=` attributes by string concatenation. Either (a) render the button without inline onclick and attach the handler via `addEventListener`, passing the email via `dataset`, or (b) mirror the safe pattern already used in the quiz row (`JSON.stringify(JSON.stringify(s))` yields a safely-escaped JS string literal). Separately, `esc()` should additionally HTML-encode `'` and `"` to harden every other attribute interpolation site.

### B-2026-11-27-2 - No rate limit on `/api/client/reset-password` allows email bombing
- **Severity:** P1
- **File(s):** `api/client/reset-password.js:8-67`
- **Area:** Client portal authentication
- **What:** The reset-request branch (body has `email` and no `token`) has no rate limiter of any kind. Public submission endpoints in this codebase already use the `ratelimit:*:<ip>` Redis pattern (see `api/submit-email.js:28`), but this endpoint skips it. Any attacker can hit it in a loop with a valid client email and generate unlimited Resend-delivered password-reset emails to that client, flooding their inbox and burning Resend quota. The "always 200 to avoid enumeration" response makes it trivial to script in parallel.
- **Repro:** `for i in $(seq 1 100); do curl -s -X POST https://www.telosathleticclub.com/api/client/reset-password -H 'Content-Type: application/json' -d '{"email":"victim@example.com"}'; done` - 100 reset emails delivered, each with a valid 1-hour reset token.
- **Impact:** Harassment of any client whose email is known or guessed. Also burns the shared RESEND_API_KEY quota and risks Resend abuse flagging / domain reputation damage, which would then break legitimate cron-delivered weekly-summary and engagement emails.
- **Fix hint:** Add the same IP-based rate limiter used in `submit-email.js` plus a per-email-bucket limiter (e.g. max 3 reset emails per target address per hour), both keyed on top of the existing Redis helper. The IP limit alone is insufficient since the target email is what matters for the victim.

### B-2026-11-27-3 - No rate limit on login endpoints allows unlimited brute-force
- **Severity:** P1
- **File(s):** `api/dashboard/login.js:3-17`, `api/client/login.js:9-56`
- **Area:** Admin and client authentication
- **What:** Neither login endpoint rate-limits attempts. `/api/dashboard/login` protects a single shared `DASHBOARD_PASSWORD` compared with a non-stretched timing-safe equality - no key derivation, no lockout. `/api/client/login` runs PBKDF2-SHA512 at 100k iterations which slows offline cracking, but online brute-forcing a weak client password (clients choose their own) is still unbounded. The timing-safe signature check in the admin session verifier (`api/lib/auth.js:27`, `signature !== expected`) is a separate minor inconsistency - the rest of the codebase uses `crypto.timingSafeEqual`.
- **Repro:** `for p in $(cat wordlist.txt); do curl -s -X POST https://www.telosathleticclub.com/api/dashboard/login -H 'Content-Type: application/json' -d "{\"password\":\"$p\"}"; done` - server accepts every attempt, no 429.
- **Impact:** Full compromise of the entire admin dashboard (same blast radius as finding #1 but via credential guess) given a weak or leaked `DASHBOARD_PASSWORD`. For client login, compromise of individual client portals - containing PII (email, phone, tier, nutrition history, workouts).
- **Fix hint:** Apply the `ratelimit:*:<ip>` pattern to both login endpoints with a much stricter budget (e.g. 10 per 15 minutes per IP). Add a separate per-account counter so one attacker across many IPs still trips a lockout per target. Consider hardening `api/lib/auth.js:27` to use `crypto.timingSafeEqual` for parity with `client-auth.js`.
