## Summary

First run of the Telos Bug Hunter. Focus: **security**. Read the two auth helpers end-to-end, every dashboard endpoint, and every client-portal endpoint, then spot-checked the two big HTML dashboards for XSS. Three real bugs surfaced — one P1 in the client-session lifecycle (portal disable does nothing until the cookie expires), one P2 data-hygiene bug in the admin client-delete flow, and one P2 gap in admin-login brute-force protection. Bootstrapped `agent/`, `docs/BUG_REPORT_SCHEMA.md`, and `focus-rotation.json` while I was here.

## Findings

### BUG-20260807-1 — Portal-disable and status-change don't revoke live client sessions

- **Severity**: P1
- **Category**: security
- **Location**: `api/lib/client-auth.js:34-52`, `api/client/daily-log.js:5`, `api/client/nutrition-log.js:5`, `api/client/training-log.js:5`, `api/client/five-four-five.js:5`, `api/client/module.js:11`, `api/client/module-progress.js:5`, `api/client/food-search.js:8`, `api/client/me.js:9`, `api/client/push-subscribe.js:5`, `api/dashboard/client-portal.js:110-124`

**What's wrong**
`verifyClientSession()` validates only the cookie's HMAC and expiry — it never re-reads the client record. The only endpoints that check `client.portalEnabled` and `client.status === 'active'` are `api/client/login.js:36-41` and `api/client/reset-password.js:34`. Every other authenticated client endpoint accepts a valid signed cookie no matter what state the client record is in.

**Why it matters**
When a coach flips a client to `portalEnabled: false` via `api/dashboard/client-portal.js` (POST with `enabled: false`) — the exact revocation UX the admin dashboard offers — the affected client can continue to read and write all of their portal data for up to 7 days (the session TTL in `client-auth.js:6`). Same for setting `status` to anything other than `'active'` via `api/dashboard/clients.js` PUT. Concretely, a client who has been offboarded / stopped paying / been asked to leave can still:
- GET their profile via `/api/client/me`
- Read and POST daily logs, nutrition logs, training logs, 545 tasks, activities, supplement completion
- Read gated learning modules that their tier grants (`api/client/module.js` still runs the tier check, but not the enabled/active check)
- Subscribe to push notifications
The coach has no in-app "kill sessions" control, so revocation is silently ineffective.

**Repro / evidence**
1. Coach creates a client, enables portal, sets a password.
2. Client logs in in a browser; `Set-Cookie: telos_client_session=…; Max-Age=604800` is issued.
3. Coach opens `/thomas` → Client Portal → toggles portal off (fires `POST /api/dashboard/client-portal` with `enabled: false`; this only DELs the `client_email` lookup and sets `portalEnabled: false` on the client record).
4. Client hits `GET /api/client/daily-log?date=…` in the still-open browser — request returns `200` and the log data. `daily-log.js:5-8` is the whole auth path:
   ```js
   var clientId = verifyClientSession(req);
   if (!clientId) return res.status(401).json({ error: 'Unauthorized' });
   ```
   No lookup of `client:{clientId}` happens, so `portalEnabled: false` is never seen.
5. Repeat for every other endpoint listed under Location — same behavior.

**Suggested fix**
Two options, either works:
- **Preferred**: extend `verifyClientSession()` (or add a `resolveClient()` wrapper) that, after HMAC verification, reads `client:{id}` and fails closed if `portalEnabled !== true` or `status !== 'active'`. One extra Redis GET per client request. Update the client endpoints to call the wrapper.
- **Alternative (cheaper, no extra Redis hit per request)**: bump a `sessionsRevokedAt` timestamp on the client record when the coach disables the portal or deactivates the client, embed the issue time in the client token payload (`{clientId}.{issuedAt}.{expires}.{sig}`), and reject in `verifyClientToken` when `issuedAt < client.sessionsRevokedAt`. This still needs a client lookup, though — the extra-GET version is simpler and safer.

Also worth adding a `/api/client/logout` call from the admin "disable portal" button so the coach can see confirmation, but that alone doesn't fix the bug (an attacker who copied the cookie won't oblige).

### BUG-20260807-2 — Deleting a client leaves the email-lookup key orphaned, blocking re-add with the same email

- **Severity**: P2
- **Category**: security
- **Location**: `api/dashboard/clients.js:143-154`, `api/dashboard/clients.js:70-73`

**What's wrong**
The DELETE handler removes `client:{id}` and the `clients_index` entry but never touches the reverse-lookup `client_email:{normalizedEmail}` that was written by `client-portal.js` when the coach first enabled the portal (or by clients.js PUT on email change). The orphan lookup still points to the now-deleted client ID.

**Why it matters**
1. **Admin workflow breaks.** The very next thing a coach usually does after deleting a stale record is re-create it — often at the same email if the person is returning. The POST handler at `clients.js:70-73` treats any non-empty `client_email:{email}` as a collision and returns `400 "Email already in use by another client"`. From the coach's UI it looks like the delete didn't work; from Redis it's an orphan.
2. **Data leakage on tombstoned client keys.** The delete also leaves every `client_dailylog:{id}:*`, `client_nutrition_log:{id}:*`, `client_training_log:{id}:*`, `client_545_*:{id}:*`, `client_supplement_log:{id}:*`, `client_activity_log:{id}:*`, `client_module_progress:{id}:*`, `client_push_sub:{id}`, and the associated ZSET indexes intact. Because IDs are monotonically issued by `INCR id:clients`, a new client will never inherit the old ID, so this is not exploitable — but it is meaningful storage bloat over time and a PII-retention question worth answering deliberately.

**Repro / evidence**
1. Create client A with email `x@y.com`, enable portal (writes `client_email:x@y.com -> <A_id>`).
2. Delete client A via `DELETE /api/dashboard/clients?id=<A_id>`. Redis still has `client_email:x@y.com`.
3. POST `/api/dashboard/clients` with `{ name: 'A2', email: 'x@y.com', tier: 'rebuild' }` → `400 {"error":"Email already in use by another client"}`.

**Suggested fix**
In the DELETE handler, before deleting `client:{id}`, GET the record, extract `email`, and add:
```js
if (client.email) await redis('DEL', 'client_email:' + normalizeEmail(client.email));
```
Separately, decide whether to cascade-delete the client's data keys or keep them for historical reporting; if keeping, prefix them (`archived_client_...`) or move them under a `deleted_clients:{id}` namespace so orphan detection is trivial. Whatever the policy is, the DELETE handler should implement it explicitly instead of leaving keys behind by accident.

### BUG-20260807-3 — Admin dashboard login has no rate limiting / lockout

- **Severity**: P2
- **Category**: security
- **Location**: `api/dashboard/login.js:3-17`, contrast with `api/submit-quiz.js:22-29`, `api/submit-email.js:27-34`, `api/submit-chs-application.js:39-46`

**What's wrong**
`api/dashboard/login.js` accepts unlimited POSTs and reports success/failure instantly. There is no per-IP counter, no exponential backoff, and no account lockout. The public submit endpoints all rate-limit at 5-10/hr per IP via Redis `INCR/EXPIRE`; the admin login endpoint does not.

**Why it matters**
`DASHBOARD_PASSWORD` is a single shared secret with no MFA. If it's compromised, an attacker gets the full `/thomas` dashboard: every client's PII, health data, revenue numbers, quiz submissions, email captures, Charleston applications, and write access to all client portal content and push notifications. `verifyPassword` is timing-safe on the byte compare but returns on a length mismatch first, so it responds in ~1ms — an attacker can trivially fire tens of thousands of guesses/hour against `https://www.telosathleticclub.com/api/dashboard/login`. Even a strong 16-char random password is fine against that, but any human-memorable password ("Telos!2024" and its ilk) is at real brute-force / password-spray risk, and there is no alerting.

**Repro / evidence**
Read `api/dashboard/login.js` in full — 17 lines, no rate-limit code. The public endpoints show the exact pattern that's missing:
```js
// submit-quiz.js:22-29
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:quiz:${ip}`;
const count = await redis('INCR', rateLimitKey);
if (count === 1) await redis('EXPIRE', rateLimitKey, 3600);
if (count > 10) return res.status(429).json({ error: 'Too many requests' });
```

**Suggested fix**
Copy the same IP-based rate-limit pattern into `dashboard/login.js` with a much tighter budget — e.g. 5 attempts per IP per 15 minutes, then 429 for an hour. On top of that, add a second global counter keyed on `ratelimit:dashlogin:global` with a higher threshold (say 50/hour) so distributed spraying still gets caught. Longer-term: rotate `DASHBOARD_PASSWORD` to something ≥ 24 random chars, and consider swapping the single shared password for magic-link auth via Resend since only one human (Thomas) actually logs in.

## Coverage notes

- Read in full: `api/lib/auth.js`, `api/lib/client-auth.js`, `api/lib/redis.js`, all files touched in the three findings above, plus `api/dashboard/{analytics,upload-video,delete-video,modules,chs-applications}.js`, `api/client/{me,notify,send-email,push-subscribe,training-log,nutrition-log,daily-log,five-four-five,module,module-progress,food-search,reset-password}.js`, `api/{submit-quiz,submit-email,submit-chs-application}.js`, `api/cron/weekly-summary.js`, `vercel.json`.
- Considered and rejected as findings today:
  - **HTML injection in coach-authored email templates** (`reset-password.js:58`, `send-email.js:107-158`). Coach-controlled inputs only; also intentional in `send-email.js` custom template. Not a bug in the current threat model.
  - **HTML injection via `item.icon` and side-menu panel `item.content`** in `client-dashboard.html:2712, 2749`. Coach-controlled, intentional (HTML panels are a documented feature). Rendering their name unescaped in the mindset drawer would be worth flagging if a client-authored path fed those fields — none does today.
  - **Timing side-channel on password length** in `auth.js:52-59` and `client-auth.js:15-21`. Reveals length only; length is not the secret. Theoretical only.
  - **CORS `Access-Control-Allow-Origin: *`** on `/api/submit-*` per `vercel.json:5-11`. Intentional — allows external embeds to submit and is bounded by per-IP rate limits.
  - **Empty `DASHBOARD_PASSWORD` fail-open?** No — `dashboard/login.js:10` guards with `!password` before calling `verifyPassword`, so an empty POST is rejected even if the env var is unset. Not exploitable.
- Not looked at yet (queued for future rotations): `sw.js`, `js/main.js`, `js/quiz.js`, `js/shop.js`, full HTML dashboards, the blog, live-site behavior, `api/cron/engagement-check.js`, half a dozen client endpoints (activity, supplements, sidemenu, etc.), Shopify integration.
