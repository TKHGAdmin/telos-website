## Bug 1 - Client login enumerates account state via distinct error messages

- **Severity**: P1
- **Area**: functional
- **File**: api/client/login.js:36
- **Verified**: yes
- **Duplicate-of**: none

**Evidence**
```js
if (!client.portalEnabled) {
  return res.status(401).json({ error: 'Portal access not enabled' });
}
if (client.status !== 'active') {
  return res.status(401).json({ error: 'Account is not active' });
}
if (!client.passwordHash || !client.passwordSalt) {
  return res.status(401).json({ error: 'Password not set - contact your coach' });
}
```

**Impact**
An attacker POSTing arbitrary email + password pairs learns from these three distinct strings (a) that a given email belongs to a real client, and (b) its portal / status / password state. Unknown emails and wrong passwords both return the generic "Invalid email or password" on lines 26, 31, and 47, so the three branches above leak account existence. The paired `api/client/reset-password.js` deliberately always returns `ok:true` to avoid this exact leak, which shows the enumeration in login is unintentional.

**Suggested fix**
Collapse all three branches (portalEnabled, status !== 'active', missing password) into the same generic `Invalid email or password` 401 response used by the unknown-email path.

## Bug 2 - No rate limiting on either login endpoint

- **Severity**: P1
- **Area**: functional
- **File**: api/dashboard/login.js:8
- **Verified**: yes
- **Duplicate-of**: none

**Evidence**
```js
const { password } = req.body;
if (!password || !verifyPassword(password)) {
  return res.status(401).json({ error: 'Invalid password' });
}
```
The whole handler is 17 lines and never touches a `ratelimit:*` key. `api/client/login.js` is the same story. By contrast, `submit-quiz.js:23-29`, `submit-email.js:28-34`, and `submit-chs-application.js:40-46` all implement per-IP `INCR + EXPIRE` counters using the same Redis client, so the pattern exists in-repo and was skipped only for the two auth surfaces.

**Impact**
Unlimited password guessing. The admin endpoint unlocks every `/api/dashboard/*` route (business data, client PII, revenue) behind a single password. The client endpoint, combined with Bug 1, lets an attacker enumerate clients and then brute-force each one.

**Suggested fix**
Copy the `ratelimit:{scope}:{ip}` INCR + EXPIRE pattern from `submit-quiz.js` into both login handlers. For client login also add a per-email counter (`ratelimit:client-login:{email}`) so distributed IP brute-forcing is still bounded per account.

## Bug 3 - Admin session HMAC signature compared with `!==` instead of timing-safe compare

- **Severity**: P2
- **Area**: security
- **File**: api/lib/auth.js:27
- **Verified**: yes
- **Duplicate-of**: none

**Evidence**
```js
const expected = crypto.createHmac('sha256', SESSION_SECRET)
  .update(payload).digest('hex');
if (signature !== expected) return false;
```
Client auth (`api/lib/client-auth.js:46-49`) correctly uses `crypto.timingSafeEqual` after a length check for the same purpose. Same-file `verifyPassword` (auth.js:58) also uses `timingSafeEqual`, so the sloppy compare is isolated to `verifyToken`.

**Impact**
A network-adjacent attacker can, in theory, measure per-byte response-time differences on the string compare to reconstruct a valid HMAC signature for a chosen `expires` payload, then forge a `telos_dash_session` cookie without knowing `SESSION_SECRET`. Realistic exploitation over the public internet is difficult given JS engine and network noise, hence P2 not P1.

**Suggested fix**
Mirror the client-auth check: `Buffer.from(signature,'hex')` and `Buffer.from(expected,'hex')`, then `if (a.length !== b.length) return false; if (!crypto.timingSafeEqual(a,b)) return false;`.

## Bug 4 - `todayStr()` returns UTC date, breaking streaks and heatmaps for non-UTC clients

- **Severity**: P2
- **Area**: functional
- **File**: client-dashboard.html:1840
- **Verified**: yes
- **Duplicate-of**: none (CLAUDE.md notes this as backlog "todayStr() UTC timezone bug" without a line cite; this report anchors it)

**Evidence**
```js
function todayStr() {
  return new Date().toISOString().split('T')[0];
}
```
The function is the sole source of "today" for the dashboard's 26 date-scoped read/write sites. Every server-side default matches (`daily-log.js:28`, `five-four-five.js:13`, `nutrition-log.js:15`, `supplement-log.js:15`, `training-log.js:31`, `activity-log.js:28`), so client and server agree on the wrong day - the boundary is UTC everywhere.

**Impact**
A client in EST (or anywhere west of UTC) logging a check-in, a set, a meal, or a supplement between 7 PM and midnight local writes to the *next* calendar day's Redis key. The Home tab's today-checklist shows their action against tomorrow, streaks miscount by up to a day around midnight, and the 30-day heatmap paints on the wrong cell.

**Suggested fix**
Replace the body with local-date formatting: build the `YYYY-MM-DD` string from `d.getFullYear()`, `d.getMonth()+1`, and `d.getDate()` with zero-padding. Have the client always send its local date in POST bodies; keep the server defaults as a last-resort fallback but log a warning when they trigger.

## Bug 5 - `module-progress` POST does not enforce tier access

- **Severity**: P3
- **Area**: functional
- **File**: api/client/module-progress.js:30
- **Verified**: yes
- **Duplicate-of**: none

**Evidence**
```js
if (req.method === 'POST') {
  var body = req.body;
  if (!body.moduleId) return res.status(400).json({ error: 'moduleId required' });
  var moduleId = body.moduleId;
  var key = 'client_module_progress:' + clientId + ':' + moduleId;
  ...
}
```
The POST handler never loads the module record and never compares `client.tier` against `mod.tierAccess`. `api/client/module.js:47-62` does this check on the read path, so the gap is asymmetric.

**Impact**
A Rebuild-tier client can POST fabricated watch progress against any `moduleId` they can guess, inflating their `client_modules_completed:{id}` ZSET. The modules index still marks the module `locked=true` on read (client/modules.js:61-69 wins over the completed flag), so this is a data-integrity / metrics issue rather than a content-access bypass.

**Suggested fix**
Fetch `module:{moduleId}` at the top of the POST branch, resolve the client tier, and 403 if the tier level is below `mod.tierAccess.minTier`.

## Coverage notes

- Every `/api/dashboard/*.js` handler except `login`/`logout` calls `verifySession` at the top; every `/api/client/*.js` data endpoint derives its Redis key from the session's own `clientId`, not from request input - no IDOR in the reviewed surface.
- Both cron endpoints (`weekly-summary.js:9-11`, `engagement-check.js:9-11`) require `CRON_SECRET` to be set and to match; they fail closed when the env var is absent.
- All four public forms POST to endpoints that exist (quiz, protein calc, hyrox, chs); all three public submit endpoints rate-limit per-IP.
- Redis keys read by client endpoints match what `dashboard/client-portal.js` writes - no key drift.
- `sw.js` cache is `telos-v1`, skips `/api/*` (line 43), and only handles GET (line 40) - no stale-data risk from the SW.
- Reset-password uses 256-bit tokens and correctly avoids email enumeration.
