**Focus:** Multi-focus (first run)
**Summary:** Four real bugs identified across security, functional, and performance. One P0 stored XSS in the admin dashboard that any anonymous visitor can trigger. One P1 field-name mismatch making the admin Overview tab show zero for all quiz/email metrics regardless of actual data.
**Bugs found:** 4

## Bug 1 - P0 - Stored XSS in admin dashboard via quiz name field

**Category:** security
**Files:**
- `thomas.html:2528`
- `api/submit-quiz.js:16-44`

**Reproduction:**
1. Anyone (no auth needed) sends `POST /api/submit-quiz` with body `{"name": "aa onmouseover=alert(1) ", "email": "a@b.co"}`. The endpoint does zero sanitization of `name` and stores it verbatim in Redis.
2. Admin opens `/thomas` and clicks the Leads tab, which calls `loadQuizSubmissions()` at `thomas.html:2512`.
3. At `thomas.html:2528` the whole submission object is injected into an HTML attribute via `JSON.stringify(JSON.stringify(s))`:
   ```js
   html += '<td><button ... onclick="addLeadFromQuiz(' + JSON.stringify(JSON.stringify(s)) + ')">...';
   ```
   `JSON.stringify` only escapes `"` and `\` for JS - it does NOT HTML-escape. The double-stringified string gets concatenated into an HTML attribute delimited by `"`, so the first `"` inside the payload closes the `onclick` attribute, and anything after a space before the next `"` is parsed as a NEW attribute on the `<button>` element.
4. With payload `aa onmouseover=alert(1) ` (no `"` or `\` so nothing gets escaped), the HTML parser emits a button with a real `onmouseover="alert(1)"` attribute. Hovering the + Pipeline button on that row fires the handler in the admin's authenticated session.
5. Every other field in the row (`s.name`, `s.email`) correctly passes through `esc()` on lines 2524-2525, so this is specifically the raw-object attribute injection on 2528 that is unsafe.

**Impact:**
Any unauthenticated internet user can plant JS that runs in an authenticated admin session on `/thomas`. The session cookie is HttpOnly, so it cannot be exfiltrated directly - but the injected script runs same-origin against every admin endpoint (`/api/dashboard/clients`, `/api/dashboard/pipeline`, `/api/dashboard/emails`, etc.) and can read full client PII, salted PBKDF2 password hashes, pipeline leads, ad spend, revenue, Charleston applications, and anything else the admin can see; it can also mutate state (delete clients, reset passwords, change portal credentials). This is a plant-once trigger-forever vector - the submission lives in Redis until manually removed.

**Suggested fix:**
Replace the raw `JSON.stringify(JSON.stringify(s))` sink on `thomas.html:2528` with a `data-*` attribute whose value is run through `esc()`, and read it via `this.dataset.submission` inside `addLeadFromQuiz`. Alternatively, keep the submissions in a module-level array and pass only the index: `onclick="addLeadFromQuiz(' + i + ')"`. Also add input length caps and HTML-stripping in `api/submit-quiz.js` as defense in depth (quiz `name` has no legitimate reason to contain `<`, `>`, or `onmouseover`).

**Confidence:** high

## Bug 2 - P1 - Admin Overview tab shows 0 for all quiz/email counters

**Category:** functional
**Files:**
- `thomas.html:1008`
- `thomas.html:1017`
- `thomas.html:1023`
- `thomas.html:1080-1081`
- `api/dashboard/stats.js:30-44`

**Reproduction:**
1. `api/dashboard/stats.js` returns `{ totalQuizSubmissions, totalProteinEmails, totalHyroxEmails, quizThisWeek, ... }` (camelCase, specific per-source counters).
2. `thomas.html` renders the Overview tab using `stats.total_submissions`, `stats.total_emails`, and `stats.week_submissions` (snake_case, keys that stats.js never emits).
3. Because every key is undefined, the `|| 0` branches fire on lines 1008, 1017, 1023, 1080-1081. The Overview stat cards and Quick Summary section always display:
   - "Quiz Completions: 0"
   - "0 emails captured"
   - "Quiz submissions: 0"
   - "Email captures: 0"
4. Verified by tracing the Overview `loadStats`-equivalent code against the actual API response shape.

**Impact:**
The admin's primary at-a-glance dashboard shows all four lead metrics as zero even when the business is actively collecting quiz and email leads. The underlying data is captured correctly and visible on the Leads tab, but the Overview misrepresents the funnel. Compounding effect: the admin may think the quiz is broken and stop promoting it.

**Suggested fix:**
In `thomas.html` lines 1008/1017/1023/1080/1081, change the key reads to match `stats.js`:
- `stats.total_submissions` -> `stats.totalQuizSubmissions`
- `stats.total_emails` -> `(stats.totalProteinEmails + stats.totalHyroxEmails)`
- `stats.week_submissions` -> `stats.quizThisWeek`

**Confidence:** high

## Bug 3 - P2 - Quiz Score and Date columns always show "-" in admin Leads tab and CSV export

**Category:** functional
**Files:**
- `thomas.html:2526-2527`
- `thomas.html:2619`
- `api/submit-quiz.js:31-40`

**Reproduction:**
1. `api/submit-quiz.js` stores each submission with keys `name`, `email`, `phone`, `scores`, `totalScore`, `page`, `submittedAt`, `ip`.
2. `thomas.html:2526-2527` renders submissions using `s.score` (expecting the score) and `s.created_at` (expecting the timestamp) - neither key is ever set by the writer.
3. `s.score != null` on line 2526 evaluates to `false` because undefined == null, so the Score cell renders `-` for every row. Likewise `fmtDate(s.created_at)` on line 2527 returns `-` because the function short-circuits when its input is falsy.
4. The CSV export at line 2619 does the same thing: `rows.push([s.name, s.email, s.score, s.created_at])` writes empty score/date columns to the exported file.

**Impact:**
The admin cannot see quiz scores or submission dates in the Leads tab table, and the "Export CSV" download is missing those two columns for every row - which breaks the main workflow for sorting/filtering leads by quality.

**Suggested fix:**
Pick a convention and apply it in both producer and consumer. Simplest: change `thomas.html` lines 2526, 2527, 2619 to read `s.totalScore` and `s.submittedAt`. Also update line 2574 for email captures (`em.created_at` -> `em.submittedAt`) and the email CSV export at line 2627.

**Confidence:** high

## Bug 4 - P2 - Hero About photo ships 1.9 MB with no lazy loading on mobile

**Category:** performance
**Files:**
- `images/thomas.jpeg` (1,897,318 bytes, 1206x2136)
- `index.html:252`
- `chs.html:946`

**Reproduction:**
1. `images/thomas.jpeg` is 1.9 MB and 1206x2136 px on disk.
2. `index.html:252` and `chs.html:946` reference it with a plain `<img src="images/thomas.jpeg">` - no `loading="lazy"`, no `width`/`height`, no responsive `srcset`, no modern-format alternative (WebP/AVIF).
3. On the homepage the About section is below the fold (hero + how-it-works sections render first), yet the full-size JPEG is fetched eagerly on initial page load.
4. Grep confirms only `client-dashboard.html` and `chs.html` use `loading="lazy"` anywhere; `index.html` has no lazy loading on any image.

**Impact:**
Mobile users on 4G pay roughly 2 MB of transfer per visit to the homepage for an image they may never scroll to, and the lack of intrinsic dimensions causes CLS when the image finally paints. Likely 1-3s LCP regression on slow connections and a visible quality hit to Core Web Vitals / Vercel analytics.

**Suggested fix:**
Re-export `images/thomas.jpeg` at a sensible display width (720px wide, mozjpeg q80 should bring it under 150 KB) and add a WebP sibling. On the two `<img>` tags: add `loading="lazy"`, `decoding="async"`, explicit `width`/`height`, and wrap in `<picture>` with WebP source. The two other speaking photos (`thomas-speaking-close.jpeg` 216 KB, `thomas-speaking-wide.jpeg` 251 KB) are also below the fold and should be marked `loading="lazy"` as a cheap one-line win.

**Confidence:** high
