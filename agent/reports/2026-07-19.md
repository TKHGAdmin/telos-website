## P1-1: Portal enable silently hijacks another client's login email

**File(s):** `api/dashboard/client-portal.js:115-118`, `api/dashboard/clients.js:121-132`

**What's wrong**
When Thomas enables the portal for a client, `client-portal.js` unconditionally overwrites the `client_email:{normalizedEmail}` mapping without checking whether that email is already owned by a different client:

```js
// api/dashboard/client-portal.js
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));  // no owner check
}
```

Meanwhile, `clients.js` PUT only checks for email conflicts when `client.portalEnabled` is `true` at the time of the update:

```js
// api/dashboard/clients.js:121
if (body.email !== undefined && body.email !== JSON.parse(existing).email && client.portalEnabled) {
  // conflict check + mapping update only runs in this branch
}
```

Together these two gaps create a silent takeover path.

**Repro**
1. Client A exists with `email = alice@example.com`, portal enabled. Redis has `client_email:alice@example.com -> A`.
2. Client B exists with `email = bob@example.com`, portal **disabled**.
3. Admin edits Client B in the dashboard and changes email to `alice@example.com`. The PUT handler skips the conflict check because `client.portalEnabled` is false, so B's record now reads `email: alice@example.com` and no Redis mapping change occurs.
4. Admin ticks "Portal enabled" for Client B. `client-portal.js` runs `SET client_email:alice@example.com -> B`, silently overwriting A's mapping.
5. Client A can no longer log in - their email now resolves to B's client id. Password verification fails and the response is a generic "Invalid email or password."

**Fix sketch**
Before the `SET` in `client-portal.js`, do `GET client_email:{email}`; if it exists and points to a different id, return 400 with a duplicate-email error. Also add the same conflict check to the "email changed" branch in `clients.js` regardless of `portalEnabled` state.

**Why P1**
Silent data-integrity bug affecting client login. Two active clients required, but Thomas has multiple active clients today, so the exposure is real. Recovery requires manual Redis surgery.

## P1-2: Deleting a client leaves an orphan `client_email` mapping that blocks re-adding them

**File(s):** `api/dashboard/clients.js:143-153`

**What's wrong**
The DELETE branch removes `client:{id}` and the sorted-set entry but does not remove the `client_email:{normalizedEmail}` mapping created when the portal was enabled:

```js
if (req.method === 'DELETE') {
  // ...
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

**Repro**
1. Create a client with email `test@example.com` and enable their portal. Redis now has `client_email:test@example.com -> <id>`.
2. Delete the client via the dashboard.
3. Try to re-create a client (same person, same email). POST at `clients.js:70-73` fails with `"Email already in use by another client"` because the orphan mapping still resolves.
4. If someone tries to log in with `test@example.com`, `login.js` fetches the id, then fails at `client:{id}` lookup and returns a generic 401 - not a critical error, but the orphan is now essentially dead-lock waste.

**Fix sketch**
In the DELETE branch, read the existing client first, and if `portalEnabled` and `email` are set, `DEL client_email:{normalizeEmail(email)}` before removing the record. Consider also clearing the derived per-client keys (`client_dailylog:*`, `client_nutrition_plan:*`, etc.) or at least documenting that they persist.

**Why P1**
Small blast radius per event but 100% reproducible and it silently blocks a common admin action (re-onboarding a returning client). Fix is a two-line change plus tests.

## P2-1: `submit-chs-application.js` records raw `X-Forwarded-For` as the client IP and as a rate-limit key

**File(s):** `api/submit-chs-application.js:40-46`, and the same pattern in `submit-quiz.js:23-28` and `submit-email.js:28-33`.

**What's wrong**
```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:chs:${ip}`;
```

`X-Forwarded-For` is a comma-separated list (`client, proxy1, proxy2`). Vercel prepends the real client IP, but any client-supplied value is preserved in front. A malicious submitter can send `X-Forwarded-For: <random-per-request>` in their request, and their client IP will be appended after by the platform, producing a distinct key per request:

```
ratelimit:chs:<attacker-supplied-random>, <real-ip>
```

Every request writes to a different rate-limit key, defeating the 5-per-hour throttle. The same value is stored in the persisted application record as `ip`.

**Fix sketch**
Take the first token: `const ip = (req.headers['x-forwarded-for'] || '').split(',')[0].trim() || req.headers['x-real-ip'] || 'unknown';`. Consider also validating that the value looks like an IPv4/IPv6 address before using it in a Redis key.

**Why P2**
Not a P1 because the endpoint has no direct auth/billing impact and Vercel already provides basic bot defenses in front. But the rate limit is the only wall between random abuse and Redis writes, and it is effectively bypassable today. Same code shape in two other public endpoints, so one fix propagates.

## P3-1: `js/shop.js` builds an `onclick` handler by string-concatenating an image URL

**File(s):** `js/shop.js:169-173`

**What's wrong**
```js
thumbsEl.innerHTML = allImages.map(function(img, idx) {
  return '<div class="product-thumb' + (idx === 0 ? ' active' : '') + '" onclick="switchProductImage(this, \'' + img.src + '\')">' +
    '<img src="' + img.src + '" alt="Image ' + (idx+1) + '">' +
    '</div>';
}).join('');
```

`img.src` is embedded inside a single-quoted JS string inside an HTML attribute with no escaping. Shopify CDN URLs are unlikely to contain single quotes, but if a URL ever includes one (URL-encoded query params can escape into the DOM parser oddly, or a custom domain image reference could), the attribute breaks and could execute injected code. `escapeHtml(product.title)` is used two lines up on the same element, so the escape helper is available and just not applied here.

**Fix sketch**
Wrap `img.src` with `escapeHtml(...)` for the attribute, and prefer attaching the click handler via `addEventListener` after render rather than serializing into `onclick=`.

**Why P3**
Real bug, but the input source is a trusted CDN today, so exploitation would need a supply-chain angle. Filing so it doesn't get re-invented elsewhere.

## Summary line for email

Two P1 bugs in the client management path: (1) portal-enable can silently hijack another client's login email if admin renames emails while portals are disabled, and (2) deleting a client leaves an orphan email mapping that blocks re-adding them. Both fixable in a few lines of `api/dashboard/clients.js` + `client-portal.js`. Plus one bypassable rate limit and one XSS-shaped code smell in the shop page.
