## Summary

Three real, high-confidence findings. All three are missing IP rate-limits on sensitive endpoints. The pattern is that write endpoints called from marketing forms (quiz, email capture, Charleston application) already have inline `ratelimit:` guards via Redis `INCR`, but the *auth* endpoints — which are far more sensitive — do not. The code is small and the fix is a copy-paste of the pattern already in `api/submit-quiz.js`.

Focus for today was Functional, but the crawl surfaced these while tracing login and password-reset flows end to end. Reporting them because they're concrete, verifiable, and low-noise — not padding.

## P1-1 — Admin dashboard login has no rate limiting; password brute-force is unbounded

- **Severity:** P1
- **Category:** Auth / security-adjacent
- **File:** `api/dashboard/login.js` (all 17 lines)

**What's wrong.** The handler validates `password` against `DASHBOARD_PASSWORD` with `crypto.timingSafeEqual` and returns a session cookie. There is no per-IP counter, no delay, no lockout. Every other write endpoint (`api/submit-quiz.js`, `api/submit-email.js`, `api/submit-chs-application.js`) uses the `ratelimit:<scope>:<ip>` Redis pattern. This one — the most sensitive endpoint on the site, gating the entire `/thomas` dashboard including client PII, revenue, ad spend, and Charleston applications — doesn't.

Since the whole dashboard is a single shared password, a successful brute-force gives the attacker everything.

**Repro.**
```bash
for i in $(seq 1 10000); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST https://www.telosathleticclub.com/api/dashboard/login \
    -H 'Content-Type: application/json' \
    -d "{\"password\":\"guess$i\"}"
done
```
Nothing throttles this. Vercel's platform-level abuse detection is not a substitute for endpoint-level rate limiting on auth.

**Fix.** Copy the pattern from `api/submit-quiz.js:22-29`:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:dashlogin:${ip}`;
const count = await redis('INCR', rateLimitKey);
if (count === 1) await redis('EXPIRE', rateLimitKey, 3600);
if (count > 10) return res.status(429).json({ error: 'Too many attempts' });
```

Consider a stricter budget (e.g. 5/hr per IP) since this is auth, not a form.

## P1-2 — Client portal login has no rate limiting

- **Severity:** P1
- **Category:** Auth / security-adjacent
- **File:** `api/client/login.js:17-59`

**What's wrong.** Same class as P1-1. `POST /api/client/login` looks up `client_email:{email}` in Redis, verifies the PBKDF2 hash, and issues a session cookie. No rate limiter. Once an attacker knows any real client email (they leak from social, from the CHS application flow, or from enumeration on password-reset behavior), the password is the only barrier. PBKDF2 with 100k SHA-512 iterations makes each *server-side* attempt costlier, which slows this to some extent — but it doesn't help against distributed guessing and, if the coach-issued initial password is short/guessable (a real risk in a small business, coach-set flow), it's still worth the attacker's time.

Also: repeated PBKDF2 100k iterations under load is itself a cheap DoS vector — one CPU-bound login attempt per request, no gate.

**Repro.** Same shape as P1-1 with `{"email":"known@address","password":"guess"}`.

**Fix.** Same `ratelimit:` pattern, keyed on IP *and* on `email`:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const ipKey = `ratelimit:clientlogin:${ip}`;
const emailKey = `ratelimit:clientlogin_email:${normalizeEmail(body.email)}`;
const [ipCount, emailCount] = await Promise.all([
  redis('INCR', ipKey),
  redis('INCR', emailKey),
]);
if (ipCount === 1) await redis('EXPIRE', ipKey, 3600);
if (emailCount === 1) await redis('EXPIRE', emailKey, 3600);
if (ipCount > 20 || emailCount > 10) return res.status(429).json({ error: 'Too many attempts' });
```

Rate-limit *before* doing the PBKDF2 verify, otherwise the DoS-via-PBKDF2 angle isn't fixed.

## P2 — Password reset endpoint has no rate limit; Resend email flood + financial DoS

- **Severity:** P2
- **Category:** Abuse / financial
- **File:** `api/client/reset-password.js:20-67`

**What's wrong.** `POST /api/client/reset-password` with just `{ email }` triggers a Resend API call to send a password-reset email whenever the email matches an active portal-enabled client. The endpoint intentionally returns `200 { ok: true }` in every case to prevent enumeration — which is correct — but there is no rate limiter of any kind.

Two concrete abuse paths:

1. **Financial DoS.** Resend bills per email. An attacker who scrapes any handful of client emails (or guesses common addresses in the coaching space) can loop `POST reset-password` and rack up the Resend bill. The endpoint doesn't even require a valid email — every hit costs a Redis roundtrip; every hit that matches a real client costs a Resend send.
2. **Targeted harassment.** For a known real client, an attacker can spam their inbox with legitimate-looking Telos password reset emails at whatever rate they want. Bad UX and reputationally bad.

Because responses are uniform `200 { ok: true }`, response *timing* still leaks whether the email exists (the Resend call adds latency on the success path). Rate limiting fixes the abuse cases and the response-timing distinguisher becomes harder to exploit.

**Fix.** Same pattern; rate-limit by IP *and* by normalized email so a single attacker can't rotate IPs to spam one victim, and a single IP can't spam many victims:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const ipKey = `ratelimit:pwreset_ip:${ip}`;
const emailKey = `ratelimit:pwreset_email:${normalizeEmail(body.email)}`;
// ...INCR + EXPIRE both, cap at ~5/hr each, return 200 { ok: true } (do NOT expose 429) so enumeration stays blocked
```

Return `200 { ok: true }` on the *rate-limit* branch too, so an attacker can't use a 429 to distinguish real vs. fake emails.
