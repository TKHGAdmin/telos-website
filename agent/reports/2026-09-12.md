## Finding 1 - Pricing gate is trivially bypassable; quiz lead capture accepts blank forms

- **ID:** BUG-2026-09-12-1
- **Severity:** P1
- **Area:** Functional
- **File(s):** `js/quiz.js:225`, `js/quiz.js:247`, `index.html:580`, `pricing.html:594`

### Repro / Trace
1. Open `/pricing` (or the homepage quiz section).
2. Click through all 8 questions.
3. On the lead-capture step, leave "First name" and "Email" empty.
4. Click "See Your Score".

The click handler at `js/quiz.js:225` runs unconditionally:
- The button is `type="button"` (`index.html:580`, `pricing.html:594`), so the browser never enforces the `required` attribute on the email input.
- `js/quiz.js:247` sets `localStorage.setItem('telosQuizCompleted', 'true')` before validating anything - `pricing.html` reads this key to unlock the price cards.
- The `fetch('/api/submit-quiz', ...)` returns HTTP 400 (`Name and email required`), but the `.catch(function() {})` at line 269 swallows the failure silently.
- Results render either way.

### Expected vs Actual
- **Expected:** Empty name/email should block the transition; nothing is stored, nothing unlocks.
- **Actual:** Empty submissions unlock pricing AND appear to complete the funnel while producing zero leads on the backend.

### User Impact
Any visitor who can click 8 buttons can view gated prices without giving a name or email. Every "polite" abandoner (who taps See Your Score to see if it's real) is lost as a lead. This is the top-of-funnel form for the entire pricing page.

### Suggested Fix
In `setupLeadCapture` at `js/quiz.js:225`, guard the whole block:

```js
if (!nameInput.value.trim() || !emailInput.value.trim()) {
  // show inline error; do NOT set localStorage or fetch
  return;
}
```

Or - safer - change the button to `type="submit"` and bind to the form's `submit` event so the browser validates `required` first.

### Confidence
High

## Finding 2 - Deleting a client leaves an orphan email-lookup row; the email is bricked forever

- **ID:** BUG-2026-09-12-2
- **Severity:** P2
- **Area:** Functional
- **File(s):** `api/dashboard/clients.js:143`, `api/dashboard/client-portal.js:117`, `api/dashboard/clients.js:70`, `api/client/login.js:29`

### Repro / Trace
1. Create client Alice at `alice@x.com` in `/thomas`.
2. Open Client Portal, enable her portal - this writes `client_email:alice@x.com -> <id>` at `api/dashboard/client-portal.js:117`.
3. Delete Alice via the Clients tab (`DELETE /api/dashboard/clients?id=...`).
   - Handler at `clients.js:143` only removes `client:{id}` and the `clients_index` ZSET entry. The `client_email:` key is left behind.
4. Try to re-add a client with `alice@x.com`: POST fails at `clients.js:70` with `"Email already in use by another client"`.
5. Try `POST /api/client/login` with `alice@x.com`: `client_email:` resolves to the deleted id, then `GET client:{id}` returns null, and the login endpoint returns `"Invalid email or password"` at `api/client/login.js:29`.

### Expected vs Actual
- **Expected:** Delete cleans up all Redis keys tied to that client, including `client_email:{normalizedEmail}`.
- **Actual:** The lookup row is orphaned. Neither creation nor login works for that email again without manual Redis surgery.

### User Impact
Coach cannot restore a mistakenly-deleted client under the same email, and cannot recycle an old client's address for a new signup. Manifests silently as "the form rejects me" or "the client says login is broken."

### Suggested Fix
In the DELETE branch at `clients.js:143`, read the record before deleting and remove the email lookup:

```js
var existingRaw = await redis('GET', 'client:' + id);
if (existingRaw) {
  var existing = JSON.parse(existingRaw);
  if (existing.email) {
    var { normalizeEmail } = require('../lib/client-auth');
    await redis('DEL', 'client_email:' + normalizeEmail(existing.email));
  }
}
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

### Confidence
High

## Finding 3 - Engagement cron re-emails every inactive client every day (no throttle)

- **ID:** BUG-2026-09-12-3
- **Severity:** P2
- **Area:** Functional
- **File(s):** `api/cron/engagement-check.js:61`, `vercel.json` (cron schedule for `/api/cron/engagement-check`)

### Repro / Trace
1. Portal-enabled client with `emailEnabled !== false` stops logging on day N.
2. On day N+3 the cron matches `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3` and sends the "We miss you at Telos" email.
3. Day N+4: same condition still matches, same email sent again.
4. Day N+5, N+6, N+7, ... same email every day until the client either logs in or is deactivated.

No last-sent record is stored; nothing throttles the send.

### Expected vs Actual
- **Expected:** One re-engagement email per inactivity streak, or at most one every N days (e.g., 7).
- **Actual:** One "We miss you" email per inactive client per day, indefinitely.

### User Impact
An inactive client who sees the site as spam for 5-7 straight days will mark it as spam - which hurts sender reputation for every other legitimate email the domain sends (weekly summaries, password resets, receipts). Also directly increases the odds a paying client on a rough week unsubscribes and churns.

### Suggested Fix
Before the send at `engagement-check.js:76`, gate on a per-client last-sent key with a 7-day TTL:

```js
var throttleKey = 'client_last_engagement_email:' + client.id;
var alreadySent = await redis('GET', throttleKey);
if (alreadySent) continue;
// ... send email ...
await redis('SET', throttleKey, String(Date.now()), 'EX', 604800); // 7 days
```

### Confidence
High
