## Summary

One P1 data-integrity bug in the admin client-deletion path: the DELETE handler in
`api/dashboard/clients.js` removes only the primary `client:{id}` blob and the
`clients_index` sorted-set entry, but leaves behind the `client_email:{email}`
lookup and roughly twenty other client-scoped keys (nutrition, training, 545,
supplements, mindset, resources, sidemenu, daily logs, and their date indexes).

The most immediate impact is that a deleted client's email address becomes
permanently unusable in the admin UI — the very next attempt to add a new client
with that email fails with "Email already in use by another client," even though
no visible client owns it. Coach workflow blocker.

## Findings

### 1. [P1] Deleting a client leaves the email-lookup key behind, blocking re-use of the address

- **File:** `api/dashboard/clients.js:143-154`
- **Severity:** P1
- **Category:** data-integrity
- **Repro steps:**
  1. In `/thomas` → Clients, create a client with email `foo@example.com`.
  2. Open the Client Portal tab for that client and click "Enable Portal" (this
     writes `client_email:foo@example.com → {id}` via `api/dashboard/client-portal.js:117`).
  3. Return to Clients and delete the client.
  4. Try to create a new client with the same email `foo@example.com`.
- **Expected:** The new client is created successfully — the deleted client's
  email should be freed.
- **Actual:** Server returns HTTP 400 `{"error":"Email already in use by another
  client"}`. The check at `api/dashboard/clients.js:70-73`
  (`existingEmailOwner = await redis('GET', 'client_email:' + normalized)`)
  still resolves to the deleted client's ID, because the DELETE handler never
  ran `DEL client_email:...`. The email is now effectively burned.
- **Root cause:** The DELETE handler only issues
  `DEL client:{id}` and `ZREM clients_index {id}`. It never touches:
  - `client_email:{normalizedEmail}` — email→id lookup used by login and by the
    duplicate-email check above.
  - `client_nutrition_plan:{id}`, `client_mindset:{id}`, `client_resources:{id}`,
    `client_545_goals:{id}`, `client_545_routine:{id}`,
    `client_training_program:{id}`, `client_sidemenu:{id}`,
    `client_supplement_plan:{id}` — all coach-set portal content.
  - `client_dailylog:{id}:*`, `client_nutrition_log:{id}:*`,
    `client_training_log:{id}:*`, `client_545_daily:{id}:*`,
    `client_supplement_log:{id}:*`, `client_activity_log:{id}:*` — daily logs.
  - `client_dailylogs_index:{id}`, `client_nutrition_logs_index:{id}`,
    `client_training_logs_index:{id}`, `client_545_index:{id}`,
    `client_supplement_logs_index:{id}`, `client_activity_logs_index:{id}` — ZSET indexes.
  - `client_push_sub:{id}`, `client_modules_watching:{id}`,
    `client_modules_completed:{id}`, `client_module_progress:{id}:*` — PWA and modules.
- **Suggested fix:** Before the two existing DEL/ZREM calls, load the client
  record to grab their email, then issue a pipelined batch of `DEL` on all
  client-scoped keys plus `DEL client_email:{normalizedEmail}`. For the
  date-scoped keys, read the date list from each `*_index:{id}` ZSET first,
  then delete each. Sketch:

  ```js
  var raw = await redis('GET', 'client:' + id);
  var client = raw ? JSON.parse(raw) : {};
  var email = client.email
    ? require('../lib/client-auth').normalizeEmail(client.email)
    : null;

  var dateIndexes = [
    'client_dailylogs_index', 'client_nutrition_logs_index',
    'client_training_logs_index', 'client_545_index',
    'client_supplement_logs_index', 'client_activity_logs_index',
  ];
  var perDateKeys = [
    'client_dailylog', 'client_nutrition_log', 'client_training_log',
    'client_545_daily', 'client_supplement_log', 'client_activity_log',
  ];
  var scalarKeys = [
    'client:', 'client_nutrition_plan:', 'client_mindset:',
    'client_resources:', 'client_545_goals:', 'client_545_routine:',
    'client_training_program:', 'client_sidemenu:',
    'client_supplement_plan:', 'client_push_sub:',
    'client_modules_watching:', 'client_modules_completed:',
  ];

  // Collect all dates from each index, build DELs for the per-date blobs
  // and for the index itself, then pipeline everything.
  ```

  At minimum, adding a single `DEL client_email:{email}` unblocks the coach's
  primary workflow; the rest is orphaned data that costs storage and could
  confuse future analytics.

- **Confidence:** high — traced through create → enable-portal → delete →
  recreate paths and confirmed against the storage key list in `CLAUDE.md`.
