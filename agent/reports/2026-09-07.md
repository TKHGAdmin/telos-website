## BUG-2026-09-07-001 - Deleting a client with portal enabled orphans the `client_email:*` reverse-lookup key, blocking re-add with same email

**Severity:** P2 (affects admin in a real, recurring scenario; requires manual Redis intervention to unblock)

**File / lines:**
- `api/dashboard/clients.js:143-154` (DELETE handler - missing cleanup)
- `api/dashboard/clients.js:68-73` (POST duplicate-email check that later trips on the orphan)
- `api/dashboard/client-portal.js:114-118` (where the `client_email` key is first written)

**What is wrong:**
The `DELETE /api/dashboard/clients` handler removes the `client:{id}` blob and the `clients_index` ZSET entry, but never touches the `client_email:{normalizedEmail}` reverse-lookup. That reverse-lookup is written by `client-portal.js` POST whenever `portalEnabled=true`, and is only deleted along the explicit `enabled=false` branch of that same endpoint. If an admin deletes a client whose portal was ever enabled without first flipping portal access off, the email key survives forever and the client-creation duplicate-email check (`clients.js:70-73`) treats the email as still owned.

Relevant DELETE handler (unchanged in the diff below):
```js
// api/dashboard/clients.js:143
if (req.method === 'DELETE') {
  try {
    var id = req.query.id || (req.body && req.body.id);
    if (!id) return res.status(400).json({ error: 'ID required' });
    await redis('DEL', 'client:' + id);
    await redis('ZREM', 'clients_index', String(id));
    return res.status(200).json({ ok: true });
    // <-- no cleanup of `client_email:{email}` here
  } ...
}
```

**Reproduction:**
1. As admin, `POST /api/dashboard/clients` with `{ name, email: "foo@example.com", tier: "growth" }` -> client id `N` created.
2. In the /thomas Client Portal tab, enable the portal for client `N` (or `POST /api/dashboard/client-portal` with `{ clientId: N, enabled: true, password: "at-least-8" }`). This writes `client_email:foo@example.com = N`.
3. `DELETE /api/dashboard/clients?id=N`. `client:N` and the `clients_index` entry are removed; `client_email:foo@example.com` remains.
4. `POST /api/dashboard/clients` with the same email `foo@example.com` -> responds `400 { error: "Email already in use by another client" }` because the orphaned key still resolves.

**Failure scenario / impact:**
A returning coaching client cannot be re-onboarded under their real email without either (a) using a different email or a `+tag` suffix, or (b) manually deleting the `client_email:foo@example.com` Redis key via the Upstash console. Reset-password and login flows are unaffected (both bail on the missing `client:{id}` blob), so there is no direct security impact - purely a data-integrity / admin-usability defect.

**Suggested fix (do NOT apply in this run; reporting only):**
Before the two existing `redis('DEL' | 'ZREM' ...)` calls, GET the client, parse it, and if it has an email (portal-enabled or not, since the email key only exists when portal was enabled but a defensive `DEL` is harmless), `DEL client_email:{normalizeEmail(email)}`. Example sketch:
```js
var raw = await redis('GET', 'client:' + id);
if (raw) {
  try {
    var c = JSON.parse(raw);
    if (c && c.email) {
      var { normalizeEmail } = require('../lib/client-auth');
      await redis('DEL', 'client_email:' + normalizeEmail(c.email));
    }
  } catch (e) {}
}
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

**Confidence:** High. The read path is confirmed by inspecting every writer/reader of `client_email:*` (`api/dashboard/client-portal.js`, `api/dashboard/clients.js`, `api/client/login.js`, `api/client/reset-password.js`); no delete-side cleanup exists anywhere else.

## BUG-2026-09-07-002 - `POST /api/client/reset-password` has no rate limit; every hit triggers a Resend API call and creates a Redis token

**Severity:** P3 (real cost/quota concern but requires knowing at least one valid client email; no auth bypass)

**File / lines:** `api/client/reset-password.js:20-67`

**What is wrong:**
Every other public POST endpoint in the project (`submit-quiz.js:23-29`, `submit-email.js:28-34`, `submit-chs-application.js:40-46`) uses the `ratelimit:{scope}:{ip}` INCR+EXPIRE pattern to cap requests per IP per hour. The password-reset endpoint is public, unauthenticated, and has none. For any known-valid client email it will unconditionally:
1. `SETEX password_reset:{random32} 3600 clientId` (fills Redis with hourly-expiring keys).
2. `fetch` Resend to send a real email if `RESEND_API_KEY` is present (burns paid quota, and floods the real client's inbox).

The email-enumeration guard (returning 200 for unknown emails without side effects) is correct, but it does not protect against an attacker who has enumerated one valid email out-of-band.

**Reproduction:** Any adversary with a known active-portal client email can issue thousands of `POST /api/client/reset-password { email: "known@..." }` per hour from a single IP. Each is a Resend charge and an inbox item for the real client. There is no back-off, no captcha, no per-email throttle.

**Failure scenario / impact:** Attacker-driven cost inflation on the Resend account, plus an inbox-flood harassment vector against a specific client. Also inflates Upstash key count (though the 1h TTL bounds it).

**Suggested fix:** Add the same `ratelimit:pwreset:{ip}` INCR pattern used in the other three public endpoints - `max 5/hr` matches the CHS handler; additionally consider a per-normalized-email lockout key (e.g., `SETEX ratelimit:pwreset_email:{email} 300 1` -> 5-minute cooldown per address) to blunt the inbox-flood angle even when the attacker rotates IPs.

**Confidence:** High. Direct read of `api/client/reset-password.js` versus the three sibling endpoints; the omission is unambiguous.

## BUG-2026-09-07-003 - `POST /api/client/daily-log` accepts unbounded `notes`; every peer endpoint caps text length

**Severity:** P3 (inconsistency with codebase norm; storage/DoS by an authenticated bad actor)

**File / lines:** `api/client/daily-log.js:77`

**What is wrong:**
```js
if (body.notes !== undefined) log.notes = body.notes;
```
No `.slice(N)`, no type coercion, no length guard. Compare to sibling client-write endpoints, all of which explicitly cap text fields:
- `api/client/training-log.js:54` -> `(body.notes || '').slice(0, 1000)`
- `api/client/five-four-five.js:68,81,102` -> `.substring(0, 500)` / `.substring(0, 300)` / `.substring(0, 500)`
- `api/dashboard/chs-applications.js:58` -> `String(body.notes).slice(0, 4000)`

The daily-log key is per-day (`client_dailylog:{clientId}:{YYYY-MM-DD}`), so an authenticated client can POST a multi-MB `notes` for every past date they choose, driving up Redis memory and slowing the pipeline reads that fan out over 30 days in `client-portal.js:47-79` and the weekly-summary cron.

**Reproduction:** Authenticated client sends `POST /api/client/daily-log { date: "2026-09-07", notes: "X".repeat(5_000_000) }`. Redis stores it; subsequent GETs return the 5 MB payload. Repeat across many dates to fill more storage.

**Failure scenario / impact:** Realistic upside is a self-inflicted client dashboard slowdown; realistic downside is a churn client leaving behind ballooned per-day entries that never expire (no TTL is set on daily logs). Not a security bug on its own, but the endpoint is the only client-write path in the codebase without the guard, and adding the same one-line `.slice(0, N)` closes the gap.

**Suggested fix:** Mirror the neighbouring endpoints: `log.notes = String(body.notes).slice(0, 2000);` (or whatever cap the product-side prefers - `training-log.js`'s 1000 seems the closest analogue).

**Confidence:** High for the missing-guard claim; the "who cares" line is what makes this a P3 rather than a P2 - it needs authentication and the harm scales with abuse, not one-shot.
