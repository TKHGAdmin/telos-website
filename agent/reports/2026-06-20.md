## P2-01 — Weekly summary email reports "Current Streak: 0 days" almost every Monday

**File:** `api/cron/weekly-summary.js:86-90`

**What's wrong.** The streak-counting loop walks the 7-day daily-log array starting at index 0 (today) and breaks the moment a day has no log:

```js
// Count streak (from today backwards)
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

The cron is scheduled for Monday 14:00 UTC = 9am ET (`vercel.json:21`). At that hour most active clients haven't done their Monday morning check-in yet, so `weekData[0][0]` is empty, the loop breaks immediately, and `streak = 0` is sent to every client - regardless of whether they actually have a 30-day streak going.

The body renders this directly: `'Current Streak: <strong>' + stats.streak + ' days</strong>'` (line 131 of `weekly-summary.js`).

**Repro.** Set a client up who logged yesterday (Sunday) and the prior 6 days. Run the cron before that client logs in Monday morning. Email says "Current Streak: 0 days."

**Why it matters.** This is the marquee retention email Telos sends each week. Telling a consistent client they have a 0-day streak undermines exactly the behavior the email is meant to reinforce. It also looks broken, which erodes trust in the rest of the numbers in the email.

**Suggested fix.** Skip today (start the loop at `d = 1`) - or treat today's absence as neutral and only break on a missing prior day. The `avgScore` calculation has the same shape but is less affected because it averages rather than terminating, so it's less urgent there.

## P2-02 — Duplicate client emails accepted at creation; later silently locks first client out of portal

**Files:**
- `api/dashboard/clients.js:69-73` (creation gate)
- `api/dashboard/client-portal.js:114-118` (portal enable - blind SET)

**What's wrong.** Duplicate-email enforcement on client creation only consults the `client_email:{email}` lookup index:

```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

But that index is only populated when **portal is enabled**, via `client-portal.js:115-117`:

```js
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));
}
```

That `SET` is unconditional - no "does this key already point to a different client" guard.

**Repro sequence.**
1. Admin creates Client A with email `foo@bar.com`, portal not enabled. No `client_email:` mapping.
2. Admin creates Client B with email `foo@bar.com`, portal not enabled. The check at `clients.js:70` passes (mapping is null). Both clients now share an email in their primary records.
3. Admin enables portal for Client A. Sets `client_email:foo@bar.com -> A.id`. Client A logs in fine.
4. Admin enables portal for Client B. Silently overwrites `client_email:foo@bar.com -> B.id`.
5. Client A tries to log in. `login.js:24` resolves their email to **B's** id, loads B's record, checks A's password against B's hash → 401. Client A is permanently locked out of the portal with no warning to the admin.

**Why it matters.** Coach onboarding workflow is to add the client record first (often without portal), then enable portal later when the welcome email goes out. The two-step flow is exactly the path that triggers this. The "Email already in use" check at step 2 is the user's only signal, and it's hollow.

**Suggested fix.** Two options that compose:
1. In `clients.js` POST, also scan existing client records (or maintain a `client_email_all:{email}` lookup that's set on creation, independent of portal state). Reject creation if any other client has that email.
2. In `client-portal.js` POST, before the `SET 'client_email:'` call, GET the key first - if it returns a different id, refuse the operation with "Email collision: client {id} already owns this email."

## P3-01 — Quiz retake submits the same lead twice to `/api/submit-quiz`

**File:** `js/quiz.js:221-275`

**What's wrong.** `setupLeadCapture()` attaches a fresh click handler each time it runs:

```js
function setupLeadCapture() {
  const form = quizLeadCapture.querySelector('form');
  const submitBtn = quizLeadCapture.querySelector('.quiz-see-score-btn');

  submitBtn.addEventListener('click', function(e) {
    // ... fetch('/api/submit-quiz', ...) ...
  });
}
```

The retake flow (`resetQuiz()` at line 416) tears down state and re-runs the quiz, eventually reaching `quizQuestionCard` lines 211-215, which calls `setupLeadCapture()` again. The old click handler is never removed - so after one retake the submit button has **two** click handlers, both firing in sequence, both POSTing to `/api/submit-quiz`. Three retakes → four POSTs per click. Each retake adds another.

**Repro.** Complete the quiz once on `pricing.html` or `index.html` → click "Retake" → fill in and submit again. Inspect Network: two POSTs to `/api/submit-quiz` for the second submit. Admin dashboard "Submissions" tab will show duplicates.

**Why it matters.** Pollutes the lead pipeline with duplicates. The `submit-quiz` rate-limiter caps at 10 per IP per hour, so the user can also self-DOS their own submission via 5 retakes.

**Suggested fix.** Either:
- Move the `addEventListener` outside `setupLeadCapture()` (run once at DOMContentLoaded, read the latest `quiz.userName/userEmail/userPhone` at click time), or
- Use a named handler and call `submitBtn.removeEventListener` before re-adding, or
- Replace the button via `submitBtn.replaceWith(submitBtn.cloneNode(true))` before re-binding.
