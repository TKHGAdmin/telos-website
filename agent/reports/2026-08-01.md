## Summary

First run of the Telos Bug Hunter, scoped to functional issues. Two confirmed bugs: (1) the product detail page grid layout is broken because the newly-added thumbnail row was inserted as a sibling of the info column instead of being nested under the image, so on any product with 2+ images the thumbnails sit in the top-right cell and shove the title/price/add-to-cart down into the bottom-left, ruining the shopping experience; (2) deleting a client from the admin dashboard leaves the `client_email:{email}` Redis lookup orphaned, which blocks ever re-adding a client with that same email address.

### BUG-20260801-01
- **Severity**: P1
- **Area**: shop / product-detail
- **Files**: `product.html:765-780`, `js/shop.js:160-177`
- **Summary**: Product detail page grid layout collapses for any product with multiple images — thumbnails render in the info column and push the title/price/add-to-cart button below the image.
- **Impact**: Every product with more than one image (added in commit `f5cb8c4` "add image gallery with thumbnails") is unreadable on desktop. Shopper cannot see the title, price, or Add-to-Cart until they scroll below the fold, which will suppress conversions on the shop page.
- **Reproduction / Evidence**: `.product-detail.loaded` uses `display: grid; grid-template-columns: 1fr 1fr` (product.html:106-108). The container has THREE direct children in this order:
  ```html
  <div class="product-detail" id="productDetail">
    <div class="product-detail-image" id="productImage"></div>
    <div class="product-detail-thumbs" id="productThumbs"></div>   <!-- added in f5cb8c4 -->
    <div class="product-detail-info">...</div>
  </div>
  ```
  Auto-placement puts the image in row-1/col-1, the thumbs row in row-1/col-2 (where the info was supposed to go), and the info column wraps to row-2/col-1. Result: `[image] [thumbs] / [info] [empty]` instead of `[image] [info] / [thumbs] [ ]`.
- **Suggested fix**: Wrap the image and thumbs together so the grid only sees two direct children:
  ```html
  <div class="product-detail-media">
    <div class="product-detail-image" id="productImage"></div>
    <div class="product-detail-thumbs" id="productThumbs"></div>
  </div>
  <div class="product-detail-info">...</div>
  ```
  Or explicitly grid-position the thumbs (`grid-column: 1; grid-row: 2;`) and the info (`grid-column: 2; grid-row: 1 / span 2;`).
- **Confidence**: high — verified against the diff in commit `f5cb8c4` and the surviving CSS grid definition.

### BUG-20260801-02
- **Severity**: P2
- **Area**: admin dashboard / client CRUD
- **Files**: `api/dashboard/clients.js:143-153`
- **Summary**: `DELETE /api/dashboard/clients` removes the `client:{id}` record and the `clients_index` entry but never removes the `client_email:{normalizedEmail}` lookup, so that email stays permanently reserved in Redis.
- **Impact**: If a portal-enabled client is deleted and Thomas later tries to re-add them (or add a different person who reuses the same email), `POST /api/dashboard/clients` fails at line 71 with `"Email already in use by another client"` — even though no active client owns it. There is no admin UI to clean this up; only a manual Redis edit resolves it. Also affects `client_dailylog:*`, `client_nutrition_log:*`, `client_545_*`, `client_training_log:*`, `client_supplement_log:*`, `client_activity_log:*`, and `client_push_sub:*` keys, all of which leak on delete.
- **Reproduction / Evidence**:
  1. In `/thomas`, create a client with email `test@example.com`, enable the portal (this calls `client-portal.js` which SETs `client_email:test@example.com` → id).
  2. Delete that client from the Clients tab.
  3. Try to add a new client with `test@example.com`. The POST returns 400 "Email already in use by another client" (`api/dashboard/clients.js:71`).
  Root cause is the DELETE branch at line 143:
  ```js
  if (req.method === 'DELETE') {
    var id = req.query.id || (req.body && req.body.id);
    if (!id) return res.status(400).json({ error: 'ID required' });
    await redis('DEL', 'client:' + id);
    await redis('ZREM', 'clients_index', String(id));
    return res.status(200).json({ ok: true });
  }
  ```
  Missing: `DEL client_email:{email}` (need to read client first to get email), plus a sweep of the log-index ZSETs to clear per-client history.
- **Suggested fix**: Before the `DEL client:{id}`, GET the client record, and if `portalEnabled` or `email` is present, `DEL client_email:{normalizeEmail(email)}`. Optionally also DEL the per-client index ZSETs and their members. Do the cleanup in a `redisPipeline` for atomicity.
- **Confidence**: high — the DELETE branch code is small and the email lookup lifecycle is only handled in `client-portal.js` (SET) and `clients.js` PUT (SET/DEL on email change).

## Not reported

- Push notification stub in `api/client/notify.js` — code comment explicitly notes VAPID / RFC 8291 encryption is unimplemented; treating this as known incomplete work, not a bug.
- `daily-log.js` storing `body.water: 0` and `body.steps: 0` as `null` (via `parseFloat(x) || null`) — edge case that only affects users deliberately logging zero, minor.
- Shopify Storefront token embedded in `js/shop.js` — this is a public read-only token by design; not a secret.
- CHS rate-limit trusts `x-forwarded-for` — acceptable on Vercel edge; not exploitable at this scale.
- `verifyPassword` in `api/lib/auth.js` compares string length before `timingSafeEqual` — leaks 1 bit (password length), acceptable for a single-admin dashboard.
