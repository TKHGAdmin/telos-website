## BUG-20261024-1: Engagement reminder cron emails inactive clients every single day with no cooldown

- **Severity**: P1
- **File**: `api/cron/engagement-check.js:61`
- **Status**: new

### What's wrong

The cron runs daily (`"schedule": "0 15 * * *"` in `vercel.json`). For every active, portal-enabled client, it checks the last 5 days of daily logs and sends an "engagement reminder" email whenever the most recent log is 3+ days old OR there is no log in the last 5 days. There is no record of whether a reminder was already sent, so a client who stops checking in receives a new reminder email every 24 hours — day 3, day 4, day 5, day 6, day 7… each one with subject "We miss you at Telos". For a client who takes a week off, that's five identical emails in a row. This is the exact pattern that trains people to filter the sender into spam.

### Reproduction

1. Pick a client where `status === 'active'`, `portalEnabled === true`, `emailEnabled !== false`, and `email` is set.
2. Have them not create any `client_dailylog:{id}:{date}` entries for 5+ consecutive days.
3. Trigger `GET /api/cron/engagement-check` with the correct `Authorization: Bearer $CRON_SECRET` header once per calendar day.
4. Observe: on day 3 Resend receives a POST to `/emails`. On day 4 another POST. On day 5 another. The outer loop at `engagement-check.js:36`–`95` has no "already sent" short-circuit — look at the `if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3)` block at line 61 and the surrounding function; nothing writes a timestamp back to the client record after sending.

### Suggested fix

After a successful send, write `client.lastEngagementSentAt = new Date().toISOString()` back to `client:{id}` and skip the send if `now - lastEngagementSentAt < 72h` (or whatever cadence Thomas wants — probably once per 7-day stretch of inactivity, not daily).

```js
// after sendResendEmail succeeds for a client
client.lastEngagementSentAt = new Date().toISOString();
await redis('SET', 'client:' + client.id, JSON.stringify(client));

// at the top of the per-client loop
if (client.lastEngagementSentAt) {
  var since = Date.now() - new Date(client.lastEngagementSentAt).getTime();
  if (since < 7 * 86400000) continue; // one reminder per week max
}
```

## BUG-20261024-2: Deleting a portal-enabled client orphans the email-to-ID lookup, blocking email reuse forever

- **Severity**: P1
- **File**: `api/dashboard/clients.js:143`
- **Status**: new

### What's wrong

The DELETE handler for `/api/dashboard/clients` removes `client:{id}` and the `clients_index` entry, but does NOT remove `client_email:{normalizedEmail}` → `{id}` lookup that was created when the client's portal was enabled. The POST handler (lines 70–73) then checks that exact key for uniqueness and rejects any new client that tries to reuse the email — even though the client it points to no longer exists. The admin has no way to clear this from the dashboard; they'd need direct Redis access.

Blast radius: Thomas creates a client, enables portal, deletes the client later (bad fit, duplicate, test record). He never gets to re-enroll that person under the same email.

### Reproduction

1. Admin POST `/api/dashboard/clients` with `{name: "Test", email: "x@y.com", tier: "rebuild"}`. Say it returns `id: 42`.
2. Admin POST `/api/dashboard/client-portal` with `{clientId: 42, enabled: true, password: "longenough"}`. This writes `client_email:x@y.com → "42"` (see `client-portal.js:115–118`).
3. Admin DELETE `/api/dashboard/clients?id=42`. This deletes `client:42` and `ZREM`s from `clients_index`.
4. Admin POST `/api/dashboard/clients` again with the same `{email: "x@y.com", ...}`. Response: 400 `"Email already in use by another client"` — but no other client has that email. The lookup is stale.

### Suggested fix

In the DELETE handler, read the client first so you know their email, then clean every per-client key. At minimum:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });

  var raw = await redis('GET', 'client:' + id);
  if (raw) {
    try {
      var existing = JSON.parse(raw);
      if (existing.email) {
        var { normalizeEmail } = require('../lib/client-auth');
        await redis('DEL', 'client_email:' + normalizeEmail(existing.email));
      }
    } catch (e) {}
  }
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

Deeper cleanup (dailylog, training-log, nutrition-log, 545, supplement, activity, push-sub, their indexes) is a separate P3 item worth doing later to avoid Redis bloat on deleted clients, but the email-lookup leak is the only one that breaks a user-facing workflow.
