## BUG-2026-06-23-01 — Deleting a client orphans Redis keys and blocks email reuse

- **Severity:** P1
- **Area:** Admin / data integrity
- **File:** `api/dashboard/clients.js:143-153`
- **Status:** new

### Symptom

When the coach deletes a client from the `/thomas` Clients tab, the underlying record and the `clients_index` entry are removed — but every other Redis key tied to that client is left behind:

- `client_email:{normalizedEmail}` (the login lookup)
- `client_nutrition_plan:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_training_program:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_545_goals:{id}`, `client_545_routine:{id}`
- All daily logs: `client_dailylog:{id}:{date}`, `client_training_log:{id}:{date}`, `client_nutrition_log:{id}:{date}`, `client_supplement_log:{id}:{date}`, `client_activity_log:{id}:{date}`, `client_545_daily:{id}:{date}`
- The corresponding `..._index:{id}` ZSETs

The most user-visible consequence is the `client_email:` orphan: it points at a now-nonexistent client id, so trying to re-add a client with the same email fails with `"Email already in use by another client"` at `clients.js:71-72`. The coach has no UI to clear that orphan; it requires direct Redis access.

### Reproduction

1. Create a client with email `test@example.com` and enable portal access (this writes `client_email:test@example.com → {id}`).
2. Delete that client from the Clients tab.
3. Try to create a new client with the same email.
4. POST `/api/dashboard/clients` returns 400 `"Email already in use by another client"`.

### Why it's a bug

`clients.js` lines 143-153:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

Compare to the POST flow (`clients.js:70-73`) that explicitly guards against email reuse and the client-portal POST (`client-portal.js:115-118`) that creates the `client_email:` lookup. The delete path never tears it down. The pattern for "delete a client, then create them again" — which is a plausible coach workflow during onboarding cleanup — silently breaks.

The orphaned per-client data (nutrition plans, logs, etc.) is less acute but represents a slow Redis bloat and a privacy concern: stale client data persists indefinitely.

### Suggested fix

In the DELETE handler, before removing the record, read it to obtain the email, then issue a single pipeline of:

- `DEL client_email:{normalizeEmail(client.email)}` (only if present)
- `DEL` on each `client_{kind}:{id}` static key
- For each `client_{kind}_index:{id}` ZSET, `ZRANGE 0 -1` to get the dates, then `DEL client_{kind}:{id}:{date}` for each, then `DEL` the index itself
- `DEL client:{id}` and `ZREM clients_index {id}`

A simpler interim fix is at minimum cleaning up `client_email:` so the email-reuse case is unblocked.

## BUG-2026-06-23-02 — Quiz lead-capture submit handler accumulates on retake

- **Severity:** P2
- **Area:** Lead capture / homepage + pricing quiz
- **File:** `js/quiz.js:221-276` (and `js/quiz.js:415-442` for the reset path)
- **Status:** new

### Symptom

After a user completes the quiz, clicks "Retake Quiz," and goes through it a second time, the "See My Score" submit button fires its click handler twice. This sends two POSTs to `/api/submit-quiz` for one click, writes the same data into `localStorage` twice, and runs `renderResults()` twice (kicking off two concurrent count-up `setInterval`s on the score number, which flicker against each other). Each subsequent retake-and-submit cycle adds another handler.

### Reproduction

1. Open the homepage, scroll to the quiz, complete all 8 questions.
2. Submit the lead-capture form. Watch the Network tab → 1 POST to `/api/submit-quiz`.
3. Click "Retake Quiz" on the results card.
4. Complete the quiz again, submit. Network tab → 2 POSTs.
5. Repeat → 3, 4, ... POSTs per click.

### Why it's a bug

`setupLeadCapture()` (line 221) is called from `handleAnswerSelect` whenever the last question is answered. Inside, it unconditionally attaches a new listener:

```js
function setupLeadCapture() {
  const form = quizLeadCapture.querySelector('form');
  const submitBtn = quizLeadCapture.querySelector('.quiz-see-score-btn');

  submitBtn.addEventListener('click', function(e) { ... });
}
```

The button is the same DOM node across retakes; `resetQuiz()` does not clone, replace, or remove listeners. So every time the user reaches the lead-capture step, one more handler stacks on the button.

The same anti-pattern affects the retake button at line 397 (`retakeBtn.addEventListener('click', resetQuiz)` inside `renderResults`), which will get re-attached each time results render. The retake handler is idempotent so it doesn't show user-visible breakage, but it's the same pattern and should be fixed together.

Server-side, this skews the `quiz_submissions` count for any returning visitor, and produces duplicate leads in the dashboard's Submissions tab. Both submissions land because the JSON has a different `submittedAt` ms, so the `ZADD` dedup doesn't collapse them.

### Suggested fix

Either:

- Move `submitBtn.addEventListener(...)` outside `setupLeadCapture` and attach it once on `DOMContentLoaded`, reading from the `quiz` state at click time.
- Or, before attaching, replace the button: `submitBtn = submitBtn.cloneNode(true); old.replaceWith(submitBtn);` then attach.

Apply the same fix to the retake button inside `renderResults()`.

## BUG-2026-06-23-03 — Engagement-check cron emails inactive clients every single day

- **Severity:** P2
- **Area:** Cron / email
- **File:** `api/cron/engagement-check.js:61-94`
- **Status:** new

### Symptom

The daily cron sends a "We miss you at Telos" reminder to any active, portal-enabled client whose last `client_dailylog:` entry is 3+ days old. There is no record of when a reminder was last sent, so the cron sends a fresh email every single day the client remains inactive. A client who goes inactive for a week receives 5 identical "We miss you" emails (days 3, 4, 5, 6, 7).

### Reproduction

Read `engagement-check.js` end-to-end. The `if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3)` branch fires the email without consulting any prior-send state. Re-run the cron the next day with the same client still inactive → same condition → same email.

There's no `lastReminderSentAt` field on the client record, and no `engagement_reminder_sent:{clientId}` key written anywhere in the codebase (verified via grep).

### Why it's a bug

Functional: this is a logic error that produces email spam. A coach trying to keep clients engaged via gentle nudges will instead train them to mark Telos emails as spam, which then breaks the cold-onboarding emails and the weekly summary deliverability via the shared `noreply@telosathleticclub.com` sender reputation.

### Suggested fix

After successfully calling the Resend API for a client, write a key like:

```js
await redis('SETEX', 'engagement_reminder:' + client.id, 4 * 86400, '1'); // 4-day TTL
```

And gate the send on `!(await redis('GET', 'engagement_reminder:' + client.id))`. That makes the email at most once every 4 days while keeping the cron daily.
