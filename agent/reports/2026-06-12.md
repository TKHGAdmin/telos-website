**Focus:** Functional
**Total findings:** 3
**Scope:** API handlers under `api/dashboard/` and `api/lib/` (auth + client lifecycle paths). First-run pass; agent infrastructure under `agent/` and `docs/BUG_REPORT_SCHEMA.md` was bootstrapped during this run.

## BUG-20260612-01 — Deleting a client orphans the `client_email:` lookup and blocks re-use of the email

- **Severity:** P1
- **Area:** api/dashboard
- **File(s):** api/dashboard/clients.js:143-154

### What's wrong

The admin DELETE handler removes `client:{id}` and the `clients_index` ZSET member, but it does not remove the `client_email:{normalizedEmail}` reverse lookup. That lookup was created by `api/dashboard/client-portal.js` when the portal was enabled. After deletion, the email is still bound to the now-deleted ID, so the POST create path (line 70-73) rejects any new client with that email as "Email already in use by another client." There is no admin UI to clear it — the coach has to touch Redis manually.

### Repro / evidence

`api/dashboard/clients.js` DELETE handler:

```js
if (req.method === 'DELETE') {
  try {
    var id = req.query.id || (req.body && req.body.id);
    if (!id) return res.status(400).json({ error: 'ID required' });
    await redis('DEL', 'client:' + id);
    await redis('ZREM', 'clients_index', String(id));
    return res.status(200).json({ ok: true });
  } catch (err) { ... }
}
```

Compare with where the lookup is created (`api/dashboard/client-portal.js:115-118`):

```js
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));
}
```

And the create-time uniqueness check (`api/dashboard/clients.js:70-73`):

```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

Reproduction:
1. Create client `c1` with email `x@y.com`, enable portal → `client_email:x@y.com` = c1.id.
2. Delete `c1` via the admin "Delete" button (`thomas.html:1413-1424` calls `DELETE /api/dashboard/clients?id=c1`).
3. Try to create a new client `c2` with `x@y.com` → server returns 400 "Email already in use by another client" pointing at the deleted record.

Same handler also leaves behind every per-client record listed in CLAUDE.md (`client_dailylog:{id}:*`, `client_dailylogs_index:{id}`, `client_545_*`, `client_training_*`, `client_supplement_*`, `client_nutrition_*`, `client_activity_*`, `client_mindset:{id}`, `client_resources:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_nutrition_plan:{id}`, `client_training_program:{id}`, `client_545_goals:{id}`, `client_545_routine:{id}`). That is a separate orphan-data issue with lower urgency (storage waste, no functional blocker).

### Suggested fix

In the DELETE handler, before removing the record:

1. Read the existing client record (`GET client:{id}`) to recover `client.email` and `client.portalEnabled`.
2. If `portalEnabled` was true and `email` is set, `DEL client_email:{normalizeEmail(email)}` — but only if its current value still matches this client's ID (defensive: avoid clobbering a lookup that's been re-bound to another client during an email-swap edge case).
3. Optionally fan-out to remove the per-client sub-keys above (or schedule a janitor). At minimum, fix the email lookup — that's the part that breaks user flow.

### Confidence

high — repro traces three independent files (`clients.js` DELETE, `client-portal.js` enable, `clients.js` POST check) and lines up with the `thomas.html` admin button at line 1413-1424.

## BUG-20260612-02 — Admin session token verification uses non-constant-time string comparison

- **Severity:** P2
- **Area:** api/lib
- **File(s):** api/lib/auth.js:18-31

### What's wrong

`verifyToken` compares the HMAC signature on the admin session cookie with a plain `!==`, which short-circuits on the first differing byte. The companion `client-auth.js` does this correctly with `crypto.timingSafeEqual` on equal-length buffers (lines 46-49). The inconsistency means the admin cookie path is theoretically vulnerable to a remote timing side-channel against the session HMAC, even though `verifyPassword` in the same file (line 52-59) goes to the trouble of using `timingSafeEqual`. CLAUDE.md advertises the admin auth as "timing-safe comparison" — that promise currently only covers the password check, not session verification.

### Repro / evidence

```js
// api/lib/auth.js
function verifyToken(token) {
  if (!token) return false;
  const parts = token.split('.');
  if (parts.length !== 2) return false;
  const [payload, signature] = parts;
  const expected = crypto
    .createHmac('sha256', SESSION_SECRET)
    .update(payload)
    .digest('hex');
  if (signature !== expected) return false;   // <-- not constant-time
  const expires = parseInt(payload, 10);
  if (Date.now() > expires) return false;
  return true;
}
```

Versus `api/lib/client-auth.js:46-49` (correct):

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

### Suggested fix

Mirror the client-auth pattern in `verifyToken`: convert both `signature` and `expected` to `Buffer.from(..., 'hex')`, check `a.length === b.length`, then use `crypto.timingSafeEqual(a, b)`. Same module, same crypto import — one-line behavioral change.

### Confidence

medium — the inconsistency is real and exploitable in theory, but a successful remote timing attack against Vercel's serverless infra is impractical in practice. Flagging as a precision fix that also closes a docs/behavior gap CLAUDE.md already claims is met.

## BUG-20260612-03 — Two clients can silently share an email until portal is enabled, then "last-write-wins" the login

- **Severity:** P2
- **Area:** api/dashboard
- **File(s):** api/dashboard/clients.js:60-73, api/dashboard/client-portal.js:114-118

### What's wrong

Email uniqueness for clients is enforced only via the `client_email:{email}` lookup, and that lookup is created lazily when the portal is enabled (`client-portal.js:115-118`). A new client whose portal isn't enabled yet won't appear in the lookup, so creating a second client with the same email succeeds without warning. Worse, when each of those clients later has their portal enabled, `client_email:{email}` is overwritten unconditionally via `SET` — whichever client most recently had their portal enabled becomes the login owner of that email, silently displacing the other. The coach gets no UI signal.

### Repro / evidence

`api/dashboard/clients.js:68-73`:

```js
var { normalizeEmail } = require('../lib/client-auth');
var normalized = normalizeEmail(body.email);
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

This check is the only uniqueness gate, and it can only fire when a previously-created client has the lookup populated.

`api/dashboard/client-portal.js:114-118`:

```js
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));   // <-- unconditional overwrite
}
```

Reproduction:
1. Create client A with email `x@y.com`, do not enable portal.
2. Create client B with the same email `x@y.com` — succeeds.
3. Enable portal on A → `client_email:x@y.com` = A.id; A can log in.
4. Enable portal on B → same key is overwritten to B.id. A can no longer log in; B silently inherits the address.

### Suggested fix

Two options, either acceptable on its own:
1. At create time (`clients.js` POST), scan the existing clients list for an active client whose `email` matches `normalizeEmail(body.email)`, regardless of portal state, and reject on collision. (Linear scan, but client count is small.)
2. In `client-portal.js` POST, before the unconditional `SET`, do a `GET` on the lookup; if it exists and points at a different ID, return 400 with "Email already bound to another client — disable that client's portal first."

Option 2 is the smaller diff and prevents the silent-displacement case even if option 1 is skipped.

### Confidence

high — the gap is a direct read of the two code paths and matches the documented intent ("duplicate email check" per CLAUDE.md "Client tiers" line) which the current implementation only partially enforces.
