## P1 — Deleting a client leaves an orphan `client_email:` lookup, blocking re-use of the same email

- **ID:** 2026-10-06-01
- **Severity:** P1
- **Area:** `api/dashboard/clients.js` (DELETE handler)
- **Lines:** `api/dashboard/clients.js:143-154` (DELETE) and
  `api/dashboard/clients.js:68-73` (POST duplicate-email guard);
  the lookup is created by `api/dashboard/client-portal.js:114-118`.

### What's wrong

When the admin deletes a client, the DELETE handler removes only
`client:{id}` and the `clients_index` ZSET entry. The email → ID lookup key
`client_email:{normalizedEmail}`, which is created in `client-portal.js` the
first time the portal is enabled for that client, is **not** removed. The
POST handler for creating a new client treats the existence of that key as
"email already in use" and rejects the request with HTTP 400.

Relevant code:

```js
// api/dashboard/clients.js:143-154 (DELETE)
if (req.method === 'DELETE') {
  try {
    var id = req.query.id || (req.body && req.body.id);
    if (!id) return res.status(400).json({ error: 'ID required' });
    await redis('DEL', 'client:' + id);
    await redis('ZREM', 'clients_index', String(id));   // <-- no client_email cleanup
    return res.status(200).json({ ok: true });
  } ...
}

// api/dashboard/clients.js:68-73 (POST duplicate guard)
var normalized = normalizeEmail(body.email);
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}

// api/dashboard/client-portal.js:114-118 (where the orphan is created)
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));
}
```

### Reproduce

1. In `/thomas` → Clients, add a client with email `test@example.com`.
2. Switch to the Client Portal tab, enable the portal for that client and
   set a password. This writes `client_email:test@example.com → <id>`.
3. Delete the client from the Clients tab (confirm the modal).
4. Try to re-add any client with email `test@example.com`.
   → The POST request to `/api/dashboard/clients` returns 400 with
   `{"error":"Email already in use by another client"}`.

### Impact

Admin workflow break. The common real-world case is a client who finishes
or pauses a program, is removed, and later returns; Thomas cannot recreate
their record under the same email. There is no admin UI for inspecting or
deleting Redis keys, so the only recovery is manual Redis surgery
(`DEL client_email:<normalized-email>`). The orphan also leaves per-client
data keys behind — `client_dailylog:*`, `client_training_log:*`,
`client_nutrition_log:*`, `client_545_*`, `client_sidemenu`, `client_push_sub`,
`client_supplement_*`, `client_activity_log:*`, plus the ZSET indexes — but
these are only data bloat; the email lookup is the one that blocks a flow.

Also note: `chs-applications.js` DELETE has no analogous issue because that
record has no secondary lookup key.

### Suggested fix

Before deleting the primary record, fetch it, normalize the email, and
clean up both the lookup and the per-client content keys. Minimal patch:

```js
// api/dashboard/clients.js (DELETE)
if (req.method === 'DELETE') {
  try {
    var id = req.query.id || (req.body && req.body.id);
    if (!id) return res.status(400).json({ error: 'ID required' });

    var existing = await redis('GET', 'client:' + id);
    if (existing) {
      try {
        var client = JSON.parse(existing);
        var { normalizeEmail } = require('../lib/client-auth');
        if (client.email) {
          var email = normalizeEmail(client.email);
          // Only remove if this lookup still points at THIS client
          var owner = await redis('GET', 'client_email:' + email);
          if (String(owner) === String(id)) {
            await redis('DEL', 'client_email:' + email);
          }
        }
      } catch (e) { /* bad JSON — fall through to primary delete */ }
    }

    await redis('DEL', 'client:' + id);
    await redis('ZREM', 'clients_index', String(id));
    return res.status(200).json({ ok: true });
  } catch (err) {
    console.error('clients DELETE error:', err);
    return res.status(500).json({ error: 'Internal error' });
  }
}
```

Optional follow-up (separate change, not required to unblock the admin flow):
cascade-delete the per-client content keys and index ZSETs listed in
`CLAUDE.md` under "Client Dashboard - Redis Keys" so that re-adding a client
with the same email starts from a clean slate.
