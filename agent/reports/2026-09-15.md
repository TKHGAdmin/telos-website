# Telos Bug Hunter - 2026-09-15

## Summary

First run. Bootstrapped agent infrastructure (`agent/memory/`, `agent/reports/`, `docs/BUG_REPORT_SCHEMA.md`) which did not exist. Ran a functional-focus hunt against the recently-added Shopify shop pages (`shop.html`, `product.html`, `js/shop.js`) and the auth/API layer. Found 2 real defects on the product detail page introduced by commit `f5cb8c4` (the image gallery / thumbnails feature). Both are user-visible; neither blocks purchase, but the layout one will be immediately obvious on any product with more than one image.

## Bugs

### BUG-2026-09-15-01: Product detail thumbnails placed in wrong grid cell on desktop

- **Severity**: P2
- **Area**: `product.html` - product detail page layout
- **File**: `product.html:100-108, 765-767`
- **Introduced**: `f5cb8c4` (feat: add image gallery with thumbnails on product page)

**What's wrong**

`.product-detail.loaded` is a 2-column CSS grid (`grid-template-columns: 1fr 1fr`) with three direct children in the DOM in this order: `#productImage`, `#productThumbs`, `.product-detail-info`. Grid auto-placement fills row 1 with image (col 1) + thumbs (col 2), then wraps `.product-detail-info` onto row 2 col 1. That means on desktop the thumbnail strip appears to the RIGHT of the main image (in the column reserved for the product info) and the title/price/add-to-cart drops to a second row. On mobile the grid collapses to one column, so `image -> thumbs -> info` stacks correctly and the bug is desktop-only.

**Reproduction / evidence**

1. Load `product.html?p=<any-shopify-handle-with-2-or-more-images>` on a desktop viewport (>768px).
2. Observed: thumbnails render in the top-right cell where product title/price should live; product info gets pushed to a full second grid row below.
3. Expected: thumbnails render directly below the main image, product info stays to the right.

The DOM (product.html:765-779):

```html
<div class="product-detail" id="productDetail">
  <div class="product-detail-image" id="productImage"></div>
  <div class="product-detail-thumbs" id="productThumbs"></div>
  <div class="product-detail-info"> ... </div>
</div>
```

The CSS (product.html:100-108):

```css
.product-detail { display: none; gap: var(--spacing-3xl); }
.product-detail.loaded { display: grid; grid-template-columns: 1fr 1fr; }
```

Three grid items in a 2-column grid = the third one wraps.

**Impact**

Any product with more than one Shopify image (the whole point of the just-shipped gallery feature) renders with a broken layout on desktop. First-time shoppers hit this on the exact page that closes the sale.

**Suggested fix**

Wrap `#productImage` and `#productThumbs` in a single container div so the grid sees only two children (image-column, info-column), e.g. `<div class="product-detail-media"><div id="productImage">...</div><div id="productThumbs">...</div></div>`. Alternatively, place `#productThumbs` inside `#productImage` and adjust its position, or explicitly grid-place the info column to span two rows on the right. The wrapper is the smallest change and preserves the existing CSS.

### BUG-2026-09-15-02: Product detail page shows infinite spinner when Shopify SDK fails to load

- **Severity**: P3
- **Area**: `product.html` / `js/shop.js` - init error paths
- **File**: `js/shop.js:22-72, 502-507`
- **Introduced**: `8512e4e` (feat: add product detail page with description and image)

**What's wrong**

`shop.js` uses one shared `showEmpty()` fallback across `shop.html` and `product.html`:

```js
function showEmpty() {
  var loading = document.getElementById('shopLoading');
  var empty = document.getElementById('shopEmpty');
  if (loading) loading.style.display = 'none';
  if (empty) empty.style.display = 'block';
}
```

Those two IDs (`shopLoading`, `shopEmpty`) only exist on `shop.html`. On `product.html` the corresponding elements are `productLoading` and `productNotFound`. When `showEmpty()` runs on `product.html` (SDK 404, ad-blocker, `ShopifyBuy` undefined, or the top-level try/catch on init failure), both `getElementById` calls return null and the function silently no-ops. The product page then stays on the "Loading product" spinner forever with no error surfaced to the user.

**Reproduction / evidence**

1. Load `product.html?p=<any-handle>` with `https://sdks.shopifycdn.com` blocked (uBlock Origin's cosmetic + network lists, corporate proxy, or offline).
2. `js/shop.js:24-28` fires: `typeof ShopifyBuy === 'undefined'` -> `showEmpty()`.
3. `showEmpty()` runs against the wrong IDs -> nothing changes -> spinner spins indefinitely.

Contrast the working `product.html`-native error paths at `js/shop.js:134-138` (missing handle) and `js/shop.js:143-146` (product not found), which correctly hide `productLoading` and show `productNotFound`.

**Impact**

Small user segment (aggressive blockers, flaky networks, Shopify CDN outages). But when it hits, the failure mode is silent - the user has no signal to retry, refresh, or leave. No console message is user-visible.

**Suggested fix**

Give `showEmpty()` a page-aware branch, or add a sibling `showProductEmpty()` used from the init paths (`shop.js:24-28`, `31-35`, `69-72`) whenever the current page is the product page (detect via `document.getElementById('productDetail')`). Have it hide `productLoading` and show `productNotFound`. A minimal patch is to check both id pairs inside `showEmpty()` itself.

## Notes

- `sw.js:4` still uses `CACHE_NAME = 'telos-v1'`. `CLAUDE.md` calls out "SW cache version bump needed" in the P1-P3 backlog, so this is deliberately not reported here.
- `.html` extensions in internal links on `product.html`, `shop.html`, etc. are also in the documented backlog. Not re-reported.
- The Shopify Storefront token at `js/shop.js:15` is publishable by design (Storefront API tokens are intended for client-side use). Not a leaked secret.
- Rate limiting in `api/submit-quiz.js:23` uses `x-forwarded-for` verbatim; on Vercel this is the client IP, so no practical bypass, but worth revisiting if the site is ever fronted by a different proxy chain.

## Skipped

- **`switchProductImage` inlines `img.src` inside an `onclick` string** (`js/shop.js:170`): theoretical XSS if a Shopify CDN URL ever contained a single quote or backslash. Shopify's own CDN never produces such URLs, so risk is essentially zero. Left as a note for a future security-focus run.
- **`SESSION_SECRET` missing at runtime would throw in `crypto.createHmac`** (`api/lib/client-auth.js:28`): fail-closed behavior is acceptable; no user-visible bug unless the env var is unset in production, in which case login is already broken and obvious.
