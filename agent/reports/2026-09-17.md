## P2-1 - Deleting a client leaks their email lookup and all portal data in Redis

**File**: `api/dashboard/clients.js:143-149`
**Severity**: P2 (data leak + blocks re-use of an email address for future clients)

### What's wrong

The DELETE branch removes exactly two keys:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

Everything else associated with that client is left in Redis indefinitely. The two most consequential leaks:

1. **`client_email:{normalizedEmail}` is not deleted.** This lookup is set in `api/dashboard/client-portal.js:117` whenever a coach enables portal access for a client. After the client is deleted, the mapping still points at the now-vanished client id. The next time the coach tries to create a new client with the same email, `api/dashboard/clients.js:70-73` sees the stale mapping and rejects the request with `"Email already in use by another client"` - a false collision that can only be resolved by touching Redis directly.
2. **All per-client portal data survives.** Every key documented under "Client Dashboard - Redis Keys" in `CLAUDE.md` is orphaned: `client_dailylog:{id}:*`, `client_dailylogs_index:{id}`, `client_nutrition_plan:{id}`, `client_nutrition_log:{id}:*`, `client_nutrition_logs_index:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_545_goals/routine/daily:{id}:*`, `client_545_index:{id}`, `client_training_program:{id}`, `client_training_log:{id}:*`, `client_training_logs_index:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_supplement_log:{id}:*`, `client_supplement_logs_index:{id}`, `client_activity_log:{id}:*`, `client_activity_logs_index:{id}`.

Because client ids come from `INCR id:clients`, ids never repeat, so a *new* client will not accidentally inherit a deleted client's logs. But the data continues to live in Upstash - a privacy concern for a former client who assumes "delete" means "gone" and a storage-cost concern for a plan billed on key count.

### Reproduction

1. In `/thomas`, create a client via **Clients** tab. Give them email `test-recycle@example.com` and any tier.
2. Open **Client Portal** tab, select that client, enable portal access, and set a password. This calls `api/dashboard/client-portal.js` which writes `client_email:test-recycle@example.com` → the client's numeric id.
3. Have that client log in once at `/client-dashboard` and complete a daily check-in. This creates `client_dailylog:{id}:{date}` and a matching index entry.
4. Delete the client from the Clients tab. Only `client:{id}` and the index entry disappear.
5. In the Clients tab, try to create a new client with `test-recycle@example.com`. The POST returns `400 "Email already in use by another client"` even though no visible client owns that address.
6. Inspect Redis: `client_email:test-recycle@example.com` still resolves to the old numeric id, and every log key from step 3 is still present.

### Suggested fix (not applied; agent is read-only)

In the DELETE branch, before removing `client:{id}`, load the client record, normalize its email, and clean up:

```js
var existing = await redis('GET', 'client:' + id);
if (existing) {
  try {
    var client = JSON.parse(existing);
    if (client.email) {
      var normalized = (client.email || '').toLowerCase().trim();
      if (normalized) await redis('DEL', 'client_email:' + normalized);
    }
  } catch (e) {}
}
```

Cleaning up the per-client log keys is a larger job because Upstash REST has no `SCAN` and there's no set-of-dates index for every key family. The pragmatic move is to `DEL` the known singleton keys (`client_nutrition_plan`, `client_mindset`, `client_resources`, `client_sidemenu`, `client_supplement_plan`, `client_training_program`, `client_545_goals`, `client_545_routine`, `client_email`) and for each date-scoped family, read the ZSET index once (`ZRANGE ... 0 -1`), pipeline `DEL` for each date-suffixed key, then `DEL` the index itself.

### Why this is worth Thomas's attention

The stale email lookup is the blocking one: it silently prevents the coach from re-onboarding a lapsed lead who wants to come back, and the failure mode ("email already in use" by a client that isn't in the list) has no in-app recovery path.
