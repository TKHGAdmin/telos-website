## Bug 1 — Quiz "See Your Score" button skips required-field validation, leaking gated pricing to anonymous users

- **ID:** 2026-07-22-01
- **Severity:** P1
- **Area:** Functional / Lead capture
- **Files:**
  - `index.html:580` — `<button type="button" class="btn btn-primary quiz-see-score-btn">See Your Score</button>`
  - `pricing.html:594` — same button, same problem
  - `js/quiz.js:225-275` — click handler that sets `telosQuizCompleted` unconditionally

### What's wrong
The lead-capture form inputs have HTML5 `required` on `name` and `email`, but the "See Your Score" button is `type="button"`, not `type="submit"`. Because the browser only runs constraint validation on form submission, clicking that button never triggers the required check. The JS click handler then reads the (potentially empty) values, writes `localStorage.telosQuizCompleted = 'true'`, POSTs to `/api/submit-quiz` (which 400s silently — the `.catch` swallows it), and reveals the results.

Downstream effect on `pricing.html`: line 971 checks `localStorage.getItem('telosQuizCompleted') === 'true'` to decide whether to show the pricing overlay, so any user who clicks through the quiz once with blank fields can then view actual prices without ever leaving contact info.

### Repro
1. Open the homepage in incognito.
2. Answer the quiz questions (any answers).
3. On the "Your Score Is Ready" step, leave all fields blank.
4. Click "See Your Score" — results render.
5. Navigate to `/pricing` — the paywall overlay is bypassed, prices are visible.

### Suggested fix
Either change the button to `type="submit"` and attach the handler to the form's `submit` event, or explicitly validate in JS before setting `telosQuizCompleted` (`if (!nameInput.value.trim() || !emailInput.value.trim()) { nameInput.reportValidity(); return; }`). Apply to both `index.html` and `pricing.html`.

## Bug 2 — Deleting a client leaves behind email index and all client data, blocking re-creation with the same email

- **ID:** 2026-07-22-02
- **Severity:** P2
- **Area:** Functional / Admin dashboard
- **File:** `api/dashboard/clients.js:143-154`

### What's wrong
`DELETE /api/dashboard/clients` only issues `DEL client:{id}` and `ZREM clients_index {id}`. It never touches:
- `client_email:{normalizedEmail}` — the email→id lookup
- `client_dailylog:{id}:*`, `client_dailylogs_index:{id}`
- `client_nutrition_log:{id}:*`, `client_nutrition_logs_index:{id}`
- `client_training_log:{id}:*`, `client_training_logs_index:{id}`
- `client_supplement_log:{id}:*`, `client_supplement_logs_index:{id}`
- `client_activity_log:{id}:*`, `client_activity_logs_index:{id}`
- `client_545_goals:{id}`, `client_545_routine:{id}`, `client_545_daily:{id}:*`, `client_545_index:{id}`
- `client_nutrition_plan:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_training_program:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`
- `client_push_sub:{id}`
- `password_reset:*` tokens pointing to the deleted id

The user-visible symptom is straightforward: `clients.js:70-73` blocks creation if `client_email:{normalized}` is set, so if a portal-enabled client is deleted and Thomas tries to re-add the same person, the POST returns `"Email already in use by another client"` and the orphaned lookup still points at a now-missing client record. Everything else is silent leakage that grows over time.

### Repro
1. In `/thomas` → Clients, create a client, enable portal (this writes `client_email:{email}`).
2. Delete that client from the table.
3. Try to add a new client with the same email — the POST fails 400.

### Suggested fix
Before `DEL client:{id}`, load the client, normalize the email, and delete `client_email:{email}`. Ideally also sweep the client's data keys (SCAN with `client_*:{id}*` patterns, or delete each known key explicitly using the list in the schema). At minimum, delete the email lookup so re-creation works.

## Bug 3 — Password-reset endpoint has no rate limit; any known client email can be spammed

- **ID:** 2026-07-22-03
- **Severity:** P2
- **Area:** Functional (abuse) / Email deliverability
- **File:** `api/client/reset-password.js:20-68`

### What's wrong
Every other public POST (`submit-quiz`, `submit-email`, `submit-chs-application`) rate-limits by IP via `ratelimit:*` Redis keys. `reset-password.js` does not. An attacker who knows a client's email can hit `POST /api/client/reset-password { email }` in a loop, and each call will trigger a Resend send to that client (as long as the account exists and the portal is enabled). This burns Resend quota, floods the client's inbox, and — because the endpoint always returns 200 — the response timing/side-effects still leak whether the email is a real portal user (defeating the "return success to prevent enumeration" comment on line 24).

### Repro
1. Get any active client's email.
2. `for i in $(seq 1 50); do curl -sX POST https://www.telosathleticclub.com/api/client/reset-password -H 'Content-Type: application/json' -d '{"email":"victim@example.com"}'; done`
3. Client receives 50 reset emails.

### Suggested fix
Add the same rate-limit pattern used by the other submit endpoints, keyed by both IP and normalized email — e.g. `ratelimit:pwreset:ip:{ip}` (max 5/hr) and `ratelimit:pwreset:email:{normalizedEmail}` (max 3/hr). Perform the check before Redis lookups so the failure mode is symmetric for real and fake emails.

## Bug 4 — Rate-limit keys use the raw `X-Forwarded-For` header, so it can be bypassed by rotating the header

- **ID:** 2026-07-22-04
- **Severity:** P3
- **Area:** Functional (abuse) — weakens existing controls
- **Files:**
  - `api/submit-quiz.js:23-29`
  - `api/submit-email.js:28-34`
  - `api/submit-chs-application.js:40-46`

### What's wrong
All three endpoints do:
```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:*:${ip}`;
```
Vercel prepends the real client IP to `X-Forwarded-For` but appends any client-supplied values, so the header looks like `real-ip, attacker-supplied`. Because the key uses the whole string verbatim, an attacker can rotate `X-Forwarded-For: junk-N` on each request and land in a fresh rate-limit bucket every time. Same for `X-Real-IP` (also client-attacker-controllable) as a fallback.

Effect: the "10 quiz submissions per IP per hour" and "5 CHS applications per IP per hour" caps become "unlimited" for any attacker who knows the pattern.

### Repro
```bash
for i in $(seq 1 200); do
  curl -sX POST https://www.telosathleticclub.com/api/submit-quiz \
    -H 'Content-Type: application/json' \
    -H "X-Forwarded-For: 1.2.3.$i" \
    -d '{"name":"x","email":"x@y.z","scores":[1,1,1,1]}'
done
```
All 200 requests should succeed. With the fix, only ~10 should.

### Suggested fix
Extract only the first token before any comma, and only use `x-forwarded-for` (drop the client-controllable `x-real-ip` fallback):
```js
const xff = req.headers['x-forwarded-for'] || '';
const ip = xff.split(',')[0].trim() || 'unknown';
```
Apply the same helper in all three submit endpoints and any future public POSTs.
