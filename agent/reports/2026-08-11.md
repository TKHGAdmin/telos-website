# Telos Bug Hunter Report — 2026-08-11

**Focus:** Functional (with adjacent Security spot-check — first run, no prior coverage)
**Findings:** 8
**Approval-eligible:** 8

## Summary

First-ever Bug Hunter run against the Telos Fitness web platform. Traced
the public quiz, email-capture, Charleston application, product-detail,
client-portal, and admin-dashboard flows end to end; audited the last ~20
commits with emphasis on the just-landed product-page image gallery and
the Nutrition/FAB client-dashboard rebuild; and swept the serverless
surface for auth gaps, IDOR, SSRF, rate-limit gaps, and constant-time bugs.
Auth wiring is broadly correct (every `/api/dashboard/*` calls
`verifySession`, every `/api/client/*` derives `clientId` from the signed
cookie, both crons check `CRON_SECRET`, `food-search.js` is not SSRF-able)
but rate-limiting is inconsistently applied — three public POST endpoints
that mutate state or spend money have no throttle. One P1 visual regression
appears to have shipped with the latest commit.

## Findings

### BUG-20260811-01 — Product detail page desktop layout broken by thumbnail gallery

- **Severity:** P1
- **Area:** visual
- **Location:** `product.html:105-108` + `product.html:765-780` + `js/shop.js:161-177`
- **Status:** new
- **Confidence:** high

**What's wrong**

`.product-detail.loaded` is a two-column CSS grid
(`grid-template-columns: 1fr 1fr`) but the DOM inside `#productDetail` now
has three direct children: `#productImage`, `#productThumbs`, and
`.product-detail-info`. The grid places children in row-major order, so on
desktop the thumbs div occupies row-1 col-2 (where title/price/Add-to-Cart
used to sit) and `.product-detail-info` drops to row 2 col 1 under the
image. The thumbs div is always in the DOM even when the product has ≤1
image (`shop.js:168` only populates it when `allImages.length > 1`, but the
empty flex container still claims the grid cell).

**How a user hits it**

Visit `/product?p=<any-handle>` at a viewport wider than 768px. The title,
price, and "Add to Cart" button no longer sit next to the image — the
right column is either empty (single-image products) or shows a row of
thumbnails, and the purchase panel is pushed below the image.

**Suggested fix**

Wrap `#productImage` and `#productThumbs` in a single `.product-detail-media`
div so the grid sees exactly two children (media column, info column). The
existing thumb margin/flex styling still works inside the wrapper.

### BUG-20260811-02 — Admin dashboard login has no rate limiting

- **Severity:** P1
- **Area:** security
- **Location:** `api/dashboard/login.js:1-17`
- **Status:** new
- **Confidence:** high

**What's wrong**

`POST /api/dashboard/login` accepts unlimited attempts with no IP throttle,
no lockout, no CAPTCHA, and no MFA — the entire `/thomas` admin surface
sits behind a single shared `DASHBOARD_PASSWORD`. Other public POSTs in
this codebase (`submit-quiz.js`, `submit-email.js`,
`submit-chs-application.js`) already use a Redis `INCR` limiter, so the
pattern is available and just wasn't applied here.

**How a user hits it**

Attacker scripts a wordlist POST against `/api/dashboard/login`. Success
grants full read/write to every client record, revenue figures, ad spend,
quiz submissions and email captures (PII), Charleston applications, blob
uploads, and the admin-only email/push endpoints. Constant-time compare on
the password itself (see BUG-20260811-08) does not stop guessing at
Vercel-serverless throughput.

**Suggested fix**

Add `INCR ratelimit:dashlogin:<ip>` with `EXPIRE 900`; return 429 above a
low threshold (e.g. 5 failures / 15 min) before the `verifyPassword` call.

### BUG-20260811-03 — Client portal login has no rate limiting

- **Severity:** P1
- **Area:** security
- **Location:** `api/client/login.js:1-60`
- **Status:** new
- **Confidence:** high

**What's wrong**

`POST /api/client/login` has zero throttling. PBKDF2 at 100k iterations
slows single attempts but does not stop a parallelized dictionary attack
against a known client email; Vercel serverless invocations run
concurrently. On top of that, the failure branches at lines 36/39/42/47
return four distinct error strings, so an attacker can enumerate portal
state (enabled vs. not enabled vs. inactive vs. no-password-set vs.
wrong-password) without ever guessing correctly.

**How a user hits it**

Attacker with a list of coaching-client emails (harvestable from the
public Instagram/testimonials) runs an unthrottled credential-stuffing
attack. On success they can read the client's nutrition plan, training
program, daily logs and metrics, and overwrite their meal/training entries.

**Suggested fix**

Wrap `verifyPassword` with a Redis-backed per-IP counter (e.g. 10
attempts / 15 min) and collapse all failure branches to the same generic
`Invalid email or password` message.

### BUG-20260811-04 — Password-reset endpoint has no rate limit, enables email-bomb and Resend cost inflation

- **Severity:** P2
- **Area:** security
- **Location:** `api/client/reset-password.js:20-68`
- **Status:** new
- **Confidence:** high

**What's wrong**

`POST /api/client/reset-password` with `{email}` sends a real Resend email
every time a known email is submitted, with no per-IP or per-email cap.
The header comment ("Always return success to prevent email enumeration")
is also undermined by measurable timing differences — the found-email path
runs two extra Redis calls (`SETEX` on the token) plus a Resend `fetch`
before responding, while the unknown-email path returns immediately.

**How a user hits it**

Attacker loops `curl -X POST /api/client/reset-password
-d '{"email":"victim@x.com"}'` — victim's inbox floods with reset emails,
Resend quota burns, and the timing gap lets the attacker enumerate which
addresses are enrolled clients.

**Suggested fix**

Add `INCR ratelimit:reset:<ip>` (cap ~5/hr) and
`ratelimit:reset:email:<hash>` (cap ~3/day) before the token generation.
Optionally, on the unknown-email path, `await` a short randomized sleep to
mask the timing gap.

### BUG-20260811-05 — Client-controllable SSRF via push subscription endpoint

- **Severity:** P2
- **Area:** security
- **Location:** `api/client/push-subscribe.js:14-25` (sink) + `api/client/notify.js:62-69` (fetch)
- **Status:** new
- **Confidence:** high

**What's wrong**

`push-subscribe` stores `body.subscription` verbatim after only checking
that it exists — no validation that `.endpoint` is HTTPS or that its host
belongs to a real push provider. Later, `notify.js` executes
`fetch(subscription.endpoint, { method: 'POST', body: payload })` with no
allowlist.

**How a user hits it**

An authenticated coaching client POSTs
`{"subscription":{"endpoint":"http://169.254.169.254/latest/meta-data/"}}`
(or any internal URL, attacker webhook, or SMTP-over-HTTP target). Next
time the admin triggers a push from the dashboard, the Vercel function
issues an outbound POST from an authenticated egress path to whatever the
client picked. Response text is written to Vercel logs (`notify.js:74`),
not returned, so the disclosure is blind — but the primitive still lets
the client turn the serverless function into a POST reflector.

**Suggested fix**

In `push-subscribe.js`, require `subscription.endpoint` to be an HTTPS URL
whose host matches an allowlist (`*.googleapis.com`,
`*.push.services.mozilla.com`, `*.notify.windows.com`, `web.push.apple.com`).
Reject anything else with 400.

### BUG-20260811-06 — Quiz retake attaches duplicate submit handler, double-posts to /api/submit-quiz

- **Severity:** P2
- **Area:** functional
- **Location:** `js/quiz.js:215` + `js/quiz.js:221-276` + `js/quiz.js:415-442`
- **Status:** new
- **Confidence:** high

**What's wrong**

`setupLeadCapture()` calls `submitBtn.addEventListener('click', …)` and is
invoked every time the last question is answered (line 215). `resetQuiz()`
does not clear or replace the button, so a user who completes → clicks
Retake → completes again ends up with N stacked click handlers. Each
completion after the first posts N times to `/api/submit-quiz` and calls
`renderResults()` N times.

**How a user hits it**

Take quiz → submit → click Retake → complete again → observe two POSTs in
the Network tab, two `quiz_submissions` ZADD entries in Redis, and a
visible double-run of the ring/counter animations on the results screen.
Repeat for cumulative multiplication.

**Suggested fix**

Either attach the submit listener once during `DOMContentLoaded` and read
current form values inside the handler, or in `setupLeadCapture` do
`submitBtn.replaceWith(submitBtn.cloneNode(true))` before re-binding to
guarantee a fresh, single-listener node.

### BUG-20260811-07 — Admin session HMAC signature compared with `!==` (non-constant-time)

- **Severity:** P3
- **Area:** security
- **Location:** `api/lib/auth.js:27`
- **Status:** new
- **Confidence:** high

**What's wrong**

`verifyToken` compares the HMAC signature with a plain string `!==`:
`if (signature !== expected) return false;`. `client-auth.js:44-46`
already does the correct thing with `crypto.timingSafeEqual` — this file
just wasn't updated to match.

**How a user hits it**

Remote timing attack against `verifySession`: attacker submits crafted
`{expires}.{guess}` cookies and measures response-time gaps to walk the
HMAC hex digit-by-digit, eventually forging an admin session cookie
without knowing `SESSION_SECRET`. Difficult over WAN but a real
defense-in-depth gap given the exact-same file uses the safe pattern
elsewhere.

**Suggested fix**

Replace lines 26-27 with an equal-length check followed by
`crypto.timingSafeEqual(Buffer.from(signature, 'hex'),
Buffer.from(expected, 'hex'))`, mirroring `api/lib/client-auth.js:44-46`.

### BUG-20260811-08 — Admin password length leaked by early length-mismatch return

- **Severity:** P3
- **Area:** security
- **Location:** `api/lib/auth.js:55`
- **Status:** new
- **Confidence:** high

**What's wrong**

`verifyPassword` returns early when input length differs from expected
length (`if (inputStr.length !== expected.length) return false;`) before
running `timingSafeEqual`. The remote response-time gap between "length
mismatch" and "length match, hash compare ran" leaks the exact byte length
of `DASHBOARD_PASSWORD`.

**How a user hits it**

Combined with the missing admin login rate limit (BUG-20260811-02), an
attacker sweeps input lengths 1–64, learns the exact password length, and
prunes the search space of any subsequent guessing / dictionary attack by
orders of magnitude.

**Suggested fix**

Always hash both inputs to fixed size before comparing (e.g.
`crypto.createHash('sha256').update(x).digest()`) and always call
`timingSafeEqual` on the two 32-byte buffers.
