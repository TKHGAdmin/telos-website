## BUG-2026-08-06-01 — thomas.jpeg served at 6× the pixel size it renders at

**Severity**: P1
**Category**: Performance / bandwidth
**Files**:
- `images/thomas.jpeg` (1.9 MB, 1206 × 2136 px)
- `index.html:252`
- `chs.html:946`
- `css/style.css:2284` (`.about-photo { max-height: 350px }`)

### What's wrong
`images/thomas.jpeg` is a 1.9 MB portrait JPEG at 1206 × 2136 pixels. It is the hero portrait in the About section of both the homepage (`/`) and the Charleston landing page (`/chs`). CSS caps its render height at `max-height: 350px` (`css/style.css:2284`), meaning the browser downloads ~6× more pixel data than it will ever display. At a plausible column width of ~500 px, a 500 × 350 image would be well under 100 KB at high JPEG quality.

There is no `<picture>` element, no `srcset`, and no smaller variant file in `images/` — every visitor to the homepage or Charleston page downloads the full 1.9 MB regardless of device.

### Impact
- Homepage and Charleston page are the two primary marketing landing pages. Both take a bandwidth hit on every cold visit.
- On a 3G mobile connection (~400 KB/s), this single image is a ~4.5 s download that pushes LCP well past Google's "good" threshold.
- The two secondary photos (`thomas-speaking-wide.jpeg` at 248 KB, `thomas-speaking-close.jpeg` at 212 KB) sit in the same section and add to the pain, though they're much less oversized (712 × 1104 and 725 × 1086).

### Reproduce
```bash
$ file images/thomas.jpeg
images/thomas.jpeg: JPEG image data ... 1206x2136, components 3
$ du -h images/thomas.jpeg
1.9M    images/thomas.jpeg
$ grep -n 'max-height' css/style.css | grep about-photo
2284:  max-height: 350px;
```
Open `/` in DevTools → Network. Confirm the 1.9 MB image transfer for the About section.

### Suggested fix
Generate a properly-sized variant (e.g., `thomas@800.jpeg` at 800 × 1418, ~100–150 KB at Q80) and swap the `<img src>` on `index.html:252` and `chs.html:946`. If retina crispness matters, use a `srcset` pair (1× and 2×). No CSS change needed.

## BUG-2026-08-06-02 — Below-fold images on `/` and `/chs` are not lazy-loaded

**Severity**: P2
**Category**: Performance / initial paint
**Files**:
- `index.html:252`, `index.html:258`, `index.html:261`
- `chs.html:922`, `chs.html:925`, `chs.html:928`, `chs.html:946`, `chs.html:950`, `chs.html:953`

### What's wrong
The About section on the homepage and every image on the Charleston page below the hero lacks `loading="lazy"`. The only image with an explicit loading hint anywhere on the site is `chs.html:824` (the hero, which correctly uses `loading="eager" fetchpriority="high"`). Every other `<img>` uses the browser default (`eager`), so they compete with critical resources during initial page load.

### Impact
- Combined with BUG-01, the homepage About section forces the browser to download 1.9 MB + 212 KB + 248 KB (~2.4 MB) of below-fold images during the initial load.
- Removes 9 image requests from the critical path across the two pages once fixed.
- Free perf win — one attribute per image, no CSS or JS changes.

### Reproduce
```bash
$ grep -n 'loading=' index.html chs.html
chs.html:824:      <img src="images/chs-hero.jpg" alt="" loading="eager" fetchpriority="high">
```
Only one image on the whole site sets `loading`. Every other `<img>` inherits `eager`.

### Suggested fix
Add `loading="lazy"` (and, if you want, `decoding="async"`) to the nine below-fold `<img>` tags listed above. Keep the CHS hero on `eager`.
