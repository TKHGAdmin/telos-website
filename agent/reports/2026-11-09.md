## Summary

First run. Focus: functional. I traced the critical client flows (auth, logging, modules, cron) end-to-end from admin UI through serverless API through client UI. One real bug found: a data-shape mismatch in the course-modules feature where the admin UI stores `tierAccess` as an object but the client-facing API reads it as an array, causing the `/api/client/modules` endpoint to throw a `TypeError` and the client dashboard's Learn tab to fail with "Failed to load modules" the first time anyone edits a module in the admin.

## Findings

### [BUG-2026-11-09-01] `tierAccess` shape mismatch breaks the client Learn tab after any admin edit

- **Severity:** P1
- **Area:** `api/client` + `admin/thomas`
- **File(s):** `thomas.html:2365-2370`, `api/dashboard/modules.js:124`, `api/client/modules.js:62-69`, `api/client/module.js:51-61`
- **Status:** new

**What's wrong.** The admin UI and the client API disagree on the shape of `tierAccess`. `thomas.html:2365` builds the save payload as an **object of booleans** (`{ rebuild: true, growth: true, lifestyle: true, lifestyle_plus: true }`). The admin PUT handler at `api/dashboard/modules.js:124` writes that object straight into Redis unchanged. The client-side readers at `api/client/modules.js:62-69` and `api/client/module.js:51-61` assume `tierAccess` is an **array of tier strings** and call `(m.tierAccess || []).forEach(...)` on it, which throws `TypeError: m.tierAccess.forEach is not a function` for objects.

The admin dashboard list filter at `api/dashboard/modules.js:39` has the same assumption — it calls `m.tierAccess.indexOf(tier)`, which also throws on an object.

**How to reproduce.**
1. Create a new module via the admin Courses tab in `/thomas`. On creation the API POST default at `api/dashboard/modules.js:78` writes `tierAccess: TIER_ORDER.slice()` — an array — so the module initially works.
2. Open the module in the admin, change anything, and click Save. The PUT payload sends `tierAccess` as an object (`thomas.html:2365`).
3. From that point on, GET `/api/client/modules` throws and returns 500. The Learn tab in the client dashboard shows "Failed to load modules." GET `/api/client/module?id=...` is similarly broken.
4. Confirmed in Node: `({rebuild:true}).forEach(...) → TypeError: forEach is not a function` and `({rebuild:true}).indexOf('rebuild') → TypeError: indexOf is not a function`.

**Impact.** Any active client whose account has visibility into the Learn tab sees it broken after any admin edit of any module in the catalog. One edited module poisons the whole list for every client (the client endpoint iterates all modules; one bad shape throws out of the outer `forEach`). The admin's own `?tier=` filter is also broken in the same way.

**Suggested fix.** Normalize on one shape. Easiest path with least churn: in `api/dashboard/modules.js`, coerce `body.tierAccess` to an array on write.

```js
function normalizeTierAccess(ta) {
  if (Array.isArray(ta)) return ta;
  if (ta && typeof ta === 'object') {
    return Object.keys(ta).filter(function (k) { return ta[k]; });
  }
  return TIER_ORDER.slice();
}
```

Apply it in both POST (line 78) and PUT (line 124), and backfill existing records on read in `api/client/modules.js` + `api/client/module.js` so already-edited modules recover without a migration script. The admin UI (`thomas.html:2129-2133, 2168`) can keep its object-shaped local state as long as the save step converts.
