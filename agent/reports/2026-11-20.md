## Finding 1 — Pricing gate bypassed by submitting empty quiz lead form

- **Severity:** P2
- **File(s):** `js/quiz.js:220-276`, `index.html:580`, `pricing.html:594`
- **Category:** validation
- **Confidence:** high

### Repro / trace

1. In `index.html:580` and `pricing.html:594`, the quiz lead-capture button is declared `<button type="button" class="... quiz-see-score-btn">See Your Score</button>`. Because the type is `button`, the browser does **not** fire native HTML5 form validation on the `required` inputs inside the surrounding `<form>`.
2. In `js/quiz.js:225`, the handler is bound to `click`, not `submit`, so the form's required-field check never runs.
3. In the handler (`js/quiz.js:233-247`), the code reads `nameInput.value`, `emailInput.value`, `phoneInput.value` and writes them into `quiz.user*` and localStorage **without any validation**:
   ```js
   quiz.userName = nameInput.value;         // may be ""
   quiz.userEmail = emailInput.value;       // may be ""
   ...
   localStorage.setItem('telosQuizCompleted', 'true');
   ```
4. The POST to `/api/submit-quiz` at `js/quiz.js:258-269` is fire-and-forget (`.catch(function() {})`). The server will 400 on empty name/email (`api/submit-quiz.js:18-20`), but `fetch` does not throw on HTTP 4xx, so the client never knows and never reverts localStorage.
5. `pricing.html:971` checks only `localStorage.getItem('telosQuizCompleted') === 'true'` to reveal the price grid.

Net result: on the pricing page, a visitor can answer the 8 quiz questions, press **See Your Score** with all three inputs empty, and immediately see the full pricing. No lead is captured server-side.

### Impact

- Defeats the stated purpose of the pricing gate (lead capture before revealing prices).
- Silent failure: Thomas sees quiz completion rates in the dashboard that look fine while actual lead rows are missing.
- Affects every pricing-page visitor who wants prices without sharing contact info — a motivated subset of total traffic.

### Suggested fix

Option A (minimal): in `js/quiz.js` `setupLeadCapture`, validate `quiz.userName` and `quiz.userEmail` (basic `/@/` check) before writing to localStorage and showing results. Show inline error state on the inputs on failure.

Option B (cleaner): change the button to `type="submit"` and bind the handler to the form's `submit` event; HTML5 `required` + `type="email"` then run before the handler fires. This matches the pattern already used on `protein-calculator.html:799` and `chs.html:1084`.

## Finding 2 — Daily engagement cron re-sends reminder emails every day a client is inactive

- **Severity:** P2
- **File(s):** `api/cron/engagement-check.js:61-94`, `vercel.json:24-26`
- **Category:** data-integrity
- **Confidence:** high

### Repro / trace

1. `vercel.json:24-26` schedules `/api/cron/engagement-check` daily at 15:00 UTC.
2. `engagement-check.js:52-58` finds the most recent daily-log within the last 5 days.
3. `engagement-check.js:61` fires the reminder email if `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`.
4. There is **no state recording "last reminder sent at"** anywhere in the handler or in the client record — grep across `api/cron/`, `api/client/`, and `api/dashboard/` returns zero matches for `lastReminder`, `lastEngagement`, `reminder_sent`, or `engagement_sent`.

So a client who stops logging for ten days receives a reminder email on **each** of days 4, 5, 6, 7, 8, 9, and 10 — seven duplicate "We miss you at Telos" emails before they return.

### Impact

- Clients get spammed. Deliverability risk: repeated similar emails are a textbook spam-filter trigger and risk the `noreply@telosathleticclub.com` sender reputation.
- Direct Resend cost: each duplicate email costs money that produces zero marginal value after the first.
- Weekly-summary cron (`weekly-summary.js:107`) uses the same sender, so trashing the sender's reputation also damages weekly digest delivery to active clients.

### Suggested fix

Record the last reminder timestamp on the client record (e.g., `client.lastEngagementReminderAt`) and skip re-sending if less than 3 days (or 7 days) have elapsed. Alternatively, store a Redis key `engagement_reminder_sent:{clientId}` with a 72h or 7-day TTL and short-circuit when it exists.

## Finding 3 — Two clients can share an email; enabling the portal on the second silently breaks the first's login

- **Severity:** P2
- **File(s):** `api/dashboard/clients.js:59-97`, `api/dashboard/client-portal.js:109-124`
- **Category:** data-integrity
- **Confidence:** high

### Repro / trace

The Redis key `client_email:<normalizedEmail>` is the login lookup used by `api/client/login.js:24` and `api/client/reset-password.js:22`. It is only written in two places:

- `api/dashboard/client-portal.js:115-118` — when enabling the portal for a client.
- `api/dashboard/clients.js:131` — when an email changes AND `client.portalEnabled` is already true.

The duplicate-email guard in `api/dashboard/clients.js:70-73` queries this same lookup:
```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

If both clients were created before either had the portal enabled, the lookup is empty and the guard passes for both. Later, `api/dashboard/client-portal.js:115-118` writes the lookup unconditionally — no check for a pre-existing owner:
```js
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));  // overwrites silently
}
```

Reproduction sequence:
1. Admin creates **Client A** with `email=foo@example.com`, portal disabled → no lookup written.
2. Admin creates **Client B** with `email=foo@example.com`, portal disabled → guard passes (lookup still empty), no lookup written.
3. Admin enables portal for Client A → `client_email:foo@example.com = A.id` written.
4. Admin enables portal for Client B → `client_email:foo@example.com = B.id` **overwrites** A's lookup.
5. From now on, A cannot log in (lookup resolves to B, so A's password hash never gets consulted). A's "Forgot password" email arrives and resets B's password instead.

### Impact

- Admin-only surface, so the attacker model is zero — but this is an easy data-integrity accident during coach workflow (typo during client onboarding, importing from a lead that already exists in another tier, etc.).
- Failure mode is silent: Client A's login just returns `Invalid email or password` with no explanation.
- Password reset mis-routing (step 5) is the worst part — the operator intends to help Client A and instead hands Client B a password-reset link.

### Suggested fix

Two changes:
1. In `api/dashboard/clients.js` POST (around line 70-73), always enforce email uniqueness by also scanning `clients_index` and comparing `client.email` on each record — not just the lookup. Reject creation of a duplicate even when neither client has the portal enabled.
2. In `api/dashboard/client-portal.js` around line 115-118, `GET` the lookup first; if it points at a different `clientId`, refuse to enable the portal and return a clear "Email already assigned to client #X" error.
