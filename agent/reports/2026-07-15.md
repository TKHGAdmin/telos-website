First run of the Bug Hunter. Focus was functional correctness across the serverless API surface (public forms, client portal, admin endpoints, cron jobs). Four findings, all reproducible from the code alone. The strongest is a data-integrity issue in client deletion that can silently lock a returning client out of the portal. Nothing in this batch is P0 — no exposed secrets, no broken auth — but the P1 is worth acting on before Thomas next deletes and re-adds anyone.

## Findings

### [P1] Client deletion leaves orphaned Redis keys and can lock the same email out of the portal

**ID:** `2026-07-15-client-delete-orphans`
**File:** `api/dashboard/clients.js:143-154`
**Category:** data-integrity

**What's wrong**
The DELETE handler for a client removes only `client:{id}` and the `clients_index` entry. The client's `client_email:{normalized}` lookup and every per-client data key (`client_dailylog:*`, `client_nutrition_log:*`, `client_545_*`, `client_training_*`, `client_supplement_*`, `client_activity_*`, and all their indexes — ~15+ keys per client) are left in Redis forever. Beyond storage bloat and lingering PII, the stale `client_email:{email}` lookup causes a concrete functional break on re-add.

**How to reproduce (code trace)**
1. Coach creates client Alice (id=42) with email `alice@x.com`, enables portal. `client_email:alice@x.com → "42"` is set in `api/dashboard/client-portal.js:117`.
2. Coach deletes Alice via `DELETE /api/dashboard/clients?id=42`. Handler at `api/dashboard/clients.js:147-148` deletes only `client:42` and removes `42` from `clients_index`. `client_email:alice@x.com` still returns `"42"`.
3. Coach later re-adds Alice with the same email. `api/dashboard/clients.js:70-73` reads `client_email:alice@x.com`, gets `"42"` back, and rejects the create with "Email already in use by another client" — even though no such client exists.
4. Worse: if the coach re-enables portal on some *other* client whose email got recycled, `login.js:24-27` gets the stale id, then line 29's `GET client:{stale_id}` returns null, so login returns 401 "Invalid email or password" with no explanation.

**Impact**
Every deleted-then-readded client hits this. In a small coaching business this is uncommon but not rare (canceled client returns, email typo requires re-create). When it happens, the failure mode is confusing — the admin UI just says the email is in use, and if they force-enable portal on a fresh record with the same email they get login failures with no obvious cause. Also every deleted client permanently retains all their personal data (weight, sleep, nutrition logs) in Redis, which is a soft privacy issue.

**Suggested fix**
In the DELETE handler, before the two `DEL`s that already exist, load the client, delete the email lookup, then fan out the per-client keys. `ZRANGE` on each `*_index:{id}` gives the exact dated keys to remove. Sketch:

```js
var raw = await redis('GET', 'client:' + id);
if (raw) {
  var c = JSON.parse(raw);
  if (c.email) {
    var email = normalizeEmail(c.email);
    await redis('DEL', 'client_email:' + email);
  }
}
var indexes = [
  'client_dailylogs_index', 'client_nutrition_logs_index',
  'client_545_index', 'client_training_logs_index',
  'client_supplement_logs_index', 'client_activity_logs_index',
];
var perDayPrefixes = [
  'client_dailylog', 'client_nutrition_log',
  'client_545_daily', 'client_training_log',
  'client_supplement_log', 'client_activity_log',
];
for (var i = 0; i < indexes.length; i++) {
  var dates = await redis('ZRANGE', indexes[i] + ':' + id, 0, -1);
  var cmds = (dates || []).map(function(d) {
    return ['DEL', perDayPrefixes[i] + ':' + id + ':' + d];
  });
  if (cmds.length) await redisPipeline(cmds);
  await redis('DEL', indexes[i] + ':' + id);
}
var singletons = [
  'client_nutrition_plan', 'client_mindset', 'client_resources',
  'client_545_goals', 'client_545_routine', 'client_training_program',
  'client_sidemenu', 'client_supplement_plan',
];
await Promise.all(singletons.map(function(k) { return redis('DEL', k + ':' + id); }));
```

### [P2] Weekly-summary email always reports a streak of 0 or 1

**ID:** `2026-07-15-weekly-streak-off-by-one`
**File:** `api/cron/weekly-summary.js:87-90`
**Category:** correctness

**What's wrong**
The streak counter loops from `d=0` (today) to `d=6` and breaks on the first missing daily log. The cron runs Monday 2pm UTC (9am ET). At that hour almost no client has done Monday's check-in yet, so the loop breaks at `d=0` and reports `streak: 0` even for a client who logged all seven prior days.

**How to reproduce (code trace)**
Cron entry in `vercel.json` fires `api/cron/weekly-summary.js` on `0 14 * * 1`. In the handler, `d=0` maps to `new Date(now - 0*86400000).toISOString().split('T')[0]` — today's UTC date. The check on line 88 is `if (weekData[0][d] && weekData[0][d].result) streak++; else break;`. Since Monday morning ET is still Monday UTC, and no Monday log exists yet, the else branch runs at `d=0` and returns `streak = 0`. The `buildWeeklySummary()` output on line 131 then hardcodes "Current Streak: 0 days" into the email.

**Impact**
Every active client with `emailEnabled !== false` receives a weekly recap that always says 0 (or 1 if they happened to log on the current Monday before 9am ET). Undermines the whole point of the weekly nudge and looks broken to the client.

**Suggested fix**
Start the streak count at `d=1` (yesterday):

```js
for (var d = 1; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

If Thomas wants to give credit for a same-day log when it does exist, keep the `d=0` check but don't `break` on absence — only bump `streak` when present, then start the actual break-on-miss loop at `d=1`.

**Confidence:** high

### [P2] Engagement-check cron sends a "we miss you" email every day forever to inactive clients

**ID:** `2026-07-15-engagement-check-daily-spam`
**File:** `api/cron/engagement-check.js:61-94`
**Category:** email-hygiene

**What's wrong**
The daily cron sends a reminder email any day a client's last log is 3+ days ago. There is no cooldown, no `lastEngagementEmailSent` timestamp, no unsubscribe check beyond the account-wide `client.emailEnabled`. A client who stops logging for a week gets seven identical emails. If they never come back, they get one every single day, indefinitely.

**How to reproduce (code trace)**
`api/cron/engagement-check.js` is scheduled daily. Lines 44-58 compute `lastLogDaysAgo` (0-4, or -1 if none of the last 5 days were logged). Line 61 sends whenever `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`. Every subsequent day the same client stays inactive, the same condition is true again, and lines 76-93 fire another email.

**Impact**
Inactive clients — the exact group most likely to be already annoyed or disengaged — get bombarded. Real risk of spam complaints against `noreply@telosathleticclub.com`, which damages deliverability of every other Telos email (including the weekly recap and password reset). Also a soft trust hit if a churned client keeps getting emails.

**Suggested fix**
Track the last engagement-email timestamp on the client record and only send if it's been at least, say, 5 or 7 days since the last one. Something like:

```js
if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3) {
  var last = client.lastEngagementEmailAt ? Date.parse(client.lastEngagementEmailAt) : 0;
  if (now - last < 5 * 86400000) continue;
  // ... send ...
  client.lastEngagementEmailAt = new Date().toISOString();
  await redis('SET', 'client:' + client.id, JSON.stringify(client));
}
```

**Confidence:** high

### [P2] Public rate limits bypass with a spoofed X-Forwarded-For prefix

**ID:** `2026-07-15-xff-rate-limit-bypass`
**File:** `api/submit-quiz.js:23`, `api/submit-email.js:28`, `api/submit-chs-application.js:40`
**Category:** rate-limit

**What's wrong**
All three public form endpoints build the rate-limit key from `req.headers['x-forwarded-for']` verbatim. On Vercel serverless, a client-supplied `X-Forwarded-For` header is preserved and Vercel appends the real client IP after it. So a caller can send `X-Forwarded-For: <random>` on every request, producing a fresh bucket string each time (`ratelimit:quiz:abc, 1.2.3.4`, `ratelimit:quiz:def, 1.2.3.4`, ...) and never tripping the limit.

**How to reproduce**
```bash
for i in $(seq 1 50); do
  curl -s -X POST https://www.telosathleticclub.com/api/submit-quiz \
    -H "Content-Type: application/json" \
    -H "X-Forwarded-For: attacker-$i" \
    -d '{"name":"Bot","email":"b@x.com","scores":[],"totalScore":0}'
done
```
Every request will succeed. The "max 10 per hour" cap does nothing because each request's bucket key is unique.

**Impact**
An attacker can flood the CHS application table, the quiz submissions ZSET, and the email captures ZSETs at will. Redis storage grows unbounded, and the dashboard's Leads and Charleston tabs get filled with junk that Thomas has to hand-triage. Not catastrophic, but it defeats the mitigation that's already in the code.

**Suggested fix**
Take the rightmost entry of the header, which is what Vercel appends and the client cannot forge past. Extract to a helper in `api/lib/`:

```js
function clientIp(req) {
  var xff = req.headers['x-forwarded-for'] || '';
  var parts = xff.split(',').map(function(s) { return s.trim(); }).filter(Boolean);
  return parts[parts.length - 1] || req.headers['x-real-ip'] || 'unknown';
}
```

Then use `clientIp(req)` in all three submit endpoints.

**Confidence:** high
