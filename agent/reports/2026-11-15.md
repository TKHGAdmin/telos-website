## BH-001 — Enabling portal silently takes over another client's email reservation

**Severity**: P1
**File**: `api/dashboard/client-portal.js:115-118` (combined with `api/dashboard/clients.js:121`)

### What's wrong

When the admin enables the client portal for a client, `client-portal.js` unconditionally writes the email reservation:

```js
// client-portal.js:115-118
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));  // overwrites any existing owner
}
```

It never checks whether `client_email:{email}` already belongs to a different client. Meanwhile `clients.js` PUT only guards email uniqueness for clients that are *already* portal-enabled (`line 121`: `... && client.portalEnabled`). So it is possible to set a non-portal client's email to one that is already reserved, then enable the portal — and the `SET` on line 117 silently overwrites the original owner's lookup.

### Reproduction

1. Admin creates Client A with email `alice@example.com`, enables portal. Redis: `client_email:alice@example.com → "A"`.
2. Admin creates Client B with email `bob@example.com`, portal disabled.
3. Admin edits Client B, changes email to `alice@example.com`. `clients.js` PUT skips the duplicate check (line 121 guard requires `client.portalEnabled`, which is still false for B). The record saves fine.
4. Admin enables portal for Client B. `client-portal.js` POST hits line 117: `SET client_email:alice@example.com → "B"`.
5. Client A logs in with `alice@example.com` + their real password. Server looks up `client_email:alice@example.com → "B"`, fetches Client B, password check against B's hash fails → 401. **Client A is locked out of their own portal with no error that explains why.**

### Impact

Admin UI promises "duplicate email check" (per `CLAUDE.md`) but the guarantee can be bypassed by a specific — and plausible — sequence of edits. The harm is silent lockout of a paying client with no server-side alert and no obvious cause in the admin UI.

### Suggested fix

In `client-portal.js` before `SET`:

```js
var email = normalizeEmail(client.email);
var currentOwner = await redis('GET', 'client_email:' + email);
if (currentOwner && String(currentOwner) !== String(client.id)) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
await redis('SET', 'client_email:' + email, String(client.id));
```

And drop the `&& client.portalEnabled` guard on `clients.js:121` so email-change collisions are caught regardless of portal state.

## BH-002 — `engagement-check` cron spams inactive clients every single day

**Severity**: P1
**File**: `api/cron/engagement-check.js:61-93` (plus `vercel.json:24-25`: daily schedule)

### What's wrong

The cron runs daily (`"schedule": "0 15 * * *"`). For every active client with `portalEnabled` and no daily log in the last 3 days, it sends a "We miss you at Telos" email. There is **no tracking of when the last reminder was sent** and no backoff.

Relevant block:

```js
// line 61
if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3) {
  // ... build and send email, no "last-reminded-at" check anywhere
  sent++;
}
```

### Reproduction

1. A client stops logging into the portal on day 0.
2. Day 3: cron fires → email #1 sent.
3. Day 4: cron fires → the client is still inactive (log window still doesn't have a hit) → email #2 sent.
4. Day 5, 6, 7 ... : same email keeps going out every 24 h for as long as the client remains inactive AND remains `status: 'active'` + `portalEnabled: true`.

In a typical churn case (client quietly drifts away for 2 weeks before deciding whether to cancel) this is 12+ identical emails from the same sender.

### Impact

- Mailbox-level: recipients mark as spam → damages Resend sender reputation for `noreply@telosathleticclub.com`, which is the same sender used for password resets and weekly summaries. A reputation hit degrades deliverability for the entire system.
- Product: the email is annoying enough that it's likely to push a wavering client toward cancellation rather than re-engagement.

### Suggested fix

Track `client.lastEngagementEmailAt` (or a Redis key `client_last_reminder:{id}` with a TTL) and only send if last reminder was ≥ N days ago (N = 5 or 7 is reasonable). Minimal change inside the `if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3)` block:

```js
var lastSent = await redis('GET', 'client_last_reminder:' + client.id);
if (lastSent && (now - parseInt(lastSent, 10)) < 5 * 86400000) continue;
// ... send email
await redis('SET', 'client_last_reminder:' + client.id, String(now));
```

## BH-003 — Deleting a client leaks the `client_email:` reservation

**Severity**: P1
**File**: `api/dashboard/clients.js:143-154`

### What's wrong

The DELETE handler removes two keys and nothing else:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
return res.status(200).json({ ok: true });
```

If the deleted client ever had their portal enabled, `client_email:{normalizedEmail}` → `id` was written (by `client-portal.js:117`) and **is never cleaned up**. The reservation record outlives the client.

### Reproduction

1. Admin creates Client A with email `alice@example.com`, enables portal. Redis: `client_email:alice@example.com → "A"`.
2. Client A ends their engagement. Admin deletes Client A via the dashboard.
3. Months later, a new prospect also named Alice signs up with `alice@example.com`. Admin tries to create her in the dashboard → `clients.js:70-73` finds the stale `client_email:alice@example.com → "A"` reservation → **"Email already in use by another client"** error, pointing at a deleted (phantom) ID.

The admin has no in-app way to clear the stale key; they have to reach into Redis manually.

### Impact

- Blocks creation of new clients that reuse any email from a past, deleted client. This will accumulate over the life of the business.
- Confusing error message ("Email already in use by another client") when no such client exists.

### Suggested fix

In the DELETE handler, fetch the client first, read its email, and clean up:

```js
var raw = await redis('GET', 'client:' + id);
if (raw) {
  try {
    var c = JSON.parse(raw);
    if (c.email) {
      var { normalizeEmail } = require('../lib/client-auth');
      await redis('DEL', 'client_email:' + normalizeEmail(c.email));
    }
  } catch (e) {}
}
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

Also worth considering (but not required for this bug): cleanup of per-client data keys (daily logs, nutrition logs, training logs, 545, etc.). Keeping them is arguably a feature (restore / audit), but blocking email reuse is clearly not.

## BH-004 — Weekly summary email reports `streak: 0` for everyone on Monday morning

**Severity**: P2
**File**: `api/cron/weekly-summary.js:87-90` (combined with `vercel.json:20-22`: schedule `0 14 * * 1` = Monday 14:00 UTC = 09:00 ET)

### What's wrong

The streak loop walks today-backwards and short-circuits on the first missing log:

```js
// line 87
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

`d = 0` is today's date (per the loop above that built `weekData`). But the cron fires at 09:00 ET Monday, and almost no client will have submitted a daily log yet for Monday at 9 AM. `weekData[0][0]` is empty, so the loop breaks immediately and `streak = 0`.

### Reproduction

1. Any client who logged every day Sunday, Saturday, Friday, Thursday, Wednesday, Tuesday, and the prior Monday.
2. Monday 09:00 ET: cron runs. They have not checked in yet today.
3. Email they receive says:
   > Current Streak: **0 days**

Even though they just completed a 7-day run.

### Impact

Undermines the exact value prop of the weekly summary (reward consistency). A client whose real streak is 7 gets a demoralizing "0 days" headline.

### Suggested fix

Start from `d = 1` (yesterday) and only count today if it's actually logged:

```js
// optionally count today only if logged, then walk yesterday backwards
if (weekData[0][0] && weekData[0][0].result) streak++;
for (var d = 1; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

Or, equivalently, skip today entirely and advertise the stat as "streak through yesterday."

## BH-005 — `X-Forwarded-For` taken verbatim as rate-limit key

**Severity**: P2
**Files**:
- `api/submit-quiz.js:23-29`
- `api/submit-email.js:28-34`
- `api/submit-chs-application.js:40-46`

### What's wrong

All three public submit endpoints build the rate-limit key the same way:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:quiz:${ip}`;    // or :email: / :chs:
const count = await redis('INCR', rateLimitKey);
```

On Vercel, a client-supplied `X-Forwarded-For` is preserved and the real edge IP is *appended*, so a request sent with `X-Forwarded-For: 1.2.3.4` arrives at the function with a header like `1.2.3.4, <real-ip>`. The code uses the whole string as the rate-limit key. An attacker that varies the prefix per request (`X-Forwarded-For: <random>`) gets a fresh bucket on every submission, which defeats the whole rate limit.

Vercel's recommended source for the client IP is `x-real-ip` (or `request.ip` on newer runtimes), which is set by the edge and cannot be overridden by the client.

### Reproduction

```bash
for i in $(seq 1 100); do
  curl -X POST https://www.telosathleticclub.com/api/submit-quiz \
    -H "Content-Type: application/json" \
    -H "X-Forwarded-For: 10.$((RANDOM%255)).$((RANDOM%255)).$((RANDOM%255))" \
    -d '{"name":"x","email":"x@y.z","scores":[1,1,1,1],"totalScore":4}'
done
```

Every request lands in its own `ratelimit:quiz:<spoofed>, <real>` bucket, so the 10-per-hour cap never trips. Submissions pile up in `quiz_submissions` ZSET.

### Impact

The three affected endpoints each have a Redis write per request (`ZADD` to a quiz / email / CHS application index) plus a Redis `INCR`. With the limit gone:
- Quiz submissions / CHS applications / tool-page email captures can be flooded, polluting the admin dashboard with junk leads.
- Redis write volume is uncapped; sustained abuse burns through the Upstash Pay-as-you-go budget.

Not a data-exfiltration bug, but it defangs the only abuse control these endpoints have.

### Suggested fix

Switch to `x-real-ip` (Vercel sets it reliably) with a safe fallback to the last entry of `x-forwarded-for`:

```js
function clientIp(req) {
  var real = req.headers['x-real-ip'];
  if (real) return real;
  var xff = req.headers['x-forwarded-for'] || '';
  var parts = xff.split(',');
  return (parts[parts.length - 1] || '').trim() || 'unknown';
}
```

Then `const ip = clientIp(req);` in all three endpoints.
