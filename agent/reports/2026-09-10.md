### 1. Summary

Focused on the serverless API layer today: auth libs, admin CRUD, client portal endpoints, cron jobs, and the service worker. Four real defects surfaced - one P1 in the admin client-delete flow, two P2s in submission validation and course-module tier gating, and one P3 in service-worker scope.

### 2. Findings

#### [P1] Deleting a client leaves orphan `client_email` lookup, blocking email reuse

- **Location:** `api/dashboard/clients.js:143-154`
- **What's wrong:** The DELETE handler only removes `client:{id}` and the `clients_index` ZSET entry. It never deletes the reverse `client_email:{normalizedEmail} -> clientId` lookup that `client-portal.js:117` writes when portal is enabled.
- **Why it matters:** After deleting a client whose portal was ever enabled, creating a new client with the same email (or restoring the same person) fails at `clients.js:70-73` with "Email already in use by another client" - even though the referenced client is gone. Thomas has no in-UI way to clear the stale lookup; only manual Redis surgery fixes it. All the per-client Redis keys (`client_dailylog:{id}:*`, `client_training_log:{id}:*`, `client_545_daily:{id}:*`, `client_supplement_log:{id}:*`, `client_activity_log:{id}:*`, `client_push_sub:{id}`, etc.) also stick around forever.
- **Repro / evidence:**
  ```
  POST /api/dashboard/clients { name:"A", email:"a@x.com", tier:"growth" }
  POST /api/dashboard/client-portal { clientId:<A>, enabled:true, password:"..." }
    -> writes client_email:a@x.com = <A>
  DELETE /api/dashboard/clients?id=<A>
    -> only DELs client:<A> and ZREM clients_index
    -> client_email:a@x.com still points to <A>
  POST /api/dashboard/clients { name:"A2", email:"a@x.com", tier:"growth" }
    -> 400 "Email already in use by another client"
  ```
- **Suggested fix:** In the DELETE handler, `GET client:{id}` before deleting, then `DEL client_email:{normalizeEmail(client.email)}` alongside the existing DEL and ZREM. Consider a second pass that also drops the client's per-day log keys via the four `*_index` ZSETs it already maintains, so deleted clients don't accrete indefinitely.
- **Confidence:** high

#### [P2] `/api/submit-quiz` accepts anything non-empty as an email

- **Location:** `api/submit-quiz.js:16-20`
- **What's wrong:** The validation is `if (!email || !name)` - it never checks for an `@` or an email-like shape. `api/submit-email.js:18` requires `email.includes('@')` and `api/submit-chs-application.js:35` uses a regex. Quiz submissions are the odd one out.
- **Why it matters:** The quiz is the single biggest top-of-funnel lead source (homepage inline + pricing-gate overlay), and the submissions flow straight into `quiz_submissions` in Redis and from there into Thomas's Leads tab. Any typo, "no thanks", or hostile bot fill becomes a poisoned lead row he has to manually cull.
- **Repro / evidence:** `curl -X POST /api/submit-quiz -d '{"name":"x","email":"nope"}'` returns `{ok:true}` and stores the row.
- **Suggested fix:** Add the same `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` check the CHS endpoint uses (or at minimum `email.includes('@')` to match `submit-email.js`) and return 400 on failure.
- **Confidence:** high

#### [P2] Modules with an empty `tierAccess` array return "Upgrade to lifestyle_plus" for everyone

- **Location:** `api/client/module.js:50-61`
- **What's wrong:** `minTier` is seeded at `999` and only lowered inside the `mod.tierAccess.forEach`. If `tierAccess` is `[]` or `undefined`, `minTier` stays `999`, and the check `clientTierLevel < minTier` is true for every client (max level is 3 for `lifestyle_plus`). The response is `403 { error: "Upgrade required", requiredTier: TIER_ORDER[999] || "lifestyle_plus" }`, which is misleading: no upgrade exists that would fix this.
- **Why it matters:** `api/dashboard/modules.js:124` is `if (body.tierAccess !== undefined) mod.tierAccess = body.tierAccess;` - so if the module editor sends an empty selection, the module gets saved with `tierAccess: []` and becomes invisible to every tier, including the top one. The admin has no way to diagnose this from the client-facing error, and older imported records may already be missing the field.
- **Repro / evidence:** Any module document with `tierAccess: []` (or the key absent). GET `/api/client/module?id={that}` as a `lifestyle_plus` client -> 403 "Upgrade required, lifestyle_plus".
- **Suggested fix:** Treat empty/missing `tierAccess` as "open to all tiers" in `module.js` (set `minTier = 0` when the array has no entries), or reject the save in `dashboard/modules.js` with 400 when `tierAccess` is a zero-length array so admins get a real error instead of a silently unreachable module.
- **Confidence:** medium

#### [P3] Service worker at `/sw.js` registers with default scope `/`, controlling the whole site

- **Location:** `client-dashboard.html:4949` and `sw.js:1-71`
- **What's wrong:** `navigator.serviceWorker.register('/sw.js')` is called with no `scope` option. Because `sw.js` is at the site root, the default scope becomes `/`. Once any visitor has loaded `/client-dashboard`, the SW intercepts every GET on the origin - the marketing pages, all 23 blog articles, `/thomas`, tool pages - and the fetch handler at `sw.js:60-70` runs `cache.put` on every successful response.
- **Why it matters:** The SW was written for the client portal only per `CLAUDE.md` ("push notifications and static asset caching" scoped to the portal). Site-wide interception means (a) each cache-busted CSS/JS version (`?v=15`, `?v=16`, ...) is stored as a distinct entry and never evicted - cache grows without bound; (b) `/thomas` admin HTML gets cached, so a logged-in admin who briefly goes offline can see a stale shell of the dashboard; (c) any future change to the SW fetch logic affects the entire marketing site, not just the portal.
- **Repro / evidence:** In DevTools -> Application -> Service Workers after visiting `/client-dashboard`, the SW's scope shows `https://www.telosathleticclub.com/`. Then navigate to any blog page - the request is served through the SW.
- **Suggested fix:** Pass an explicit scope: `navigator.serviceWorker.register('/sw.js', { scope: '/client-dashboard/' })`. Alternatively, move `sw.js` under a client-portal path so its max scope is naturally constrained. Bump the SW cache name at the same time so existing over-scoped registrations get evicted.
- **Confidence:** medium
