# Telos Bug Hunter - 2026-06-26

## Summary

First run of the agent. Focus: **Functional**. Inspected the Vercel cron jobs, public API submission endpoints, admin and client auth endpoints, the new Shopify-integrated `shop`/`product` pages, and the navigation refactor that moved Resources and FAQ behind a Tools dropdown.

Four real bugs identified, one P1 (engagement-check cron emails inactive clients daily forever) plus two P2s (no rate limiting on login endpoints; client DELETE leaves orphan PII and a blocked email mapping) and one P3 (mobile nav on shop/product/chs is missing Resources and FAQ after the Tools-dropdown refactor).

## Findings

### BUG-2026-06-26-01: Engagement cron spams inactive clients with a "We miss you" email every single day

- **Severity**: P1
- **Area**: cron / client email
- **File(s)**: `api/cron/engagement-check.js:43-94`, `vercel.json:21-24`
- **Symptom**: Once a client crosses the 3-days-inactive threshold, they receive a "We miss you at Telos" email every day until they either log a check-in or have their `emailEnabled` flag turned off. Real users will report this as spam, and Resend reputation/unsubscribe rates will suffer.
- **Root cause**: The cron only looks at the last 5 days of `client_dailylog:{id}:{date}` keys and sends an email whenever `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`. There is no "last reminder sent" marker, no cooldown, and no per-client throttle. The cron schedule in `vercel.json` is `0 15 * * *` (daily), so the same condition fires every 24 hours.
- **Reproduction**:
  1. Create an active client with `portalEnabled: true` and a real `email`.
  2. Let them log a daily check-in 4 days ago, then nothing else.
  3. Trigger `/api/cron/engagement-check` with the correct `CRON_SECRET` today, tomorrow, the next day. The same `to: [client.email]` Resend POST fires every run.
- **Fix sketch**: After sending, write a `client_engagement_sent:{id}` key with a 3-7 day TTL and skip the client when that key exists. Alternatively, only send on the day the inactivity threshold is *first* crossed by tracking the last reminder timestamp inside the `client:{id}` record.

### BUG-2026-06-26-02: DELETE client leaves orphaned PII and a permanently-blocked email mapping

- **Severity**: P2
- **Area**: admin dashboard / Redis hygiene / data privacy
- **File(s)**: `api/dashboard/clients.js:143-154`
- **Symptom**: When Thomas removes a client from the dashboard, the `client_email:{normalizedEmail}` lookup, all daily logs, training logs, supplement logs, activity logs, 545 records, nutrition plan, mindset, resources, and side-menu config remain in Redis. Two concrete consequences: (a) that email address can never be re-used to create a new portal client (the duplicate-email check rejects it), and (b) all PII for a deleted client is retained indefinitely, which is a GDPR/CCPA exposure once a client requests deletion.
- **Root cause**: The DELETE handler only calls `redis('DEL', 'client:' + id)` and `redis('ZREM', 'clients_index', String(id))`. None of the satellite keys documented in `CLAUDE.md` (`client_email:*`, `client_dailylog:*`, `client_dailylogs_index:*`, `client_545_*`, `client_training_*`, `client_supplement_*`, `client_activity_log:*`, `client_nutrition_*`, `client_mindset:*`, `client_resources:*`, `client_sidemenu:*`) are cleaned up.
- **Reproduction**:
  1. Create a client `foo@example.com`, enable portal (this writes `client_email:foo@example.com -> id`).
  2. Log some check-ins so `client_dailylog:{id}:2026-06-26` exists.
  3. DELETE the client from the dashboard.
  4. Try to create a new client with `foo@example.com` -> server returns `400 Email already in use by another client` even though there is no visible client.
  5. Inspect Redis -> the daily log keys and indices are still present.
- **Fix sketch**: In the DELETE handler, first `GET client:{id}`, parse, then in a single pipeline: `DEL client_email:{normalizeEmail(client.email)}`, `DEL client_dailylogs_index:{id}` and all members it references, `DEL client_545_index:{id}` and members, `DEL client_supplement_logs_index:{id}` and members, `DEL client_training_logs_index:{id}` and members, `DEL client_activity_logs_index:{id}` and members, `DEL client_nutrition_logs_index:{id}` and members, plus the singleton keys `client_nutrition_plan:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_training_program:{id}`, `client_545_goals:{id}`, `client_545_routine:{id}`. Finally `DEL client:{id}` and `ZREM clients_index`.

### BUG-2026-06-26-03: No rate limiting on `/api/dashboard/login` or `/api/client/login`

- **Severity**: P2
- **Area**: auth / abuse
- **File(s)**: `api/dashboard/login.js:1-17`, `api/client/login.js:1-60`
- **Symptom**: Both login endpoints accept unlimited POSTs from the same IP. The admin endpoint protects a single password (`DASHBOARD_PASSWORD`) that gates the entire revenue/client/PII dashboard; the client endpoint protects individual client portals. An attacker can run an online dictionary attack with no friction.
- **Root cause**: Both handlers go straight from `req.body` validation to `verifyPassword`/`verifyClientSession` and return. The public submission endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) all use a Redis `INCR + EXPIRE` rate-limit pattern, but it was never applied to the login routes. Note also that `api/client/login.js` returns four distinguishable error strings ("Portal access not enabled", "Account is not active", "Password not set - contact your coach", "Invalid email or password"), which makes email enumeration trivial and amplifies the brute-force risk.
- **Reproduction**:
  1. `for i in $(seq 1 1000); do curl -X POST https://www.telosathleticclub.com/api/dashboard/login -H 'Content-Type: application/json' -d "{\"password\":\"guess-$i\"}"; done` -> all 1000 requests are processed; no 429.
  2. Same for `/api/client/login` with a known email -> the response body confirms whether the email exists (different message) and you can hammer the password unimpeded.
- **Fix sketch**: Reuse the existing pattern in `submit-chs-application.js:39-46`: `INCR ratelimit:login:{ip}` (and `ratelimit:client-login:{ip+email}`), `EXPIRE` on first hit, reject with 429 after a small number of failed attempts. For the client login, also collapse all failure branches into a single generic "Invalid email or password" message and only differentiate after successful authentication.

### BUG-2026-06-26-04: Mobile nav on shop, product, and chs is missing "Resources" and "FAQ" after the Tools-dropdown refactor

- **Severity**: P3
- **Area**: navigation / mobile UX
- **File(s)**: `shop.html:703-719`, `product.html:694-710`, `chs.html` (mobile-menu block)
- **Symptom**: On phones, users on the Shop, Product detail, and Charleston landing pages cannot reach the Resources hub or the FAQ from the nav. Desktop hover dropdown works fine; mobile menu just doesn't list those items.
- **Root cause**: Commit `9319f9d` moved Resources and FAQ into the desktop "Tools" dropdown. The mobile menus in `index.html` and the blog templates use a `.mobile-dropdown` structure (the toggle handler lives in `js/main.js:43-48`), but `shop.html`, `product.html`, and `chs.html` only have a flat `<ul>` with no dropdown structure and no entries for Resources or `index.html#faq`. Grep: `mobile-dropdown` is present in `index.html`, blog pages, `main.js`, and `style.css` only.
- **Reproduction**:
  1. Open `https://www.telosathleticclub.com/shop` on a phone (or DevTools mobile emulator <=768px).
  2. Tap the hamburger.
  3. The menu shows System, Charleston, Protein Calc, Hyrox Predictor, Shop, cart, Client Login, Book a Call. No Resources, no FAQ.
- **Fix sketch**: Add the same `.mobile-dropdown` block used in `index.html` to the three mobile menus, or simply add flat `<li><a href="resources">Resources</a></li>` and `<li><a href="index.html#faq">FAQ</a></li>` entries since these pages have no other dropdown to group with. Pick one pattern and use it consistently across all three pages.

## Notes

- The `agent/` and `docs/` directories did not exist before this run; I bootstrapped `docs/BUG_REPORT_SCHEMA.md`, `agent/memory/focus-rotation.json`, and an empty `agent/memory/decisions.jsonl`. Tomorrow's focus is **Visual/UX**.
- The Shopify Storefront token in `js/shop.js:15` is intentionally public (Storefront API tokens are designed to be exposed client-side), so it is **not** flagged as a bug.
- The admin `verifyToken` in `api/lib/auth.js:18-31` uses `signature !== expected` instead of `crypto.timingSafeEqual`. The timing channel against an HMAC is impractical in this environment so it doesn't make the bar today, but worth tightening on the next security pass.
- The `submit-quiz.js` / `submit-chs-application.js` rate limiters key on `req.headers['x-forwarded-for']` which Vercel sets but which is a comma-separated list when the request transits multiple proxies. Not a bug per se on Vercel today, but the key choice is fragile; consider using `x-real-ip` first instead.
