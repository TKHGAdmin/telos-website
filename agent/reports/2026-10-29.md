## P1-01: Quiz tab's "+ Pipeline" button is broken on every submission

**File:** `thomas.html:2528`
**Severity:** P1 - breaks a daily admin workflow for 100% of real data

### What's wrong

```js
html += '<td><button class="btn btn-sm btn-gold" onclick="addLeadFromQuiz(' +
  JSON.stringify(JSON.stringify(s)) + ')">+ Pipeline</button></td>';
```

`JSON.stringify(JSON.stringify(s))` produces a JS string literal like
`"{\"name\":\"John\",\"email\":\"john@test.com\",\"score\":50}"` - but those inner
double-quotes are **not** HTML-escaped and the whole thing is embedded directly inside
a double-quoted `onclick="..."` attribute. The HTML parser terminates the attribute at
the first inner `"`, leaving `onclick="addLeadFromQuiz("` - a syntax error.

### Reproduction (confirmed in Playwright)

```
PAGEERROR: Failed to execute 'click' on 'HTMLElement': Unexpected end of input
```

Rendered DOM shows attribute truncated to `addLeadFromQuiz(` with the rest parsed as
garbage attribute names. The button does nothing when clicked.

Because every quiz submission has `name`, `email`, and `scores`, every row's JSON
contains `"`, so this is not an edge case - **it's broken 100% of the time**.

### Fix sketch

Either:
- `data-row` attribute on the button + `addLeadFromQuiz(this.dataset.row)`, with
  `esc(JSON.stringify(s))` (safe because the attribute is quoted and `esc` escapes `<>&`),
  or
- `encodeURIComponent(JSON.stringify(s))` inside the attribute + `decodeURIComponent` in
  the handler.

Git history (`git log -S addLeadFromQuiz`) shows this line was added in commit `b9b065a`
("Track backend, admin dashboard, and client PWA in git") and has never been touched -
so the button has never worked. Thomas has presumably been adding quiz leads to the
pipeline manually via the Pipeline tab's modal.

## P2-01: Email tab's "+ Pipeline" button breaks on emails containing an apostrophe

**File:** `thomas.html:2575`
**Severity:** P2 - breaks for a real but small subset of users

### What's wrong

```js
html += '<td><button class="btn btn-sm btn-gold" onclick="addLeadFromEmail(\'' +
  esc(em.email) + '\')">+ Pipeline</button></td>';
```

`esc()` escapes `&`, `<`, `>` (and nbsp) only - **not `'`** - because it serializes a
text node and HTML5's text-node serialization does not quote-escape. An email like
`o'brien@example.com` renders as:

```
onclick="addLeadFromEmail('o'brien@example.com')"
```

...which parses as `addLeadFromEmail('o')` followed by stray text, and the browser
reports `missing ) after argument list`.

Confirmed in the same Playwright run:
```
PAGEERROR: Failed to execute 'click' on 'HTMLElement': missing ) after argument list
```

`api/submit-email.js` only validates `email.includes('@')`, so apostrophe-containing
emails do get stored. Local-part apostrophes are valid per RFC 5321.

### Fix sketch

Same approach as P1-01 - `data-email` attribute (where `esc` is safe inside quoted
attributes for everything except `"`), or encodeURIComponent round-trip.

Also worth tightening `esc()` itself to escape `'` and `"` so this whole class of bug
goes away.

## P2-02: Deleting a client orphans the email-lookup key - email can't be reused

**File:** `api/dashboard/clients.js:143-154`
**Severity:** P2 - operational / data-integrity

### What's wrong

The DELETE handler removes only `client:{id}` and the `clients_index` ZSET entry:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

It never removes `client_email:{normalizedEmail}` (set by the client-portal POST and by
the PUT email-change path). Once a client is deleted, that email address is still
mapped to the dead ID, so re-creating a client with the same email returns
`"Email already in use by another client"` (set at `clients.js:71-73`).

Login still fails safely: `api/client/login.js:29` fetches `client:{clientId}` which is
now null, so the user gets `Invalid email or password` - **not an auth bypass**, but
the email becomes a permanent dead reference.

The DELETE also leaves behind every per-client Redis key:
`client_dailylog:*`, `client_dailylogs_index:*`, `client_nutrition_plan:*`,
`client_nutrition_log:*`, `client_mindset:*`, `client_resources:*`, `client_545_*:*`,
`client_training_program:*`, `client_training_log:*`, `client_training_logs_index:*`,
`client_sidemenu:*`, `client_supplement_plan:*`, `client_supplement_log:*`,
`client_supplement_logs_index:*`, `client_activity_log:*`, `client_activity_logs_index:*`.

### Fix sketch

In DELETE, after loading the client record:
1. `DEL client_email:{normalizeEmail(client.email)}` if `client.portalEnabled && client.email`
2. For each per-client key family, if the index ZSET exists, scan it and `DEL` each
   dated key, then `DEL` the index itself.

The email-mapping cleanup is the small, high-value piece; the per-client log cleanup is
optional (orphan data costs Redis memory but doesn't break anything).

## What I looked at and ruled out

- **`js/shop.js:15` Shopify Storefront Access Token** - public by design, not a leak.
- **`set-password.html:195` Supabase anon key** - public by design (RLS-governed).
- **`api/lib/auth.js:27` non-constant-time HMAC compare** - theoretical only; HMAC
  signatures without the secret are already uncrackable in reasonable time, HTTPS
  masks fine-grained timing, and `verifyPassword` already uses `timingSafeEqual`.
- **`esc()` not escaping quotes** inside admin `innerHTML` - audited all 50 occurrences
  in `thomas.html`; only the two above actually inject user-controlled text into a
  quoted attribute. The pipeline/client/content modals use `esc()` on numeric DB IDs,
  which are safe.
- **`sw.js` `telos-v1` cache name** - already in CLAUDE.md "Known Limitations" backlog.
- **Tool pages missing main.js** - already in CLAUDE.md backlog.
- **Weekly-summary streak computation starts at UTC today** - overlaps with the known
  `todayStr()` UTC bug in CLAUDE.md, so not re-reported.
