## P1 - Engagement cron emails inactive clients every day

**ID:** 2026-10-02-01
**File:** `api/cron/engagement-check.js`
**Lines:** 36-94

### What's wrong
The engagement-check cron runs **daily** (CLAUDE.md: "Daily 3pm UTC") and sends a "We miss you at Telos" email to any active client whose last daily-log is 3+ days old (line 61). There is no "last reminder sent" throttle. Once a client crosses the 3-day inactivity threshold, they will receive the same reminder email **every day until they log**.

A client who disengages for a week will receive 4-5 duplicate reminder emails. That is spam, both practically and in the eyes of mailbox providers; it will train Gmail/Apple Mail/Outlook to send Telos mail to the Promotions tab or junk, hurting deliverability of the weekly summary and (eventually) the transactional password-reset emails that share the `telosathleticclub.com` sending domain.

### How to reproduce
1. Create a client with `portalEnabled: true` and `status: 'active'`.
2. Have them log in once (so Redis has data for them) and then stop checking in.
3. Wait 3 days. Trigger the cron. Observe one email.
4. Trigger the cron again the next day without the client having logged. Observe a second identical email.

### Suggested fix
Record `client.lastEngagementReminderAt` (or a dedicated Redis key like `engagement_reminder_sent:{clientId}` with a 7-day TTL) when the email is dispatched. Before sending, check that no reminder has been sent in the last N days (7 feels right). Also consider escalating language: Day 3 "we miss you", Day 10 "checking in", Day 30 "final check-in".

### Confidence
High. The code path is linear and the daily schedule is explicit in both `CLAUDE.md` and the cron declaration.

## P2 - Rate-limit bypass via spoofed X-Forwarded-For

**ID:** 2026-10-02-02
**File:** `api/submit-quiz.js:23`, `api/submit-email.js:28`, `api/submit-chs-application.js:40`
**Lines:** cited above

### What's wrong
All three public-submit endpoints derive their per-IP rate-limit key from `req.headers['x-forwarded-for']` taken as-is:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:quiz:${ip}`;
```

On Vercel, a client can set its own `X-Forwarded-For` header; the edge **appends** the real client IP rather than overwriting. The function therefore sees `attacker-value, real-ip` and the rate-limit key varies with whatever the attacker puts in `attacker-value`. An attacker who rotates the fake prefix (`1.1.1.1`, `1.1.1.2`, ...) gets a fresh rate-limit bucket per request and can flood the submit endpoints indefinitely. Impact:

- Quiz: unlimited junk submissions pollute the `quiz_submissions` ZSET and the dashboard pipeline.
- Email: unlimited email captures bloat `email_protein_calculator` / `email_hyrox_predictor`.
- CHS: unlimited application rows in `chs_application:{id}` + the ZSET - and because each application triggers no outbound send, the only cost is Redis storage. Still, it defeats the stated 5/hr/IP limit and makes manual triage painful.

### How to reproduce
Send repeated `POST /api/submit-email` requests with varying `X-Forwarded-For: 1.2.3.N` (N incrementing). Observe that none are 429'd.

### Suggested fix
Use the **right-most** entry of `x-forwarded-for` (that's the IP Vercel's edge added) rather than the raw header string:

```js
const xff = (req.headers['x-forwarded-for'] || '').split(',');
const ip = (xff[xff.length - 1] || req.headers['x-real-ip'] || 'unknown').trim();
```

Alternatively, prefer `req.headers['x-vercel-forwarded-for']`, which Vercel sets itself and clients cannot forge. Apply the same change to `api/client/reset-password.js` once rate-limiting is added there (see 2026-10-02-03).

### Confidence
High on the mechanism (Vercel's XFF behavior is documented); medium on real-world impact - no live exploitation is visible but the hole is open.

## P2 - Password-reset endpoint has no rate limiting (email-spam amplifier)

**ID:** 2026-10-02-03
**File:** `api/client/reset-password.js`
**Lines:** 20-67

### What's wrong
`POST /api/client/reset-password` with `{ email }` triggers a Resend email to the client's address every time it is called. There is **no rate-limit guard** on this endpoint (unlike the public submit endpoints which at least try, however imperfectly - see 2026-10-02-02).

Impact scenarios:
1. **Spam amplification against a known client.** An attacker who knows a client email (easy - the quiz capture surfaces them in the admin dashboard, and some are publicly discoverable) can hammer the endpoint and the client receives arbitrarily many "Reset Your Telos Client Portal Password" emails. This is a textbook email-abuse pattern that gets reported to Resend and risks suspending the Telos sending domain.
2. **Resend quota drain.** Every call costs one Resend credit. A scripted loop can drain the account in minutes.
3. **Redis bloat.** Every call writes `password_reset:{token}` with a 1-hour TTL. Low volume but unbounded during an attack.

The code intentionally returns `{ ok: true }` on unknown emails to prevent enumeration (good), but that same uniform-success behavior means a rate-limit by email is only triggered for real accounts; the right dimension is per-IP.

### How to reproduce
Loop `curl -X POST /api/client/reset-password -d '{"email":"known-client@example.com"}'` and observe no 429 and (if `RESEND_API_KEY` is set) one email per iteration.

### Suggested fix
Add a per-IP rate limit (e.g. 5/hour) **and** a per-email-target rate limit (e.g. 3/hour, keyed on the normalized email, applied *after* the enumeration-safe success response is prepared - so a hit still returns `{ ok: true }` but silently skips the Resend call). Pattern should mirror the submit endpoints but use the fixed XFF parsing from 2026-10-02-02.

### Confidence
High. The code path is explicit and the mitigation is uncontroversial.
