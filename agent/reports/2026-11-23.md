## Summary

Six real security issues in the serverless API, concentrated in auth and rate-limiting. The P1 (rate-limit bypass on all three public write endpoints) and the two P2s on client auth (email enumeration, unlimited password-reset email trigger) are quick to fix and would meaningfully reduce abuse surface. The P3s are hygiene — worth bundling in with the fixes but not urgent on their own.

## Findings

### P1 20261123-01: Rate limits on all public write endpoints bypassable via spoofed `X-Forwarded-For`

- **File**: `api/submit-chs-application.js:40`, `api/submit-email.js:28`, `api/submit-quiz.js:23`
- **Category**: rate-limiting
- **Observed**: All three use the raw request header as the Redis rate-limit key:
  ```js
  const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
  const rateLimitKey = `ratelimit:chs:${ip}`;
  ```
- **Why it's wrong**: On Vercel, `x-forwarded-for` is a chain. The platform appends the real client IP, but anything the client sends arrives in the string too. An attacker who sets `X-Forwarded-For: foo` gets a key of `ratelimit:chs:foo, <realIP>`; changing `foo` on each request produces a fresh bucket every time. The documented 5/hr Charleston-application cap and 10/hr quiz/email caps all collapse to "unlimited for anyone who tries once". A scripted attacker can flood Redis with junk applications, fill the Charleston admin queue, and (for the quiz/email endpoints) harvest lead-list slots or burn Redis storage.
- **Fix sketch**: Use `req.headers['x-real-ip']` (Vercel sets it to the single real client IP) as the primary key, or parse the last entry of `x-forwarded-for` after splitting on `,`. Apply to all three endpoints in one commit since they share the pattern.
- **Confidence**: high

### P2 20261123-02: Client login leaks account existence via distinct error messages

- **File**: `api/client/login.js:36-47`
- **Category**: auth-weakness / enumeration
- **Observed**: Login returns different 401 messages depending on client state:
  - `"Portal access not enabled"` — client exists, portal disabled
  - `"Account is not active"` — client exists, inactive
  - `"Password not set - contact your coach"` — client exists, no password
  - `"Invalid email or password"` — unknown email, or wrong password
- **Why it's wrong**: Any attacker who knows (or guesses) a client's email can observe the response and learn (a) whether they are a Telos client at all, and (b) what state their account is in. The password-reset endpoint deliberately mitigates enumeration by always returning `{ok:true}` (`api/client/reset-password.js:25-36`); this endpoint undoes that effort. For a small, high-ticket client roster this is a real privacy issue (membership itself is sensitive).
- **Fix sketch**: Collapse every pre-password-check failure to the same 401 body `{error: 'Invalid email or password'}`. Keep the distinct messages for logs, not for the response.
- **Confidence**: high

### P2 20261123-03: Password-reset endpoint has no rate limit — unlimited mail to any email

- **File**: `api/client/reset-password.js:20-67`
- **Category**: rate-limiting / abuse
- **Observed**: `POST /api/client/reset-password` with `{email}` calls Resend once per request for any valid, portal-enabled client email, with no IP or email-based throttle. The endpoint correctly returns `{ok:true}` for unknown emails without sending, but *also* returns `{ok:true}` for known ones after firing a send.
- **Why it's wrong**: An attacker who knows a client email can trigger a flood of `Reset Your Telos Client Portal Password` emails into that inbox (harassment, phishing-cover). Costs: client-side reputation hit, Resend quota burn, and — because each hit also writes a `password_reset:<token>` key with 1h TTL — Redis bloat. It also pairs with finding 02 for cheap enumeration.
- **Fix sketch**: Add a per-email counter (`SETEX ratelimit:pwreset:<email> 3600 N`, cap 3/hr) plus a per-IP counter mirroring the submit-* pattern (after fix 01). Apply before the Resend call, after the enumeration-safe early return.
- **Confidence**: high

### P2 20261123-04: Client login has no rate limit — online password brute force available

- **File**: `api/client/login.js` (whole file)
- **Category**: auth-weakness / brute force
- **Observed**: Nothing throttles `POST /api/client/login`. Each attempt runs PBKDF2-100k (~100ms CPU), but Vercel scales concurrency, so an attacker can run many parallel attempts per second against a single account.
- **Why it's wrong**: Password minimum is 8 chars with no complexity rule (`api/client/reset-password.js:72`, `api/dashboard/client-portal.js:100`). An 8-char lowercase password (26^8 ≈ 2·10^11) is not plausible to crack online, but common-password lists (top 10k, top 100k) definitely are — a few hours at a few hundred RPS clears the top 10k. Combined with finding 02, the attacker knows exactly which emails to target.
- **Fix sketch**: Redis-backed counter keyed by `email` *and* by IP; e.g. after 5 failed attempts in 15 min, return 429 for 15 min. Keep attempts counter incrementing on every call reaching the PBKDF2 check (before success); reset on success. Cheaper variant: a shared `ratelimit:login:<ip>` cap of 20/15min as a floor.
- **Confidence**: high

### P3 20261123-05: Admin HMAC signature compared with `!==`, admin password compare short-circuits on length

- **File**: `api/lib/auth.js:27` and `api/lib/auth.js:55-58`
- **Category**: auth-weakness / timing
- **Observed**:
  ```js
  // line 27 — verifyToken
  if (signature !== expected) return false;
  // line 55-58 — verifyPassword
  if (inputStr.length !== expected.length) return false;
  const inputBuf = Buffer.from(inputStr, 'utf-8');
  const expectedBuf = Buffer.from(expected, 'utf-8');
  return crypto.timingSafeEqual(inputBuf, expectedBuf);
  ```
  The sibling library `api/lib/client-auth.js` uses `crypto.timingSafeEqual` for both operations (lines 17-20, 46-49).
- **Why it's wrong**: Both branches leak timing. HMAC forgery via remote timing is impractical over the public internet, but the inconsistency with `client-auth.js` is itself a maintenance risk — a reader seeing one pattern in one file and another in the sibling will drift further. The length-based early-return on `verifyPassword` tells an attacker the length of `DASHBOARD_PASSWORD` in one request (compare response times: input length matching vs not matching). Length alone isn't a compromise, but combined with a leaked GitHub config or any future second-factor it narrows the search space.
- **Fix sketch**: Mirror `client-auth.js`: compare signatures and passwords with `crypto.timingSafeEqual` after a length-safety cast (`Buffer.alloc`). Keep the length-mismatch branch but have it compare against a zeroed buffer of the expected length so timing is uniform.
- **Confidence**: medium (the practical exploit path is weak, the hygiene argument is strong)

### P3 20261123-06: `DELETE /api/dashboard/clients` orphans the `client_email:` lookup

- **File**: `api/dashboard/clients.js:143-153`
- **Category**: data-integrity
- **Observed**:
  ```js
  // DELETE
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  ```
  No cleanup of `client_email:<normalizedEmail>`, no cleanup of any of the ~15 per-client keys enumerated in CLAUDE.md (`client_dailylog:*`, `client_training_program:*`, `client_push_sub:*`, etc).
- **Why it's wrong**: The email-lookup entry still points at the deleted client ID. Two failure modes:
  1. `POST /api/dashboard/clients` later tries to create a client with the same email and hits `"Email already in use by another client"` (line 72) even though no live client owns it.
  2. `POST /api/client/login` resolves `client_email:` → a stale ID, then `GET client:<staleId>` returns `null` and the login returns a generic 401. Not exploitable, just confusing when it recurs.
  The orphaned per-client data (logs, nutrition plans, training programs) is also a soft GDPR / data-minimization issue — a deleted client's historical logs sit in Redis forever.
- **Fix sketch**: In the DELETE branch, before `DEL client:<id>` read the client, grab `normalizeEmail(client.email)`, then also `DEL client_email:<email>`. For the per-client data, a second pass that enumerates known key prefixes and deletes them — or a `SCAN client_*:<id>*` pattern — closes the data-retention gap in one place.
- **Confidence**: high

## Not reported (deliberately excluded)

- **`api/client/push-subscribe.js` lets a logged-in client submit an arbitrary `subscription.endpoint`, which `api/client/notify.js` then POSTs to** — technically an SSRF primitive, but (a) requires valid client credentials, (b) Vercel serverless egress has no privileged internal network to pivot into, (c) `notify.js` is explicitly a placeholder with VAPID not yet wired up. Revisit if VAPID ships.
- **`api/dashboard/upload-video.js` content-type check is attacker-controlled (`req.query.type || contentType`)** — admin-only endpoint, admin is the trust boundary, not worth a bug.
- **`js/shop.js:170` interpolates Shopify image `src` into an `onclick="switchProductImage(this, '…')"` attribute without escaping** — theoretical XSS, but the `src` comes from Shopify's own CDN, which won't emit single quotes in a URL. Noted in `learnings.md`, not reported.
- **Cron handlers use `req.headers.authorization !== 'Bearer ' + process.env.CRON_SECRET`** — plain `!==`, not timing-safe. Vercel invokes these; secret is not practically brute-forceable over HTTP.
- **`verifyClientToken` splits the token on `.` and requires exactly 3 parts** — safe as long as `clientId` stays numeric (it's issued by `INCR id:clients`), which it does today. Would break if the ID scheme ever changed to UUIDs or dotted strings; flagging in `learnings.md` instead of as a bug.
- **`submit-chs-application.js` stores the raw `ip` on the application record** — PII minor, not a bug, intentional for abuse triage.
- **`reset-password.js:58` interpolates `client.name` into the email HTML unescaped** — name comes from admin-authored client records, not user input. Not an XSS vector in this app; would be if client self-signup ever lands.
