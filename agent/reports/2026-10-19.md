## Findings

### [P2] Product detail "Add to Cart" button sticks on "Error - Retry" after a failed-then-successful retry

- **ID**: `2026-10-19-01`
- **File**: `js/shop.js:223-249`
- **Area**: Functional
- **Reproduction**:
  1. On `product.html?p=<any-product-handle>`, click the big gold "Add to Cart" button while offline (or with the network tab set to Offline in devtools, or with the Shopify Storefront API returning a 5xx).
  2. The handler at line 244-248 catches the error and sets `btnElement.innerHTML = 'Error - Retry'`, then re-enables the button.
  3. Restore the network and click the (now relabeled) "Error - Retry" button again. This time the request succeeds and the cart badge updates.
  4. Observe: at line 227 `origHTML = btnElement.innerHTML` was captured AFTER the failure, so it holds the string `"Error - Retry"`. The success path at line 242 restores `btnElement.innerHTML = origHTML` inside the 2500 ms `setTimeout`, locking the button on `"Error - Retry"` permanently even though the item is in the cart.
  5. The sibling `addToCart` function at `js/shop.js:304-340` does NOT have this bug - it hardcodes the restore markup at line 331-333 instead of capturing it.
- **Impact**: Any user whose first add-to-cart attempt fails and who retries will see the button say "Error - Retry" after the successful retry. The item IS in the cart (the drawer and badge update), but the button text contradicts that and will push users to click again, double-adding or giving up. Likelihood scales with mobile users on flaky networks.
- **Suggested fix**: Capture `origHTML` once at page load (inside `loadProductDetail`, before the first click), not on every click. Or match the sibling pattern in `addToCart` and hardcode the restore markup. Simplest patch: at line 227, replace `var origHTML = btnElement.innerHTML;` with the exact HTML of the default button state as a string literal.

### [P3] `js/shop.js` loaded with mismatched cache-busting versions on shop.html vs product.html

- **ID**: `2026-10-19-02`
- **File**: `shop.html:841` (`js/shop.js?v=1`) and `product.html:822` (`js/shop.js?v=2`)
- **Area**: Functional
- **Reproduction**:
  1. `grep -n 'shop.js?v=' shop.html product.html` returns two different versions pointing at the same file.
  2. Both URLs resolve to the same current `js/shop.js` today, so no end-user is broken right now.
  3. Next time anyone edits `js/shop.js` and bumps only one of the two HTML files, users whose browser cached one URL will get an inconsistent shop script across the two pages until the forgotten page is also bumped. The product-detail Add-to-Cart and the grid Add-to-Cart share the same module - divergence here is a real risk.
- **Impact**: Not user-facing today. High probability of a user-facing bug on the next shop.js change if the convention is not corrected. Classic maintainability trap - cheap to fix now, expensive to debug later.
- **Suggested fix**: Align both files to the same version (`?v=2` on both, or bump to `?v=3` on both). Consider documenting in CLAUDE.md that `js/shop.js` is referenced from two pages and both must be bumped together, same way the stylesheet convention is already documented.
