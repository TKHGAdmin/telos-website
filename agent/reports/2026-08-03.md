## BUG-1: Deleting a client orphans the `client_email:` lookup, blocking re-add with the same email

### Severity
P2

### Location
`api/dashboard/clients.js:143-154`, `api/dashboard/clients.js:70-73`

### Summary
The DELETE handler removes the `client:{id}` record and the `clients_index` entry, but never touches the `client_email:{normalized}` lookup that was written when the portal was enabled. The POST handler unconditionally rejects any new client whose normalized email already exists in that lookup. Result: after deleting a client with portal access, that email is permanently blocked from being re-added through the admin UI.

### Reproduction
1. In `/thomas` Clients tab, create client A with `foo@bar.com`.
2. Open Client Portal tab, enable portal for client A. This writes `client_email:foo@bar.com = "<A.id>"` (see `api/dashboard/client-portal.js:115-118`).
3. Return to Clients tab and delete client A. The DELETE handler runs:
   - `DEL client:<A.id>`
   - `ZREM clients_index <A.id>`
   - It does NOT run `DEL client_email:foo@bar.com`.
4. Try to add a new client with the same email `foo@bar.com`. The POST handler executes `GET client_email:foo@bar.com`, sees the stale value `"<A.id>"`, and returns `400 { error: 'Email already in use by another client' }`.

Contrast with `api/dashboard/modules.js:160-186`, which correctly cleans up all secondary indexes on delete.

### Impact
A common real-world scenario: a coach removes a churned client, then that client returns and the coach tries to re-onboard them. The UI hard-blocks re-creation with no recovery path exposed through any admin endpoint. Only manual Redis intervention unblocks it.

### Suggested fix
In the DELETE branch, fetch the client first and delete the email lookup if present:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });
  var raw = await redis('GET', 'client:' + id);
  var promises = [
    redis('DEL', 'client:' + id),
    redis('ZREM', 'clients_index', String(id))
  ];
  if (raw) {
    try {
      var c = JSON.parse(raw);
      if (c.email) {
        var { normalizeEmail } = require('../lib/client-auth');
        promises.push(redis('DEL', 'client_email:' + normalizeEmail(c.email)));
      }
    } catch (e) {}
  }
  await Promise.all(promises);
  return res.status(200).json({ ok: true });
}
```

Also consider clearing `client_push_sub:{id}` and, optionally, the client-scoped log ZSETs.

## BUG-2: Weekly summary email always reports a 0-day streak

### Severity
P2

### Location
`api/cron/weekly-summary.js:86-90`

### Summary
The streak counter in the Monday recap starts at `d = 0` (today, UTC) and breaks the first time a daily log is missing. The cron fires at 2 pm UTC on Monday (9 am ET). At that hour no client has yet logged Monday, so `weekData[0][0].result` is empty, the loop breaks on the first iteration, and every client with a real prior-week streak receives an email claiming "Current Streak: 0 days".

### Reproduction
1. As a client, log every day of the prior week (Mon-Sun).
2. On the following Monday morning, before logging that day, let `weekly-summary` cron fire (or invoke it manually with the `CRON_SECRET` header).
3. Inspect the resulting email body. Line built in `buildWeeklySummary()` renders "Current Streak: 0 days" (from `stats.streak`), even though the actual streak is 7.

Code trace:

```js
// api/cron/weekly-summary.js:87-90
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;                                     // d=0 (today) has no log yet -> break
}                                                 // streak = 0
```

### Impact
Every active portal client with `emailEnabled !== false` receives a weekly recap whose headline "streak" number is almost always 0. This actively misleads the client, undermines the credibility of the recap, and buries whatever real signal the email is meant to convey (avg score, workouts, days logged).

### Suggested fix
Skip today when today is empty, and only break on subsequent gaps:

```js
var startD = (weekData[0][0] && weekData[0][0].result) ? 0 : 1;
for (var d = startD; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

Or compute the streak as the length of the longest suffix of consecutive logged days ending on today or yesterday.

## BUG-3: Retaking the quiz duplicates the API submission (and doubles again on each retake)

### Severity
P2

### Location
`js/quiz.js:221-276` (`setupLeadCapture`), `js/quiz.js:395-412` (retake / view-pricing wiring inside `renderResults`)

### Summary
`setupLeadCapture()` and `renderResults()` both call `addEventListener` on the same DOM buttons every time they run. `resetQuiz()` reverts state and shows the intro but does not remove those listeners, so each retake stacks one more click handler on the "See My Score" submit button, the "Retake" button, and the "View Pricing" button. On the Nth completion after N-1 retakes, submitting the lead form fires N POSTs to `/api/submit-quiz` (and writes to `localStorage` N times).

### Reproduction
1. Load `/` (or `/pricing` overlay). Take the quiz to the lead form. Fill it in. Click "See My Score". Observe one POST to `/api/submit-quiz` in DevTools Network tab.
2. Click "Retake". Complete the quiz again with any answers. Click "See My Score".
3. Observe TWO POSTs to `/api/submit-quiz` with identical payloads in the same tick.
4. Retake once more. Now THREE POSTs per submission.

Relevant lines:

```js
// js/quiz.js:225 - added every time setupLeadCapture() runs
submitBtn.addEventListener('click', function(e) { ... /* POSTs to submit-quiz */ });

// js/quiz.js:397 - added every time renderResults() runs
retakeBtn.addEventListener('click', resetQuiz);

// js/quiz.js:403 - added every time renderResults() runs (pricing page)
viewPricingBtn.addEventListener('click', function() { ... });
```

### Impact
Duplicate lead records land in the `quiz_submissions` ZSET (each entry is a JSON blob, so `ZADD` with the same score+member is deduplicated only if the JSON string is byte-identical, which it usually is not because `submittedAt` differs by a few ms). The dashboard Leads tab shows the same person multiple times, distorting funnel metrics and creating duplicate outreach. Rate limit (10/hr/IP) hides the worst case but not the common 2-3-quiz-retake pattern.

### Suggested fix
Either bind the click handlers once at DOM ready (outside `setupLeadCapture` and `renderResults`) and have those functions only refresh state, or replace the buttons with cloned nodes before attaching, e.g.:

```js
function setupLeadCapture() {
  const form = quizLeadCapture.querySelector('form');
  const oldBtn = quizLeadCapture.querySelector('.quiz-see-score-btn');
  const submitBtn = oldBtn.cloneNode(true);
  oldBtn.parentNode.replaceChild(submitBtn, oldBtn);
  submitBtn.addEventListener('click', function(e) { ... });
}
```

Apply the same treatment to `.quiz-retake-btn` and `.quiz-view-pricing-btn` in `renderResults()`.
