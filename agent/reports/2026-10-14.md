## P1-1 - Admin dashboard login has no rate limiting

- **Location:** `api/dashboard/login.js:1-17`
- **Severity:** P1
- **Category:** Authentication / brute force

**Repro.** POST to `/api/dashboard/login` with any `{password: "..."}` body in a loop. There is no `INCR`/`EXPIRE` guard and no IP-based throttle. `verifyPassword` returns in constant time (good), but nothing caps the attempt rate.

**Impact.** The admin surface is protected by a single shared `DASHBOARD_PASSWORD` secret. With no throttle, an attacker who guesses or discovers the admin URL can run an offline-speed online brute force. A compromise exposes every client's PII, nutrition plans, revenue data, and portal credentials.

**Suggested fix.** Mirror the pattern already in `api/submit-chs-application.js:40-46`: `INCR ratelimit:dash_login:<ip>` with a 15-min window and a low ceiling (e.g. 10 attempts). Add an exponential lockout after N failures. Separately, consider promoting to a per-admin password + 2FA given the single-tenant blast radius.

## P1-2 - Client portal login has no rate limiting

- **Location:** `api/client/login.js:9-60`
- **Severity:** P1
- **Category:** Authentication / brute force

**Repro.** Same as P1-1 against `/api/client/login`. The handler calls `verifyPassword` (PBKDF2, which is intentionally slow server-side, ~100ms per attempt) but nothing limits concurrent attempts across a client pool.

**Impact.** An attacker who scrapes a client's email from leaks or social media (clients often use their public business email) can brute force the password. PBKDF2 slows a single-threaded attack, but concurrent parallel attempts across many client accounts aren't gated. A compromise exposes that client's logs, nutrition data, training program, and side-menu custom content.

**Suggested fix.** `INCR ratelimit:client_login:<ip>` and separately `INCR ratelimit:client_login:<email>` so an attacker can't pivot IPs to bypass per-user caps. 10 attempts per 15 min per key is standard.

## P2-1 - Email enumeration via differentiated client login errors

- **Location:** `api/client/login.js:37, 40, 43` vs `:27, :31, :47`
- **Severity:** P2
- **Category:** Information disclosure

**Repro.** POST `/api/client/login` with `{email: "known-but-disabled@x.com", password: "x"}`. Response: `{"error":"Portal access not enabled"}` or `"Account is not active"` or `"Password not set - contact your coach"`. POST with a non-existent email: `{"error":"Invalid email or password"}`. The attacker now knows which addresses correspond to real clients and in what portal state.

**Impact.** Lets an attacker enumerate the client roster from a public endpoint. Also tells them which clients haven't completed setup - prime phishing targets ("Hi, your coach asked me to help you finish setting up your password...").

**Suggested fix.** Collapse all failure branches to a single generic `{error: "Invalid email or password"}` (401). Log the real reason server-side only. Same pattern that `reset-password.js:24` already uses correctly ("Always return success to prevent email enumeration").

## P2-2 - Rate limits keyed on spoofable client header

- **Location:** `api/submit-chs-application.js:40`, `api/submit-quiz.js:23`, `api/submit-email.js:28`
- **Severity:** P2
- **Category:** Rate limit bypass

**Repro.** POST to any of the three public submit endpoints with header `X-Forwarded-For: 1.2.3.4` (incremented on each call). The handler uses the raw header value as the Redis rate-limit key: `ratelimit:chs:1.2.3.4`. An attacker rotates the header and hits the endpoint indefinitely without ever being throttled.

**Impact.** Floods Redis with junk `chs_application` and `quiz_submissions` entries (each stored as a sorted-set member keyed on timestamp - no dedupe). Each junk application also triggers an `INCR` + `SET` + `ZADD` which costs ~3 Upstash commands per submission. At the Vercel/Upstash free-tier cost per command, this is a cheap denial-of-wallet.

**Suggested fix.** On Vercel, prefer `req.headers['x-vercel-forwarded-for']` which Vercel sets to the client's real IP and is not reflectable from upstream. If falling back to `x-forwarded-for`, split on `,` and take the **last** entry (the one Vercel's edge appended), not the raw string. Also add a per-fingerprint secondary key (e.g. hash of User-Agent + IP).

## P3-1 - Admin session signature compared with `!==` (not timing-safe)

- **Location:** `api/lib/auth.js:27`
- **Severity:** P3
- **Category:** Timing attack / inconsistency

**Repro.** `verifyToken` does `if (signature !== expected) return false;` where both strings are hex-encoded HMAC-SHA256 outputs. JS string equality short-circuits on first mismatched byte, leaking signature-prefix match length in response-time variance. The sibling `api/lib/client-auth.js:46-49` already does this correctly with `crypto.timingSafeEqual` on `Buffer.from(..., 'hex')`.

**Impact.** Low in practice - a network-side attacker would need to average thousands of timed probes against a server with highly variable latency (serverless cold starts, Vercel edge routing) to extract bytes, and even then has to brute force the remaining space. But the fix is one line and the inconsistency between the two files is likely an oversight.

**Suggested fix.** Replace `api/lib/auth.js:27` with:
```js
const sigBuf = Buffer.from(signature, 'hex');
const expBuf = Buffer.from(expected, 'hex');
if (sigBuf.length !== expBuf.length) return false;
if (!crypto.timingSafeEqual(sigBuf, expBuf)) return false;
```

While there, consider the same hardening in `verifyPassword` at `auth.js:52-59` - it's already timing-safe for equal-length inputs, but the length early-return at line 55 leaks password length. For a shared admin password that's a minor concern, but worth tightening.

## Not reported (considered and dismissed)

- **Shopify Storefront token in `js/shop.js:15`.** Shopify Storefront access tokens are explicitly designed to be public client-side credentials. Not a leak.
- **`document.createTextNode` doesn't escape quotes in `client-dashboard.html:1831`.** Technically true, but every call site either uses the escaped output in element text content (safe) or inside an attribute whose dynamic value is server-generated (`custom_<timestamp>_<hex>` ids in `thomas.html:1862`) with no quote chars. No actual XSS path.
- **HTML injection in password-reset email first-name interpolation (`api/client/reset-password.js:58`).** Client names are set exclusively by the admin, not by self-registration. An attacker can't inject their own name field. Low-impact self-pwn.
- **Admin session payload is just `{expires}`.** No admin id is encoded, but there's only one admin, so a session is correctly scoped. HMAC-SHA256 prevents forgery without `SESSION_SECRET`.
