# Bugs

## BUG-20260726-01 — DELETE /api/dashboard/clients orphans `client_email:*` lookup and all per-client Redis data

- **Severity:** P1
- **File(s):** `api/dashboard/clients.js:143-154`
- **Repro:** In the /thomas dashboard, enable the portal for a client (which sets `client_email:{normalized_email} → clientId` in `client-portal.js:114-118`), then delete that client. Try to add a new client with the same email address.
- **Effect:** The new client creation fails at `clients.js:70-73` with `"Email already in use by another client"` because the `client_email:*` reverse-lookup key is never removed. In addition, every derived per-client key survives forever in Redis: `client_dailylog:{id}:*`, `client_dailylogs_index:{id}`, `client_nutrition_plan:{id}`, `client_nutrition_log:{id}:*`, `client_nutrition_logs_index:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_545_goals:{id}`, `client_545_routine:{id}`, `client_545_daily:{id}:*`, `client_545_index:{id}`, `client_training_program:{id}`, `client_training_log:{id}:*`, `client_training_logs_index:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_supplement_log:{id}:*`, `client_supplement_logs_index:{id}`, `client_activity_log:{id}:*`, `client_activity_logs_index:{id}`, `client_push_sub:{id}`. Slow Redis-storage leak plus a hard "can't re-add this email" failure mode.
- **Fix hint:** Before `DEL client:{id}`, load the record; if `portalEnabled && email`, also `DEL client_email:{normalizeEmail(email)}`; then iterate the `_logs_index` ZSETs to `DEL` each date-keyed entry (or accept a soft-delete/status-change convention and remove the DELETE route from the admin UI).

```js
// api/dashboard/clients.js:143-154
if (req.method === 'DELETE') {
  try {
    var id = req.query.id || (req.body && req.body.id);
    if (!id) return res.status(400).json({ error: 'ID required' });
    await redis('DEL', 'client:' + id);
    await redis('ZREM', 'clients_index', String(id));
    return res.status(200).json({ ok: true });
    // no cleanup of client_email:*, no cleanup of any client_* derived key
```

## BUG-20260726-02 — Weekly summary email reports streak = 0 for every client every Monday

- **Severity:** P1
- **File(s):** `api/cron/weekly-summary.js:86-90`
- **Repro:** Cron runs Monday 2pm UTC / 9am ET (`vercel.json` schedule). The streak loop starts at `d = 0` (today) and breaks on the first day without a `client_dailylog:*` entry. At 9am ET Monday, no client has logged Monday's check-in yet, so the loop breaks immediately.
- **Effect:** Every recipient sees `Current Streak: 0 days` (`weekly-summary.js:131`) even when they logged all six prior days. The recap becomes actively demoralizing rather than motivating, and the "streak" number in that email is effectively always noise.
- **Fix hint:** Skip today when it has no log — start counting from `d = 1` when `weekData[0][0].result` is falsy, or walk `ZREVRANGE client_dailylogs_index:{clientId}` and count consecutive dates back from the most recent entry.

```js
// api/cron/weekly-summary.js:86-90
// Count streak (from today backwards)
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;              // ← Monday 9am, d=0 (today) is empty → break at 0
}
```

## BUG-20260726-03 — `/api/client/login` has no rate limit; unlimited password guesses per known email

- **Severity:** P2
- **File(s):** `api/client/login.js:9-59`
- **Repro:** POST to `/api/client/login` with a valid client email and arbitrary passwords in a loop. There is no `INCR ratelimit:*` guard anywhere in the handler (compare `api/submit-quiz.js:22-29` which does throttle by IP).
- **Effect:** An attacker who knows or guesses a client email can grind passwords without server-side throttling. PBKDF2-100k-SHA512 (`client-auth.js:11`) makes each try slow, but this is the client's only login gate, and burning CPU on the Vercel function also has a real dollar cost per attempt. Also no lockout / no signal to the client that guessing is happening.
- **Fix hint:** Mirror the pattern in `submit-quiz.js` — after `verifyPassword` fails, `INCR ratelimit:client-login:{ip}` (and optionally `ratelimit:client-login-email:{normalizedEmail}`) with a 1-hour TTL, reject at 10+.

## BUG-20260726-04 — `/api/client/reset-password` has no rate limit; email-flood + Resend cost amplifier

- **Severity:** P2
- **File(s):** `api/client/reset-password.js:20-67`
- **Repro:** POST `{email: <target>}` to `/api/client/reset-password` repeatedly. Handler always returns `200 ok:true` (correctly, to prevent enumeration), but each portal-enabled email triggers a Resend send with no throttle.
- **Effect:** An attacker can spam any portal-enabled client's inbox with password-reset emails, and each request incurs a Resend billing call. Because the response is uniform whether the email exists or not, a naïve script can hit the endpoint at network line-rate.
- **Fix hint:** `INCR ratelimit:pwreset:{ip}` (1h TTL, cap ~5) before the `if (RESEND_API_KEY)` block. Optionally also `INCR ratelimit:pwreset-email:{normalizedEmail}` inside the "clientId exists" branch so a single victim can't be flooded from many IPs.

## BUG-20260726-05 — `notify.js` push send is not RFC 8291 compliant; will silently fail once VAPID keys are set

- **Severity:** P3
- **File(s):** `api/client/notify.js:47-76`
- **Repro:** Set `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` env vars (per CLAUDE.md, currently optional/unset). Then trigger a push via the admin dashboard.
- **Effect:** The code POSTs a plain JSON body directly to `subscription.endpoint` with no VAPID JWT `Authorization` / `Crypto-Key` headers and no aes128gcm content encryption. FCM, Mozilla Autopush, and Apple Web Push all reject this. Every push will return non-2xx and the handler will swallow it as `{ ok: true, warning: 'Push delivery uncertain' }` (line 75) — the admin gets a green checkmark for a delivery that never happened. Currently masked because the VAPID-keys-missing early-return at line 41-45 short-circuits before the broken code runs. This ships the day someone remembers to set the env vars.
- **Fix hint:** Either add the `web-push` npm dependency and use it (the file even has a comment acknowledging this at line 56), or keep the endpoint in "queued/logged only" mode until real encryption is wired in — remove lines 47-76 so nothing runs when keys are present, and update the response to be explicit about not-yet-sent.
