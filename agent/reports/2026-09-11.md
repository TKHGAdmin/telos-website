## Bug 1 — P1 — "+ Pipeline" button in Leads tab is broken (SyntaxError on click)

**Location:** `thomas.html:2528` inside `loadQuizSubmissions()`.

**What's wrong.** Each row of the Leads → Quiz Submissions table renders a "+ Pipeline" button as:

```js
html += '<td><button class="btn btn-sm btn-gold" onclick="addLeadFromQuiz(' + JSON.stringify(JSON.stringify(s)) + ')">+ Pipeline</button></td>';
```

The outer `JSON.stringify` emits literal `"` characters. When concatenated into `onclick="..."`, the very first inner `"` closes the HTML attribute. The final rendered HTML is:

```html
<button ... onclick="addLeadFromQuiz("{\"name\":\"Test\",...}")">+ Pipeline</button>
```

The `onclick` attribute value the browser stores is just `addLeadFromQuiz(` — an unclosed function call.

**Reproduction.** I loaded the exact concatenation pattern in headless Chromium via Playwright:

```
parsed onclick: "addLeadFromQuiz("
PAGEERROR: Unexpected end of input
result: ERROR: Uncaught SyntaxError: Unexpected end of input
```

The button renders visually but does nothing except throw when clicked. Any admin trying to promote a quiz-submission lead into the pipeline via this shortcut hits a dead button.

**Why it's user-facing.** This is the documented flow for turning quiz leads into pipeline entries. It's been shipped this way for at least the current commit series (no touch since `b9b065a` per git log).

**Suggested fix.** Two options:
1. HTML-encode the outer quotes: replace `JSON.stringify(JSON.stringify(s))` with `'\'' + esc(JSON.stringify(s)).replace(/'/g, '&#39;') + '\''` and wrap the onclick in single quotes. Then `JSON.parse` inside `addLeadFromQuiz`.
2. Attach the handler after render via `.addEventListener`, keyed off a `data-lead-id`. Cleaner and avoids the whole quoting mess.

## Bug 2 — P1 — Rate-limit bypass via spoofable `x-forwarded-for`

**Location:** `api/submit-quiz.js:23`, `api/submit-email.js:28`, `api/submit-chs-application.js:40`.

**What's wrong.** All three public submission endpoints derive the rate-limit key from `x-forwarded-for` first, falling back to `x-real-ip`:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const rateLimitKey = `ratelimit:quiz:${ip}`;
```

On Vercel, clients can send their own `x-forwarded-for` header; Vercel appends the real client IP to it rather than replacing it. So a request with `X-Forwarded-For: aaa` arrives as `aaa, <real-ip>`; a follow-up with `X-Forwarded-For: bbb` arrives as `bbb, <real-ip>`. The full header string is used as the rate-limit key, so each spoofed value gets its own bucket. The 10/hr quiz limit and 5/hr Charleston-application limit are trivially bypassable.

**Impact.** Someone can spam:
- unlimited quiz submissions (fills Redis, pollutes leads dashboard, wastes Resend quota downstream if leads ever autoresponder)
- unlimited email captures on `submit-email` (protein/hyrox tool pages)
- unlimited Charleston applications (fills `chs_applications_index` ZSET, pushes real leads down the page)

Not a data-loss vulnerability, but abuse-facing and cheap to exploit.

**Suggested fix.** On Vercel, `x-real-ip` is always the actual client IP — swap the precedence:

```js
const ip = req.headers['x-real-ip']
        || (req.headers['x-forwarded-for'] || '').split(',').pop().trim()
        || 'unknown';
```

The `.split(',').pop()` fallback picks the last element (which is what Vercel appended) rather than the client-controllable head.

## Bug 3 — P2 — Client login leaks account existence via distinct error messages

**Location:** `api/client/login.js:26-45`.

**What's wrong.** The login endpoint returns five different responses depending on which check fails:
- No such email → `"Invalid email or password"`
- Email exists but no portal enabled → `"Portal access not enabled"`
- Email exists but status ≠ active → `"Account is not active"`
- Email exists but no password set → `"Password not set - contact your coach"`
- Wrong password → `"Invalid email or password"`

An attacker can enumerate which addresses have Telos client accounts by testing emails with any dummy password and reading the response. Given `api/client/reset-password.js` correctly returns `{ok:true}` unconditionally to prevent enumeration, login is inconsistent with the documented posture.

**Impact.** Low — client roster isn't secret, and the exploit is enumeration only, not credential theft. But it does turn public email lists into a list of "these people are Telos clients," which is a small but real privacy leak.

**Suggested fix.** Collapse the four "email valid, other check failed" branches into the same generic `"Invalid email or password"` (401), and only distinguish server-side (log the actual reason for debugging). Optionally: still fast-path a `passwordHash`/`passwordSalt`-missing account so `verifyPassword` isn't called on nothing, but return the same string.
