## P1-01 - Daily engagement cron spams inactive clients every day

**Where:** `api/cron/engagement-check.js`, lines 36-94. Also configured in `vercel.json` at `0 15 * * *` (daily 15 UTC).

**What:**
The cron runs daily. For each active client with `portalEnabled` and email on, it looks at the last 5 days of `client_dailylog:*`. If none exist in days 0-2 (i.e., inactive 3+ days), it sends an "It's been N+ days since your last check-in" email via Resend.

There is **no suppression check**. Nothing records that a reminder was already sent to this client today / this week. So a client who stays inactive for, say, 10 days receives a reminder **every single day from day 3 through day 10 (8 emails)**. From the client's perspective this is nagging that is likely to produce an unsubscribe (or at best, train them to tune out Telos email).

**Why it matters:**
- UX: the reminder loses signal fast and reads as mass-mail / nagging.
- Cost: Resend bills per email; a dozen inactive clients could trigger hundreds of unneeded sends per month.
- Deliverability: repeated non-engaged sends to the same address hurt sender reputation and increase chance of future legitimate emails going to spam.

**Reproduction:**
1. Create a test client, enable portal, verify the account has `emailEnabled !== false`.
2. Do not log for 4+ days.
3. On each of days 3, 4, 5, 6..., observe a new "We miss you at Telos" email arrives after the daily cron runs.

**Suggested fix shape (not applied - read-only agent):**
Record a `client_engagement_sent:{clientId}:{YYYY-MM-DD}` key with a TTL of ~7 days (or stamp `client.lastEngagementEmailAt` on the client record). Before line 77's `fetch`, check that key / field and skip if a reminder went out in the last N days (3-7 is reasonable; one reminder per inactivity streak would be ideal).

## P2-01 - Duplicate client-email guard is a no-op on create

**Where:** `api/dashboard/clients.js` POST handler, lines 59-97 (specifically the check at lines 70-73).

**What:**
On client create the handler does:
```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```
But the handler **never writes** the `client_email:{normalized}` lookup after creating the client (lines 75-92). Grepping the repo confirms the lookup is only populated by:
- `api/dashboard/client-portal.js` line 117 (when portal is enabled)
- `api/dashboard/clients.js` line 131 (when email is changed AND portal is already enabled)

So between "client created" and "portal enabled", the lookup is empty, and the duplicate-email check at line 70 unconditionally passes. Thomas can create two client records with the same email (easy to do by accident when re-importing or when a client re-signs up); the problem is latent until one of them enables portal access.

**Why it matters:**
Admin flow correctness. The field is labeled a duplicate-email guard but doesn't guard. Also compounds P2-02 below: once two records share an email, enabling portal on each will clobber the other's login.

**Reproduction:**
1. In `/thomas` -> Clients, create "Client A" with `test@example.com`.
2. Immediately create "Client B" with the same `test@example.com`.
3. Observe both save successfully; no "Email already in use" error.

**Suggested fix shape:**
After `redis('SET', 'client:' + id, ...)` and `redis('ZADD', 'clients_index', ...)` on lines 90-91, also write `redis('SET', 'client_email:' + normalized, String(id))`. Mirror the DELETE handler to clean the lookup when a client is removed (currently lines 143-154 only delete the client record and index entry, leaving the email lookup orphaned).

## P2-02 - Enabling portal access can silently steal another client's login

**Where:** `api/dashboard/client-portal.js` POST handler, lines 109-124 (specifically the SET at line 117).

**What:**
When the admin enables portal for a client, the code writes:
```js
if (client.portalEnabled && client.email) {
  var email = normalizeEmail(client.email);
  await redis('SET', 'client_email:' + email, String(client.id));
}
```
This SET is unconditional - no check for an existing owner. If a different client already owns that email lookup (either because of P2-01 above, or because the admin fixed a typo by swapping emails between two records, or because a former client was deleted but their lookup wasn't cleaned up), the SET overwrites the previous owner. The previous client's login now resolves to the new client's record on `/api/client/login` (lines 24-25 of `api/client/login.js`), and the previous client is locked out.

Related: the `clients.js` PUT at lines 100-140 does check for an existing owner at lines 124-127 and returns 400 - but that only fires on *email change* and only when `client.portalEnabled` is already true. The initial enable-portal path has no such guard.

**Why it matters:**
Silent data integrity failure. A legitimate admin action (enabling portal access) can lock an existing paying client out of the dashboard, with no error message surfaced in the admin UI.

**Reproduction:**
1. Create Clients A and B with the same email (see P2-01 reproduction).
2. Enable portal access for A, set a password. Confirm A can log in.
3. Enable portal access for B, set a password.
4. Try to log in as A - the session now points to B's client record. A is effectively locked out of their own portal.

**Suggested fix shape:**
Before the SET at line 117, do a GET and reject (`400 'Email already in use by another client'`) if a different client already owns the lookup. Mirror the exact check pattern from `clients.js` lines 124-127.

## Patterns observed (seeded into learnings.md)

- `client_email:*` lookup lifecycle is inconsistent across endpoints: created on portal-enable, deleted on portal-disable, not touched on create, not touched on delete. Any future client-identity work should centralize this.
- All three outbound Resend email paths (`reset-password.js`, `cron/engagement-check.js`, `cron/weekly-summary.js`) interpolate `client.name` into HTML without escaping. Admin-controlled surface today, worth tagging for the security-focus day in case the field ever becomes client-editable.
- Public rate limiters key off raw `req.headers['x-forwarded-for']` with no parsing, which Vercel's chain-prepended value makes trivially bypassable. Flagged in learnings; defer the write-up to the security-focus day.

## Not reported (confidence too low or out of scope)

- `verifyToken` admin HMAC compare uses `!==` not `timingSafeEqual` (`api/lib/auth.js:27`). Technically a timing side-channel but infeasible to exploit against HMAC-SHA256 signatures over HTTPS. Deferring to the security day with an explicit "do not re-flag unless a concrete attack path shows up" note.
- Weekly summary cron uses a rolling 7-day window ending at run time rather than the previous Mon-Sun week. Minor UX / counting oddity; low confidence it's unintentional rather than deliberate "last 7 days".
- Non-cleanup of orphaned `client_dailylog:*` / `client_training_log:*` keys on client DELETE. Storage cost only; not user-visible.
