## Finding 1 - Product detail page shows infinite loading spinner when Shopify SDK fails to initialize

- **ID:** 2026-09-09-1
- **Severity:** P2
- **Category:** Functional (frontend)
- **Files:** `js/shop.js:26,33,71,502-506`, `product.html:752,758`

### What is wrong

`shop.js` defines a single `showEmpty()` helper (lines 502-506) that hides a `#shopLoading` element and shows a `#shopEmpty` element:

```js
function showEmpty() {
  var loading = document.getElementById('shopLoading');
  var empty = document.getElementById('shopEmpty');
  if (loading) loading.style.display = 'none';
  if (empty) empty.style.display = 'block';
}
```

Both `#shopLoading` and `#shopEmpty` exist **only on `shop.html`** (lines 766, 775). The product detail page (`product.html`) has different ids: `#productLoading` and `#productNotFound` (lines 752, 758).

`showEmpty()` is called from three init-time locations, all of which run before the page-specific `loadProductDetail()` handler is reached:

- `shop.js:26` when the Shopify Buy SDK global (`ShopifyBuy`) is undefined - e.g. the CDN script `sdks.shopifycdn.com/js-buy-sdk/v3/latest/index.umd.min.js` is blocked by an ad/tracker blocker or fails to load.
- `shop.js:33` when the config placeholder check trips (not a real failure mode today, but a defensive path).
- `shop.js:71` when any exception is thrown inside the init try block - Shopify checkout create/fetch throwing, `localStorage.setItem` throwing in private-mode Safari, network hiccup.

On `product.html`, every one of these paths silently no-ops (both `getElementById` calls return `null`, both `if (el)` guards fail, nothing changes). The `.product-loading` spinner element (visible by default) keeps spinning indefinitely with no error message, no retry button, no fallback.

### Failure scenario

1. Visitor clicks a product card on `shop.html`, navigating to `product?p=some-handle`.
2. The Shopify Buy SDK script fails to load (common reasons: uBlock Origin's default blocklist includes many Shopify third-party trackers, corporate proxy blocks unknown CDNs, transient network failure, DNS blip).
3. `DOMContentLoaded` fires, `typeof ShopifyBuy === 'undefined'` on `shop.js:24` evaluates true.
4. `showEmpty()` is called - it looks for `#shopLoading` and `#shopEmpty`, neither exists, returns silently.
5. `.product-loading` (present in initial HTML on `product.html:752-755`) never gets `display: none`.
6. User sees a spinning circle with the text "Loading product" forever. No error, no way to recover other than manually navigating away.

Same outcome for any exception inside the init try (line 37-68) - most notably `shopifyClient.checkout.create()` failing.

### Recommended fix

Either (a) make `showEmpty()` handle both pages by hiding whichever loading element exists and showing whichever fallback element exists, or (b) branch at each call site by detecting the page. Minimal patch:

```js
function showEmpty() {
  var loading = document.getElementById('shopLoading') || document.getElementById('productLoading');
  var empty = document.getElementById('shopEmpty') || document.getElementById('productNotFound');
  if (loading) loading.style.display = 'none';
  if (empty) empty.style.display = 'block';
}
```

`#productNotFound`'s copy ("This product may have been removed or the link is incorrect.") is not perfectly right for "SDK failed to load", but it's finite and points the user back to the shop, which is strictly better than an infinite spinner.

### Confidence

High. Confirmed by cross-checking element ids in both HTML files with `Grep`. Reproduces trivially in any browser by blocking `sdks.shopifycdn.com` in DevTools' request-blocking panel, then reloading `product?p=<any handle>`.

## Finding 2 - `/api/client/login` has no rate limiting

- **ID:** 2026-09-09-2
- **Severity:** P2
- **Category:** Security (auth)
- **File:** `api/client/login.js` (whole file, 60 lines)

### What is wrong

The client login handler validates email + password (PBKDF2-SHA512, 100k iterations) and returns a session cookie. There is **no rate limit** anywhere in the file. Compare to every public form endpoint in the codebase:

- `api/submit-quiz.js:22-29` - 10/hr per IP.
- `api/submit-email.js:27-34` - 10/hr per IP.
- `api/submit-chs-application.js:39-46` - 5/hr per IP.

An attacker who knows a client's email address (readily discoverable - clients register through public forms) can:

- Automate login attempts against that email at whatever throughput the PBKDF2 verify allows (~10-30 attempts/sec/IP for 100k-iter SHA-512 on serverless Node) with no server-side throttling.
- Cost the site owner Vercel invocation budget for each attempt.
- Eventually crack weak coach-set initial passwords.

The 100k PBKDF2 rounds slow single-attempt guessing but do not substitute for rate limiting. Coaches also occasionally set predictable initial passwords ("Telos2025!", client's first name + year, etc.) that fall to online guessing well before the hash cost becomes meaningful.

### Failure scenario

1. Attacker discovers a client email via a company staff page, prior data breach, or the public quiz/CHS forms.
2. Attacker runs an online brute-force against `POST /api/client/login` with `{"email":"target@x.com","password":"<guess>"}`, iterating a common-password list.
3. Nothing throttles them. Nothing alerts. Vercel logs the requests but no code path acts on them.
4. On the first hit, they receive `Set-Cookie: telos_client_session=…`, and the client portal is theirs.

### Recommended fix

Mirror the public-form pattern in `login.js` - e.g. a stricter one, keyed on **both** IP and email so a single distributed attacker can't fan out cheaply:

```js
var ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
var ipKey = 'ratelimit:login:ip:' + ip;
var ipCount = await redis('INCR', ipKey);
if (ipCount === 1) await redis('EXPIRE', ipKey, 900); // 15 min window
if (ipCount > 20) return res.status(429).json({ error: 'Too many attempts' });

var emailKey = 'ratelimit:login:email:' + normalizeEmail(body.email);
var emailCount = await redis('INCR', emailKey);
if (emailCount === 1) await redis('EXPIRE', emailKey, 900);
if (emailCount > 10) return res.status(429).json({ error: 'Too many attempts' });
```

Consider also collapsing the four distinct 401 messages (invalid email/password, portal not enabled, account not active, password not set) into a single generic response to eliminate user enumeration on this endpoint.

### Confidence

High. Confirmed by reading the full file and by `Grep` for `ratelimit` under `api/client/` - no matches.

## Finding 3 - `/api/client/reset-password` has no rate limiting

- **ID:** 2026-09-09-3
- **Severity:** P2
- **Category:** Security (abuse / cost)
- **File:** `api/client/reset-password.js:20-68`

### What is wrong

The reset-request branch (case 1 in the handler) sends a transactional email through Resend to any registered, portal-enabled client every time it is called. It correctly returns `{ok: true}` regardless of whether the address is registered (to avoid enumeration), but it has **no rate limit** - not per IP, not per target email, not per token generation.

An attacker or a broken client can:

- Spam the same registered email address with reset messages indefinitely, harassing the recipient and threatening the sender's Resend reputation.
- Rack up Resend API charges (free tier is 3k emails/mo, then paid).
- Race-condition-abuse the `password_reset:<token>` TTL by generating a huge number of live tokens; each is cryptographically random 32-byte hex so guessing them isn't a threat, but the Redis footprint grows.

### Failure scenario

1. Attacker discovers a client email (see Finding 2's discovery vectors).
2. Attacker POSTs `{"email":"target@x.com"}` to `/api/client/reset-password` in a loop from any IP.
3. Target inbox gets flooded. If Resend's abuse detector kicks in, the sending domain (`noreply@telosathleticclub.com`) may be throttled or reputation-damaged, breaking legitimate reset flow for real clients.

### Recommended fix

Same shape as Finding 2 - rate-limit per IP and per target email, before the email is enqueued:

```js
var ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
var ipKey = 'ratelimit:reset:ip:' + ip;
var ipCount = await redis('INCR', ipKey);
if (ipCount === 1) await redis('EXPIRE', ipKey, 3600);
if (ipCount > 5) return res.status(200).json({ ok: true }); // silent drop, preserve enumeration resistance

var emailKey = 'ratelimit:reset:email:' + email;
var emailCount = await redis('INCR', emailKey);
if (emailCount === 1) await redis('EXPIRE', emailKey, 3600);
if (emailCount > 3) return res.status(200).json({ ok: true }); // silent drop
```

Return the same `{ok: true}` on rate-limit hit to preserve the existing "don't leak enumeration" property.

### Confidence

High. Confirmed by full-file read - no `ratelimit`, no INCR guard, no per-target throttle.

## Finding 4 - Admin session HMAC signature comparison is not timing-safe

- **ID:** 2026-09-09-4
- **Severity:** P3
- **Category:** Security (crypto hygiene)
- **File:** `api/lib/auth.js:22-27`

### What is wrong

`verifyToken` compares the received HMAC signature against the recomputed expected signature with a plain string `!==`:

```js
const expected = crypto
  .createHmac('sha256', SESSION_SECRET)
  .update(payload)
  .digest('hex');
if (signature !== expected) return false;
```

The client-auth counterpart (`api/lib/client-auth.js:42-49`) correctly uses `crypto.timingSafeEqual`:

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

Both files were plainly written by the same author (identical structure, identical HMAC construction), so this is a copy-forward miss rather than a deliberate difference.

### Failure scenario

The realistic exploit path here is narrow: an attacker measures response-time variance for `verifyToken` over many requests to infer bytes of a valid signature for their crafted `expires` value. Over the public internet, jitter dominates the tiny timing signal from a 64-hex-byte string compare, and the payload space (a `Date.now()` int) is small enough that many collisions have to happen concurrently. So this is very unlikely to be exploited in practice - but the fix is trivial (three lines, already implemented in the sibling file), and the current asymmetry is the kind of thing a security review will flag anyway.

### Recommended fix

Port the pattern from `client-auth.js:46-49` verbatim:

```js
const a = Buffer.from(signature, 'hex');
const b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return false;
if (!crypto.timingSafeEqual(a, b)) return false;
```

Keep the existing `Date.now() > expires` check afterwards.

### Confidence

High for the code inconsistency; low for real-world exploitability. Included at P3 because the fix is one-line-equivalent and eliminates a class of finding.
