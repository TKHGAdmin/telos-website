## BUG-2026-11-02-01 — Auth endpoints have no rate limiting (P1 / Security)

**Where:** `api/dashboard/login.js`, `api/client/login.js`, `api/client/reset-password.js`

**What:** The three authentication endpoints accept unlimited POST attempts from a single IP. `vercel.json` sets no platform-level limits either. The three public form endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) each use a Redis-backed per-IP `ratelimit:*` counter — so the primitive exists in-repo; it was simply never wired to auth.

**Why it matters:**
- `/api/dashboard/login` protects the entire admin surface (clients, revenue, lead pipeline, Charleston applications). A single `DASHBOARD_PASSWORD` string with no lockout is brute-forceable at serverless throughput.
- `/api/client/login` protects every client's PII (daily logs, body-comp data, nutrition plans).
- `/api/client/reset-password` can be used to flood a client's inbox with reset emails (and burn through the Resend quota) by looping on the "request a reset email" branch.

**Repro:** `curl -X POST https://www.telosathleticclub.com/api/dashboard/login -d '{"password":"guess"}' -H 'Content-Type: application/json'` returns 401 and will do so forever. Public form endpoints under the same deployment return 429 after ~5-10 requests from the same IP.

**Suggested fix:** Reuse the `ratelimit:*` Redis pattern used in `api/submit-*.js`. For login endpoints a conservative budget (e.g. 10/hour/IP for admin login, 20/hour/IP+email for client login) kills brute-force without blocking real users who mistype a password. For reset-password request flow, 5/hour/IP+email.

## BUG-2026-11-02-02 — Client login error messages enable user enumeration (P2 / Security)

**Where:** `api/client/login.js` lines 36-44

**What:** The handler returns four distinct 401 responses depending on account state:
- `"Invalid email or password"` — unknown email
- `"Portal access not enabled"` — email registered, portal disabled
- `"Account is not active"` — email registered, client inactive
- `"Password not set - contact your coach"` — email registered, portal enabled, no password yet

An attacker can enumerate which emails belong to active Telos clients, and even distinguish current/paused/pre-onboarding states, by comparing responses. The companion `api/client/reset-password.js` already does the right thing — line 24 comment: *"Always return success to prevent email enumeration"* — so the inconsistency is clearly an oversight.

**Why it matters:** Low-friction OSINT on who your clients are. For a coaching business where client identity can be sensitive (body-comp, mental health, etc.), this is a privacy issue beyond the generic enumeration concern.

**Suggested fix:** Collapse all four branches to a single generic `"Invalid email or password"` 401. If a specific message is needed for the "password not set" case, surface it only after a successful password check (which can't happen if there's no hash — but at least you've gated on knowing the password).

## BUG-2026-11-02-03 — Admin `verifyToken` uses non-timing-safe signature comparison (P3 / Security)

**Where:** `api/lib/auth.js` line 27

**What:**
```js
if (signature !== expected) return false;
```

The admin cookie signature is checked with plain `!==`. The client version (`api/lib/client-auth.js` lines 46-49) uses `crypto.timingSafeEqual` for the exact same comparison, so the author clearly knew the pattern — it just wasn't applied to the admin path.

**Why it matters:** In theory a remote attacker could use response-time differences to byte-by-byte reconstruct a valid HMAC and forge an admin session without the password. In practice this is extremely hard over the public internet against a serverless function with variable latency — hence P3 — but it's a one-line fix for a well-known footgun and the inconsistency across the two files is worth closing.

**Suggested fix:** Mirror the client-auth pattern:
```js
const sigBuf = Buffer.from(signature, 'hex');
const expBuf = Buffer.from(expected, 'hex');
if (sigBuf.length !== expBuf.length) return false;
if (!crypto.timingSafeEqual(sigBuf, expBuf)) return false;
```
