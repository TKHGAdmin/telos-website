## Summary

## Findings

### [P1] 2026-09-20-01 - Engagement cron re-sends "we miss you" email every day the client stays inactive

- **File:** `api/cron/engagement-check.js:61`
- **Severity:** P1
- **Category:** functional
- **Reproduction:** A portal-enabled active client stops logging on Monday. The daily cron runs Thursday and sends the "It's been 3+ days since your last check-in" email. Nothing writes a "last engagement sent" key. Friday's cron re-reads the same 5-day log window, still finds no logs, sends the identical email. Same again Saturday, Sunday, Monday. Four to five duplicate emails per inactive week per client.
- **Suggested fix:** Track a `client_engagement_sent:{id}` key with a 5-7 day TTL and short-circuit when it exists (or bump a `lastEngagementSentAt` field on the client record and require N days between sends).
- **Confidence:** high

### [P1] 2026-09-20-02 - Deleting a client leaves the email lookup and all portal data behind

- **File:** `api/dashboard/clients.js:143`
- **Severity:** P1
- **Category:** functional
- **Reproduction:** In `/thomas`, create client `foo@x.com` and enable the portal (that sets `client_email:foo@x.com` -> id via `api/dashboard/client-portal.js:117`). Delete the client from the Clients tab. Try to re-create a client with `foo@x.com`: POST at `clients.js:70` sees the stale `client_email:` key and returns "Email already in use by another client" even though no client owns that email. All per-day keys (`client_dailylog:*`, `client_nutrition_log:*`, `client_training_log:*`, `client_545_daily:*`, `client_supplement_log:*`, `client_activity_log:*`) and their ZSET indexes also stay in Redis forever, plus the coach-set plan keys (`client_nutrition_plan:*`, `client_training_program:*`, `client_mindset:*`, `client_resources:*`, `client_sidemenu:*`, `client_supplement_plan:*`, `client_545_goals:*`, `client_545_routine:*`) and any push subscription.
- **Suggested fix:** In the DELETE handler, before removing `client:{id}`, read the client, normalize its email, and issue `DEL client_email:{normalized}`. Then iterate the per-day ZSET indexes for that client and delete each dated key plus the index. Consider grouping with a `redisPipeline` since there are many keys.
- **Confidence:** high

### [P2] 2026-09-20-03 - A module saved with no tier boxes checked becomes inaccessible to every tier, including lifestyle_plus

- **File:** `api/client/module.js:50` (same pattern in `api/client/modules.js:62`)
- **Severity:** P2
- **Category:** functional
- **Reproduction:** In the admin Modules editor, open an existing module and uncheck every tier box, then Save. `api/dashboard/modules.js:124` writes `tierAccess: []` verbatim (the POST path at line 78 defaults to all tiers, but PUT does not). The client dashboard then calls GET `/api/client/module?id=...`. In `module.js:50`, `minTier` starts at 999 and the empty `mod.tierAccess` array leaves it at 999. `clientTierLevel` maxes out at 3 (lifestyle_plus), so `clientTierLevel < 999` is always true and the endpoint returns `403 {error: 'Upgrade required', requiredTier: 'lifestyle_plus'}` even to a lifestyle_plus client. In the module list the same code marks every module `locked: true`.
- **Suggested fix:** In `module.js` and `modules.js`, treat empty or missing `tierAccess` as "all tiers" (set `minTier = 0` when the loop produces nothing). Alternatively, make PUT in `api/dashboard/modules.js:124` reject an empty array or normalize it to the full tier list.
- **Confidence:** high

### [P2] 2026-09-20-04 - Client login has no rate limiting; every other public endpoint does

- **File:** `api/client/login.js`
- **Severity:** P2
- **Category:** security
- **Reproduction:** `api/submit-quiz.js:25`, `api/submit-email.js:30`, and `api/submit-chs-application.js:42` all use `ratelimit:*:{ip}` counters. `api/client/login.js` has no such counter, no captcha, and no lockout on repeated 401s. An attacker who knows a client email can send unbounded parallel POSTs. PBKDF2 100k slows each server response but does not cap throughput per IP. Given the small user set and the 8-character minimum password, this is real exposure.
- **Suggested fix:** Add the same `ratelimit:clientlogin:{ip}` INCR/EXPIRE pattern used by the other submit endpoints (say 20 attempts per 15 minutes per IP), and consider a second counter keyed on the normalized email for account-targeted lockout.
- **Confidence:** high
