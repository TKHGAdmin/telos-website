## BUG-2026-10-26-01 — P1 — Login endpoints have no rate limiting

**Files:**
- `api/dashboard/login.js` (full file)
- `api/client/login.js` (full file)

**Problem:** Both login endpoints accept unlimited password-guess attempts. Compare the submit endpoints (`api/submit-quiz.js:22-29`, `api/submit-email.js:27-34`, `api/submit-chs-application.js:39-46`) which all implement an `INCR` + `EXPIRE` rate-limit pattern against the client IP — the login endpoints omit it.

**Impact:**
- Admin login: `DASHBOARD_PASSWORD` can be brute-forced online. Even a strong password is weaker without a cap; a weak one is defenseless. A compromised admin password hands over every client's PII (email, phone, intake notes, logs) and the ability to send push notifications to clients.
- Client login: An attacker who knows a client's email can brute-force that client's password at line rate. Clients choose their own passwords (minimum 8 chars via `reset-password.js:72`), so weak passwords are plausible.

**Repro steps:**
1. From any IP, `POST /api/dashboard/login` with `{ password: "attempt1" }` → 401.
2. Repeat with different passwords unbounded. No `429` ever returned, no cookie or token required between attempts.
3. Same for `POST /api/client/login` with any known client's email.

**Fix sketch (not applied — read-only agent):**
Add the same `INCR` + `EXPIRE` pattern already used in `submit-quiz.js` to both login handlers, keyed on IP (and ideally also on email for the client login, to prevent a distributed attacker from draining the per-IP budget cheaply). A tight budget like 5 attempts per IP per 15 min is standard for admin logins.

**Severity rationale:** P1 (not P0) because the admin password is server-controlled and presumably strong, and the client-portal data is sensitive but not life-safety. P0 would be reserved for "already breached" or "trivially bypass."

## BUG-2026-10-26-02 — P2 — Admin session HMAC verification is not timing-safe

**File:** `api/lib/auth.js:27`

**Problem:**
```js
if (signature !== expected) return false;
```
Uses JS native string comparison, which short-circuits on first-differing byte. The equivalent client-side helper (`api/lib/client-auth.js:46-49`) uses `crypto.timingSafeEqual`:
```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```
The admin path should match. Separately, `verifyPassword` (`auth.js:55`) performs an early-return on length mismatch *before* `timingSafeEqual`, which leaks the length of `DASHBOARD_PASSWORD` via timing — the length check should happen in constant time or be elided (`timingSafeEqual` already enforces equal length).

**Impact:** Theoretical in practice over the internet (network jitter dominates HMAC-comparison timing by orders of magnitude), but this is a hardening gap on the admin surface, which is the one surface where a token-forgery or password-length oracle would be most harmful. More concretely, it's an **inconsistency** — the client auth got this right, the admin auth didn't. Easy to fix, zero behavioral change.

**Repro steps:** Code review; not externally observable.

**Fix sketch:** Mirror the client-auth pattern:
```js
const expectedBuf = Buffer.from(expected, 'hex');
const signatureBuf = Buffer.from(signature, 'hex');
if (expectedBuf.length !== signatureBuf.length) return false;
if (!crypto.timingSafeEqual(signatureBuf, expectedBuf)) return false;
```
For `verifyPassword`, feed both buffers to `timingSafeEqual` directly and let it reject mismatched lengths without an early return that leaks the password length.

## BUG-2026-10-26-03 — P2 — Product-detail image gallery concatenates Shopify URLs into an `onclick` attribute

**File:** `js/shop.js:166-174`

**Problem:**
```js
imageEl.innerHTML = '<img src="' + allImages[0].src + '" alt="' + escapeHtml(product.title) + '">';

if (allImages.length > 1 && thumbsEl) {
  thumbsEl.innerHTML = allImages.map(function(img, idx) {
    return '<div class="product-thumb' + (idx === 0 ? ' active' : '') + '" onclick="switchProductImage(this, \'' + img.src + '\')">' +
      '<img src="' + img.src + '" alt="Image ' + (idx+1) + '">' +
      '</div>';
  }).join('');
}
```
Two issues on each image URL:
1. **Attribute-value injection:** `img.src` is pasted inside a double-quoted `src="..."` without escaping. A URL containing `"` would break out of the attribute.
2. **JS-string injection:** `img.src` is also pasted inside a single-quoted JS string inside an `onclick="..."` attribute. A URL containing `'` would break out of the JS string and execute arbitrary JS when a user clicked that thumbnail.

**Impact:** Low real-world risk right now — Shopify-generated CDN URLs don't contain quotes under normal use. But the pattern is unsafe-by-construction: if Shopify ever changes URL encoding, if a store admin uploads a file with a crafted name that leaks into a signed URL, or if the API shape expands to include user-controlled fields, this breaks. The product-card builder (`shop.js:273-298`) handles the title/type/description correctly via `escapeHtml` — the gallery renderer is the outlier.

**Repro steps:**
1. In the browser console on `/product?p=some-handle`, monkeypatch `shopifyClient.product.fetchByHandle` to return a product whose first image `.src` is `foo' onerror='alert(1)` (standing in for a hypothetical malicious URL).
2. Observe JS execution when the gallery renders.

**Fix sketch:**
- Build the gallery with `document.createElement('div')` + `img.src = ...` (DOM assignment is safe), or
- Pass the URL into `switchProductImage` via `data-src` and read it off `this.dataset.src` inside the handler, dropping the string-concat entirely.

**Severity rationale:** P2 because today the data source does not practically contain hostile strings, but the construction is XSS-shaped and should be fixed defensively.

## BUG-2026-10-26-04 — P3 — `chs.html` loads `main.js` without a cache-bust version

**File:** `chs.html:1050`

**Problem:**
```html
<script src="js/main.js"></script>
```
Every other public page (`index.html`, `pricing.html`, `privacy.html`, `product.html`, `resources.html`, `shop.html`, `terms.html`) loads `js/main.js?v=2`. `chs.html` loads the bare path. If `main.js` is updated, Charleston-page visitors keep serving the stale cached copy from Vercel/CDN/browser until it naturally expires.

Separately: `shop.html:841` references `js/shop.js?v=1` while `product.html:822` references `js/shop.js?v=2`. The two cache-bust URLs resolve to the same file, so there is no correctness bug today, but the versions should match (or shop.html should be bumped forward) to keep hygiene consistent and avoid double-downloading the same file.

**Impact:** Polish / cache-hygiene gap. Nothing broken today, but on the next `main.js` change, Charleston-page visitors risk a stale JS load until their cache turns over.

**Fix sketch:**
- `chs.html:1050` → `<script src="js/main.js?v=2"></script>`
- `shop.html:841` → `<script src="js/shop.js?v=2"></script>` (match product.html)
