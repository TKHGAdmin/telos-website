# Telos Bug Hunter — 2026-10-08

## Summary
Inaugural run, functional focus. Three bugs confirmed. One is a P0 that silently breaks the entire Charleston (`/chs`) application form on first submit — this has been live since April 2026 and the only visible symptom is that nothing happens when a prospect clicks "Submit Application". The other two are server-side logic bugs: inactive clients get the engagement reminder email every single day (no cooldown), and deleted clients leave an orphan email index that blocks re-adding the same email.

## Findings

### [P0] 20261008-01: Charleston application form silently fails on every submit

**Severity:** P0
**Area:** chs.html (`js` inline in page)
**Status:** new

**What's wrong**
The CHS application form's submit handler reads the "Full Name" input as `form.name.value.trim()`. `name` is a defined IDL attribute on `HTMLFormElement` (it reflects the form's own `<form name="…">` attribute), so `form.name` returns a string, not the input element. The form in `chs.html` has no `name=` attribute, so `form.name` is the empty string `""`. The next access, `.value`, is `undefined`, and `.trim()` on `undefined` throws a `TypeError`. The error fires before the button text ever changes or any fetch runs, so from the user's perspective they click "Submit Application" and nothing happens — no error, no success, no network request. The form has been in this state since the page was deployed on 2026-04-15 (commit `3d87367`). Thomas has very likely been losing every in-person Charleston lead the page produces.

**Where**
- `chs.html:1089` — `name: form.name.value.trim(),` inside the submit handler. All the other sibling fields (`email`, `phone`, `goals`, `history`, `availability`) go through the same `form.<name>` pattern but those names don't collide with native `HTMLFormElement` properties, so they resolve to the named-element getter and work. Only `form.name` is broken.
- `chs.html:991-1029` — the form itself. No `name` attribute on the `<form>` tag, and the Full Name input is `<input id="chs-name" name="name" ...>`.

**Repro / evidence**
1. Open https://www.telosathleticclub.com/chs on any browser.
2. Fill in every field (name, email, phone, goals, history, availability, pick a service).
3. Click **Submit Application**.
4. Open DevTools → Console. You'll see a `TypeError: Cannot read properties of undefined (reading 'trim')` and no POST to `/api/submit-chs-application` in the Network tab.

The relevant snippet:
```js
form.addEventListener('submit', function (e) {
  e.preventDefault();
  statusEl.classList.remove('visible', 'error');

  var data = {
    name: form.name.value.trim(),   // form.name === "" → "".value === undefined → .trim() throws
    email: form.email.value.trim(),  // these work; email/phone/goals/… aren't reserved props
    ...
  };
  // never reached ↓
  if (!data.name || !data.email || ...) { ... }
  submitBtn.disabled = true;
  submitBtn.textContent = 'Sending...';
  fetch('/api/submit-chs-application', ...);
});
```

**Suggested fix**
Switch the one broken access to a form of lookup that doesn't collide with native `HTMLFormElement` properties. The smallest change — one character edit — is:

```js
name: form.elements['name'].value.trim(),
```

(`form.elements` is an `HTMLFormControlsCollection`, which does expose `"name"` via its named getter.) Equivalently, use `document.getElementById('chs-name').value.trim()`. While you're there, consider renaming the input to `name="full_name"` so the pitfall doesn't come back; add a backend alias if you don't want to touch the API payload shape.

### [P2] 20261008-02: Engagement-check cron re-emails inactive clients every day with no cooldown

**Severity:** P2
**Area:** api/cron/engagement-check.js
**Status:** new

**What's wrong**
The daily engagement-check cron (3pm UTC) finds every client whose most recent daily log is ≥ 3 days old and sends a "We miss you at Telos" email. It never records that it already sent one, and nothing on the client record is checked for cooldown. So a client who stops logging in gets this email on day 3, day 4, day 5, day 6, day 7, … once every 24 hours until they log in or Thomas marks them inactive. For a client already feeling bad about falling off, this reads as nagging, and after a few repeats it's a legitimate spam-filter risk for the `telosathleticclub.com` sending domain.

**Where**
- `api/cron/engagement-check.js:61-94` — the whole "send reminder" block. Trigger is `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`, and there is no `client.lastEngagementSentAt` (or equivalent) read or written anywhere in this file or elsewhere in the repo (grep confirmed).
- `vercel.json:24-26` — the cron runs daily (`0 15 * * *`), amplifying the problem.

**Repro / evidence**
Simulate a client whose last daily log is 3 days old and nothing newer. Trigger the cron (or wait a day). Then wait another 24 hours without the client logging in. Trigger it again. Both runs will send `client.email` the identical reminder. There is no state anywhere that could suppress the second send.

The condition in context:
```js
// Send reminder if inactive for 3+ days
if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3) {
  var daysSince = lastLogDaysAgo === -1 ? 5 : lastLogDaysAgo;
  // … builds and sends email …
  // No write to client.lastEngagementSentAt before/after.
}
```

**Suggested fix**
Add a `client.engagementRemindedAt` timestamp. Before sending, skip if `now - engagementRemindedAt < 7 * 86400000` (one email per week is plenty of nagging). After a successful Resend call, update `client.engagementRemindedAt = Date.now()` and `redis('SET', 'client:' + client.id, JSON.stringify(client))`. Reset the timestamp to `null` when a fresh daily log arrives in `api/client/daily-log.js` POST, so re-engagement is noticed the next time the client lapses.

### [P2] 20261008-03: Deleting a client leaves an orphan `client_email:` key that blocks re-adding the same email

**Severity:** P2
**Area:** api/dashboard/clients.js
**Status:** new

**What's wrong**
`DELETE /api/dashboard/clients` removes `client:{id}` and `ZREM`s it from `clients_index`, but it does not remove `client_email:{normalizedEmail}`. For any client whose portal was enabled, that key was created by `client-portal.js` POST and points at the deleted id. The next time an admin tries to re-add a client with the same email, the duplicate check in `clients.js` POST (`existingEmailOwner = await redis('GET', 'client_email:' + normalized)`) finds the stale id and returns 400 "Email already in use by another client" — even though no client with that email actually exists. There is no way to recover from the admin UI short of hitting Redis directly.

**Where**
- `api/dashboard/clients.js:143-154` — DELETE handler. It never calls `redis('DEL', 'client_email:' + …)` and never reads the client first to learn what email to clean up.
- `api/dashboard/clients.js:70-73` — the duplicate-email check that will then falsely reject a re-add.
- `api/dashboard/client-portal.js:115-118` — where the `client_email:` key is written when portal is enabled.

**Repro / evidence**
1. Create a client `alice@example.com` in `/thomas` → Clients.
2. Enable the portal for Alice (sets `client_email:alice@example.com` → id in Redis).
3. Delete Alice from the Clients tab.
4. Try to re-add Alice with the same email. The POST returns `{"error":"Email already in use by another client"}` because the orphan key still exists.

**Suggested fix**
In the DELETE handler, read the client first so you know its email, then clean up the index. Minimal diff:

```js
if (req.method === 'DELETE') {
  var id = req.query.id || (req.body && req.body.id);
  if (!id) return res.status(400).json({ error: 'ID required' });
  var raw = await redis('GET', 'client:' + id);
  if (raw) {
    try {
      var c = JSON.parse(raw);
      if (c.email) {
        var { normalizeEmail } = require('../lib/client-auth');
        await redis('DEL', 'client_email:' + normalizeEmail(c.email));
      }
    } catch (e) {}
  }
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

Optional follow-up: also tear down per-client Redis keys (`client_dailylog:{id}:*`, `client_training_log:{id}:*`, etc.) if you don't want to retain history after deletion — but that's a separate decision; the orphan-email fix stands on its own.
