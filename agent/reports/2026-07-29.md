## Findings

### BUG-2026-07-29-01 — chs.html nav is missing the "Client Login" link

- **Severity**: P2
- **File**: `chs.html`
- **Lines**: 794-800 (desktop nav), 808-814 (mobile menu)
- **Category**: Functional / navigation regression
- **Status**: New

**What's wrong**

The Charleston landing page (`/chs`) is the only public marketing page whose nav omits the "Client Login" link. `CLAUDE.md` states:

> All 28 public pages (5 root + 23 blog) have a "Client Login" link before "Book a Call" in both desktop and mobile navs.

Verified by `grep -L "Client Login" *.html blog/*.html`:
- All 5 other root pages (`index`, `pricing`, `resources`, `protein-calculator`, `hyrox-predictor`, `shop`, `product`) include it.
- All 23 blog pages include it.
- **`chs.html` does not include it — neither in the desktop `.nav-links` list (lines 794-800) nor in the mobile `.mobile-menu` list (lines 808-814).**

**Reproduce**

1. Open `https://www.telosathleticclub.com/chs` on desktop → nav shows Services / Events / The Coach / Online Coaching / Apply. No Client Login.
2. Same page on mobile → hamburger reveals the same items. No Client Login.

**Impact**

An existing coaching client who lands on the Charleston page (via ad, email, or the "Online Coaching" cross-link from the main site → back navigation) has no path to their portal from the nav. They must retype the URL or find the link somewhere else on the marketing site. This is exactly the kind of dead-end the "Client Login link on every public page" convention was set up to prevent.

**Suggested fix**

Add before the Apply CTA in both the desktop `<ul class="nav-links">` and the mobile `<div class="mobile-menu"> <ul>`:

```html
<li><a href="client-dashboard" class="nav-client-login">Client Login</a></li>
```

The `chs.html` custom nav CSS (`.nav-links > li > a`, lines 139-155) will style it consistently with the other items.

### BUG-2026-07-29-02 — Admin session token verification is not timing-safe

- **Severity**: P3
- **File**: `api/lib/auth.js`
- **Line**: 27
- **Category**: Security hygiene / code consistency
- **Status**: New

**What's wrong**

`verifyToken()` in the admin auth library compares the HMAC-SHA256 signature with a plain string `!==`:

```js
if (signature !== expected) return false;
```

The corresponding client-side auth (`api/lib/client-auth.js` lines 46-49) correctly uses `crypto.timingSafeEqual`:

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

The admin token gates the entire `/thomas` dashboard (CRUD on clients, revenue, pipeline, ad spend, etc.) — it's the more sensitive of the two, yet it uses the weaker comparison.

**Impact**

In practice, timing attacks against HMAC-SHA256 hex comparisons over public HTTPS/Vercel Edge are not exploitable — jitter dwarfs the signal, and each guess requires a full round-trip. This is a **code-consistency / hygiene** finding, not an active vulnerability. Worth fixing because:

1. It's a one-liner and matches the pattern already used in `client-auth.js`.
2. If Thomas ever swaps the transport or exposes the endpoint behind a lower-jitter proxy, the theoretical risk becomes marginally more real.
3. Static analyzers flag `!==` on HMAC comparisons as a standard finding — worth pre-empting.

**Suggested fix**

Replace lines 22-27 in `api/lib/auth.js` with:

```js
const expected = crypto
  .createHmac('sha256', SESSION_SECRET)
  .update(payload)
  .digest('hex');
const sigBuf = Buffer.from(signature, 'hex');
const expBuf = Buffer.from(expected, 'hex');
if (sigBuf.length !== expBuf.length) return false;
if (!crypto.timingSafeEqual(sigBuf, expBuf)) return false;
```

Also worth noting for future review: `verifyPassword()` on line 55 short-circuits on `inputStr.length !== expected.length`, which leaks the password length via timing. That's an even smaller theoretical issue, but the same fix pattern applies.

### BUG-2026-07-29-03 — shop.js loaded with mismatched cache-busting versions on shop.html vs product.html

- **Severity**: P3
- **Files**: `shop.html` line 841, `product.html` line 822
- **Category**: Maintenance / stale-cache risk
- **Status**: New

**What's wrong**

Both pages load the same `js/shop.js` file but with different query strings:

- `shop.html:841` → `<script src="js/shop.js?v=1"></script>`
- `product.html:822` → `<script src="js/shop.js?v=2"></script>`

Since these are different URLs from the browser's cache perspective, a returning visitor will fetch `shop.js` twice and store two cached copies. That's harmless today. **The real risk is on the next edit**: if `js/shop.js` changes and only one of the two `?v=` values is bumped, users who visited the page with the un-bumped version will keep getting the stale copy from cache, and the shop cart / product-detail behavior will diverge between the two pages.

The same file was hit by a real bug already (`c1e3162`: `fix: update Shopify Buy SDK to v3 (old CDN was 404)`), suggesting shop.js will keep evolving. The convention (per CLAUDE.md) of a single project-wide `?v=N` on shared assets exists for exactly this reason.

**Reproduce**

```bash
grep -n "shop.js" shop.html product.html
# shop.html:841:  <script src="js/shop.js?v=1"></script>
# product.html:822:  <script src="js/shop.js?v=2"></script>
```

**Impact**

Silent staleness after future edits. No user-visible impact right now.

**Suggested fix**

Bump both pages to the same version (whichever is higher — `?v=2`). Optionally align with the shared `?v=16` used for `style.css`, or standardize on `?v=N` where N tracks the last edit generation.
