### [P1] weekly-summary-streak-always-zero - Weekly summary email always shows "Current Streak: 0 days"

**File:** `api/cron/weekly-summary.js:86-90`
**Category:** correctness

**What's wrong:**
The streak calculation counts consecutive logged days starting from `d = 0` (today, in UTC) and breaks on the first missing day. The cron is scheduled `0 14 * * 1` in `vercel.json` - Monday 14:00 UTC, i.e., 9-10am ET. Very few clients will have submitted their Monday daily-log entry before the cron fires, so `weekData[0][0]` is empty for essentially every recipient and the loop breaks immediately at `d = 0`. Every client receives the email with "Current Streak: 0 days" regardless of how consistent they actually are - a coach-branded email that materially misrepresents each client's progress.

**How to reproduce / failure scenario:**
1. A client has logged their daily check-in every day for the previous 4 Sundays through Saturdays (perfect week).
2. Weekly-summary cron fires Monday 14:00 UTC.
3. Client's Monday log doesn't exist yet (they haven't opened the app).
4. Loop: `d = 0` -> no `weekData[0][0].result` -> break. `streak = 0`.
5. Email body renders "Current Streak: **0 days**" next to "Days Logged: **6 / 7**" (which correctly reflects yesterday-back). The two fields contradict each other and the client's real behavior.

**Suggested fix:**
Start the streak walk from `d = 1` (yesterday), or check whether today has a log first and only include today when it exists. The `avgScore` calculation on the same day-0 slot has a milder version of the same problem - it always includes a zero-scored "today" and drags the average down - so consider excluding day 0 there too, or renaming the metric to reflect the intended window (previous 7 full days).

### [P2] client-delete-orphans-email-lookup - Deleting a client leaves `client_email:` lookup dangling, blocks re-adding same email

**File:** `api/dashboard/clients.js:143-154`
**Category:** data-integrity

**What's wrong:**
`DELETE /api/dashboard/clients` removes `client:{id}` and the `clients_index` ZSET member but does NOT remove the `client_email:{normalizedEmail}` reverse lookup (which is created in `api/dashboard/client-portal.js:117` when the portal is enabled, and updated in `clients.js:130-131` on email change). Grep confirms: no `DEL client_email:` call exists in `clients.js DELETE`. As a result, the lookup key survives after the client is gone and points at a stale ID.

**How to reproduce / failure scenario:**
1. Admin creates client X with email `jane@example.com` and enables their portal -> `client_email:jane@example.com` -> `X`.
2. Admin deletes client X.
3. Admin tries to re-add jane@example.com as a new client (e.g., she re-signs after a break).
4. `clients.js` POST hits the duplicate-email guard at line 70-73 (`existingEmailOwner = GET client_email:jane@example.com` returns stale ID `X`) and refuses with `"Email already in use by another client"`, even though no such client exists in `clients_index` or `client:X`.
5. Recovery requires a direct Redis operation - there is no admin UI for it.

**Suggested fix:**
In the DELETE handler, load the client's record first, `normalizeEmail(client.email)`, and `DEL client_email:{normalizedEmail}`. Same treatment for other per-client sub-keys (`client_dailylog:{id}:*`, `client_nutrition_log:{id}:*`, `client_training_program:{id}`, `client_545_*:{id}`, etc.) would be a good cleanup pass but is a separate issue.

### [P2] reset-password-no-rate-limit - Password reset endpoint has no rate limit; enables inbox flooding and Resend quota burn

**File:** `api/client/reset-password.js` (whole file - no `INCR ratelimit:*` anywhere)
**Category:** abuse-resistance

**What's wrong:**
Public form endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) all rate-limit by IP (5-10/hour). `api/client/reset-password.js` does not - an attacker can hit the "request reset" branch as often as they like. If they know or guess a real client's email, each request triggers a real Resend API call to `client.email`. Consequences:
1. Real clients get flooded with password-reset emails (harassment / phishing enablement - each mail is a valid reset link).
2. Resend usage costs accrue per send.
3. Domain reputation degrades if a target reports the mail as spam.

**How to reproduce / failure scenario:**
1. Attacker knows `jane@example.com` is a Telos client (or guesses from a public source).
2. Script hits `POST /api/client/reset-password` with `{"email": "jane@example.com"}` 1000 times.
3. Server generates 1000 reset tokens, calls Resend 1000 times, Jane receives 1000 emails, each a real reset link (any one of which she could click and be prompted to set a new password, i.e., locked out until she notices).

**Suggested fix:**
Add the same rate-limit pattern used in `submit-*.js`: `INCR ratelimit:reset:{ip}` + `EXPIRE 3600`, cap at 5-10/hour. Consider adding a second per-email cap (`INCR ratelimit:reset-email:{normalizedEmail}`) at 3/hour so a single account can't be flooded from many IPs.

### [P3] reset-password-timing-leaks-email-existence - "Always return 200" email-enumeration defense is defeated by timing side channel

**File:** `api/client/reset-password.js:19-67`
**Category:** security

**What's wrong:**
The comment on line 24 says `"Always return success to prevent email enumeration"`. The response body is indeed identical in all branches, but the code path for a valid email does: (a) an extra `GET client:{id}`, (b) `crypto.randomBytes(32)`, (c) `SETEX password_reset:*`, and (d) `await fetch("https://api.resend.com/emails", ...)`. That outbound HTTP call typically adds 200-1000ms to the response. The unknown-email branch (line 25-27) returns after a single Redis GET. An attacker can distinguish real vs fake emails by measuring response time.

**How to reproduce / failure scenario:**
1. Attacker POSTs `{"email":"real@x.com"}` -> response takes ~800ms (Resend call happens).
2. Attacker POSTs `{"email":"fake@x.com"}` -> response takes ~30ms (early return).
3. Repeat over a candidate list to enumerate valid customer emails.

**Suggested fix:**
Cheapest: kick off the Resend call in the background (don't `await` it) so the response returns immediately in both branches. Better: also add the rate limit from the previous finding so timing-based enumeration is throttled to a useless rate.
