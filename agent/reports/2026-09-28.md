## BUG-2026-09-28-01 · P1 · Deleting a client leaves orphaned `client_email:` mapping, blocking future signups with the same email

**Category:** functional / data-integrity  
**File:** `api/dashboard/clients.js:143-154` (DELETE handler)  
**Related:** `api/dashboard/clients.js:70-73` (POST email-uniqueness check), `api/dashboard/client-portal.js:114-124` (where the mapping is created)

### What's wrong
The DELETE handler only removes two keys:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

But when the client portal was enabled for that client, `client-portal.js:117` wrote a `client_email:{normalizedEmail} -> {clientId}` reverse-lookup. That mapping is never touched on delete, so it lingers forever.

CLAUDE.md lists **17** additional per-client keys/indexes that also leak (`client_dailylog:*`, `client_nutrition_plan:*`, `client_nutrition_log:*`, `client_545_*`, `client_training_*`, `client_mindset:*`, `client_resources:*`, `client_sidemenu:*`, `client_supplement_*`, `client_activity_*`, `client_modules_*`, `client_module_progress:*`), but those are only wasted storage — the email mapping is the one that changes user-visible behavior.

### Reproduction
1. Create client Alice with `alice@example.com`, enable portal (writes `client_email:alice@example.com`).
2. `DELETE /api/dashboard/clients?id=<Alice's id>`.
3. Try to create a new client with `alice@example.com`.
4. POST returns `400 { error: "Email already in use by another client" }` (line 72) — the mapping still points at Alice's now-nonexistent client id.

### Impact
- Coaches cannot recreate a client with the same email after churn/delete without manual Redis surgery. Realistic when a client leaves, returns, or Thomas fixes a data-entry mistake.
- Secondary: password-reset requests for the deleted email hit `reset-password.js:22-27`, resolve to the dead clientId, then silently succeed at line 26 (email-enumeration guard) — no email is sent, but the branch is confusing.

### Suggested fix
Inside the DELETE handler, read the record first, then delete the email lookup (and, ideally, the daily/training/nutrition/545/supplement/activity/module indexes) atomically:

```js
var raw = await redis('GET', 'client:' + id);
var promises = [
  redis('DEL', 'client:' + id),
  redis('ZREM', 'clients_index', String(id)),
];
if (raw) {
  var c = JSON.parse(raw);
  if (c.email) {
    var { normalizeEmail } = require('../lib/client-auth');
    promises.push(redis('DEL', 'client_email:' + normalizeEmail(c.email)));
  }
  // Optionally also DEL/ZREM the per-client indexes listed in CLAUDE.md.
}
await Promise.all(promises);
```

## BUG-2026-09-28-02 · P2 · Weekly summary emails report "0 day streak" for every client who hasn't logged yet Monday morning

**Category:** functional / correctness  
**File:** `api/cron/weekly-summary.js:87-90`

### What's wrong
The streak is computed by walking forward from `d = 0` (today, UTC) and breaking on the first missing daily log:

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

The cron is scheduled for **Monday 2pm UTC (9am ET)** per `CLAUDE.md`. Almost no client has logged their Monday check-in by 9am ET — so `weekData[0][0]` is empty, the loop breaks immediately, and the email says `Current Streak: 0 days`, even for a client with a perfect 6-day Sun–Sat run.

### Reproduction
- Give a test client a daily-log entry for Sun, Sat, Fri, Thu, Wed, Tue (6 days).
- Trigger the cron before that same client's Monday log exists.
- The email body renders `Current Streak: 0 days`.

### Impact
- Every active portal client with `emailEnabled !== false` receives a demotivating "0 day streak" line at the top of their Monday recap. Directly contradicts the app's positioning ("consistency is what drives results") and undermines the value of the daily log.
- Compounds each week: after the first misleading email, clients may distrust the metric.

### Suggested fix
When today's log is missing, start counting from *yesterday* instead of returning 0:

```js
var startIdx = (weekData[0][0] && weekData[0][0].result) ? 0 : 1;
for (var d = startIdx; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

(Same fix pattern is worth applying anywhere the app computes streaks from `todayStr()` — the client-dashboard streak is on the known backlog for the related timezone reason.)

## BUG-2026-09-28-03 · P2 · `daily-log` silently converts legitimate zero values to `null` for water, weight, and steps

**Category:** functional / data-loss  
**File:** `api/client/daily-log.js:74-76`

### What's wrong
```js
if (body.weight !== undefined) log.weight = parseFloat(body.weight) || null;
if (body.water !== undefined) log.water  = parseFloat(body.water)  || null;
if (body.steps !== undefined) log.steps  = parseInt(body.steps, 10) || null;
```

The idiom `parseFloat(x) || null` treats `0` (a valid, meaningful value) as falsy, coercing it to `null`. `water = 0` and `steps = 0` are legitimate honest inputs (client forgot the bottle, took a full rest day). Storing them as `null` conflates "user did not log this field" with "user reported zero," which downstream calculations (nutrition score, activity feed, 7-day trend, coach's dashboard view) then interpret as missing data.

### Reproduction
1. As an authenticated client, `POST /api/client/daily-log` with `{"date":"2026-09-28","water":0,"steps":0}`.
2. GET the same log — response shows `water: null, steps: null`.
3. Expected: `water: 0, steps: 0`.

### Impact
- Silent data loss on the daily check-in. Weekly summary "Days Logged" counts may under-count because helpers likely treat `null` fields as unset.
- Health tracking correctness: a coach reviewing a client who honestly reports "0 water today" cannot distinguish that from "client skipped the field."
- Sleep/energy/stress/mood are safe (lines 70-73 use `Math.max(1, Math.min(5, parseInt(...) || 0))`, and 0 clamps to 1 — a *different* small bug worth noting but scored lower since 0 is out of the 1-5 UI range anyway).

### Suggested fix
Use explicit `Number.isFinite` / `isNaN` checks instead of `||`:

```js
if (body.weight !== undefined) {
  var w = parseFloat(body.weight);
  log.weight = Number.isFinite(w) ? w : null;
}
if (body.water !== undefined) {
  var wa = parseFloat(body.water);
  log.water = Number.isFinite(wa) ? wa : null;
}
if (body.steps !== undefined) {
  var s = parseInt(body.steps, 10);
  log.steps = Number.isFinite(s) ? s : null;
}
```

## BUG-2026-09-28-04 · P3 · Engagement-check cron re-emails the same inactive client every single day

**Category:** functional / UX regression  
**File:** `api/cron/engagement-check.js:60-94`

### What's wrong
The cron runs daily. Its send condition is `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`. There is no "we already sent this client an engagement email in the last N days" throttle. A client who stops logging on Day 0 gets:

| Day | lastLogDaysAgo | Email sent? |
|-----|----------------|-------------|
| 3   | 3              | ✔ "3+ days" |
| 4   | 4              | ✔ "4+ days" |
| 5   | 5              | ✔ "5+ days" |
| 6+  | -1 (fallback)  | ✔ "5+ days" (every day forever) |

### Reproduction
- Any active portal client with `emailEnabled !== false` who stops logging for 4+ days.
- Observe Resend logs (or check inbox) — the same `subject: 'We miss you at Telos'` is sent daily.

### Impact
- Spam-tier UX. Clients on the fence about churning are more likely to unsubscribe or mark as spam, which harms domain reputation for the transactional mailer used by password reset and weekly summary.
- Cron cost inflates linearly with inactivity duration.

### Suggested fix
Add a Redis marker on send with a 7-day TTL:

```js
var throttleKey = 'engagement_sent:' + client.id;
var already = await redis('GET', throttleKey);
if (already) continue;
// … send email …
await redis('SETEX', throttleKey, 7 * 86400, '1');
```

Alternative: only send on days 3, 7, 14 (escalation ladder), then stop.

## BUG-2026-09-28-05 · P3 · `POST /api/client/module-progress` does not check tier access, letting any tier mark higher-tier modules complete

**Category:** functional / authorization gap  
**File:** `api/client/module-progress.js:30-95`  
**Contrast with:** `api/client/module.js:48-61` (correctly enforces `403 Upgrade required`)

### What's wrong
`module.js` (single-module GET) correctly refuses to serve a module the client's tier does not include. `modules.js` (list) marks such modules `locked: true`. But `module-progress.js` POST accepts any `moduleId` in the request body and writes to `client_module_progress:{clientId}:{moduleId}` plus `client_modules_watching:{clientId}` / `client_modules_completed:{clientId}` — no tier gate.

### Reproduction
1. Log in as a `rebuild`-tier client (lowest tier).
2. Discover a lifestyle_plus module id from the frontend (they're shown in the list marked `locked`).
3. `POST /api/client/module-progress` with `{"moduleId": <that id>, "completed": true}`.
4. That module id lands in the client's `client_modules_completed` ZSET. Their completedCount goes up.

### Impact
- Not a data-breach — the module content itself remains behind `module.js`'s 403.
- Corrupts client analytics: `completedCount` in the modules list response and any coach-side progress dashboard reflect completions the client never earned.
- Provides a trivial way to spoof progress in future scoring/leaderboard features.

### Suggested fix
Before writing progress, load the module and check tier:

```js
var modRaw = await redis('GET', 'course_module:' + moduleId);
if (!modRaw) return res.status(404).json({ error: 'Module not found' });
var mod = JSON.parse(modRaw);
var clientRaw = await redis('GET', 'client:' + clientId);
var client = JSON.parse(clientRaw);
var clientLvl = tierLevel(client.tier); // extract to shared helper
var minTier = 999;
(mod.tierAccess || []).forEach(function(t) {
  var l = tierLevel(t);
  if (l < minTier) minTier = l;
});
if (clientLvl < minTier) return res.status(403).json({ error: 'Upgrade required' });
```

Consider moving `tierLevel` into `api/lib/` so `modules.js`, `module.js`, and `module-progress.js` share one implementation.
