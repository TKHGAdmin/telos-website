## Bug 1 — Quiz gate on pricing page can be bypassed with an empty form

- **ID:** 2026-07-13-01
- **Severity:** P2
- **Category:** Functional / lead capture
- **Files:** `js/quiz.js:220-275`, `pricing.html:585-594`, `index.html:571-580`

### What's wrong

The "See Your Score" button that gates the pricing page is a `type="button"`, so the browser's `required` attribute on the name/email/phone inputs is never enforced. The click handler in `quiz.js` calls `e.preventDefault()`, reads the input values without validating them, then unconditionally:

1. Sets `localStorage.telosQuizCompleted = 'true'` (line 247)
2. Fires a fire-and-forget `fetch('/api/submit-quiz')` with `.catch(function(){})` swallowing any 400 response (line 258)
3. Displays the results overlay (line 273)

`pricing.html:971` uses `localStorage.getItem('telosQuizCompleted') === 'true'` to decide whether to hide the overlay. So a single empty click permanently unlocks the pricing page for that browser and no lead is captured server-side (the API rejects the empty payload but the client never sees the rejection).

The exact same flow runs inline on the homepage quiz (`index.html`) — same bug, same file (`quiz.js` shared).

### Repro

1. Open `/pricing` in a browser with no `telosQuizCompleted` in localStorage.
2. Click through the 8 quiz questions (any answers).
3. On the lead-capture screen, leave name/email/phone blank.
4. Click "See Your Score".

**Expected:** browser blocks with "please fill out this field" (or the JS validates), form is not submitted, pricing stays gated.
**Actual:** results overlay shows; pricing content is revealed; refreshing the page shows pricing directly with no gate. `/api/submit-quiz` returns 400 but the client never surfaces or reacts to that.

### Impact

- Defeats the primary purpose of the gate (contact-info capture in exchange for pricing).
- Anyone motivated to see prices without leaving contact info can do so with one click of empty inputs.
- Legitimate leads submitting mistyped/blank forms silently disappear because the fetch failure isn't handled.

### Suggested fix (not applied — read-only agent)

Two options, either is enough:

- **Simplest:** change the button to `type="submit"`, attach the handler to `form.addEventListener('submit', ...)` instead of `submitBtn.addEventListener('click', ...)`, and let the native `required` validation gate the flow. Keep `e.preventDefault()` to prevent navigation.
- **Or:** add explicit validation at the top of the current click handler:
  ```js
  if (!nameInput.value.trim() || !emailInput.value.trim() ||
      !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(emailInput.value.trim())) {
    // show inline error, don't proceed
    return;
  }
  ```
  Only then set `localStorage.telosQuizCompleted` and show results — ideally after the fetch resolves 200, so a network failure doesn't silently unlock the gate either.

### Confidence: High

Traced end to end. Both call sites (homepage inline quiz and pricing overlay) share the same JS module and the same broken button pattern.

## Bug 2 — Quiz option double-tap can double-count points and duplicate the submit handler

- **ID:** 2026-07-13-02
- **Severity:** P3
- **Category:** Functional / edge case
- **File:** `js/quiz.js:178-217`

### What's wrong

After a user clicks a quiz option, the code adds points and sets a 400 ms `setTimeout` before advancing (`handleAnswerSelect`, line 197-218). During that 400 ms window the option buttons are not disabled. A second click — on the same button (mobile double-tap) or on a different option in the same question — fires the handler again, adding a second batch of points.

On the final question (question 7), each of those clicks also queues a call to `setupLeadCapture()` (line 215). `setupLeadCapture` attaches a fresh `submitBtn.addEventListener('click', ...)` every time (line 225) with no de-dup. So two clicks in the 400 ms window on the final question wire two submit handlers, and clicking "See Your Score" submits the quiz twice and shows results twice.

### Repro

1. Complete 7 quiz questions normally.
2. On question 8, click one option, then immediately click a second option before the 400 ms auto-advance fires.
3. Fill out the lead form and click "See Your Score".

**Expected:** one clean submission, one results render.
**Actual:** `POST /api/submit-quiz` fires twice (visible in DevTools Network tab), `renderResults()` runs twice, and the scores include points from both options.

Mobile users are the most exposed here — a nervous tap on a fresh answer button often registers as two clicks.

### Impact

- Two lead records per submission (junk in the pipeline table).
- Distorted quiz scores for some users (a client who accidentally double-taps gets extra points).
- Not user-facing severe, but pollutes analytics and the `/thomas` pipeline.

### Suggested fix

Disable the option buttons the instant one is clicked. In `renderQuestion` (line 176), stash the option nodes; in `handleAnswerSelect` set `optionsContainer.querySelectorAll('.quiz-option').forEach(b => b.disabled = true)` as the first line. Also guard `setupLeadCapture()` against being called twice — e.g. check a `leadCaptureBound` flag before wiring the listener.

### Confidence: High

Reading the code the race is unambiguous; the 400 ms window and lack of disable/guard flag are visible on the page in front of me.
