## Findings

### Finding 1 — P1 — Admin login has no rate limit; unlimited brute-force

**Area:** `api/dashboard/login`
**Severity:** P1
**Status:** new
**ID:** 2026-10-09-01

**What's wrong**
`/api/dashboard/login` validates the posted password against `DASHBOARD_PASSWORD` and returns 401 on mismatch, but applies no rate limit, no lockout, and no CAPTCHA. The same codebase already uses a `redis INCR + EXPIRE 3600` rate-limit pattern on every public form endpoint (`submit-quiz.js`, `submit-email.js`, `submit-chs-application.js`), yet the one endpoint that gates the entire business dashboard — quiz data, client PII, revenue, Charleston applications, email captures — has no such protection.

**Where**
- `api/dashboard/login.js:1-17` — handler body; no `ratelimit:*` INCR anywhere.
- Compare: `api/submit-chs-application.js:40-46`, `api/submit-quiz.js:22-29`, `api/submit-email.js:27-34`.

**Repro / Evidence**
```js
// api/dashboard/login.js — entire handler
module.exports = async function handler(req, res) {
  if (req.method !== 'POST') return res.status(405).json({ error: 'Method not allowed' });
  const { password } = req.body;
  if (!password || !verifyPassword(password)) {
    return res.status(401).json({ error: 'Invalid password' });
  }
  const token = createToken();
  res.setHeader('Set-Cookie', getSessionCookie(token));
  return res.status(200).json({ ok: true });
};
```
A script hitting `POST /api/dashboard/login` with `{"password": "guess"}` in a loop will not be slowed or blocked by anything in this file.

**Impact**
Anyone who knows the `/thomas` URL (public, linked from nav as "Client Login" is distinct — `/thomas` is reachable by anyone who guesses or discovers the route) can run an offline-style dictionary attack online against the admin password. A compromise exposes the entire admin dashboard: quiz leads, email captures, client roster, revenue, Charleston applications.

**Suggested fix**
Mirror the existing pattern used in `submit-chs-application.js:40-46`. Something like:

```js
const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
const key = `ratelimit:dashlogin:${ip}`;
const count = await redis('INCR', key);
if (count === 1) await redis('EXPIRE', key, 3600);
if (count > 10) return res.status(429).json({ error: 'Too many attempts' });
```
Keep the cap tight (5-10 per hour per IP). Optionally also add a global `ratelimit:dashlogin:global` bucket as a backstop against distributed attempts.

**Confidence:** High

### Finding 2 — P1 — Client login has no rate limit; unlimited brute-force on client portal

**Area:** `api/client/login`
**Severity:** P1
**Status:** new
**ID:** 2026-10-09-02

**What's wrong**
`/api/client/login` has the same missing-rate-limit issue as the admin endpoint. It accepts `email + password`, runs PBKDF2 verification, and returns 401 on failure — but nothing stops a caller from issuing thousands of attempts against a known client email. The admin tier has one credential; the client portal has many (every active client), so this is a wider attack surface in terms of accounts that could be compromised.

**Where**
- `api/client/login.js:9-60` — full handler, no `ratelimit:*` INCR.
- `api/client/reset-password.js` should also be checked for the same gap (not read in this run).

**Repro / Evidence**
```js
// Nothing between method check and the pbkdf2 verification throttles attempts.
var email = normalizeEmail(body.email);
var clientId = await redis('GET', 'client_email:' + email);
// ...
if (!verifyPassword(body.password, client.passwordHash, client.passwordSalt)) {
  return res.status(401).json({ error: 'Invalid email or password' });
}
```

Secondary observation (same file): the error strings differentiate failure modes — `"Portal access not enabled"`, `"Account is not active"`, `"Password not set - contact your coach"` all tell an attacker that an email is a real client. Combined with the timing difference between the "email not found" early-return (fast) vs. the valid-email PBKDF2 path (~100ms slower), this is low-cost client-email enumeration.

**Impact**
Any attacker who can enumerate or guess a client email can brute-force that client's password with no throttle. A compromised client portal account exposes the client's logs (sleep, weight, stress, mood, nutrition entries, training logs, 545 goals, notes) and lets the attacker overwrite that data. Also leaks the full roster of client emails via enumeration.

**Suggested fix**
Two changes in `api/client/login.js`:

1. Add the shared rate-limit pattern. Prefer a per-email bucket in addition to per-IP so one attacker can't lock a victim out by hammering their email from varied IPs — but at minimum add per-IP:
   ```js
   const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
   const key = `ratelimit:clientlogin:${ip}`;
   const count = await redis('INCR', key);
   if (count === 1) await redis('EXPIRE', key, 3600);
   if (count > 10) return res.status(429).json({ error: 'Too many attempts' });
   ```
2. Collapse the differentiated error strings. Return a single generic `"Invalid email or password"` for every pre-auth failure (missing client, disabled portal, inactive status, missing password hash, wrong password). Keep the "contact your coach" guidance for the explicit account-management flow, not the login response.

Optionally, to flatten timing, run a dummy PBKDF2 with a fixed salt on the "email not found" branch so response times don't partition into two populations. (Low priority once rate limit is in place.)

Mirror both changes in `api/client/reset-password.js` after reviewing it.

**Confidence:** High

### Finding 3 — P2 — Admin session HMAC verification uses non-timing-safe comparison

**Area:** `api/lib/auth.js`
**Severity:** P2
**Status:** new
**ID:** 2026-10-09-03

**What's wrong**
`verifyToken` in `api/lib/auth.js` compares the submitted session-cookie signature to the expected HMAC with `!==`, which short-circuits on the first byte mismatch. The equivalent function in `api/lib/client-auth.js` (newer code) already does this correctly with `crypto.timingSafeEqual` and the explicit length check. The admin version was never brought up to parity.

**Where**
- `api/lib/auth.js:18-31` — `verifyToken`.
- Compare: `api/lib/client-auth.js:34-52` — `verifyClientToken` does it correctly.

**Repro / Evidence**
```js
// api/lib/auth.js:23-27  (admin — NOT timing-safe)
const expected = crypto
  .createHmac('sha256', SESSION_SECRET)
  .update(payload)
  .digest('hex');
if (signature !== expected) return false;
```

```js
// api/lib/client-auth.js:42-49  (client — timing-safe, the pattern to adopt)
var expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

**Impact**
Theoretical only — forging an admin session HMAC via timing side-channel over the public internet is impractical because network jitter dominates per-byte timing differences. Still, this is an inconsistency with the newer, hardened pattern in `client-auth.js`, and the fix is three lines. Also note that the admin password check in the same file (`verifyPassword`, line 55) short-circuits on `inputStr.length !== expected.length`, which leaks the exact admin-password length via response timing — same class of issue, same cheap fix.

**Suggested fix**
In `api/lib/auth.js`, mirror the hex-decode + length-check + `timingSafeEqual` pattern used in `client-auth.js:42-49` inside `verifyToken`. In the same file, drop the length-based short-circuit in `verifyPassword` and compare the two buffers with `timingSafeEqual` after padding or hashing both sides to a common length (one approach: hash both inputs through `crypto.createHash('sha256')` then `timingSafeEqual` on the digest buffers).

**Confidence:** High
