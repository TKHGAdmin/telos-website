## BUG-2026-11-01-01 - P1 - Daily engagement cron spams clients inactive 3+ days

**File**: `api/cron/engagement-check.js:61-94`
**Focus**: Functional

### Repro
1. Enable the portal for a client, mark them `active`, don't set `emailEnabled: false`.
2. Let them skip daily check-ins for 3 days.
3. Vercel's cron hits `/api/cron/engagement-check` daily at 15:00 UTC.
4. Every day thereafter, the client receives an "It's been N+ days since your last check-in" email. Day 3 → email. Day 4 → email. Day 5 → email. Day 10 → email. The cron has no state tracking "last engagement email sent", no cooldown, and the "inactive" branch (line 61) also matches `lastLogDaysAgo === -1`, so it keeps sending even after the 5-day lookback window is exceeded.

### Why it matters
A client who disengages for a week gets 5+ identical reminder emails. That's spam, reads as desperate, and in Resend/Gmail terms it damages sender reputation. The template subject ("We miss you at Telos") also looks worse on each repeat.

### Suggested fix
Before sending, read `client_last_engagement_email:{clientId}` from Redis. If it's less than ~5 days old, skip. After sending, `SETEX` it to a week. One extra round-trip per inactive client, same email volume ceiling as weekly-summary.

## BUG-2026-11-01-02 - P1 - Weekly summary reports streak = 0 for clients who logged every day except today

**File**: `api/cron/weekly-summary.js:87-90`
**Focus**: Functional

### Repro
1. Enable the portal for a client, give them a 6-day streak (daily check-ins Sun through Fri).
2. Monday 09:00 ET (14:00 UTC) the weekly-summary cron fires. At that moment, the client has not yet done today's check-in.
3. The streak loop starts at `d = 0` (today), finds no log, breaks immediately, reports `streak = 0`.
4. The email shows "Current Streak: 0 days" even though the client is on a 6-day streak.

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

### Why it matters
The weekly recap is the one touchpoint most clients will see. It's supposed to reinforce consistency. Today, it tells 100% of consistent-but-haven't-checked-in-yet-this-morning clients their streak is zero. The dashboard separately shows the "correct" streak, so the client sees a direct contradiction between the two surfaces.

### Suggested fix
Start the streak loop at `d = 1` (yesterday) when today's log is missing, OR count from the first day with a log and stop at the first gap.

```js
var startD = (weekData[0][0] && weekData[0][0].result) ? 0 : 1;
for (var d = startD; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

## BUG-2026-11-01-03 - P2 - Password reset endpoint has no rate limit; attacker can spam reset emails to any client

**File**: `api/client/reset-password.js:20-67`
**Focus**: Functional (adjacent to Security but mechanism is functional)

### Repro
1. Attacker learns a client email address (e.g. from a public testimonial, a referral, LinkedIn).
2. Attacker POSTs `{"email": "victim@example.com"}` to `/api/client/reset-password` repeatedly, from one or many IPs.
3. Each request issues a Resend API call sending a "Reset your Telos password" email to the victim.
4. The endpoint has no per-IP, per-email, or per-client rate limit. No cooldown between resets. Compare with `submit-chs-application.js:40-46` which rate-limits 5/hour per IP.

### Why it matters
Email-bomb vector: hundreds of password-reset emails arrive in a victim's inbox over minutes. Secondary damage: Resend quota and sender-reputation hit; Thomas may be charged per email over quota.

The endpoint is already careful about enumeration (returns 200 regardless of whether the email exists), which is good — but the Resend call still fires on real matches, so the attacker learns which addresses are clients by timing the response if they're patient.

### Suggested fix
Rate-limit the request-reset branch: `ratelimit:reset:{normalizedEmail}` + `ratelimit:reset:ip:{ip}`. 3 requests per hour per email, 10 per IP. Mirror the `submit-chs-application.js` pattern.

## BUG-2026-11-01-04 - P2 - `POST /api/dashboard/clients` can create duplicate-email clients; later portal enable silently hijacks the earlier client's login

**File**: `api/dashboard/clients.js:60-97` and `api/dashboard/client-portal.js:114-118`
**Focus**: Functional

### Repro
1. Admin creates client A with email `jane@example.com`. `clients.js` POST does NOT write `client_email:{normalized}`; that key is only written when the portal is enabled (in `client-portal.js:117` via `redis('SET', ...)`).
2. Admin enables portal for A → `client_email:jane@example.com` now points to A's id. A logs in fine.
3. Admin creates client B, also with email `jane@example.com`. The duplicate check in `clients.js:70-73` looks up `client_email:jane@example.com`, which exists → check RETURNS error "Email already in use". Good.
4. BUT: step 2 is required for the check to fire. If the admin creates A and B *before* enabling the portal for either (common for a batch intake), both records are created, no key is written, no error. Then the admin enables portal for A, then for B. The B enable (`client-portal.js:117` is an unconditional `SET`) overwrites the `client_email` key to point at B. A can no longer log in - their email now routes to B.
5. From A's point of view: "I set my password last week, now login says invalid credentials." From the admin's point of view: no error was ever raised; data looks fine in both client records.

### Why it matters
Silent client-login takeover. A real possibility whenever Thomas imports or sets up more than one client in a batch and either (a) types the wrong email on one of them, or (b) the same email is submitted twice via the quiz / consult flows and converted.

### Suggested fix
Two changes:
- In `clients.js` POST (after line 73): if a POST with no portalEnabled is allowed, still check for `client_email` duplicates AND also scan `clients_index` for an existing client with the same normalized email. OR: refuse to create a client with an email that any existing client already has.
- In `client-portal.js:117`: before `SET`, check if the key exists and points to a different client id. If so, return 409.
