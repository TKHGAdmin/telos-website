## BUG-2026-09-24-001 — P1 — Engagement-check cron re-sends "we miss you" email every single day

**Where:** `api/cron/engagement-check.js:61`

**What breaks:**
The daily engagement cron finds clients whose last daily log is 3+ days old and sends a reminder email. It never records that it sent one — no `lastEngagementEmailAt`, no per-client cooldown key — so the *same* client gets the *same* reminder email again the next day, and every day after, until they log in.

The look-back window is only 5 days (`for (var d = 0; d < 5; d++)` on line 45). Any client inactive for **6+ days has `lastLogDaysAgo === -1` forever**, so churned/paused clients receive the "we miss you" email indefinitely.

**Reproduce:**
1. Active client stops logging on Monday.
2. Thursday's cron fires → client gets email #1 ("3+ days inactive").
3. Friday's cron fires → same client gets email #2.
4. Saturday's cron fires → same client gets email #3.
5. …every day until they log or leave.

**Impact:** Deliverability damage (Resend spam complaints, sender reputation), churn acceleration (annoyed clients unsubscribe or mark as spam), inbox trust loss. Directly harms retention — the opposite of what this cron is supposed to do.

**Fix sketch:** On send, `SETEX engagement_sent:{clientId} 86400*3 1`. Skip clients with that key set. Or store `lastEngagementEmailAt` on the client record and gate on `>= 72h` since last send.

## BUG-2026-09-24-002 — P1 — Deleting a client leaves orphan data and blocks re-adding the same email

**Where:** `api/dashboard/clients.js:143-154` (DELETE handler)

**What breaks:**
```js
if (req.method === 'DELETE') {
  ...
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  return res.status(200).json({ ok: true });
}
```

The handler removes only the client record and index entry. It leaves behind:

- `client_email:{normalizedEmail}` → still points to deleted id
- `client_dailylog:{id}:{date}` and its ZSET index
- `client_nutrition_log:{id}:{date}`, `client_nutrition_plan:{id}`
- `client_training_log:{id}:{date}`, `client_training_program:{id}`
- `client_545_goals:{id}`, `client_545_routine:{id}`, `client_545_daily:{id}:{date}`, `client_545_index:{id}`
- `client_supplement_plan:{id}`, `client_supplement_log:{id}:{date}`
- `client_activity_log:{id}:{date}`
- `client_mindset:{id}`, `client_resources:{id}`, `client_sidemenu:{id}`
- `client_push_sub:{id}`

**Reproduce (the workflow-breaking part):**
1. Coach creates client "sarah@example.com" and enables portal → `client_email:sarah@example.com → 42` is set.
2. Client cancels; coach deletes them from `/thomas` Clients tab.
3. Sarah returns three months later. Coach tries to re-create her → `POST /api/dashboard/clients` hits the check at `clients.js:70`:
   ```js
   var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
   if (existingEmailOwner) return res.status(400).json({ error: 'Email already in use by another client' });
   ```
   `existingEmailOwner === "42"` (the deleted id). Creation is refused with a misleading "already in use" message. Coach has to manually delete the Redis key.

**Impact:**
- **Business workflow blocker:** returning clients cannot be re-added without Redis surgery.
- **Data accumulation:** every deleted client permanently retains all their daily logs, meals, training history, etc. Upstash Redis is billed on data size — this grows without bound.
- **Compliance:** any GDPR/CCPA "delete my data" request Thomas honors via the admin UI actually leaves the client's records intact.

**Fix sketch:** In the DELETE handler, before `DEL client:{id}`:
1. Read the client, `DEL client_email:{normalizeEmail(client.email)}` if present.
2. Read `client_dailylogs_index:{id}` → for each date, DEL the corresponding log key; then DEL the index. Repeat for nutrition, training, 545, activity, supplement.
3. DEL scalar keys: `client_nutrition_plan`, `client_mindset`, `client_resources`, `client_training_program`, `client_sidemenu`, `client_supplement_plan`, `client_545_goals`, `client_545_routine`, `client_push_sub`.
Consider a `redisPipeline` to keep it one round-trip.

## BUG-2026-09-24-003 — P2 — New-client email uniqueness check is only enforced after someone enables portal

**Where:** `api/dashboard/clients.js:68-73` (POST create) vs. `api/dashboard/client-portal.js:110-118` (portal enable)

**What breaks:**
Two independent bugs meet in the middle:

1. `clients.js` POST (create) *reads* `client_email:{normalized}` to guard duplicates but **never writes it**. Only `client-portal.js` writes that mapping, and only when portal is enabled.
2. `client-portal.js` POST does `SET client_email:{email} → clientId` (line 117) **without checking whether another client already owns that mapping**.

**Reproduce:**
1. Coach creates client A (`alice@x.com`, id=10), portal disabled → `client_email:alice@x.com` is **not set**.
2. Coach creates client B by mistake (`alice@x.com`, id=11), portal disabled → the check at line 70 finds nothing, so creation succeeds. Two clients now share an email.
3. Coach enables portal for A → `client_email:alice@x.com → 10`. A can log in.
4. Coach later enables portal for B (thinking it's a different client) → `client_email:alice@x.com → 11`, overwritten silently. **A can no longer log in** (their email now maps to B's password hash).

**Impact:**
- Silent lockout: A hits "Invalid email or password" with no diagnostic. Debugging requires Redis inspection.
- Data-integrity blind spot: two client records exist with the same login identity; whoever enabled portal last wins.
- The portal-enable step is a stealth uniqueness-enforcer with no error surface, so the mistake compounds instead of getting rejected at input time.

**Fix sketch:**
- In `clients.js` POST: also `SET client_email:{normalized} → id` on successful create, so the uniqueness gate works from creation onward. Delete the mapping in DELETE (see BUG-002) and on email-change.
- In `client-portal.js` POST: before `SET client_email:...`, check if the key already exists with a different `clientId` and refuse with a clear 400. Same treatment when disabling then re-enabling under a changed email.
