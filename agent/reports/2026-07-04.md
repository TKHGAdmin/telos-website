## Bugs

### BUG-1 - P2 - shop.js loaded with mismatched cache-busting versions on shop and product pages

- **File(s):** shop.html, product.html
- **Location:** shop.html:841, product.html:822
- **What's wrong:** Both pages source the same file `js/shop.js`, but with different query-string versions. `shop.html:841` references `js/shop.js?v=1` while `product.html:822` references `js/shop.js?v=2`. The two URLs are distinct cache keys pointing at the same file. If a future edit to shop.js only bumps one of them, the browser will happily hold two divergent cached copies of the cart/checkout logic (old on one page, new on the other) as the user navigates between shop and product. That state split is hard to diagnose in the field because Shopify checkout IDs live in localStorage across pages.
- **Repro / evidence:**
  ```
  shop.html:840-841
    <script src="https://sdks.shopifycdn.com/js-buy-sdk/v3/latest/index.umd.min.js"></script>
    <script src="js/shop.js?v=1"></script>

  product.html:821-822
    <script src="https://sdks.shopifycdn.com/js-buy-sdk/v3/latest/index.umd.min.js"></script>
    <script src="js/shop.js?v=2"></script>
  ```
- **Impact:** Any user who visits both shop.html and product.html across a deploy that touches shop.js can end up with mismatched JS between the two tabs. Symptoms would look like cart totals, add-to-cart handlers, or the Escape-to-close cart behavior working on one page and not the other. Silent to logs.
- **Suggested fix:** Pick one version (e.g. `?v=2`) and use it in both files. Long-term, adopt the same convention CSS already uses ("all pages get bumped together") and document it in CLAUDE.md next to the CSS versioning rule.

### BUG-2 - P3 - Mobile nav has no way to reach Resources or FAQ from pricing, shop, product, resources, or chs pages

- **File(s):** pricing.html, shop.html, product.html, resources.html, chs.html
- **Location:** pricing.html:533-543, shop.html:703-719, product.html mobile-menu block, resources.html:294-304, chs.html:807-816
- **What's wrong:** Commit 9319f9d ("refactor: move Resources and FAQ into Tools dropdown") added Resources and FAQ under the desktop Tools dropdown on the affected pages but did NOT put them under an equivalent mobile Tools group. The result: on mobile (hamburger menu) on those five pages there is no path to `/resources` or `/#faq` at all. Only index.html got a real Tools dropdown on mobile; protein-calculator.html and hyrox-predictor.html still expose Resources as a flat mobile link but not FAQ. chs.html's custom hotel-style nav omits both intentionally, but is now the only path to those on mobile if a user lands there first.
- **Repro / evidence:**
  ```
  # audited via
  grep -A 30 '<div class="mobile-menu">' <page> | grep -E "resources|Resources|faq|FAQ"

  index.html                → resources + FAQ present
  protein-calculator.html   → resources present, FAQ missing
  hyrox-predictor.html      → resources present, FAQ missing
  pricing.html              → both missing
  shop.html                 → both missing
  product.html              → both missing
  resources.html            → both missing (self-page is at least on resources)
  chs.html                  → both missing (custom nav)
  ```
- **Impact:** Mobile users on any of those pages who want the FAQ or the blog hub have to bounce back to homepage first. Not catastrophic (Resources is reachable from footer on some pages, FAQ is in-page on index), but it's a nav dead-end that shows up as a bounce, not an error.
- **Suggested fix:** Add a mobile Tools dropdown (mirroring the desktop dropdown) to the shared mobile-menu template across pricing, shop, product, resources, and consider whether chs.html should include a "More from Telos" section on mobile. As a minimum patch, add `<li><a href="resources">Resources</a></li>` and `<li><a href="index.html#faq">FAQ</a></li>` inline in each affected mobile menu.

### BUG-3 - P3 - product.html serves generic static SEO for every product; social share previews are identical regardless of product

- **File(s):** product.html
- **Location:** product.html:1-19
- **What's wrong:** The product detail page is fully JS-rendered against the Shopify Buy SDK, but the static HTML head has:
  - Hardcoded `<title>Product - Telos Athletic Club</title>`
  - Generic `meta[name=description]` that never mentions the product
  - No Open Graph tags (og:title, og:description, og:image, og:url, og:type)
  - No Twitter card tags
  - No canonical link
  - No Product / Offer structured data (compare shop.html, which does have @type: Store schema)

  Search bots and social scrapers that don't run JS see the same head for every `?p=xxx`. Twitter, LinkedIn, iMessage, and most link-unfurlers fall in this bucket.
- **Repro / evidence:**
  ```
  product.html:6-7
    <title>Product - Telos Athletic Club</title>
    <meta name="description" content="Premium training guides, nutrition templates, and performance resources from Telos Athletic Club.">
  ```
  No og:, twitter:, link[rel=canonical], or application/ld+json anywhere in the head.
- **Impact:** Every product link shared to social media or messaging previews as the same generic tile. In-Shopify checkout still works fine, but organic and shared-link discovery is degraded — the shop reads as an unfinished page from the outside.
- **Suggested fix:** Either server-render product metadata (would require moving product.html off pure static to a Vercel function or adding a lightweight `[...handle].js` rewrite that hydrates the head), or as a quick patch, use the Shopify Storefront API at build time / via a small serverless function to generate a per-product static shell with proper og:title, og:image, canonical, and a Product+Offer JSON-LD block. Even a client-side patch to update `document.title` + inject og: meta on load closes the gap for JS-capable scrapers.
