# Telos Bug Hunter Report - 2026-06-06

## Summary

Functional sweep across the quiz lead-capture flow, public submit endpoints, auth libs, and the two cron jobs. Two real defects found, both P2: a duplicate-submission bug in the Execution Score Quiz when a user retakes it, and an unthrottled engagement-reminder cron that emails inactive clients every single day until they log back in. Both are reproducible from code alone.

## Bug 1 - Quiz retake double-submits to /api/submit-quiz (and N-submits after N retakes)

- **Severity:** P2
- **Area:** `js/quiz.js`
- **First seen:** 2026-06-06

### What's wrong

`setupLeadCapture()` and `renderResults()` both attach event listeners to long-lived DOM elements (`.quiz-see-score-btn` and `.quiz-retake-btn`) without ever removing prior listeners. Each retake re-runs these functions, so listeners accumulate on the same buttons.

Practical effect: the first run posts once to `/api/submit-quiz`. After one retake, clicking "See Your Score" fires two listeners and posts twice. After two retakes, three times. The dashboard sees duplicate quiz submissions for the same lead, and the Redis ZSET `quiz_submissions` stores each duplicate as a separate member (each post has a unique `submittedAt` timestamp, so dedup does not happen). It also burns through the 10-per-hour IP rate limit faster than intended.

### How to reproduce

1. Open `index.html` or `pricing.html`.
2. Take the quiz, fill name/email/phone, click "See Your Score" - one POST to `/api/submit-quiz` lands in Redis.
3. Click "Retake Assessment", run the quiz again, click "See Your Score" - two identical POSTs land in Redis (one duplicate lead).
4. Each subsequent retake adds another duplicate.

Code references:

- `js/quiz.js:225` - `submitBtn.addEventListener('click', function(e) { ... })` inside `setupLeadCapture()`, which is called from `handleAnswerSelect` (line 215) on every traversal of the final question.
- `js/quiz.js:397` - `retakeBtn.addEventListener('click', resetQuiz)` inside `renderResults()`, called once per results render. Less harmful (resetQuiz is idempotent) but the same leak pattern.

### Suggested fix

Either attach the listeners once at module init (outside `setupLeadCapture`/`renderResults`), or guard against double-binding. The smallest local fix: clone-and-replace the button to wipe prior listeners before binding, e.g.

```js
const oldBtn = quizLeadCapture.querySelector('.quiz-see-score-btn');
const submitBtn = oldBtn.cloneNode(true);
oldBtn.parentNode.replaceChild(submitBtn, oldBtn);
submitBtn.addEventListener('click', ...);
```

Same treatment for `.quiz-retake-btn` inside `renderResults()`.

## Bug 2 - Engagement-check cron emails inactive clients every day with no cooldown

- **Severity:** P2
- **Area:** `api/cron/engagement-check.js`
- **First seen:** 2026-06-06

### What's wrong

The cron runs daily (`0 15 * * *` in `vercel.json`). It flags any portal-enabled active client whose most recent `client_dailylog:*` is 3+ days old, and sends a "We miss you at Telos" email via Resend. There is no record of having already sent an email - no `engagement_last_sent:{clientId}` key, no cooldown check.

Result: a client who stops logging in for a week receives a reminder email on day 3, day 4, day 5, day 6, and day 7. That is exactly the kind of behavior that triggers spam reports / unsubscribes from a small, premium B2C list. This is a real product defect for a high-touch coaching brand whose entire pitch is "we don't nag".

### How to reproduce

Code trace, `api/cron/engagement-check.js:36-94`:

1. Loop walks every active, portalEnabled, emailEnabled client.
2. Probes the last 5 days of `client_dailylog:{id}:{date}` keys.
3. If the most recent log is 3+ days old (or no log in 5 days), it sends the reminder unconditionally.
4. No write back to Redis tracking the send. Next day's run repeats the same decision tree for the same client.

For a client whose last log was on day 0, the cron sends on day 3 and every subsequent day until they log again.

### Suggested fix

Track the most recent send and gate on a cooldown (e.g. 4-7 days):

```js
var lastSent = await redis('GET', 'engagement_last_sent:' + client.id);
if (lastSent && (now - parseInt(lastSent, 10)) < 4 * 86400000) continue;
// ... send ...
await redis('SET', 'engagement_last_sent:' + client.id, String(now));
```

Cooldown of 4 days means a client gets at most one reminder per inactivity window, with a follow-up only if they remain dark. Pair with a hard cap (e.g. max 2 reminders per 30 days) if Thomas wants to be extra cautious.
