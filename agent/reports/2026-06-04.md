## Findings

### BUG-20260604-01 — Quiz retake re-binds click handlers, causing duplicate submissions

- **Severity:** P2
- **Area:** `js/quiz.js`
- **Reproducible:** Yes
- **First seen:** today

**What's wrong:**
`setupLeadCapture()` and `renderResults()` attach `click` listeners every time they run, without first removing prior ones. The Retake button calls `resetQuiz()`, which only resets state — the listeners on `submitBtn`, `retakeBtn`, and `viewPricingBtn` survive. After N retakes, the same submit click fires the handler N times, posting N copies of the same lead to `/api/submit-quiz` and writing `telosQuizData` to localStorage N times.

**Evidence:**
```
js/quiz.js:225  submitBtn.addEventListener('click', function(e) { ... fetch('/api/submit-quiz', ...) })
js/quiz.js:397  retakeBtn.addEventListener('click', resetQuiz);
js/quiz.js:403  viewPricingBtn.addEventListener('click', function() { ... });
```
`setupLeadCapture` and `renderResults` are both invoked anew on each quiz completion; `resetQuiz` (lines 416-442) does not detach listeners.

**Why it matters:**
Anyone who retakes the quiz (a normal user action — the Retake button is explicitly rendered in results) generates duplicate submissions in the `quiz_submissions` ZSET that powers the Leads tab. The dashboard ends up tracking inflated numbers and the same lead appears multiple times.

**Suggested fix:**
Bind the listeners once (either at DOMContentLoaded or behind a one-time guard), or clone+replace the buttons inside `setupLeadCapture` / `renderResults` to drop prior handlers before re-attaching.

### BUG-20260604-02 — Deleting a client orphans the `client_email` lookup

- **Severity:** P2
- **Area:** `api/dashboard/clients.js`
- **Reproducible:** Yes
- **First seen:** today

**What's wrong:**
The DELETE handler removes `client:{id}` and the `clients_index` entry, but never removes `client_email:{normalizedEmail}`. That Redis key was set when the client's portal was enabled (`api/dashboard/client-portal.js:115-118`). Two consequences:

1. The "email already in use" check (`api/dashboard/clients.js:70-73`) hits the orphaned key forever, so the email is permanently unusable for any future client.
2. If someone manually reuses the email later, the lookup still points to the deleted client id, and `api/client/login.js:29-32` will lookup `client:{deletedId}`, get null, and return 401 — the user sees "Invalid email or password" with no recovery path through the UI.

**Evidence:**
```
api/dashboard/clients.js:143-154
if (req.method === 'DELETE') {
  ...
  await redis('DEL', 'client:' + id);
  await redis('ZREM', 'clients_index', String(id));
  // <-- missing: DEL client_email:{normalizeEmail(client.email)}
  return res.status(200).json({ ok: true });
}
```
Compare with the PUT handler (lines 120-132), which does maintain the lookup on email change.

**Why it matters:**
Admin-facing data corruption. The "unique email enforced" guarantee in CLAUDE.md silently breaks, and recovery requires manual Redis surgery.

**Suggested fix:**
Before `DEL client:{id}`, read the client, and if `portalEnabled && email`, also `DEL client_email:{normalizeEmail(client.email)}`.

### BUG-20260604-03 — Rate-limit key trusts the full `x-forwarded-for` chain

- **Severity:** P3
- **Area:** `api/submit-quiz.js`, `api/submit-email.js`, `api/submit-chs-application.js`
- **Reproducible:** Yes
- **First seen:** today

**What's wrong:**
All three public submit endpoints derive their per-IP rate-limit key from the raw `x-forwarded-for` header:

```
api/submit-quiz.js:23           const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
api/submit-email.js:28          const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
api/submit-chs-application.js:40 const ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
```

Vercel's edge prepends the real client IP, but does not strip subsequent values. An attacker who sends `X-Forwarded-For: 1.2.3.4` causes the request header seen by the function to be `<real-ip>, 1.2.3.4`. Cycling that trailing value yields a different rate-limit key every request, bypassing the 10/hr (quiz, email) and 5/hr (CHS) limits.

**Evidence:**
Manual test against the live `/api/submit-quiz` endpoint with `curl -H 'X-Forwarded-For: 9.9.9.9' ...` and `... 8.8.8.8` etc. produces a different `ratelimit:quiz:<chain>` key each time — INCR returns 1 every time.

**Why it matters:**
Submits can be flooded by a single attacker, polluting the Leads tab, the CHS applications inbox, and burning Redis write quota.

**Suggested fix:**
Use only the first hop:
```js
const ip = (req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown')
  .split(',')[0].trim();
```

### BUG-20260604-04 — Admin session signature compared with non-timing-safe `!==`

- **Severity:** P3
- **Area:** `api/lib/auth.js`
- **Reproducible:** Yes (by inspection)
- **First seen:** today

**What's wrong:**
`verifyToken` compares the HMAC signature against the expected value using `!==`, a standard string equality that short-circuits on the first mismatching byte:

```
api/lib/auth.js:18-31
function verifyToken(token) {
  ...
  if (signature !== expected) return false;
  ...
}
```

The companion implementation for client sessions (`api/lib/client-auth.js:46-49`) does it correctly with `crypto.timingSafeEqual`. CLAUDE.md describes admin auth as "HMAC-signed session cookies (timing-safe comparison)" — the code doesn't match its own contract.

**Why it matters:**
The HMAC payload here is just the expiry timestamp, so practical exploitation is narrow — but the codebase already has the timing-safe pattern available two files over, and the docs claim it's in use. Drift between two parallel auth modules is also a maintenance hazard.

**Suggested fix:**
Replace lines 23-27 with the same `Buffer.from(...) + timingSafeEqual` pattern used in `client-auth.js`.

### BUG-20260604-05 — Engagement cron has no cooldown; sends nudge daily

- **Severity:** P3
- **Area:** `api/cron/engagement-check.js`
- **Reproducible:** Yes
- **First seen:** today

**What's wrong:**
The daily 15:00 UTC cron sends a "we miss you" email to every active+portal-enabled client whose most recent `client_dailylog` is 3+ days old. It records nothing about whether a reminder has already gone out, so the email is re-sent every subsequent day the client stays inactive:

```
api/cron/engagement-check.js:61-94
if (lastLogDaysAgo === -1 || lastLogDaysAgo >= 3) {
  ... fetch('https://api.resend.com/emails', ...)
}
```

A client on vacation for 10 days receives 8 identical reminder emails.

**Why it matters:**
Pestering paying clients is a churn risk and a deliverability risk (recipients flag the address as spam, future legitimate mail is hurt). It's also wasted Resend quota.

**Suggested fix:**
After a successful send, write `client.lastEngagementEmailAt = new Date().toISOString()` back to the client record and skip the send if it's within the last ~5 days.
