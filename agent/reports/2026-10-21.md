## Summary

First run of the Bug Hunter against the marketing site. Focus was Performance. Two findings, both on the public homepage and the Charleston (`/chs`) landing page, both centered on image delivery. The headline issue is a 1.9MB unresized JPEG served to every homepage visitor; the follow-on is that neither page uses `loading="lazy"` on below-the-fold imagery, so the same image also blocks `/chs` on page load. Fixing both is a small-diff, high-signal performance win and would meaningfully improve mobile LCP on the two highest-value marketing pages.

Noted but intentionally NOT reported: items already listed in `CLAUDE.md` under "Bug crawl P1-P3 backlog" and "Known Limitations" (tool pages missing `main.js`, `.html` extensions in internal links, `todayStr()` UTC timezone bug, SW cache version bump).

## Findings

### [BUG-20261021-01] 1.9MB unresized hero portrait on homepage and /chs

- **Severity:** P1
- **File(s):** `images/thomas.jpeg` (1,897,318 bytes, 1206×2136), referenced by `index.html:252` and `chs.html:946`
- **Area:** marketing-site
- **Reproducible:** yes

**What is wrong**

`images/thomas.jpeg` is a 1.9MB JPEG at 1206×2136 — an unresized export (EXIF shows Lightroom Classic 14.4 origin). It is served as-is from the About section of the homepage and the About section of `/chs`. No responsive variants, no WebP/AVIF, no `width`/`height` attributes, no `loading` attribute. On the two highest-value marketing surfaces, this one file dominates total page weight.

**Why it matters**

Every first-time homepage visit downloads ~1.9MB just for the founder portrait, on top of fonts, CSS, and other imagery. On a typical 4G mobile connection (~1.5 MB/s effective), that's over a second of transfer for a single below-the-fold image. The same image is loaded again on `/chs` — a landing page actively driving in-person Charleston applications — where it pushes total page weight well past 2.5MB. LCP and bandwidth cost both suffer. Also triggers CLS risk since no intrinsic dimensions are set.

**Suggested fix**

Export two JPEG variants (e.g., 600×1063 for mobile at ~90KB, 900×1594 for desktop at ~180KB), optionally add a WebP sibling, reference them via `<picture>` with `srcset`/`sizes`, and set `width`/`height` on the `<img>`. If keeping the single tag, at minimum resize the source to ~900px wide, re-encode to a reasonable quality (~82), and add `loading="lazy"` + `decoding="async"` on both references (see BUG-20261021-02).

### [BUG-20261021-02] Below-the-fold images missing `loading="lazy"` on index.html and chs.html

- **Severity:** P2
- **File(s):** `index.html:252,258,261`; `chs.html:922,925,928,946,950,953`
- **Area:** marketing-site
- **Reproducible:** yes

**What is wrong**

Every `<img>` on `index.html` and `chs.html` except the `/chs` hero (`chs.html:824`, correctly tagged `loading="eager" fetchpriority="high"`) is loaded eagerly despite sitting well below the fold. The author clearly knows the attribute — it's used on the hero — so the misses look like oversights rather than an intentional pattern. The only `loading="lazy"` in the entire repo is a single occurrence inside `client-dashboard.html`.

- Homepage About section (`index.html:252,258,261`): 3 portraits totaling ~2.37MB served on initial load.
- `/chs` events strip + About row (`chs.html:922,925,928,946,950,953`): 6 images totaling ~2.6MB served on initial load.

**Why it matters**

Eager-loading below-fold images contends with font and hero-image fetches for bandwidth on the critical path, pushing out LCP and INP on mobile. On `/chs` in particular this interacts with BUG-20261021-01 to make the page's first paint noticeably heavier than it needs to be. Browsers support native `loading="lazy"` across all modern targets with no polyfill needed.

**Suggested fix**

Add `loading="lazy" decoding="async"` to the six `/chs` below-fold images and the three homepage About images. Keep `loading="eager" fetchpriority="high"` on the `/chs` hero as-is. One-line edit per `<img>`; no CSS or layout changes required.
