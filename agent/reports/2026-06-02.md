## TKHG-2026-06-02-1 — Quiz lead capture bypasses required-field validation

**Severity**: P1
**Area**: Public marketing — lead capture
**Files**:
- `js/quiz.js:225-275`
- `index.html:576-581`
- `pricing.html:589-595`

**Repro**:
1. Visit `https://www.telosathleticclub.com/` (or `/pricing`).
2. Start the Execution Score quiz and answer all 8 questions.
3. On the "Your Score Is Ready" lead-capture screen, leave Name + Email blank.
4. Click **See Your Score**.

**Observed**:
- The button has `type="button"`, so clicking it does not submit the `<form>`. Native `required` validation is therefore skipped.
- `js/quiz.js:225` registers a click listener that reads `nameInput.value` / `emailInput.value` directly with no length, presence, or format checks.
- `localStorage.setItem('telosQuizCompleted', 'true')` is set unconditionally at line 247.
- The `fetch('/api/submit-quiz', ...)` call uses `.catch(function(){})` (line 269) so the server's 400 ("Name and email required") is silently swallowed.
- The user is shown the results page anyway via `renderResults()` at line 274.

**Impact**:
- Lead capture is bypassable; the quiz becomes a free score calculator with no contact data captured.
- On `pricing.html` the same bug means pricing is unlocked even though no lead was recorded (the quiz overlay uses the same `js/quiz.js`).
- `submit-quiz.js` per-IP rate-limit counter still increments before validation, so even legitimate submissions on the same network can hit the 10/hour cap faster than expected.

**Suggested fix**:
- In `js/quiz.js`, inside the click handler, add presence + simple regex validation on `nameInput.value` and `emailInput.value` and bail with an inline error before touching localStorage or calling fetch.
- Alternatively change the button to `type="submit"` and move the logic into a `form.addEventListener('submit', ...)` so native `required` runs first.
- Only call `localStorage.setItem('telosQuizCompleted', 'true')` after the `/api/submit-quiz` `fetch` resolves with `res.ok === true`.

**Confidence**: High. Reproducible from code reading alone; the protein-calculator and hyrox-predictor email gates both validate correctly and provide a working pattern to copy.

## TKHG-2026-06-02-2 — Weekly-summary email almost always reports streak = 0

**Severity**: P1
**Area**: Client engagement — cron / email
**File**: `api/cron/weekly-summary.js:86-90`

**Repro**:
1. Onboard a portal-enabled active client.
2. Have them log a daily check-in every day for the prior 7 days (Sun through Sat).
3. Skip Monday's check-in (or wait until Vercel cron runs Monday at 14:00 UTC = ~09:00–10:00 ET, before they've opened the app).
4. Receive the "Your Weekly Telos Recap" email.

**Observed**:
The streak loop is:
```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```
`d = 0` corresponds to *today* (Monday). If the client has not yet logged today's check-in — which is the realistic state at 9–10 AM ET — the loop breaks immediately and the email shows `Current Streak: 0 days` even for a client who hit 7 consecutive prior days.

**Impact**:
- The "Current Streak" stat is the single most motivating number in the email and it is misleading for the majority of recipients on the morning the cron fires.
- Demoralizing for the most-engaged clients (highest streak = most likely to see streak=0 if they haven't yet checked in for Monday).
- Trust erosion on a flagship coach-to-client touchpoint.

**Suggested fix**:
Skip an empty `d = 0` only if it is "today" (don't reset the streak on the day the cron runs):
```js
var startIdx = 0;
if (!weekData[0][0] || !weekData[0][0].result) startIdx = 1; // skip today if no log yet
for (var d = startIdx; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```
Or change the cron to fire at end-of-day local time when "today" is likely to have a log, but the skip-today fix is cleaner.

**Confidence**: High. The cron schedule (`0 14 * * 1` in `vercel.json`) and the off-by-one streak start are both deterministic from code.

## TKHG-2026-06-02-3 — Deleting a client orphans `client_email:` lookup, permanently blocks re-add

**Severity**: P1
**Area**: Admin dashboard — client lifecycle
**Files**:
- `api/dashboard/clients.js:142-154` (DELETE)
- `api/dashboard/clients.js:69-73` (POST email-existence check)
- `api/dashboard/client-portal.js:115-118` (where the lookup is created)

**Repro**:
1. From `/thomas` → Clients, create a client `Alice <alice@example.com>`.
2. Open the Client Portal tab for Alice, enable portal access, set a password. This creates the Redis key `client_email:alice@example.com -> {aliceId}`.
3. Back in Clients, click **Delete** on Alice (calls `DELETE /api/dashboard/clients?id={aliceId}`).
4. Try to re-add a client with email `alice@example.com`.

**Observed**:
- Step 3 only runs `DEL client:{id}` and `ZREM clients_index, id` (lines 147–148). It does not `DEL client_email:{normalizedEmail}` and does not touch any of the per-client data keys (`client_dailylog:*`, `client_nutrition_log:*`, `client_training_log:*`, `client_545_*`, `client_supplement_*`, `client_activity_log:*`, all their indexes, plan keys, sidemenu, etc.).
- Step 4 fails with HTTP 400 `"Email already in use by another client"` (clients.js:71-73) because the orphaned lookup is still pointing at the deleted id.

**Impact**:
- An email that was ever portal-enabled can never be reused after a client is deleted. Real-world cases: someone signs up, gets deleted by mistake, re-onboards a week later — admin must manually purge the Redis key or change the client's email permanently.
- Storage leak: all per-client tracking data persists in Redis forever after deletion. With 8 indexes plus 365 daily keys per client per data type, a deleted long-time client easily leaves >2,000 dead keys behind. Not urgent today, but compounds over time.

**Suggested fix**:
In `api/dashboard/clients.js` DELETE handler, after fetching the client record (which currently isn't read at all):
```js
var raw = await redis('GET', 'client:' + id);
if (raw) {
  var client = JSON.parse(raw);
  if (client.email) {
    var { normalizeEmail } = require('../lib/client-auth');
    await redis('DEL', 'client_email:' + normalizeEmail(client.email));
  }
}
// then the existing DELs
```
Cleaning up the data keys is a larger change (would need to scan or maintain a per-client key registry); at minimum, clear the email lookup so re-adds work. The data-leak side can be a follow-up.

**Confidence**: High. Verified by tracing POST → portal-enable → DELETE → POST again paths; no `client_email:` deletion exists anywhere in the DELETE flow.

## TKHG-2026-06-02-4 — Engagement-check cron has no dedup; re-sends "we miss you" daily

**Severity**: P2
**Area**: Client engagement — cron / email
**File**: `api/cron/engagement-check.js:60-94`

**Repro**:
1. Set up an active portal-enabled client.
2. Have them not log a daily check-in for 7+ days.
3. Observe their inbox.

**Observed**:
The cron runs daily at 15:00 UTC. For every client whose last log is ≥ 3 days ago, it fires a Resend email. There is no per-client `lastEngagementEmailSentAt` field, no Redis key, and no "skip if sent in last N days" check. So a client inactive for 10 days will receive 8 identical "We miss you at Telos" emails (days 3 through 10).

**Impact**:
- Spammy at best, deliverability damage at worst — repeated identical subject lines + sender + recipient triggers Gmail/Outlook bulk-folder routing. That can quietly degrade the deliverability of *all* Telos emails (weekly summaries, password resets) sent from `noreply@telosathleticclub.com`.
- Negative brand impression for the exact users the email is trying to win back.

**Suggested fix**:
Before sending, write `client_engagement_sent:{clientId}` with a TTL of e.g. 5 days; skip the send if the key exists:
```js
var sentKey = 'client_engagement_sent:' + client.id;
if (await redis('GET', sentKey)) continue;
// ... send email ...
await redis('SETEX', sentKey, 5 * 86400, '1');
```

**Confidence**: Medium-high. The functional behavior is unambiguous from the code. Severity drops to P2 only because it's plausibly the intended design ("nag daily until they log in"); flagging for Thomas's call on intent.
