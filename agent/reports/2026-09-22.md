## BUG-2026-09-22-001

- **Severity:** P1
- **Category:** Functional / Correctness (cron job)
- **File:** `api/cron/weekly-summary.js`
- **Lines:** 87-90

### Summary
The Monday weekly summary email always shows `Current Streak: 0 days` for any client who has not yet logged their daily check-in today (Monday). Since the cron fires at 09:00 ET Monday, virtually every client receives an email that misrepresents their streak as zero.

### Reproduction (code trace)
1. `vercel.json` schedules `api/cron/weekly-summary` at `0 14 * * 1` (Mon 14:00 UTC = 09:00-10:00 ET depending on DST).
2. The handler iterates `d = 0..6`, where `d = 0` is today (Monday). It fetches `client_dailylog:{id}:{today}`.
3. Streak counter at lines 87-90:
   ```js
   for (var d = 0; d < 7; d++) {
     if (weekData[0][d] && weekData[0][d].result) streak++;
     else break;
   }
   ```
   At 09:00 Monday, the client has not opened the app yet today, so `weekData[0][0]` is empty. The loop breaks on the first iteration and `streak = 0` regardless of last week's consistency.
4. `buildWeeklySummary` renders "Current Streak: 0 days" and the client sees a misleading value in their inbox.

### Proposed fix
Start the streak count from `d = 1` (yesterday) when today has no log yet, treating "today not-yet-logged" as still in the streak. Alternatively, break the streak only when a *past* day is missing:
```js
var startD = (weekData[0][0] && weekData[0][0].result) ? 0 : 1;
for (var d = startD; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

### Why it matters
The whole point of the weekly summary is retention through positive reinforcement. Showing "0-day streak" to a 30-day consistent client is worse than sending no email at all.

## BUG-2026-09-22-002

- **Severity:** P2
- **Category:** Data integrity / Correctness
- **File:** `api/dashboard/clients.js`
- **Lines:** 143-153 (DELETE handler)

### Summary
Deleting a client from the dashboard removes only the `client:{id}` record and the `clients_index` ZSET entry. It leaves behind: the email lookup key, the password reset token (if any), and every log/plan under that client id (nutrition, training, 545, supplements, activity, push subscription, side menu, mindset, resources).

### Reproduction
1. Create client A with email `a@x.com`, tier `rebuild`, portal enabled. Populate at least one daily log.
2. In Redis, `client:{A}`, `client_email:a@x.com`, `client_dailylog:{A}:{today}`, and index ZSETs all exist.
3. DELETE `/api/dashboard/clients?id={A}`. Handler runs:
   ```js
   await redis('DEL', 'client:' + id);
   await redis('ZREM', 'clients_index', String(id));
   ```
4. `client_email:a@x.com` still points to `{A}`. If the coach now creates client B with the same email, POST rejects with "Email already in use" because the orphan lookup still hits. If the lookup is manually purged and B is created, and B ever tries to log in, `client_email:a@x.com` -> `{A}` -> `client:{A}` (deleted) -> 401 "Invalid email or password".
5. All daily logs, plans, and index ZSETs for A remain in Redis indefinitely.

### Proposed fix
Delete all keys under the client's namespace in a pipeline, plus the email lookup:
```js
var raw = await redis('GET', 'client:' + id);
var client = raw ? JSON.parse(raw) : null;
var cmds = [
  ['DEL', 'client:' + id],
  ['ZREM', 'clients_index', String(id)],
];
if (client && client.email) {
  var { normalizeEmail } = require('../lib/client-auth');
  cmds.push(['DEL', 'client_email:' + normalizeEmail(client.email)]);
}
// Also delete the per-client namespace: dailylog, nutrition_log, training_log,
// supplement_log, activity_log, 545_daily, plus their indexes and the coach-set
// plans (nutrition_plan, mindset, resources, training_program, sidemenu,
// supplement_plan, 545_goals, 545_routine, push_sub).
```
Enumerate keys via `SCAN client_*:{id}:*` if needed, since Upstash REST supports it.

### Why it matters
Redis storage grows without bound; email collisions after re-creation silently break login for the new client; deleted client data is not actually deleted (privacy risk if the coach's mental model is "I deleted them").

## BUG-2026-09-22-003

- **Severity:** P2
- **Category:** Security / Abuse
- **File:** `api/client/reset-password.js`
- **Lines:** 20-67 (Case 1: request reset email)

### Summary
The password-reset request endpoint has no rate limit. Every other public POST endpoint in the codebase (`submit-quiz.js`, `submit-email.js`, `submit-chs-application.js`) uses a Redis INCR+EXPIRE pattern. This one does not.

### Reproduction
1. Attacker knows or guesses a client's email address (`victim@example.com`).
2. Attacker sends `POST /api/client/reset-password` with `{email: "victim@example.com"}` in a tight loop.
3. For every request where the email matches a portal-enabled client, the handler generates a fresh reset token and calls the Resend API, sending an email to the client.
4. No throttle exists. The attacker can flood the victim's inbox and rack up Resend usage costs on the Telos account.
5. Even for non-matching emails, unlimited requests are accepted and return `200 {ok:true}` (correctly, to prevent enumeration) - but the endpoint still burns Redis GETs.

### Proposed fix
Add the same IP rate-limit pattern used elsewhere. Example:
```js
var ip = req.headers['x-forwarded-for'] || req.headers['x-real-ip'] || 'unknown';
var count = await redis('INCR', 'ratelimit:reset:' + ip);
if (count === 1) await redis('EXPIRE', 'ratelimit:reset:' + ip, 3600);
if (count > 3) return res.status(429).json({ ok: true }); // still 200-ish to avoid enumeration
```
Optionally also throttle per-email (`ratelimit:reset_email:{normalized}`) so an attacker cannot rotate IPs to spam one victim.

### Why it matters
Cheap DoS on a client's inbox, direct cost on the Telos Resend account, and (because reset tokens have 1-hour TTL) a rolling window of usable tokens if any leak somewhere.

## BUG-2026-09-22-004

- **Severity:** P2
- **Category:** Convention violation / UX
- **Files:** `chs.html`, `pricing.html`, `product.html`, `protein-calculator.html`, `resources.html`, `shop.html`, `hyrox-predictor.html`
- **Occurrences:** Nav logo, nav menu items, mobile nav, footer links (grep `href="index.html`)

### Summary
CLAUDE.md is explicit: "All internal links use clean URLs without `.html` extension" and Vercel's `cleanUrls: true` handles it. Seven public pages still link to `index.html` (and `index.html#anchor`) in their nav and footer. Every click on the "TELOS FITNESS" logo or a `#how-it-works` anchor from these pages triggers a 301 redirect from `/index.html` to `/`.

### Reproduction
1. `grep -n 'href="index\.html' *.html` shows 40+ occurrences across the seven files above.
2. Example: `pricing.html:509` = `<a href="index.html" class="nav-logo">TELOS FITNESS</a>`.
3. Load `https://www.telosathleticclub.com/pricing`, click the logo. Network tab shows:
   - `GET /index.html` -> `301` -> `/`
   - `GET /` -> `200`
   Two round trips instead of one, plus the redirect adds ~50-200 ms on a mobile connection.

### Proposed fix
Replace with clean URLs everywhere:
- `href="index.html"` -> `href="/"`
- `href="index.html#how-it-works"` -> `href="/#how-it-works"`
- `href="index.html#about"` -> `href="/#about"`
- `href="index.html#faq"` -> `href="/#faq"`
- `href="index.html#quiz"` -> `href="/#quiz"`

Blog articles (in `/blog/`) already use `../` prefix and would need `../` -> `../` (unchanged) or `../#anchor` per the same convention. Spot-check after the sweep.

### Why it matters
Small perf regression on every internal home-link click, and it violates a convention CLAUDE.md flags as important. Once the sweep is done, add a lint check or a `grep` guard in CI to keep it from regressing.

## BUG-2026-09-22-005

- **Severity:** P3
- **Category:** Security best-practice / Internal consistency
- **File:** `api/lib/auth.js`
- **Line:** 27

### Summary
The admin HMAC session signature check uses plain string comparison (`signature !== expected`). The client-auth counterpart (`api/lib/client-auth.js` lines 46-49) does the same check via `crypto.timingSafeEqual`. Same repo, same threat model - so this is an inconsistency, not a design choice.

### Reproduction (code trace)
`api/lib/auth.js` line 18-31:
```js
function verifyToken(token) {
  ...
  const expected = crypto.createHmac('sha256', SESSION_SECRET).update(payload).digest('hex');
  if (signature !== expected) return false;   // <- non-timing-safe
  ...
}
```
vs `api/lib/client-auth.js` line 34-52:
```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;   // <- timing-safe
```

### Proposed fix
Mirror the client-auth pattern:
```js
const sigBuf = Buffer.from(signature, 'hex');
const expBuf = Buffer.from(expected, 'hex');
if (sigBuf.length !== expBuf.length) return false;
if (!crypto.timingSafeEqual(sigBuf, expBuf)) return false;
```
Guard the length check to avoid `timingSafeEqual` throwing on mismatched lengths.

### Why it matters
Network timing attacks on HMAC signature verification are hard to exploit in practice (network jitter dwarfs the per-byte comparison delta), but the fix is trivial and the two auth systems should behave identically. Also brings the file in line with CLAUDE.md's "timing-safe comparison" language for the admin session.
