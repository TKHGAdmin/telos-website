## P1 — `images/thomas.jpeg` is 1.9 MB (1206×2136), served eagerly on two public landing pages

**Files:**
- `index.html:252` — About section, "about-photo" slot
- `chs.html:946` — Charleston "About the Coach" section

**Category:** performance — image sizing / critical-path payload

### What's wrong
`images/thomas.jpeg` is a 1,897 KB JPEG at **1206 × 2136 px**. It is loaded with a plain `<img src="...">` tag — no `loading="lazy"`, no `srcset`, no responsive sizing. The display slot is a portrait "about photo" card that renders at roughly 400–600 CSS px wide on desktop and ~340 CSS px wide on mobile, so at even a 2× DPR the image needs to be ~1200 px wide at most — and for the mobile breakpoint, closer to 680 px. The file is therefore ~5–10× larger than its display requires.

Because the tag has no `loading="lazy"`, the browser kicks off the download during the initial HTML parse on both pages, on cellular that alone adds ~1.5–3 s to Largest Contentful Paint.

Both pages reference the same file, so this hits the homepage AND the Charleston application landing page — the two pages most likely to carry paid-ad traffic.

### Reproduction / evidence
```
$ identify images/thomas.jpeg
images/thomas.jpeg JPEG 1206x2136 1206x2136+0+0 8-bit sRGB 1.80942MiB

$ grep -n 'thomas\.jpeg' index.html chs.html
index.html:252:  <img src="images/thomas.jpeg" alt="Thomas Kern - Telos Fitness founder" class="about-photo">
chs.html:946:    <img src="images/thomas.jpeg" alt="Thomas Kern, Founder of Telos Athletic Club">
```

Neither `<img>` has a `loading`, `srcset`, `sizes`, or `width`/`height` attribute.

### Suggested fix
1. Re-encode the source at 1200 × 2126 at JPEG quality ~80, which should land around **200–280 KB** (saving ~1.6 MB per page view) — a drop-in replacement, no markup change needed.
2. (Better) Add a responsive `srcset` with a 680-wide variant for mobile and a 1200-wide for retina-desktop, plus `sizes` matching the actual slot.
3. Add `loading="lazy"` and `decoding="async"` to both tags — the About section is comfortably below the fold on both pages (index.html hero ends at line 124; About starts at line 245).

## P2 — Below-the-fold images lack `loading="lazy"` across three public pages

**Files (26 `<img>` tags without any `loading` attribute):**
- `index.html:252,258,261` — About section photos (`thomas.jpeg` 1.9 MB, `thomas-speaking-wide.jpeg` 246 KB, `thomas-speaking-close.jpeg` 211 KB)
- `chs.html:922,925,928,946,950,953` — Events gallery (3 images, ~232 KB) and About (3 images, ~2.4 MB total)
- `coaches.html:314-317, 331-339, 376-381` — hero rig (acceptable) PLUS member scene (7 phone screens, ~506 KB) and coach dashboard scene (6 images, ~844 KB), all below the hero and gated by scroll

**Category:** performance — eager loading of below-fold imagery

### What's wrong
The repo already demonstrates the correct pattern — `coaches.html:360–367` adds `loading="lazy"` to the phone-grid gallery figures. The same page's earlier scroll scenes (lines 330–339 and 376–381) and the About sections on `index.html` and `chs.html` do not. Browsers therefore eagerly fetch every scene image during initial HTML parse, including images that only appear after several scroll steps (the `.on` class is toggled by the page's own scroll-driven JS — the browser cannot infer visibility from that).

For `coaches.html` the eager payload is dominated by ~1.3 MB of scene screenshots that the user will see only if they scroll through the whole narrative. For `index.html` and `chs.html` the eager payload is dominated by `thomas.jpeg` (see P1), but the two Harbor-Entrepreneur speaking shots add ~457 KB more.

### Reproduction / evidence
```
$ grep -nE '<img[^>]+>' *.html | grep -v 'loading=' | wc -l
26
```
Contrast with the correct pattern already in the repo:
```
coaches.html:360: <figure><div class="phone">...<img src="images/coaches/app-today.jpg" ... loading="lazy"></div>...</figure>
```

### Suggested fix
Add `loading="lazy"` (and `decoding="async"`) to every `<img>` whose rendered position is below the first viewport. Concretely:
- `index.html:252,258,261`
- `chs.html:922,925,928,946,950,953`
- `coaches.html:331-337, 339, 376-381` (keep the four hero `.rig` images on 314-317 eager; they are the hero)

The hero `.rig` image on `coaches.html:317` (`app-today.jpg`, 90 KB) is a reasonable candidate for `fetchpriority="high"` since it is the central visible phone.
