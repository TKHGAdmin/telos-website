## Summary

First run of the Bug Hunter, focused on functional correctness across the serverless API surface. Three P1 findings: an orphan Redis key on client deletion that blocks re-adding the same email, and two endpoints that ship without rate limits and can be abused for email-bombing and admin brute-force. All three are high-confidence, single-file fixes.

## Findings

#### BUG-20260820-01 - Password reset endpoint has no rate limit, enables email-bombing and Resend quota abuse

- **Severity:** P1
- **File(s):** `api/client/reset-password.js:20-67`
- **Category:** security
- **Reproduction:** Any anonymous caller POSTs `{ "email": "victim@example.com" }` to `/api/client/reset-password` in a loop. Each request that matches an enabled portal client fires a Resend email to that address. There is no IP or per-target throttle.
- **Impact:** An attacker who knows or guesses a client's email (or Thomas's own address) can flood their inbox with "Reset Your Telos Client Portal Password" emails, get the sending domain flagged for abuse by Resend, and burn through the Resend monthly quota. The three public POST endpoints (`submit-quiz`, `submit-email`, `submit-chs-application`) already implement `INCR + EXPIRE` rate limiting, so the pattern is established.
- **Suggested fix:** Add the same `ratelimit:reset:{ip}` counter (e.g. 5 per hour) around the reset-request branch, and consider a secondary per-target-email counter (`ratelimit:reset_target:{normalizedEmail}`, 3 per hour) to prevent single-address bombing from rotating IPs.
- **Confidence:** high

Password reset endpoints are one of the most common email-abuse vectors on the internet. The endpoint intentionally returns 200 for unknown emails to prevent enumeration, which is correct, but that same design lets attackers hit it repeatedly at zero cost to themselves while every hit that lands on a real client triggers an outgoing email.

#### BUG-20260820-02 - Admin login has no rate limit, entire /thomas dashboard vulnerable to brute force

- **Severity:** P1
- **File(s):** `api/dashboard/login.js:3-17`
- **Category:** security
- **Reproduction:** POST `{ "password": "guess" }` to `/api/dashboard/login` in a loop. `verifyPassword` uses `crypto.timingSafeEqual` (good) but there is no counter, backoff, or IP block, so an attacker gets unlimited attempts.
- **Impact:** The single shared `DASHBOARD_PASSWORD` gates the entire admin surface: full client roster with emails and phone numbers, revenue, pipeline, Charleston applications, quiz leads, and CRUD on client portal content. If the password is weak or leaked, unlimited attempts make this a one-command compromise. Unlike the client login (which uses PBKDF2 100k iterations per attempt, slowing brute-force to hundreds per second), this endpoint returns in a few milliseconds.
- **Suggested fix:** Wrap the handler with the same `INCR + EXPIRE` rate-limit pattern used in `submit-quiz.js` (e.g. `ratelimit:dashlogin:{ip}` at 10 per hour). Also consider adding a global `ratelimit:dashlogin:global` counter so a single distributed attack cannot rotate IPs.
- **Confidence:** high

The admin password protects far more sensitive data than any client account, yet is the least defended endpoint. The consistent site pattern is IP-based `INCR + EXPIRE`; applying it here brings the endpoint in line with the rest of the codebase without any new dependencies.

#### BUG-20260820-03 - Deleting a client leaves orphan client_email lookup, blocks re-adding the same email

- **Severity:** P1
- **File(s):** `api/dashboard/clients.js:143-154`, `api/dashboard/client-portal.js:115-118`, `api/dashboard/clients.js:70-73`
- **Category:** functional
- **Reproduction:** 1) Create a client with email `foo@bar.com` and enable their portal (this SETs `client_email:foo@bar.com` -> clientId in `client-portal.js:117`). 2) Delete the client from the Clients tab. `clients.js` DELETE removes `client:{id}` and the `clients_index` entry but never touches `client_email:*`. 3) Attempt to re-create a client with `foo@bar.com`. `clients.js:70-73` finds the stale lookup and returns 400 "Email already in use by another client".
- **Impact:** Thomas cannot re-add a former client with their original email without manually deleting the Redis key from Upstash console. This is a plausible real workflow: a lifestyle client leaves, comes back three months later, gets rejected at re-onboarding with a misleading error. It also creates dangling data - the stale lookup will happily match on future POSTs and can cause "phantom" account collisions.
- **Suggested fix:** In the DELETE branch, before deleting `client:{id}`, `GET` the client record, normalize the stored email, and `DEL client_email:{normalizedEmail}` when portal was enabled. Same pattern as the disable branch in `client-portal.js:121-124`.
- **Confidence:** high

The wider "delete doesn't cascade" issue affects many keys (daily logs, nutrition logs, 545, training, etc. - see `learnings.md`), but only the email lookup produces a user-visible failure in the admin workflow. The other orphans are storage bloat, not defects.

- `js/quiz.js:317-323` `countInterval = 1200 / totalScore` would produce `Infinity` if `totalScore === 0`. Minimum possible score is 8 (1 point per question x 8), so unreachable today. Deferred.
