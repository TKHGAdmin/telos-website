# Telos Bug Hunter — 2026-08-24

**Focus:** Functional
**Findings:** 2
**Approval-ready:** yes

## Summary

First run of the bug hunter. Focused on functional correctness across the API layer (admin dashboard, client portal, submit endpoints) and the recently added shop / product detail flow. Two real regressions surfaced: a client-delete cleanup leak in the admin API that permanently blocks re-use of an email address, and a broken CSS grid layout on the product detail page caused by the new thumbnail gallery (commit f5cb8c4). Everything else read as intentional or matched a documented convention in `CLAUDE.md`.

## Findings

### BUG-20260824-01 — Deleting a client leaks the email reservation, blocking re-creation with the same email

- **Severity:** P1
- **Area:** api/dashboard/clients.js (admin client roster)
- **File(s):** `api/dashboard/clients.js:143-154`, cross-reference `api/dashboard/clients.js:70-73`, `api/dashboard/client-portal.js:115-124`
- **Reproduction:**
  1. In `/thomas` → Client Portal, create a client with email `foo@bar.com` and enable portal access. `client-portal.js:117` sets `client_email:foo@bar.com` → that client's ID.
  2. In the Clients tab, delete that client. `clients.js` DELETE (lines 143-154) runs `DEL client:{id}` and `ZREM clients_index`, but never touches `client_email:foo@bar.com`.
  3. Try to add a new client with email `foo@bar.com`. The POST handler at `clients.js:70-73` does `GET client_email:foo@bar.com`, finds the orphaned pointer to the now-deleted ID, and returns `400 "Email already in use by another client"`.
  4. The admin is permanently blocked from using that email again without manually deleting the Redis key.
- **Impact:** Any admin workflow that creates → deletes → re-creates a client with the same email fails at step 3. Common real cases: a wrong tier picked at create time and re-created, a client cancels then re-signs up, or a test client cleaned out during setup. The message ("in use by another client") is misleading — no such client exists. Also leaves other derived keys orphaned (`client_dailylog:{id}:*`, `client_nutrition_plan:{id}`, `client_training_program:{id}`, `client_545_*:{id}*`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_push_sub:{id}`, `client_modules_watching:{id}`, etc.), which is a secondary storage-hygiene issue.
- **Recommendation:** In the DELETE handler, fetch the client record first, and if it exists, also `DEL client_email:{normalizeEmail(client.email)}`. For thoroughness, also delete the ancillary keys listed above (or scan them with `SCAN client:*:{id}:*` if the key layout supports it). Mirror the pattern used in `client-portal.js:121-124` for portal-disable.
- **Confidence:** high

### BUG-20260824-02 — Product detail page layout is broken on desktop: thumbnail gallery displaces the info column

- **Severity:** P1
- **Area:** product.html / shop.js (product detail page)
- **File(s):** `product.html:765-780` (DOM), `product.html:100-114` (grid CSS), `js/shop.js:160-177` (populates the thumbs div)
- **Reproduction:**
  1. Open `/product?p=<any-handle>` on a desktop viewport (≥ 768px).
  2. `.product-detail` uses `display: grid; grid-template-columns: 1fr 1fr;` (`product.html:106-108`).
  3. It has THREE direct children in this order: `#productImage`, `#productThumbs`, `.product-detail-info` (`product.html:766-779`). Auto-placement fills the 2-column grid row-major, so:
     - Row 1, Col 1 → `#productImage`
     - Row 1, Col 2 → `#productThumbs` (this is where the info column used to sit before commit f5cb8c4)
     - Row 2, Col 1 → `.product-detail-info` (title, price, Add to Cart, description)
     - Row 2, Col 2 → empty
  4. Result: the price, Add to Cart button, and description end up BELOW the product image in the left column, not beside it. On single-image products, the empty `#productThumbs` div still occupies row 1 / col 2, so the layout is broken for every product, not just multi-image ones.
  5. Sanity check with `git log --oneline js/shop.js product.html` — layout worked before commit `f5cb8c4 feat: add image gallery with thumbnails on product page` (2026-05-20), which added the thumbs sibling into a 2-column grid that only expects two children.
- **Impact:** The primary product-page conversion layout is visually broken on desktop. Add to Cart still functions, but price and CTA render below the fold on tall product images, with an empty cell to the right of the info block — reads as broken/unfinished on the main revenue-generating page.
- **Recommendation:** Wrap the image + thumbs in a single grid child so the grid still sees two children:
  ```html
  <div class="product-detail">
    <div class="product-detail-gallery">
      <div class="product-detail-image" id="productImage"></div>
      <div class="product-detail-thumbs" id="productThumbs"></div>
    </div>
    <div class="product-detail-info">...</div>
  </div>
  ```
  No CSS change needed beyond letting `.product-detail-gallery` be `display: block` (default is fine).
- **Confidence:** high

## Notes

- The client cookie token format `{clientId}.{expiry}.{signature}` (`api/lib/client-auth.js:23-52`) is safe because `clientId` comes from `INCR id:clients` (numeric only) — no risk of dot-in-id breaking the 3-part split. Worth remembering if the ID scheme ever changes.
- `sw.js` caches every non-API `GET` response indefinitely into `telos-v1` (line 60-70). Not a bug on its own, but the cache will grow unbounded over time and the CLAUDE.md note about bumping the cache name on updates is critical — worth revisiting on the next Performance rotation.
