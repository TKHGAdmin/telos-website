## P1-01 — Client portal login has no rate limit (password brute-force)

- **File:** `api/client/login.js` (whole file)
- **Focus:** Functional / Security overlap
- **Severity:** P1

**What's wrong.** The endpoint accepts unlimited `POST` attempts per IP or per email. Every other public form on the site (`submit-quiz`, `submit-email`, `submit-chs-application`) has a Redis-backed rate limit (5–10/hr/IP). Login does not.

**How to reproduce.**
1. `POST /api/client/login` with `{"email":"real-client@…","password":"…"}` in a loop.
2. There is no `429` at any count. `verifyPassword` is 100k-iteration PBKDF2, so throttled — but an attacker can still spray common passwords against the entire client list unimpeded, and if they know an email, they can brute-force offline-style (though bounded by PBKDF2 cost per attempt).

**Impact.** Anyone who guesses a client's password wins full access to that client's coaching data (nutrition plans, training program, daily logs, personal goals, coach notes). A leaked client email + a weak password = takeover.

**Suggested fix.** Same pattern used in `submit-quiz.js` lines 22-29 — key on both `ratelimit:login:ip:{ip}` (e.g. 20/hr) and `ratelimit:login:email:{normalizedEmail}` (e.g. 5/15min). Return 429 before calling `verifyPassword` so PBKDF2 isn't wasted.

## P1-02 — Admin dashboard login has no rate limit

- **File:** `api/dashboard/login.js:1-17`
- **Focus:** Functional / Security overlap
- **Severity:** P1

**What's wrong.** `/api/dashboard/login` accepts unlimited attempts. `DASHBOARD_PASSWORD` is a single shared secret; a successful guess grants read/write access to every client record, revenue data, ability to send email as `noreply@telosathleticclub.com`, and to upload/delete Vercel Blob assets.

**How to reproduce.** `POST /api/dashboard/login` with `{"password":"..."}` in a loop. `verifyPassword` uses timing-safe comparison but there's no throttle around it.

**Impact.** Single-secret admin auth with unbounded attempts = brute-force risk. If `DASHBOARD_PASSWORD` is a passphrase of typical human strength, an attacker with a wordlist and a script can compromise the entire business dashboard.

**Suggested fix.** Add an IP-based rate limit (e.g. 5 attempts per 15 minutes per IP), returning 429 before `verifyPassword`. Log failures. Consider an exponential lockout on repeated failures from the same IP.

## P1-03 — Deleting a portal-enabled client orphans the email lookup key

- **File:** `api/dashboard/clients.js:143-154` (DELETE handler)
- **Focus:** Functional
- **Severity:** P1

**What's wrong.** `DELETE /api/dashboard/clients?id=…` removes:
- `client:{id}` (line 147)
- `clients_index` ZSET entry (line 148)

It does NOT remove `client_email:{normalizedEmail}` — that key is only ever cleared by `client-portal.js:123` (portal-disable) or by `clients.js:130` (email change while portal enabled). It is created by `client-portal.js:117` when the portal is enabled.

**How to reproduce.**
1. Create client Bob with email `bob@example.com`.
2. Enable portal for Bob (in the Client Portal tab). Redis now has `client_email:bob@example.com → {bobId}`.
3. Delete Bob via the Clients tab.
4. Try to create a new client with `bob@example.com`. `clients.js:70-73` returns `400 "Email already in use by another client"` — but no client actually owns that email; `client:{bobId}` is gone.
5. Additionally, if someone tries to log in with `bob@example.com`, `login.js:24` resolves the ID, then `login.js:29 GET client:{bobId}` returns null → the login shows "Invalid email or password". Not a security leak, but confusing to debug for the coach if Bob calls asking why he can't log in.

**Impact.** Emails become permanently un-reusable once a portal-enabled client has been deleted. In a small coaching business with client churn, this will bite within months. There is no admin UI to purge the orphaned key — Thomas would need to shell into Upstash.

**Suggested fix.** In `clients.js` DELETE (after line 146, before line 147): parse the existing client, `DEL client_email:{normalizeEmail(client.email)}`. Also consider a follow-up sweep of `client_dailylog:{id}:*`, `client_nutrition_log:{id}:*`, `client_training_log:{id}:*` etc., or explicitly document that deleted-client data is retained.

## P1-04 — `reset-password` endpoint has no rate limit (Resend quota + client-inbox spam)

- **File:** `api/client/reset-password.js:1-68` (request-reset branch)
- **Focus:** Functional
- **Severity:** P1

**What's wrong.** Anyone can POST `{"email":"…"}` to `/api/client/reset-password` unlimited times. Each hit for a real, portal-enabled client email sends a Resend email. There is no `ratelimit:reset:…` guard.

**How to reproduce.**
1. Loop `POST /api/client/reset-password` with a known client email.
2. That client receives a "Reset Your Telos Client Portal Password" email each time.
3. Resend API quota consumed with each request; on the free tier that's 100 emails/day → exhausted quickly, then legitimate transactional emails (weekly summary, engagement reminders) stop delivering silently.

**Impact.** Client inbox flooded (hurts sender reputation, may trigger Gmail/Outlook spam filters that then affect ALL Telos email). Resend quota can be exhausted by a single actor. The response is always `200 ok` (correctly, to prevent enumeration), so an attacker sees no throttle signal but the damage still happens.

**Suggested fix.** Per-IP rate limit (`ratelimit:reset:ip:{ip}` → 5/hr) AND per-email limit (`ratelimit:reset:email:{normalizedEmail}` → 3/day). Do the rate-limit check AFTER the "always return 200" enumeration guard, so response shape stays constant. Skip the Resend call once the per-email cap is hit even if per-IP is fine.

## P2-01 — Engagement-check cron re-emails inactive clients daily, forever

- **File:** `api/cron/engagement-check.js:36-95`
- **Focus:** Functional
- **Severity:** P2

**What's wrong.** The cron runs every day. For every active, portal-enabled client whose latest `client_dailylog:` is 3+ days old (or missing entirely — `lastLogDaysAgo === -1` after only looking back 5 days), it sends the "We miss you at Telos" email. There is no `lastEngagementEmailSentAt` field on the client, no cooldown, no `SET`+`EX` guard key.

**How to reproduce.**
1. Any client stops logging (goes on vacation, ends coaching, forgets password, etc.).
2. On day 3 they get an email — reasonable.
3. On day 4, 5, 6, 7, 8, 9… they get the SAME email, once per day, until they either log a check-in or the coach flips `client.emailEnabled = false` / `client.status !== 'active'`.

**Impact.** Real user harm: a dormant client gets 30+ identical "we miss you" emails in a month. Feels like spam, likely triggers unsubscribe pressure (there is no unsubscribe link), damages Telos sender reputation (Gmail auto-filters, Resend may throttle the domain), and hurts the brand.

**Suggested fix.** Add a cooldown key: `SETEX engagement_reminder_sent:{clientId} 604800 1` (7-day TTL) after successful send; skip the send when the key exists. Or: on send, patch `client.engagementReminderSentAt = today` and skip if within 7 days. A weekly cadence for the "we miss you" nudge is standard practice.

## Bugs considered and rejected

- **`api/lib/auth.js:27` — non-timing-safe HMAC comparison.** `signature !== expected` in `verifyToken` is not `crypto.timingSafeEqual`, unlike `client-auth.js:49`. Real inconsistency but: both strings are 64 hex chars of HMAC-SHA256 output, so length is fixed and content is uniformly high-entropy; a practical timing-attack recovery of an HMAC signature against a JavaScript runtime over the network is far below the noise floor. Flagging on a future Security-focus day if still present. Noise-adjacent for a Functional-focus day.
- **`x-forwarded-for` used unsplit for rate-limit keys** in `submit-quiz.js`, `submit-email.js`, `submit-chs-application.js`. An attacker can rotate a fake IP in the header prefix to bypass the per-IP limit. But Vercel appends the real client IP; the fake-rotate trivially defeats an IP-only limit anyway, and the exposed forms aren't high-value targets. Not worth reporting this run.
- **Shop pages — `data-variant-id="${variant.id}"` embedded in an `onclick`** (`js/shop.js:291`). Shopify variant IDs are `gid://shopify/ProductVariant/…` — safe characters; no injection risk. False positive.
- **Product detail page — `document.getElementById('productAddBtn').addEventListener('click', …)`** (`js/shop.js:208`). Called inside `loadProductDetail`, which runs once per page load. No duplicate-listener risk. False positive.
