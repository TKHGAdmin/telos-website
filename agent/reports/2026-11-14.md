### BUG-20261114-01 P1 — Weekly summary email reports a 0-day streak even for consistent clients

**File:** `api/cron/weekly-summary.js:86`
**Category:** functional

**Reproduction:**

1. A client logs a daily check-in every day Monday-Sunday last week.
2. Cron fires Monday 14:00 UTC (9am ET) per `vercel.json` schedule `"0 14 * * 1"`.
3. Streak loop starts at `d=0` (today): `weekData[0][0]` is `client_dailylog:{id}:{today}`. Today just started — no log yet.
4. The loop hits `else break` on the first iteration, so `streak` stays `0`.
5. Email renders "Current Streak: 0 days" regardless of the preceding week.

**Impact:** Every active portal client with `emailEnabled !== false` gets a weekly recap that silently zeroes out their streak. For a product whose whole pitch is consistency and execution, this directly undermines trust in the data. The avg score, workouts, and days-logged numbers are correct — only the streak is wrong.

**Suggested fix:** Start the streak scan at `d=1` (yesterday) so the week-in-review measures the completed week, not an un-started Monday. Alternatively, compute `streak` as the longest run of consecutive logged days ending on or before today.

### BUG-20261114-02 P2 — `clients.js` POST never writes `client_email:` lookup, so duplicate-email check silently fails for non-portal clients

**File:** `api/dashboard/clients.js:75`
**Category:** functional

**Reproduction:**

1. Admin creates client A with email `foo@bar.com`. POST succeeds. No `client_email:foo@bar.com` key is written (only `client:{A.id}` and `clients_index`).
2. Admin creates client B with the same email `foo@bar.com`. The duplicate check at `clients.js:70` reads `client_email:foo@bar.com`, gets `null`, allows the create.
3. Admin later enables portal on A → `client-portal.js:117` sets `client_email:foo@bar.com = A.id`. Good.
4. Admin later enables portal on B → same line overwrites to `client_email:foo@bar.com = B.id`. A can still try to log in but the lookup now points to B, so A gets "Invalid email or password" with the correct password.

**Impact:** Duplicate email prevention is advertised in CLAUDE.md (`duplicate email check`) but only works between clients that already have portal enabled. In practice, portal is often enabled days/weeks after client creation, so the window for silent duplicates is large. The failure mode is subtle: client A thinks their password is wrong.

**Suggested fix:** In the POST branch, after creating the client, write `client_email:{normalizedEmail} = String(id)` unconditionally (or at least when `email` is set), so the duplicate-check key is populated from day one. Same pattern the PUT branch already uses at `clients.js:131`.

### BUG-20261114-03 P2 — `clients.js` DELETE leaves `client_email:` lookup orphaned, blocking email reuse

**File:** `api/dashboard/clients.js:143`
**Category:** functional

**Reproduction:**

1. Client A is portal-enabled → `client_email:foo@bar.com = A.id` exists in Redis.
2. Admin deletes A via DELETE `/api/dashboard/clients?id={A.id}`. The handler calls `DEL client:{A.id}` and `ZREM clients_index A.id` only.
3. `client_email:foo@bar.com` still points to the now-deleted `A.id`.
4. Admin re-creates the client with the same email. POST hits the duplicate check at `clients.js:70` and returns `"Email already in use by another client"` — but no such client exists.

**Impact:** Admin cannot re-onboard a deleted client under the same email without manually deleting the stale Redis key. Orphaned `client_*_log:*`, `client_*_index:*`, `client_nutrition_plan:*`, etc. also persist, but they're read-by-id so they don't block reuse — just waste storage. The `client_email:` orphan is the one that actually breaks a workflow.

**Suggested fix:** In the DELETE branch, before removing the client record, parse `client:{id}` for `email` and `portalEnabled`; if portal was enabled, `DEL client_email:{normalizeEmail(email)}`. Optionally also clean up the index ZSETs listed in CLAUDE.md's "Client Dashboard - Redis Keys" section.

### BUG-20261114-04 P2 — Admin dashboard login has no rate limiting; password is brute-forceable

**File:** `api/dashboard/login.js:1`
**Category:** functional

**Reproduction:**

1. Attacker POSTs `/api/dashboard/login` with `{password: "guess"}` repeatedly.
2. Each attempt runs `verifyPassword` (timing-safe) and returns 401 on mismatch.
3. No per-IP counter, no delay, no lockout. Vercel's default function budget allows many requests per second.

**Impact:** The only thing between an attacker and the full admin surface (`/thomas` dashboard, which can read every client, every quiz submission, every revenue number, and change passwords via `client-portal.js`) is the entropy of `DASHBOARD_PASSWORD`. Every other public endpoint in this codebase has a rate limit: `submit-quiz.js`, `submit-email.js`, and `submit-chs-application.js` all use the `ratelimit:*:{ip}` pattern via `INCR` + `EXPIRE`. The one endpoint that actually protects something sensitive is the one that doesn't.

**Suggested fix:** Add the same `ratelimit:admin-login:{ip}` guard used in the submit endpoints — e.g., 10 attempts per hour per IP, returning 429 beyond that. This is defense-in-depth; it does not replace a strong password.

### BUG-20261114-05 P3 — `auth.js` verifies admin session HMAC with non-constant-time string compare; `client-auth.js` already uses `timingSafeEqual`

**File:** `api/lib/auth.js:27`
**Category:** functional

**Reproduction:**

1. `verifyToken` compares the incoming hex signature to the expected HMAC via `if (signature !== expected) return false;`.
2. The equivalent function in `client-auth.js:49` wraps both sides in `Buffer.from(..., 'hex')` and calls `crypto.timingSafeEqual`. `verifyPassword` in `auth.js:58` also uses `timingSafeEqual`. Only `verifyToken` doesn't.

**Impact:** `!==` on two strings is a theoretical timing side channel against the session HMAC. In practice Vercel's network jitter makes this extremely hard to exploit, so this is tech-debt severity. The signal worth flagging: the codebase already knows the right pattern and applied it inconsistently, which means the next person reading `auth.js` might assume the project doesn't care about constant-time compare — and copy the wrong pattern elsewhere.

**Suggested fix:** Mirror `client-auth.js:46-49` — convert both hex strings to Buffers and compare with `crypto.timingSafeEqual` after a length check.
