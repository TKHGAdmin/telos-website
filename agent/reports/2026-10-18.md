# Telos Bug Hunter — 2026-10-18

**Focus:** Security
**Scan window:** 2026-10-18 (first run — full repo at HEAD on `claude/ecstatic-gauss-6hdbz8`)
**Findings:** 5  (P0: 0, P1: 2, P2: 2, P3: 1)

## Summary

First run. Scanned every endpoint under `api/` plus the two auth libraries, both cron jobs, and the service worker. Found two concrete P1 brute-force gaps (admin login and client login have no rate limiting, while every other public endpoint does), a non-constant-time compare in the admin session verifier that the client-side auth library already does correctly, an SSRF path through client-controlled push-subscription endpoints, and a session-invalidation gap in the password reset flow. No P0s. No fabricated findings — code-only review, no runtime testing.

## Findings

### [P1] Admin login endpoint has no rate limiting

- **ID:** 2026-10-18-admin-login-no-ratelimit
- **File:** api/dashboard/login.js:1-17
- **Category:** security
- **Status:** new

**What's wrong**
`/api/dashboard/login` accepts unlimited POSTs. `verifyPassword` in `api/lib/auth.js:52-59` compares in constant time, but there is no outer INCR/EXPIRE guard, no attempt counter, and no lockout. Every other public POST endpoint in this project (`submit-quiz.js:24-29`, `submit-email.js:28-34`, `submit-chs-application.js:40-46`) caps at 5–10 requests per IP per hour using the same Redis `INCR` + `EXPIRE 3600` pattern. The admin login does not.

**Reproduce**
Code trace: `api/dashboard/login.js` reads `req.body.password`, calls `verifyPassword`, returns 401 or sets a cookie. No Redis call before the password check. Live confirmation: `for i in $(seq 1 10000); do curl -s -o /dev/null -w "%{http_code}\n" -X POST https://www.telosathleticclub.com/api/dashboard/login -H "Content-Type: application/json" -d '{"password":"guess'$i'"}'; done | sort -u` — you will only see `401`, never `429`.

**Impact**
The admin dashboard is the business's control plane: every client's health data, the lead pipeline, revenue, ad spend, and the ability to send push notifications and emails as "Telos" are all behind this single password. An attacker who guesses it owns the business. A single IP with a wordlist and no rate limit guarantees progress; a small botnet makes it trivial.

**Suggested fix**
Add the same INCR+EXPIRE pattern used in `submit-quiz.js`, but tighter — e.g., 5 attempts per IP per 15 minutes, and consider a second counter keyed on the attempted password hash so a distributed attack still trips a global cap. Return 429 on breach. On Vercel, prefer `x-forwarded-for` first-hop (not the full chain) as the IP.

### [P1] Client login endpoint has no rate limiting

- **ID:** 2026-10-18-client-login-no-ratelimit
- **File:** api/client/login.js:9-60
- **Category:** security
- **Status:** new

**What's wrong**
`/api/client/login` has the same structural gap: no INCR/EXPIRE around the password check. Combined with `api/client/reset-password.js:72` enforcing only an 8-character minimum (no complexity, no breach-list check), each client account is unlimited-guess brute-forceable.

**Reproduce**
Code trace: `api/client/login.js:17-48` — reads `body.email`/`body.password`, looks up `client_email:` → `client:` → `verifyPassword`, returns 401 or sets cookie. No rate-limit Redis call anywhere.

**Impact**
Each client account stores body-weight entries, nutrition logs, daily check-ins, 545 goals (personal), training history, and (per CLAUDE.md) can also mount through the Whop iframe. An 8-char lowercase-only password has ~2^38 bits of effective entropy at best; with unlimited attempts against a single victim this is reachable with a modest wordlist in days. More targeted than the admin: an attacker only needs to know a client's email, which the dashboard surfaces in multiple places and the "Book a Call" / reset flows don't hide.

**Suggested fix**
Same INCR+EXPIRE pattern, keyed on both IP and normalized email (two independent counters, trip on either). Return 429. Consider adding a per-account `failedLoginsSinceSuccess` field on the client record and locking after N consecutive failures until a reset email is sent.

### [P2] Admin session HMAC compared with non-constant-time `!==`

- **ID:** 2026-10-18-auth-timing-unsafe-compare
- **File:** api/lib/auth.js:27
- **Category:** security
- **Status:** new

**What's wrong**
`verifyToken` compares the request-supplied HMAC signature to the computed one with JavaScript `!==`:
```
if (signature !== expected) return false;
```
JS string equality short-circuits on the first byte difference. That leaks timing information byte-by-byte, allowing a well-resourced attacker who can time repeated requests to the dashboard to forge a valid admin session cookie without ever knowing `SESSION_SECRET`. The sibling file `api/lib/client-auth.js:46-49` performs the exact same comparison correctly, with `crypto.timingSafeEqual` on hex-decoded buffers — so the admin path is a direct one-line regression against the project's own pattern.

**Reproduce**
Code inspection. Compare `api/lib/auth.js:23-27` to `api/lib/client-auth.js:46-49`:
- client-auth: `var a = Buffer.from(signature, 'hex'); var b = Buffer.from(expected, 'hex'); if (a.length !== b.length) return null; if (!crypto.timingSafeEqual(a, b)) return null;`
- auth (admin): `if (signature !== expected) return false;`

**Impact**
Admin session cookie forgery via a cross-network timing side channel. Dangerous because the admin cookie unlocks the full dashboard (same blast radius as finding 1), and this is a sub-millisecond-granularity leak visible to any attacker with repeatable timing to the endpoint. Lower immediate exploitability than the brute-force findings — but a strictly worse ceiling, because this bypasses password strength and rate limiting entirely.

**Suggested fix**
Mirror the client-auth implementation exactly: hex-decode both sides into Buffers, length-check, then `crypto.timingSafeEqual`. The payload (expiry) itself is public and can keep plain `===` on `parseInt`.

### [P2] SSRF via unvalidated push-subscription endpoint

- **ID:** 2026-10-18-notify-ssrf
- **File:** api/client/notify.js:62-69 (sink), api/client/push-subscribe.js:16-25 (source)
- **Category:** security
- **Status:** new

**What's wrong**
`push-subscribe.js` stores `body.subscription` verbatim with no validation that `subscription.endpoint` is a legitimate push gateway (`fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com`, `web.push.apple.com`, etc.). `notify.js` later fetches that URL on admin trigger:
```
var pushRes = await fetch(subscription.endpoint, { method: 'POST', headers: {...}, body: payload });
```
Any authenticated client can register `subscription.endpoint = "http://169.254.169.254/..."` (cloud metadata IP), `"http://127.0.0.1:6379/..."`, or `"https://attacker.com/log"` and wait for admin to click "Send push." The server will then POST on their behalf.

**Reproduce**
1. Log into any client portal account (or create one through the admin).
2. From the browser console: `fetch('/api/client/push-subscribe', { method:'POST', headers:{'Content-Type':'application/json'}, body: JSON.stringify({ subscription: { endpoint: 'http://169.254.169.254/latest/meta-data/', keys: { p256dh: 'x', auth: 'x' } } }) })`.
3. Admin triggers a push notification to that client (any UI path that reaches `/api/client/notify` with the clientId).
4. The server makes a POST to the attacker-chosen URL. (Only exercised in production when `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` are set — `notify.js:41-45` early-returns otherwise, which is why this hasn't been observed yet.)

**Impact**
Classic server-side request forgery, limited by Vercel's serverless network environment (no AWS IMDS, outbound-only), but still enables: port scanning of any reachable internal address, exfiltration of request-side headers to attacker domains, and letting an attacker use the Telos server's IP to attack third parties (abuse reports then come to Thomas). Impact grows if the project ever moves off Vercel to a more permissive host.

**Suggested fix**
In `push-subscribe.js`, before storing, parse `subscription.endpoint` as a URL and reject anything whose hostname is not in a small allowlist of known push gateways. Also reject `http:` (require `https:`) and anything resolving to a private/link-local range. Fail closed on any parse error.

### [P3] Password reset does not invalidate existing client sessions

- **ID:** 2026-10-18-reset-doesnt-invalidate-sessions
- **File:** api/client/reset-password.js:71-96
- **Category:** security
- **Status:** new

**What's wrong**
Setting a new password rewrites `client.passwordHash` and `client.passwordSalt` but does not change anything that invalidates previously issued session cookies. The client token in `api/lib/client-auth.js:24-32` is `{clientId}.{expiry}.{signature}` where the signature is HMAC(SESSION_SECRET, "clientId.expiry") — it is in no way bound to the password. An attacker who got in via a leaked session (phishing, device theft, etc.) keeps full access for up to 7 days after the victim resets their password.

**Reproduce**
1. Log in as client A in browser 1; keep the `telos_client_session` cookie.
2. In browser 2, trigger "forgot password", follow the email link, set a new password.
3. Return to browser 1 — the cookie still authenticates every `/api/client/*` call until the 7-day expiry.

**Impact**
Password reset is the user's primary account-recovery lever. If it doesn't kick out other sessions, it fails its most important job. Low immediate exploitability (requires the attacker to have already compromised a session), but any user who resets their password is doing so *because* they fear compromise, and the system is silently leaving them exposed.

**Suggested fix**
Add a `sessionsInvalidatedAt` or `passwordVersion` field to the client record, bumped on every password change (both reset and future "change password" UI). Include it in the signed token payload (`{clientId}.{version}.{expiry}.{signature}`) and reject tokens whose version doesn't match the current client record.
