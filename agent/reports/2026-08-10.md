## Summary

First bug hunter run. Bootstrapped the `agent/` scaffolding and the `docs/BUG_REPORT_SCHEMA.md` (both were missing), then swept the API layer for functional and security defects with real user-flow impact. Four findings survived triage: two data-integrity / brute-force P1s in the client and admin auth paths, and two P2s covering client-side auth abuse and a rate-limit key that can be spoofed. No P0s. Recommend fixing the client-delete orphan first since it silently corrupts the coach's roster over time.

## Findings

### [P1] Deleting a client leaves an orphan `client_email:` lookup and blocks re-adding the same email

- **File:** `api/dashboard/clients.js:143-154`
- **Category:** functional
- **Confidence:** high

**What's wrong:** The DELETE handler removes `client:{id}` and drops the client from `clients_index`, but never deletes the `client_email:{normalizedEmail}` lookup that was created when the portal was enabled (`api/dashboard/client-portal.js:115-118`). The lookup keeps pointing at the deleted client's id.

**Reproduction:**
1. In `/thomas` Clients tab, create a client with any email, enable the portal (sets `client_email:{email}` -> id).
2. Delete that client.
3. Try to create a new client with the same email. The POST at `api/dashboard/clients.js:70-73` reads the still-present `client_email:{email}`, sees a non-null owner, and returns `400 {"error":"Email already in use by another client"}`. There is no admin surface to clean this up; the coach is stuck.

Additional impact: if the coach never re-adds, the orphan key is invisible dead data that also confuses `login.js` (returns 401 because `client:{id}` is missing, but only after burning a lookup fetch).

**Suggested fix:** In the DELETE branch, read the client first, and if it existed with a `client_email:` lookup, also `DEL client_email:{normalizeEmail(client.email)}` in the same batch. Mirror the cleanup already done when the portal is disabled in `client-portal.js:121-124`.

**ID:** BUG-2026-08-10-01

### [P1] No rate limit on `/api/dashboard/login` - dashboard password is brute-forceable

- **File:** `api/dashboard/login.js:1-17`
- **Category:** security
- **Confidence:** high

**What's wrong:** The admin login endpoint does a single `verifyPassword` check and returns 401 on failure with no counter, no lockout, no backoff, no CAPTCHA. The public submit endpoints (`api/submit-*.js`) all have per-IP rate limits, but the endpoint that gates the entire business dashboard - clients, revenue, quiz submissions, Charleston applications, ad spend, all of Redis - does not.

**Reproduction:** Any attacker who can reach `POST /api/dashboard/login` can attempt unlimited passwords per second from a single IP. There is no server-side signal that would slow them or notify Thomas.

**Suggested fix:** Add the same `INCR + EXPIRE` pattern used in `submit-quiz.js:22-29` keyed on `ratelimit:dashlogin:{ip}` with something conservative like 10 attempts per hour. Also consider logging failed attempts so a pattern is visible in Vercel logs.

**ID:** BUG-2026-08-10-02

### [P2] No rate limit on `/api/client/login` or `/api/client/reset-password`

- **File:** `api/client/login.js:1-60`, `api/client/reset-password.js:20-68`
- **Category:** security
- **Confidence:** high

**What's wrong:** Both client-side auth endpoints accept unlimited requests. Login can be brute-forced against any known client email. The reset-password email step can be spammed - each valid client email triggers a Resend send with no throttle, burning Resend quota and flooding the client's inbox with reset links. The endpoint intentionally returns 200 for unknown emails to prevent enumeration, but the presence-vs-absence of an actual delivered email is itself an enumeration side channel.

**Reproduction:**
- Login: POST `{email, password}` in a loop; no throttle triggers.
- Reset: POST `{email: knownClientEmail}` in a loop; each call fires a Resend email until Resend's own limits engage.

**Suggested fix:** Add per-IP `ratelimit:clientlogin:{ip}` (e.g. 10/hour) and per-email `ratelimit:reset:{normalizedEmail}` (e.g. 3/hour) using the same `INCR + EXPIRE` helper the public endpoints use. Consider also throttling per-IP on reset to stop broad enumeration sweeps.

**ID:** BUG-2026-08-10-03

### [P2] Rate-limit key uses raw `x-forwarded-for` and can be bypassed by prepending a header

- **File:** `api/submit-quiz.js:23`, `api/submit-email.js:28`, `api/submit-chs-application.js:40`
- **Category:** security
- **Confidence:** high

**What's wrong:** All three public write endpoints build their Redis key as `` `ratelimit:*:${ip}` `` where `ip` is `req.headers['x-forwarded-for']` verbatim. On Vercel that header is a comma-separated chain (`client, edge, ...`). Any caller who adds their own value to `x-forwarded-for` shifts the string and therefore shifts the Redis key, so the same real IP maps to a new bucket per header value - the rate limit does not hold.

**Reproduction:** `curl -H "x-forwarded-for: 1.2.3.$RANDOM" -X POST https://.../api/submit-quiz` in a loop. Each request lands in a fresh bucket and none exceed the 10/hour limit.

**Suggested fix:** Normalize the client identifier once: take the first token (`String(raw).split(',')[0].trim()`), or prefer `x-real-ip` which Vercel sets to the trusted client IP. Same fix in all three endpoints and any future rate-limited ones (see BUG-2026-08-10-02 and 03).

**ID:** BUG-2026-08-10-04
