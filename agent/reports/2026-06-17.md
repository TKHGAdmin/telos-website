## Findings

### BUG-2026-06-17-01 — Empty `DASHBOARD_PASSWORD` env var would allow login with empty password

- **Severity:** P1
- **Location:** `api/lib/auth.js:52-59`
- **Description:** `verifyPassword` builds `expected = DASHBOARD_PASSWORD || ''` and compares it to the submitted input with `crypto.timingSafeEqual`. Two zero-length buffers compare equal and the function returns `true`. So if `DASHBOARD_PASSWORD` is ever unset, empty, or misconfigured, submitting an empty password to `/api/dashboard/login` authenticates as admin.
- **Impact:** Full admin dashboard takeover the moment the env var is missing or accidentally blanked. Production is currently safe assuming the var is set, but the auth library should not rely on operational hygiene to stay closed — it should fail closed on missing config. This is the highest-blast-radius failure mode in the system, so it deserves a fail-safe even if today's prod is OK.
- **Reproduction:**
  1. Unset (or blank) `DASHBOARD_PASSWORD` in the Vercel env.
  2. `POST /api/dashboard/login` with `{ "password": "" }`.
  3. Endpoint returns 200 + sets `telos_dash_session` cookie. Full `/thomas` access granted.
- **Suggested fix:** Early-return `false` if the expected password is empty:
  ```js
  function verifyPassword(input) {
    const expected = DASHBOARD_PASSWORD || '';
    const inputStr = input || '';
    if (!expected) return false;            // fail closed on missing config
    if (inputStr.length !== expected.length) return false;
    // ...rest unchanged
  }
  ```
  Optionally also throw at module load if `DASHBOARD_PASSWORD` is unset, to surface misconfiguration loudly.
- **Confidence:** high

### BUG-2026-06-17-02 — `showEmpty()` only targets shop-page DOM, so product-detail page hangs on loading when Shopify init fails

- **Severity:** P2
- **Location:** `js/shop.js:502-507` (called from `:26`, `:33`, `:71`, `:92`, `:119`)
- **Description:** `js/shop.js` is shared between `shop.html` (product grid) and `product.html` (product detail). The shared error/empty-state helper:
  ```js
  function showEmpty() {
    var loading = document.getElementById('shopLoading');
    var empty = document.getElementById('shopEmpty');
    if (loading) loading.style.display = 'none';
    if (empty) empty.style.display = 'block';
  }
  ```
  hard-codes the shop page's IDs (`shopLoading`, `shopEmpty`). The product detail page uses `productLoading` and `productNotFound` instead. So whenever the Shopify Buy SDK fails to load, the SDK is undefined, the init-time `try/catch` fires, or `createFreshCheckout` rejects on `product.html`, `showEmpty()` finds nothing to toggle and the user is stranded on the loading spinner forever.
- **Impact:** Any Shopify outage, ad-blocker that blocks the Buy SDK CDN, or transient checkout-create failure leaves visitors on `/product?p=...` staring at a "Loading..." state indefinitely with no error message and no way to recover. The grid page degrades gracefully; the detail page does not.
- **Reproduction:**
  1. Open DevTools → Network → block `sdks.shopifycdn.com`.
  2. Hard reload `/product?p=<any-handle>`.
  3. Observe the loading spinner never resolves; `productNotFound` never appears.
- **Suggested fix:** Make `showEmpty()` aware of both pages, e.g.:
  ```js
  function showEmpty() {
    var loaders = ['shopLoading', 'productLoading'];
    var emptys  = ['shopEmpty', 'productNotFound'];
    loaders.forEach(function (id) { var el = document.getElementById(id); if (el) el.style.display = 'none'; });
    emptys.forEach(function (id) { var el = document.getElementById(id); if (el) el.style.display = 'block'; });
  }
  ```
- **Confidence:** high

### BUG-2026-06-17-03 — `js/shop.js` cache-buster version drift between `shop.html` and `product.html`

- **Severity:** P3
- **Location:** `shop.html:841` (`js/shop.js?v=1`) vs `product.html:822` (`js/shop.js?v=2`)
- **Description:** The two pages that load the same script use different cache-buster query params. The convention in `CLAUDE.md` for CSS is to bump the version everywhere together; the same logic applies here. Right now anyone who has visited shop.html and cached `js/shop.js?v=1` will keep using that cached copy on subsequent shop visits, but get the fresh `?v=2` copy on product.html — so the two pages can diverge on cart/checkout behavior between deploys.
- **Impact:** Low today (both `v=1` and `v=2` bytes resolve to the same file on the server) but a guaranteed footgun the next time shop.js changes: shop.html visitors will run stale code while product.html visitors get the fix. Carts could mis-sync. Worth fixing as a one-line change.
- **Reproduction:** `grep -n "shop.js?v=" *.html` shows the two values diverge.
- **Suggested fix:** Bump `shop.html:841` to `js/shop.js?v=2` (matching product.html). Then keep both in lockstep on future bumps, same as the `style.css?v=N` convention.
- **Confidence:** high

## Not-bugs investigated

- **Shopify Storefront access token hardcoded in `js/shop.js:15`.** Storefront tokens are explicitly designed to be public/client-side and are scoped to read-only storefront ops. Not a leak.
- **`.html` suffixes in 45 internal `href`s across 30 files.** Vercel `cleanUrls: true` 308-redirects `/foo.html` → `/foo`. Links still work; just one extra hop. Cosmetic, not P1.
- **Quiz fetch in `js/quiz.js` swallows errors silently.** `CLAUDE.md` documents this as intentional ("non-blocking, silent fail"). Product decision, not a bug.
- **`SESSION_SECRET` not validated at module load in `auth.js`/`client-auth.js`.** If unset, `crypto.createHmac('sha256', undefined)` throws, so the system fails closed (sessions can't be created or verified). Defense-in-depth nit, not actionable.
- **`x-forwarded-for` used directly as rate-limit key in submit endpoints.** Vercel sets this header reliably; client cannot override it. Real-world risk is negligible.
