## BUG-20261128-01 - P1 - Client DELETE leaves email reservation and per-client data orphaned

**Category:** data-integrity
**File:** `api/dashboard/clients.js:143`
**Status:** new

### Evidence
The DELETE handler only runs `DEL client:{id}` and `ZREM clients_index`. It never removes `client_email:{normalizedEmail}` (set by POST at `clients.js:70-73` and used as the uniqueness gate for new-client creation), and it never cleans any of the per-client plan/log/index keys documented in CLAUDE.md (`client_nutrition_plan`, `client_training_program`, `client_sidemenu`, `client_supplement_plan`, `client_mindset`, `client_resources`, `client_545_*`, `client_dailylog:{id}:*`, `client_dailylogs_index:{id}`, `client_nutrition_log` + index, `client_training_log` + index, `client_activity_log` + index, `client_supplement_log` + index, `client_modules_*`, `client_push_sub`, open `password_reset:*` tokens).

### Reproduction
1. In `/thomas` Clients tab, create a client with email `test@example.com` and enable the portal (writes `client_email:test@example.com` → id via `client-portal.js`).
2. Delete that client (DELETE `/api/dashboard/clients?id=N`).
3. Try to re-create a client with the same email: POST `/api/dashboard/clients` returns 400 "Email already in use by another client" (`clients.js:72`), even though no client with that id exists any longer. The only fix today is manual Redis surgery.

### Impact
- Coach can never re-onboard a churned or mistakenly-deleted client under their original email without manual Upstash intervention.
- Upstash Redis accumulates orphaned per-client plans and daily logs for every deleted client (small per client, but monotonic and visible in storage usage over months).
- No PII leak because the records have no owner to query them back, but they persist indefinitely.

### Suggested fix
In the DELETE branch, read the existing client first, then `DEL client_email:${normalizeEmail(client.email)}` and the full per-client key set (and `ZREM` the per-client ZSET indexes). At minimum, delete the email lookup so re-add is unblocked; the plan/log cleanup can land in a follow-up.

## BUG-20261128-02 - P2 - Admin verifyPassword returns true for empty input when DASHBOARD_PASSWORD is unset

**Category:** auth
**File:** `api/lib/auth.js:52`
**Status:** new

### Evidence
`verifyPassword(input)` computes `expected = DASHBOARD_PASSWORD || ''` and `inputStr = input || ''`. When the env var is unset and `input` is empty/missing, both strings have length 0, so the length-mismatch gate passes and `crypto.timingSafeEqual(Buffer.from(''), Buffer.from(''))` returns `true`. The function returns `true`.

**Why this is P2, not P0:** the only caller is `api/dashboard/login.js:10`, which short-circuits with `if (!password || !verifyPassword(password))`. An empty-string `password` is falsy, so the endpoint rejects it with 401 before `verifyPassword` ever runs. The bug is not exploitable through the current login path — it's a defense-in-depth failure in the primitive. If `login.js` is ever refactored to drop the `!password` guard (reasonable, since it feels like the sub-function's job), fail-open re-emerges and becomes an unauthenticated admin takeover of all client PII, revenue, and Charleston applications.

### Reproduction
Cannot be exploited live. To see the primitive break in isolation:
```
node -e "
process.env.SESSION_SECRET='x';
const { verifyPassword } = require('./api/lib/auth');
console.log(verifyPassword(''));  // true
console.log(verifyPassword(undefined));  // true
"
```

### Impact
No live impact today. Material risk is a future refactor of `dashboard/login.js` silently enabling empty-password login against any Vercel environment where `DASHBOARD_PASSWORD` is unset or scope-misconfigured (preview envs, forks, forgotten rotation). The cron handlers already fail-closed on missing secrets; admin auth should match.

### Suggested fix
First line of `verifyPassword`: `if (!expected) return false;` (and consider a module-load guard that throws when `SESSION_SECRET` is missing, so misconfiguration fails loud instead of quiet).

## BUG-20261128-03 - P2 - Blog articles use `../index.html` in every nav link, hitting 308 redirect

**Category:** routing
**File:** `blog/*.html` (184 occurrences across 23 articles; first hit `blog/90-day-rule.html` line 271 area)
**Status:** new

### Evidence
Grep finds exactly 184 `href="../index.html` occurrences, 8 per blog article across all 23 files (logo link, System / About / FAQ nav items, Back-to-Telos CTA, footer links). `vercel.json` sets `"cleanUrls": true`, which 308-redirects every `.html` URL to its clean form. CLAUDE.md explicitly states: "All internal links use clean URLs without `.html` extension."

### Reproduction
Load `https://www.telosathleticclub.com/blog/90-day-rule`, open DevTools Network, click the TELOS FITNESS logo or any System/About/FAQ nav item: you'll see a 308 from `/index.html` → `/` before the 200. Observable as an extra round-trip (~100-300ms on mobile/slow networks) on every blog→marketing navigation.

### Impact
Blog is the primary organic SEO surface (23 long-form articles). Every click from a blog page back into the main site pays an extra redirect. Not broken functionality, but a user-visible latency tax on inbound traffic and an explicit violation of the documented convention — any future audit flags the same gap again.

### Suggested fix
Mechanical global replace across `blog/`:
- `href="../index.html` → `href="../`
- `href="../index.html#` → `href="../#`

184 occurrences, fully deterministic.
