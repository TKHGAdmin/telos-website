# Telos Bug Report - 2026-10-04

**Focus:** functional
**Findings:** 3

## Summary

First autonomous run. Three functional bugs surfaced on high-confidence, high-signal paths: a wrong Instagram link in the homepage navigation (sends users to an unrelated handle), orphaned data on client deletion in the admin API (prevents reusing a deleted client's email), and missing rate limiting on client password reset (email-bomb and enumeration vector). All three are reproducible by code inspection; no theoretical/speculative items included.

## Findings

### 2026-10-04-01 - P2 - Nav Instagram link points to wrong handle
- **File:** `index.html:34`
- **Category:** functional
- **Summary:** The homepage navigation's Instagram "story ring" avatar links to `instagram.com/telosathleticclub` while every other reference in the site (19 occurrences in footers, blog pages, resources page, shop, and CLAUDE.md) uses `instagram.com/telos_fitness`.
- **Repro:**
  - `grep -rEhn "instagram\.com/" --include="*.html"` returns `19 instagram.com/telos_fitness` vs `1 instagram.com/telosathleticclub`.
  - The single outlier is on `index.html:34`: `<a href="https://www.instagram.com/telosathleticclub" ... title="@telosathleticclub">`.
  - CLAUDE.md "External Services" explicitly lists Instagram as `@telos_fitness`.
- **Impact:** The most prominent IG link on the site (next to the nav logo on the homepage) sends new visitors to a different account than the one the brand actually operates. If `@telosathleticclub` is unclaimed or unrelated, it is effectively a dead link / brand confusion on the primary landing page. Social proof from the real IG account is lost.
- **Suggested fix:** Change `href` to `https://instagram.com/telos_fitness` and update the `title` attribute to `@telos_fitness` to match the other 19 references. If the brand genuinely owns both accounts and the nav one is intentional, update CLAUDE.md and the footers so the site is consistent either way.

### 2026-10-04-02 - P2 - DELETE client orphans email index and portal data
- **File:** `api/dashboard/clients.js:143`
- **Category:** functional
- **Summary:** The admin `DELETE /api/dashboard/clients` handler removes `client:{id}` and the `clients_index` ZSET entry, but leaves the `client_email:{normalizedEmail}` lookup and every per-client key (daily logs, nutrition logs, training logs, 545 goals, push subscription, supplement plan, etc.) in Redis.
- **Repro:**
  - `api/dashboard/clients.js:147-148` on DELETE only issues `DEL client:{id}` and `ZREM clients_index {id}`.
  - `api/dashboard/client-portal.js:117` writes `client_email:{email}` → `{clientId}` whenever portal is enabled.
  - `api/dashboard/clients.js:70-73` (POST) rejects a new client whose email matches an existing `client_email:` entry.
  - Flow that reproduces: enable portal for client A (email alice@x.com), delete client A, then try to create a new client with alice@x.com. The POST returns `400: Email already in use by another client` even though no client with that email exists.
- **Impact:** (a) A reused email (common on a small coaching roster) is silently blocked after a delete; the admin sees a confusing "already in use" error with no owner to resolve. (b) An attacker-controlled login attempt against the orphaned email reaches `client:{id}` lookup and fails cleanly, so no auth bypass — but all historical check-ins, nutrition entries, and training logs for the deleted client remain in Redis indefinitely (data-retention / privacy concern if the deletion was performed in response to a client request).
- **Suggested fix:** In the DELETE branch, before `DEL client:{id}`: read the client, if `portalEnabled` and `email` are set, `DEL client_email:{normalizeEmail(email)}`. Then also delete the per-client keys the admin UI knows about (the same key families enumerated in CLAUDE.md "Client Dashboard - Redis Keys"). If full cascade is too risky, at minimum delete `client_email:*` and `client_push_sub:*` so email reuse and future push delivery to a stale endpoint are not broken.

### 2026-10-04-03 - P3 - Password reset endpoint has no rate limit
- **File:** `api/client/reset-password.js:20`
- **Category:** functional (security-adjacent)
- **Summary:** `POST /api/client/reset-password` with `{ email }` sends a Resend email to any matching client email with no throttle. The quiz, email-capture, and CHS submission endpoints all rate-limit by IP (`ratelimit:*:{ip}`), but this one does not.
- **Repro:**
  - `api/client/reset-password.js` has no `ratelimit:` key or counter anywhere in the handler.
  - Compare `api/submit-quiz.js:22-29`, `api/submit-email.js:27-34`, and `api/submit-chs-application.js:39-46`, which all implement `INCR` + `EXPIRE 3600` + 429 at a threshold.
  - A script hitting `POST /api/client/reset-password` 60 times with a known client email will send 60 Resend emails and generate 60 valid `password_reset:{token}` entries (SETEX 3600 each).
- **Impact:** Email-bomb vector against any known client email (deliverability pain for the client, Resend quota/reputation hit for Telos). Also enables timing-based email enumeration since the handler does extra Redis lookups + a Resend POST only when the email exists, measurably widening the "exists" vs "doesn't exist" response time even though the HTTP status is intentionally identical.
- **Suggested fix:** Mirror the pattern from `submit-email.js`: on entry, `INCR ratelimit:pwreset:{ip}`; `EXPIRE 3600` on first increment; return `429` if the count exceeds a small threshold (e.g., 5/hour). Optionally also rate-limit per target email (`ratelimit:pwreset:email:{normalizedEmail}`) at ~3/hour to blunt distributed-IP attacks against one user.
