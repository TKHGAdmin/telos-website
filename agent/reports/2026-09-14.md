## P1 - Deleting a client leaves the email lookup key behind, blocking re-add with the same email

**File:** `api/dashboard/clients.js`
**Lines:** 142-154 (DELETE handler)

### What it does
When a coach deletes a client from the admin dashboard, the handler removes `client:{id}` and the `clients_index` entry, but does **not** delete the `client_email:{normalizedEmail}` lookup key that was created when the client's portal was enabled (see `api/dashboard/client-portal.js:115-118`).

### Why it's a bug
The POST handler for creating a client refuses if an email is already in use:

```js
// clients.js:70-73
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

Because the DELETE never cleans up `client_email:*`, the stale lookup permanently owns that email address. The coach cannot re-add the same person (a very common real workflow: someone paused, deleted from roster, then rejoined). The only workaround is manually flushing the Redis key, which requires DB access most coaches won't have.

Secondary problems from the same miss:
- Password-reset lookups (`password_reset:{token}` → clientId) will point at a dead id if a reset was in flight when the delete happened, exposing "Client not found" errors in the reset flow.
- All per-client data blobs (`client_dailylog:*`, `client_training_*`, `client_nutrition_*`, `client_supplement_*`, `client_activity_*`, `client_545_*`, `client_sidemenu:*`, `client_push_sub:*`, `client_modules:*`) also leak silently on delete - storage/PII residue.

### Repro
1. Create a client with email `jane@example.com`.
2. Enable portal + set password (creates `client_email:jane@example.com`).
3. Delete the client via the admin Clients tab.
4. Try to create a new client with the same email.
5. **Expected:** succeeds. **Actual:** 400 "Email already in use by another client."

### Fix sketch
In the DELETE handler, load the client blob first, then also delete `client_email:{normalizeEmail(client.email)}` (guarded by `portalEnabled` since that's the only path that sets it), and consider a cleanup pass for the per-client data key prefixes. Also drop the ZSET indexes: `client_dailylogs_index:{id}`, `client_nutrition_logs_index:{id}`, `client_training_logs_index:{id}`, `client_supplement_logs_index:{id}`, `client_activity_logs_index:{id}`, `client_545_index:{id}`.

## P1 - Admin login has no rate limiting; single shared password is brute-forceable

**File:** `api/dashboard/login.js`
**Lines:** 1-17 (whole file)

### What it does
The admin dashboard login endpoint validates the submitted password against `DASHBOARD_PASSWORD` in constant time (good) and sets a signed cookie. There is **no rate limiting, no lockout, no captcha, no delay** on failed attempts.

### Why it's a bug
Public POST endpoints for form capture (`submit-quiz`, `submit-email`, `submit-chs-application`) all rate-limit by IP via Redis - but the endpoint that gates the *entire admin dashboard* (all client PII, all leads, all revenue data, all Charleston applications, plus the ability to send emails and push notifications to clients as "Telos") does not. An attacker who guesses the URL `/api/dashboard/login` and knows the site can fire thousands of POSTs an hour. If `DASHBOARD_PASSWORD` is anything short of a long random string, this is trivially attackable.

Blast radius on compromise:
- Read every quiz submission, email capture, and pipeline lead (all with names/emails/phones).
- Read/write the whole client roster including notes, revenue, monthlyRate.
- Set arbitrary password hashes on any client (`client-portal.js`) - full account takeover of any client portal.
- Trigger `send-email.js` and `notify.js` to blast Resend/push to all clients.

### Fix sketch
Add the same INCR/EXPIRE pattern used in `submit-quiz.js:23-29`, keyed as `ratelimit:dashlogin:{ip}`, with a much tighter cap (e.g. 5 attempts / 15 min) that returns 429 on exceed. Consider also increasing the failed-attempt window and adding a global lock (across all IPs) at a few hundred attempts / hour to defend against botnet spray.

## P2 - Weekly summary email reports streak as "consecutive days in past 7 starting from today", which is nearly always 0 or 1

**File:** `api/cron/weekly-summary.js`
**Lines:** 86-90

### What it does
The cron runs Monday 2pm UTC (9am ET). For each active client it fetches the last 7 daily-log keys and computes:

```js
// weekly-summary.js:86-90
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

`d=0` is today (UTC). If today's `client_dailylog:{id}:{today}` key doesn't exist yet, the loop breaks immediately and `streak = 0`, regardless of whether the client has a legitimate 6-day, 30-day, or 100-day streak going.

### Why it's a bug
The cron fires at 9am ET Monday - well before most clients have done a daily check-in for that Monday. The email template then reports "Current Streak: 0 days" (or 1 if they happened to log something late Sunday night ET which landed in Monday UTC, e.g. after 8pm ET Sunday). Users on a real 30-day streak get an email telling them they have 0. That's a broken retention signal, and it's the loudest number in the summary block (line 131 wraps it in `<strong style="color:#C9A84C;">`).

Also, even with today's log present, the value is capped at 7 by loop bound - a true 40-day streak reports as "7 days".

### Repro
- Client logs Sun 9pm ET → key stored as `client_dailylog:{id}:2026-09-14` (Monday UTC after conversion).
- Cron fires Mon 2pm UTC. `todayUTC = 2026-09-14`. Fetches `client_dailylog:{id}:2026-09-14` → present → streak=1. Then `d=1` fetches `2026-09-13` (their Sunday) → present → streak=2. Etc, up to 7.
- Client logs Sun 3pm ET → key stored as `client_dailylog:{id}:2026-09-13` (Sunday UTC).
- Cron fires Mon 2pm UTC. Fetches `client_dailylog:{id}:2026-09-14` → **absent** → streak stops at 0. Their real 6-day streak is not reported.

### Fix sketch
Either (a) skip today and start the streak walk from `d=1` (`yesterday`), or (b) if today is absent, start the walk from yesterday but don't count today as breaking the streak. Also read from the `client_dailylogs_index:{id}` ZSET rather than capping the walk at 7 days, so long streaks display correctly. Optionally align day boundaries to ET rather than UTC via the same `todayStr()` fix already backlogged for the client dashboard.

Lower priority than admin login and set aside for a Security-focus day.
