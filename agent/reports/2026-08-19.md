## Findings

### [P1] Product detail page: broken 2-column grid layout on desktop

- **File:** `product.html:765-780` (HTML) + `product.html:100-115` (CSS)
- **Introduced by:** commit `f5cb8c4` ("feat: add image gallery with thumbnails on product page", 2026-05-20)

**What's wrong**

`.product-detail` is a `display: grid` container with `grid-template-columns: 1fr 1fr` on viewports >768px. The thumbnail gallery commit added a third direct child (`.product-detail-thumbs`) between the image and info columns:

```html
<div class="product-detail" id="productDetail">           <!-- 2-col grid -->
  <div class="product-detail-image" id="productImage"></div>   <!-- (1,1) -->
  <div class="product-detail-thumbs" id="productThumbs"></div> <!-- (1,2) -->
  <div class="product-detail-info">...                         <!-- (2,1) -->
```

Grid places the three children in row-major order into a 2x2 grid, so on desktop:

- **Row 1 col 1:** product image (correct)
- **Row 1 col 2:** empty thumbnails strip (WRONG - product title/price/add-to-cart supposed to be here)
- **Row 2 col 1:** product info (WRONG - drops below the image)
- **Row 2 col 2:** empty

Even for single-image products the thumbs div still occupies a grid cell because `.product-detail-thumbs { display: flex; ... }` on line 120 has no `display: none` fallback.

The mobile breakpoint (`max-width: 768px` → `grid-template-columns: 1fr`) accidentally papers over the bug: all three children stack in one column in the right visual order. So the bug only shows on desktop.

**User impact:** Every desktop visitor to a product page sees the primary conversion action (title, price, Add to Cart) pushed below the fold on the wrong side of the page. On the shop's main product landing page, this materially hurts conversion.

**Failure scenario:** Load any `/product?p=<handle>` URL at ≥769px width. Title and Add to Cart button render below the image instead of beside it; a strip of thumbnails appears in the top-right where the title should be.

**Suggested fix:** Wrap image + thumbs in a single left-column container so the grid only sees two children:

```html
<div class="product-detail" id="productDetail">
  <div class="product-detail-media">
    <div class="product-detail-image" id="productImage"></div>
    <div class="product-detail-thumbs" id="productThumbs"></div>
  </div>
  <div class="product-detail-info">...
```

Or minimally: add `grid-column: 1;` to `.product-detail-thumbs` and `grid-row: 2;` to force it under the image (but that leaves an empty (1,2) cell that pushes info down — the wrapper approach is cleaner).

### [P2] `engagement-check` cron re-emails inactive clients every 24 hours

- **File:** `api/cron/engagement-check.js` (whole file, esp. lines 61-93)

**What's wrong**

The cron runs daily at 15:00 UTC and sends "we miss you" to every active client whose most recent daily log is 3+ days old. It records nothing about which clients were already emailed. So a client who last logged 4 days ago receives an identical reminder today, tomorrow, the day after, and forever until they log a check-in.

Once inactivity crosses 5 days the code stops knowing when the last log was (the search window is only 5 days deep) and forever reports "It's been 5+ days" — the copy stops updating too.

**Failure scenario:** Client stops logging on Monday. Wednesday's cron fires (3 days back), they get "3+ days" email. Thursday: "4+ days" email. Friday and onward: "5+ days" email every 24 hours indefinitely. Client marks Telos as spam.

**Suggested fix:** Track `lastEngagementEmailAt` on the client record (or as a Redis key `engagement_emailed:{clientId}` with a 7-day TTL), and only send when it's been >=7 days since the last send. Also consider stopping the drip after N unanswered sends.

### [P3] `weekly-summary` cron reports streak = 0 whenever today's log is missing

- **File:** `api/cron/weekly-summary.js:87-90`

```js
for (var d = 0; d < 7; d++) {
  if (weekData[0][d] && weekData[0][d].result) streak++;
  else break;
}
```

**What's wrong**

`d = 0` is today (UTC). The cron fires Monday at 14:00 UTC (~9:00 ET), which is early morning ET before most users have done their daily check-in. If the client hasn't logged for "today" yet, the loop breaks on iteration zero and reports `streak = 0` — even for a client who logged all seven prior days.

**Failure scenario:** Client logs Sunday through Saturday (7-day streak). Monday 9 ET the summary email lands claiming "Current Streak: 0 days". Client feels punished for consistency.

**Suggested fix:** Skip missing days at the head of the range and count consecutive days ending at the most recent log. Or just: count total logs across the 7-day window — `daysLogged` in the same file already does exactly this and is what most users expect a "streak" to mean in a weekly recap anyway.

### [P3] `api/lib/auth.js` HMAC signature compare is not timing-safe (parallel client-auth.js IS)

- **File:** `api/lib/auth.js:27`

```js
if (signature !== expected) return false;
```

vs `api/lib/client-auth.js:47-49` for the same operation:

```js
var a = Buffer.from(signature, 'hex');
var b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return null;
if (!crypto.timingSafeEqual(a, b)) return null;
```

**What's wrong**

Admin session tokens are verified with a plain string `!==` compare. That's a timing side-channel, and the two auth libraries have drifted — client-auth.js took the extra care, admin auth.js did not.

**Failure scenario / practical impact:** Very low. The token payload is only `Date.now() + 7d`, so an attacker would have to guess a valid future expiry AND run a network-side timing attack on an HMAC-SHA256 signature over a strong secret. Not exploitable in practice. But it's a defense-in-depth gap and a real inconsistency between two sibling files, so worth aligning next time either file is touched.

**Suggested fix:** Mirror the client-auth.js pattern - Buffer conversion, length check, `crypto.timingSafeEqual`.
