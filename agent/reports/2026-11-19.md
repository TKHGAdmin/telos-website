## P1-1 · Module list endpoint leaks tier-restricted video URLs to all paying clients

**File**: `api/client/modules.js`
**Lines**: 61–69, 123

### What's wrong

`GET /api/client/modules` returns the **full** module record for every published module — including `videoUrl`, `thumbnailUrl`, `description`, `duration` — and only decorates each with `m.accessible = clientTierLevel >= minTier` and `m.locked = !m.accessible`. The frontend honors `locked` (shows an "Upgrade to unlock" badge in `client-dashboard.html:5052`), but **the raw video URL is already in the JSON response** that any authenticated client can read via DevTools → Network or `fetch('/api/client/modules').then(r => r.json())`.

The single-module endpoint `api/client/module.js:56–61` **does** enforce tier access correctly (returns 403 with `requiredTier`), but that enforcement is bypassed entirely by the list endpoint.

Compounding this: `api/dashboard/upload-video.js:30` uploads to Vercel Blob with `access: 'public'`, so a leaked blob URL is directly streamable with no further auth.

### Failure scenario

1. Thomas publishes a Lifestyle+ ($6,997) module with video `https://blob.vercel-storage.com/courses/premium-xyz.mp4`.
2. A Rebuild-tier client ($1,497) logs into `/client-dashboard` and opens DevTools.
3. In console: `fetch('/api/client/modules').then(r => r.json()).then(d => d.modules.filter(m => m.locked).map(m => m.videoUrl))`.
4. They now have every premium-tier video URL. Paste into a new tab, watch for free, share with friends.

### Recommended fix

In `api/client/modules.js`, after marking `accessible`/`locked`, strip sensitive fields on inaccessible modules before returning:

```js
modules.forEach(function(m) {
  // ... existing tier check ...
  if (!m.accessible) {
    delete m.videoUrl;
    delete m.thumbnailUrl;        // optional — thumbnails are usually fine to tease
    // keep title/pillar/duration so the "locked" card can still render
  }
});
```

### Severity rationale

P1 (not P0): it requires an authenticated paying client, not an anonymous attacker, and premium content revenue is the plausible loss. If any module is particularly sensitive (e.g., contract-bound content), bump to P0.

## P1-2 · No rate limiting on admin dashboard login — unlimited password-guess attempts

**File**: `api/dashboard/login.js`
**Lines**: entire file (1–17)

### What's wrong

`POST /api/dashboard/login` validates `DASHBOARD_PASSWORD` with `verifyPassword` (timing-safe) and sets a cookie on success. There is **no rate limit, no lockout, no CAPTCHA, and no attempt counter**. Compare against `api/submit-chs-application.js:39–46` and `api/submit-quiz.js:22–29`, where public endpoints use Upstash `INCR`/`EXPIRE` for per-IP throttling — that same pattern isn't applied here.

Context: the admin dashboard is the keys to the business. A successful login gives read/write on **every** Redis-backed system: clients (names, emails, phones, tiers, revenue), pipeline (lead PII), Charleston applications (goals/history/availability), content calendar, ad spend, and the ability to **set client portal passwords** (which then owns every paying client's account).

### Failure scenario

Attacker discovers `/thomas` is password-gated (easy — the login form is just there). They launch a distributed password-spray from a residential proxy pool. With only one user to target and no throttling, they can run 10+ guesses/sec/IP indefinitely. If `DASHBOARD_PASSWORD` is anything shorter than a strong random 20-char string, it falls in days. On success, they own the business and every paying client's account.

Additionally, `api/lib/auth.js:54–59` returns `false` before `timingSafeEqual` when input length differs from the real password length:

```js
if (inputStr.length !== expected.length) return false;
```

This is a **remotely observable timing side channel on the admin password's length** — the mismatched-length path is strictly faster than the timingSafeEqual path. Combined with unlimited attempts, an attacker can first narrow the length space and then brute-force within it. See P3-2 below.

### Recommended fix

1. Add per-IP rate limit on `POST /api/dashboard/login` — e.g., 5 attempts / 15 min, same pattern as `submit-chs-application.js`:

```js
const ip = req.headers['x-forwarded-for'] || 'unknown';
const key = `ratelimit:admin-login:${ip}`;
const count = await redis('INCR', key);
if (count === 1) await redis('EXPIRE', key, 900);
if (count > 5) return res.status(429).json({ error: 'Too many attempts' });
```

2. Consider a secondary global counter keyed on `ratelimit:admin-login:global` (defense against distributed attacks) with a higher but still bounded ceiling.

3. Alert yourself when the counter is tripped — append the IP to a `admin_login_abuse` Redis list so a future dashboard tab can surface it.

### Severity rationale

P1: a single endpoint gates the entire business. The attack is unlimited-in-time and cheap. Not P0 because DASHBOARD_PASSWORD is presumably not weak, but the risk is permanent as long as the ceiling is infinity.

## P2-1 · Client login & password-reset endpoints are also unrated — per-account brute force and reset-email flood

**Files**: `api/client/login.js`, `api/client/reset-password.js`

### What's wrong

`POST /api/client/login` has no rate limit either. For client accounts specifically:

- Passwords only need 8+ characters (`api/client/reset-password.js:72`). No strength rules beyond length.
- Client emails are easy to guess (client's real email, often a contact on the site or Instagram).
- With unlimited attempts, an attacker who knows a client's email can grind an 8-char password offline-fast.

`POST /api/client/reset-password` (request-email branch, lines 20–68) is also unrated. An attacker can submit the same victim email thousands of times; each one consumes a Resend credit and sends a real reset email to the victim's inbox, creating a nuisance-level DoS and a convenient cover for a real phishing attempt.

### Failure scenario

1. Attacker lists Thomas's clients via Instagram tagged posts or site testimonials — easy to turn a name into an email guess.
2. Attacker runs `fetch('/api/client/login', {method:'POST', body:JSON.stringify({email, password: GUESS})})` at ~50 req/sec. Nothing stops them.
3. On a hit, they log into that client's dashboard — sees body metrics, daily logs, workout history, notes, etc. Plausible stalking vector.

Or, lower-stakes: they spam `/api/client/reset-password` with a target email 1000 times and the client gets 1000 "reset your password" emails.

### Recommended fix

- Rate limit `POST /api/client/login`: per-IP **and** per-target-email (to make distributed attacks still visible). 5 attempts / 15 min per email key is a reasonable start.
- Rate limit the request-email branch of `POST /api/client/reset-password`: 3 requests / hour per email, 20 per hour per IP.

### Severity rationale

P2 rather than P1: individual client blast radius is smaller than the admin blast radius, passwords are PBKDF2-protected so credential replay isn't trivial if Redis leaks, and the risk is one-client-at-a-time. But every paying client's wellness data (weight, mood, sleep, stress, notes) is at stake per account, so it's not P3.

## P3-1 · Non-constant-time comparison of `CRON_SECRET`

**File**: `api/cron/engagement-check.js`
**Line**: 9  (same pattern expected in `api/cron/weekly-summary.js`)

### What's wrong

```js
if (!process.env.CRON_SECRET || req.headers.authorization !== 'Bearer ' + process.env.CRON_SECRET) {
  return res.status(401).json({ error: 'Unauthorized' });
}
```

Plain `!==` on a secret is technically a timing oracle. Practical risk is low because (a) the secret is high-entropy and (b) network timing jitter dwarfs the signal. Noting for defense-in-depth.

### Recommended fix

```js
const auth = req.headers.authorization || '';
const expected = 'Bearer ' + (process.env.CRON_SECRET || '');
const a = Buffer.from(auth);
const b = Buffer.from(expected);
if (!process.env.CRON_SECRET || a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
  return res.status(401).json({ error: 'Unauthorized' });
}
```

### Severity rationale

P3: hardening, not an actively exploitable issue. Include only because the cron endpoints bypass all other auth and the fix is one `require('crypto')` away.

## P3-2 · `verifyPassword` leaks admin-password length via early length-mismatch return

**File**: `api/lib/auth.js`
**Lines**: 54–59

### What's wrong

```js
if (inputStr.length !== expected.length) return false;
const inputBuf = Buffer.from(inputStr, 'utf-8');
const expectedBuf = Buffer.from(expected, 'utf-8');
return crypto.timingSafeEqual(inputBuf, expectedBuf);
```

`timingSafeEqual` requires equal-length buffers, hence the early return — but that early return itself leaks length. The equal-length path does buffer allocation + HMAC-grade compare; the unequal-length path returns immediately. Over many requests an attacker can distinguish the two paths and discover the password's exact length, then limit their brute force to that length.

In isolation this is near-theoretical. Combined with **P1-2** (unlimited admin-login attempts), it becomes meaningfully easier for a brute-force attacker: they first run short bursts at many lengths to find the one whose mean latency differs, then concentrate the rest of the attack there.

### Recommended fix

Pad the compare to a fixed buffer length to eliminate the fast path:

```js
function verifyPassword(input) {
  const expected = DASHBOARD_PASSWORD || '';
  const inputStr = input || '';
  // Compare at fixed length (e.g. 128) so timing does not depend on inputs
  const pad = Buffer.alloc(128);
  const inputBuf = Buffer.concat([Buffer.from(inputStr, 'utf-8'), pad]).slice(0, 128);
  const expectedBuf = Buffer.concat([Buffer.from(expected, 'utf-8'), pad]).slice(0, 128);
  const eq = crypto.timingSafeEqual(inputBuf, expectedBuf);
  return eq && inputStr.length === expected.length;
}
```

### Severity rationale

P3 alone; rises if P1-2 isn't fixed.
