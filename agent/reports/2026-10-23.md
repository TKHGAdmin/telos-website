# Telos Bug Report — 2026-10-23 (Functional)

Three findings. One is a concrete admin-workflow bug (re-creating a deleted client is blocked by orphaned state). One is a session-management gap that effectively delays access revocation by up to seven days. One is a minor data-integrity issue in the lead-capture quiz.

## D1 — Deleting a client leaves the email lookup orphaned, so re-creating the client with the same email fails

- **Severity**: P1
- **Area**: Admin dashboard → Clients → Delete
- **Files**: `api/dashboard/clients.js:143-154`

### What's wrong

The `DELETE` handler removes two things and only two things:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

Everything else that was written for the client stays in Redis. The one that bites immediately is `client_email:{normalizedEmail}`, which the `POST` handler consults on create (lines 70-73):

```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

So after a delete, the lookup still points to the now-missing `client:{id}`. The next create for that email fails with "Email already in use by another client" even though the client is gone and the admin can't see them.

Secondary (data-hygiene) impact: the same handler also skips `client_push_sub`, `client_dailylog`, `client_nutrition_log`, `client_training_log`, `client_training_program`, `client_nutrition_plan`, `client_mindset`, `client_resources`, `client_545_*`, `client_sidemenu`, `client_supplement_plan`, `client_supplement_log`, `client_activity_log`, `client_modules_watching`, `client_modules_completed`, and `client_module_progress`. These accumulate as dead rows if clients churn.

### Repro

1. In `/thomas` → Clients, create a client with email `test@example.com`, enable the portal.
2. Delete that client.
3. Try to re-create a client with `test@example.com`.
4. Expected: client is created.
5. Actual: 400 "Email already in use by another client".

### Minimal fix sketch

In the DELETE branch, before/after deleting the `client:{id}` row, read it, pull out the email, and `DEL client_email:{normalizeEmail(email)}` when `portalEnabled` was true. The orphan-logs cleanup is a bigger job and can be a separate ticket.

## D2 — Disabling a client's portal or marking them inactive does not revoke their existing session

- **Severity**: P2
- **Area**: Client portal auth
- **Files**: `api/lib/client-auth.js:34-52` (where the check happens), every `api/client/*.js` that calls `verifyClientSession` (20+ files)

### What's wrong

`verifyClientSession` only validates the HMAC signature and the token's own `expires` timestamp. It does not look at `client:{id}` to re-check `status` or `portalEnabled`.

The login path on `api/client/login.js:36-41` rightly refuses to issue a cookie when `portalEnabled` is false or `status !== 'active'`, but the cookie's lifetime is seven days (`SESSION_DURATION` in `client-auth.js:6`). So the sequence is:

1. Client logs in while active.
2. Coach disables the portal (`client-portal.js` `POST { enabled: false }`) or marks the client `cancelled` (`clients.js` `PUT { status: 'cancelled' }`).
3. For up to seven days, the client's existing cookie continues to authenticate every `api/client/*` endpoint — including POSTs that mutate their logs, training progress, 545 tasks, nutrition entries, supplement check-ins, etc.

That contradicts the implied contract (login refuses the same client) and gives disabled clients a long tail of continued write access.

### Repro

1. Log in to the client portal as any active client. Note the `telos_client_session` cookie.
2. In `/thomas` → Client Portal, toggle "Portal Enabled" off for that client.
3. In the client tab, call `GET /api/client/me` with the cookie. Expected: 401. Actual: 200 with full client data.
4. Call `POST /api/client/daily-log` with a payload. Expected: 401. Actual: 200, log is saved.

### Minimal fix sketch

Make the client gate a helper that both verifies the token and loads the client row. Something along the lines of:

```js
async function requireActiveClient(req) {
  const id = verifyClientSession(req);
  if (!id) return null;
  const raw = await redis('GET', 'client:' + id);
  if (!raw) return null;
  const c = JSON.parse(raw);
  if (!c.portalEnabled || c.status !== 'active') return null;
  return { id, client: c };
}
```

Then every `api/client/*.js` swaps its two-line gate for `const session = await requireActiveClient(req); if (!session) return res.status(401)...`. The extra read is cheap (one Redis GET already happens in several of these endpoints anyway) and most endpoints already have the client row cached in their own flow.

## D3 — Quiz double-scores when a user taps two options inside the 400 ms auto-advance window

- **Severity**: P3
- **Area**: Public lead-capture quiz (homepage + pricing overlay)
- **Files**: `js/quiz.js:197-218`

### What's wrong

`handleAnswerSelect` adds the option's points to the pillar and then schedules the advance:

```js
quiz.scores[pillar] += option.points;
setTimeout(() => { ... renderQuestion(); ... }, 400);
```

Nothing marks the question answered. Nothing disables the sibling buttons. A fast double-tap on two different options (or the same user clicking A, then clicking C a beat later because they changed their mind) adds BOTH options' points before the timeout fires and `renderQuestion` rebuilds the DOM.

### Impact

Lead quality: an impatient tapper can submit a `totalScore` well above the 40-point ceiling. The score flows into `/api/submit-quiz` and is shown to the user as their "tier" via `getResultTier`, and it's used as a signal in `/thomas` → Leads. Not catastrophic, but it does muddy the lead-grading signal.

### Repro

1. Open `/` or `/pricing`, start the quiz.
2. On any question, quickly tap two options in under 400 ms.
3. Open DevTools console and inspect `quiz.scores`. The pillar for that question has both options' points added.

### Minimal fix sketch

Guard the handler against re-entry:

```js
function handleAnswerSelect(button, option, pillar) {
  if (quiz._answerLock) return;
  quiz._answerLock = true;
  // ...existing body...
  setTimeout(() => {
    quiz._answerLock = false;
    // ...existing advance...
  }, 400);
}
```

Or disable the sibling buttons after the first click — same effect, better feedback.

- **No rate limit on `/api/dashboard/login`** — admin password brute-force surface. PBKDF2/HMAC + a timing-safe check reduce the effective rate but don't bound it. Also Security-day material.
- **Weekly-summary task-score cap mismatch** — `api/cron/weekly-summary.js:78` adds 10 per completed task with no 50-point cap, while the dashboard contract says tasks are capped at 50%. The `Math.min(100)` on line 82 masks it unless a client happens to have more than five tasks. Needs a cross-check with the client dashboard's calculation before I can tell whether it's a cron bug or a doc-vs-code drift.
