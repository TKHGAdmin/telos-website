## BUG-20260708-01: Client DELETE orphans `client_email:` lookup and blocks re-adding same email

- **Severity**: P1
- **Category**: functional
- **File(s)**: `api/dashboard/clients.js:143-153`
- **Reproduction**:
  1. In `/thomas` → Clients, create a client with email `x@example.com`.
  2. Open the Client Portal tab and enable portal access for that client. This causes `api/dashboard/client-portal.js:117` to write `client_email:x@example.com → <clientId>`.
  3. Delete the client via the admin UI (DELETE `/api/dashboard/clients?id=<id>`). The handler only runs `DEL client:{id}` and `ZREM clients_index` — it does not remove the `client_email:` key.
  4. Try to create a new client with the same email `x@example.com`. The POST handler at `api/dashboard/clients.js:70-73` finds the orphaned lookup and returns `400 Email already in use by another client`, even though no client with that email exists.
- **Impact**: Coach cannot re-add a former client (or a new person who happens to reuse the email) after a delete. The orphaned Redis key also confuses the client-login flow at `api/client/login.js:24-32`, which reads `client_email:` first and then errors out looking up the missing `client:{id}` — masking the underlying stale-mapping cause with a generic "Invalid email or password" error.
- **Suggested fix**: Before `DEL client:{id}`, load the client record, normalize its email, and `DEL client_email:<normalized>` (only if that key still points at this `id`, to avoid clobbering a mapping that was reassigned).
- **Confidence**: high

## BUG-20260708-02: Weekly summary email always reports streak = 0 on Monday morning

- **Severity**: P2
- **Category**: functional
- **File(s)**: `api/cron/weekly-summary.js:86-90`
- **Reproduction**:
  1. `vercel.json` schedules `weekly-summary` for Monday 14:00 UTC (9am ET).
  2. In the streak loop `for (var d = 0; d < 7; d++)`, `d = 0` is today's date derived from `now`. At Mon 09:00 ET almost no client has submitted Monday's daily check-in yet, so `weekData[0][0].result` is falsy → `break` fires on the first iteration and `streak` is `0`.
  3. The email body then reports `Current Streak: 0 days` even for clients who logged Sun/Sat/Fri/etc.
- **Impact**: Weekly recap silently under-reports every client's streak (the whole point of a Monday recap covering *last* week). Coach loses trust in the metric; clients on a real streak see "0 days" and feel demoralized. Also asymmetric with the "Days Logged: X / 7" number in the same email, which does count last week correctly.
- **Suggested fix**: Start the streak scan at `d = 1` (yesterday) so today's not-yet-logged status doesn't zero the count. Alternatively, if the intent is "days ending today (inclusive)", treat a missing today as neutral: only `break` when a *past* day is missing.
- **Confidence**: high
