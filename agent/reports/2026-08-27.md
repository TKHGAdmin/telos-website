# Summary

First run of the Telos Bug Hunter. # Bugs

## [P2] Execution Score Quiz duplicates submissions on every retake

**File(s):** `js/quiz.js:225`, `js/quiz.js:397`, `js/quiz.js:403`
**Category:** functional
**Reproducibility:** always

**What's wrong.**

`setupLeadCapture()` calls `submitBtn.addEventListener('click', ...)` (line 225) every time the user reaches the lead-capture step. `renderResults()` does the same for the retake button (line 397) and the pricing-page "View Pricing" button (line 403). The underlying DOM elements are never removed or replaced across retakes - `resetQuiz()` only toggles `display`. So each retake adds one more listener to the existing button. After N retakes the submit fires N+1 times.

**Repro / failure scenario.**

On `pricing.html` (or the homepage quiz):
1. Complete the quiz, fill in name/email/phone, click "See My Score" - 1 POST to `/api/submit-quiz`.
2. Click "Retake Quiz".
3. Complete the quiz again, fill in the form, click "See My Score" - 2 POSTs fire in parallel, 2 writes to `localStorage.telosQuizData`, 2 render passes for the results screen.
4. Repeat N times: N+1 duplicate POSTs on the final submit.

**Impact.**

Every user who retakes the quiz produces duplicate lead rows in `quiz_submissions` (they land as separate ZSET members because the `submittedAt` timestamp is regenerated per fetch). The `/api/submit-quiz` per-IP rate limit is 10/hr (submit-quiz.js:27) - a curious visitor who retakes four times will burn through it (1+2+3+4 = 10) and hit `429` on the fifth attempt. Pipeline noise, wrong lead attribution, and a broken "score compare" UX. Also leaks listeners - not a leak that matters in practice at these numbers, but it is the root cause of the duplication.

**Proposed fix.**

Move the three `addEventListener` calls out of `setupLeadCapture()` / `renderResults()` and attach them once at `DOMContentLoaded` alongside the other one-time bindings, reading current state from the `quiz` object at click time. Alternatively, clone-and-replace each button before re-binding (`btn.replaceWith(btn.cloneNode(true))`).

## [P2] Deleting a client with portal access enabled orphans the email lookup and blocks reuse

**File(s):** `api/dashboard/clients.js:143`, `api/dashboard/clients.js:70`
**Category:** data-integrity
**Reproducibility:** always (when the deleted client had `portalEnabled: true` or previously had it enabled)

**What's wrong.**

The DELETE handler (lines 143-153) only removes `client:{id}` and the `clients_index` ZSET entry. It does not touch `client_email:{normalizedEmail}`, which was written by `api/dashboard/client-portal.js:117` when portal access was enabled. The email lookup is what `POST /api/dashboard/clients` (line 70) checks to guard against duplicate emails, so a stale lookup pointing at a since-deleted client id causes future creations with the same email to fail with `"Email already in use by another client"`.

The same handler also orphans the deleted client's per-day data - `client_dailylog:{id}:*`, `client_dailylogs_index:{id}`, `client_nutrition_log:{id}:*`, `client_training_log:{id}:*`, `client_supplement_log:{id}:*`, `client_activity_log:{id}:*`, `client_545_daily:{id}:*`, `client_545_index:{id}`, `client_nutrition_plan:{id}`, `client_mindset:{id}`, `client_resources:{id}`, `client_training_program:{id}`, `client_sidemenu:{id}`, `client_supplement_plan:{id}`, `client_545_goals:{id}`, `client_545_routine:{id}`, and `client_push_sub:{id}`. That's a slow Redis leak, not a functional block, so it's the secondary concern.

**Repro / failure scenario.**

1. In `/thomas` Clients tab, create a client with email `foo@example.com`.
2. In Client Portal tab, enable portal for that client (writes `client_email:foo@example.com -> <id>`).
3. Delete the client from the Clients tab.
4. Try to create a new client with the same `foo@example.com` - request to `POST /api/dashboard/clients` returns 400: "Email already in use by another client". There is no admin-facing way to clear the lookup short of a Redis CLI session.

**Impact.**

Any time Thomas offboards someone with portal access and later re-onboards them (or a household member reuses an email), client creation is blocked. It is silent from the client's perspective, but frustrating for the admin because the error message implies a different active client owns the email. Also, the orphaned per-client keys accumulate in Redis indefinitely.

**Proposed fix.**

In the DELETE branch, read `client:{id}` first (before the DEL), look up `client.email`, and if it is present, DEL `client_email:{normalizeEmail(client.email)}` alongside the client record. Optional follow-up: also DEL the per-day index ZSETs and the coach-set portal keys listed above (they can be enumerated statically from the schema in CLAUDE.md).

## [P3] Admin session token signature uses a non-timing-safe compare

**File(s):** `api/lib/auth.js:27`
**Category:** security
**Reproducibility:** conditional (defense-in-depth; not remotely exploitable in practice on Vercel)

**What's wrong.**

`verifyToken` compares the HMAC signature with `if (signature !== expected) return false;` (line 27). JavaScript's `!==` on strings short-circuits at the first differing character, so the compare's timing carries information about how many leading hex characters matched. The same repo's `api/lib/client-auth.js` (lines 46-49) does the equivalent check correctly using `crypto.timingSafeEqual` on equal-length buffers, and `verifyPassword` in this very file (lines 52-59) is also timing-safe - so this is a real inconsistency, not a deliberate design choice.

**Repro / failure scenario.**

Under an attacker model with sub-microsecond timing precision against a stable server, an attacker with a valid `expires` payload (which is public - it is the plaintext half of the token) could iterate signature bytes and time responses to `/api/dashboard/*` to recover a forged signature. In reality this is defeated by Vercel's cold-start jitter, network noise, and the 256-bit search space, so this is a defense-in-depth issue, not a live exploit vector.

**Impact.**

No observed user impact. Real cost: an inconsistency that will bite whoever adds another auth surface and mimics `auth.js` instead of `client-auth.js`, plus a lint/audit finding for anyone doing a formal security review.

**Proposed fix.**

Mirror `client-auth.js:46-49`: hex-decode both sides into `Buffer`, guard on equal length, then `crypto.timingSafeEqual(a, b)`. Also worth doing for the dashboard-password length check in `verifyPassword` at the same time (the early-return on unequal length leaks password length, but that is a lower priority since the length is short and less sensitive than the token signature).

On Vercel this header is appended-to, not overwritten, so a client-supplied prefix trivially varies the key. Low-severity (form spam only), noted in `learnings.md` for future Security rotation.
