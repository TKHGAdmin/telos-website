## Summary

First run of the Telos Bug Hunter — bootstrapped the agent memory scaffold (`agent/memory/*`, `docs/BUG_REPORT_SCHEMA.md`) alongside the hunt. Focus was functional bugs across API endpoints, auth flows, and cron jobs. Found three real, reproducible issues: an engagement email that will spam inactive clients every day, a broken duplicate-email guard on client creation, and a missing rate limit on the password-reset endpoint. All three are actionable without touching UI code, and none of them are already tracked in `CLAUDE.md`'s "Known Limitations" backlog.

## Bugs

### BUG-2026-07-20-1 — Daily "we miss you" email spams every inactive client, forever

- **Severity:** P1
- **File(s):** `api/cron/engagement-check.js:61`, `api/cron/engagement-check.js:76-93`
- **Category:** functional
- **Reproduction:** The cron `engagement-check` runs daily (`0 15 * * *` in `vercel.json`). For each active portal-enabled client, it computes `lastLogDaysAgo` from the last five days of `client_dailylog:{id}:{date}` keys, then sends a Resend email if `lastLogDaysAgo === -1 || lastLogDaysAgo >= 3`. There is no per-client "last reminder sent" record — a `grep -rn "lastReminderSent\|engagement" api/` confirms nothing is written. So any client who is 3+ days inactive gets the same "We miss you at Telos" email every single day until they log a check-in.
- **Impact:** Real user harm. A client who's away for a week returns to seven identical guilt-trip emails in their inbox. A client who churns silently gets an email every day indefinitely. Both damage the brand and the domain's sender reputation on Resend (repeat opens/deletes push complaint rates up).
- **Suggested fix:** Track the last reminder date per client — either a `client.lastEngagementEmailAt` field on the client blob, or a dedicated Redis key `client_engagement_reminder:{id}` with e.g. a 6-day TTL. Only send when the tracker is missing or older than N days (7 seems right — matches the weekly cadence of the other cron). Bonus: skip clients whose most recent daily log is older than ~30 days entirely, so long-lapsed accounts stop generating traffic.
- **Confidence:** high

### BUG-2026-07-20-2 — Duplicate-email check on client CREATE is unreachable; portal-enable can hijack another client's login

- **Severity:** P2
- **File(s):** `api/dashboard/clients.js:70-73`, `api/dashboard/clients.js:90-91`, `api/dashboard/client-portal.js:115-118`
- **Category:** functional
- **Reproduction:** `POST /api/dashboard/clients` guards against duplicates by looking up `client_email:{normalizedEmail}` (line 70). But the same handler never writes that key on create (lines 90-91 only set `client:{id}` and `ZADD clients_index`). The reverse index is only populated later, in `client-portal.js:117`, when portal access is enabled. Consequence: (a) creating a second client with the same email as an existing portal-disabled client passes the "duplicate" check silently; (b) then, when the coach enables portal on the second client, `client-portal.js:115-118` unconditionally overwrites `client_email:{email}` — with no ownership check — pointing it at the second client. The first client's portal login now returns the wrong account. Steps to reproduce: create Client A with alice@example.com (portal disabled), create Client B with the same email (succeeds — bug), enable portal on both, log in as alice — you land in whichever record was enabled second.
- **Impact:** Silent data corruption in the client roster and a broken login for whichever client got overwritten. Even without the second step, having two client records with the same email breaks the mental model of the CRM (revenue double-count, weekly summaries sent twice, etc.). Coach won't notice until a client complains they're seeing the wrong dashboard.
- **Suggested fix:** In `clients.js` POST, populate `client_email:{normalizedEmail}` alongside the other writes on line 90-91 (regardless of portal state), and keep the existing duplicate check. In `client-portal.js:115-118`, before overwriting, GET the existing owner and reject with 400 if it's a different `clientId`. Same rule in the PUT email-change branch of `clients.js:121-132` already exists (line 125) — mirror that logic here.
- **Confidence:** high

### BUG-2026-07-20-3 — Password-reset endpoint has no rate limit, allowing inbox flood + Resend quota drain

- **Severity:** P2
- **File(s):** `api/client/reset-password.js:20-67`
- **Category:** functional
- **Reproduction:** `POST /api/client/reset-password` with `{ "email": "victim@example.com" }` calls Redis, generates a new 32-byte token with a 1hr TTL, and fires a Resend email — all without any per-IP or per-email counter. Compare to `submit-quiz.js:24-29`, `submit-email.js:29-34`, and `submit-chs-application.js:40-46`, which all implement the standard `ratelimit:{name}:{ip}` INCR/EXPIRE pattern. An attacker who knows a client's email (or just tries common ones — the endpoint returns 200 either way to prevent enumeration) can trigger arbitrary numbers of "Reset Your Telos Client Portal Password" emails to that inbox from a single IP with a simple `for i in ...; curl` loop.
- **Impact:** Inbox flood for real clients (annoying enough to reset their trust in the portal), Redis storage waste (one token key per request, all with 1hr TTL), and Resend quota burn on the paid plan. Not a data-breach class bug, but the same "abuse-vector" family as unrestricted signup endpoints — worth closing before the site gets popular enough to attract it.
- **Suggested fix:** Add the same rate-limit block used by the other public endpoints, keyed by IP with a low ceiling (e.g. 3/hr) and, ideally, a second counter keyed by the normalized email address (e.g. 5/day) so that even a distributed attack can't spam one victim. Both checks must happen BEFORE the Resend call. Return the same 200 shape on rate-limit rejection to preserve the anti-enumeration behavior.
- **Confidence:** high
