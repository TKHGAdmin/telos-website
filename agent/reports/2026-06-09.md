## [P1] Quiz lead capture submit button bypasses required-field validation

**ID**: bug-2026-06-09-01
**Status**: new
**File(s)**: `index.html:580`, `pricing.html:594`, `js/quiz.js:225-275`
**Category**: functional
**Confidence**: high

### What's wrong

The "See Your Score" button at the end of the quiz lead capture form is
declared as `<button type="button">` instead of `<button type="submit">`.
Because it never triggers form submission, the `required` attributes on the
name and email inputs (lines 577-578 of index.html, 591-592 of pricing.html)
are never evaluated. The click handler in `js/quiz.js` reads the field values
unconditionally and posts whatever is there - including empty strings.

The server endpoint `api/submit-quiz.js` rejects empty name/email with a 400,
but the fetch in `quiz.js:269` ends in `.catch(function() {})` and the user is
still shown the results screen. So the user perceives a successful submission;
the dashboard never receives the lead.

### How to reproduce

1. Open the homepage, scroll to the Execution Score Quiz section, click
   "Start the Diagnostic".
2. Answer all 8 questions (any answers work).
3. On the lead-capture step, leave the Name and Email fields blank.
4. Click "See Your Score".

Expected: the browser blocks submission and focuses the empty field
(because both inputs have `required`).

Actual: the score screen renders. The `submit-quiz` POST returns 400 silently
and no row is written to Redis. `localStorage.telosQuizCompleted` is set to
`true`, so on `pricing.html` the pricing is also unlocked despite no lead
having been captured.

Reference excerpt from `js/quiz.js:225-275`:
```
submitBtn.addEventListener('click', function(e) {
  e.preventDefault();
  // ...captures values, no validation...
  fetch('/api/submit-quiz', { ... }).catch(function() {});
  quizResults.style.display = 'block';
  renderResults();
});
```

### Why it matters

The quiz is the primary lead capture on both `index.html` and `pricing.html`,
and on the pricing page it is the gate that reveals tier prices. Any quiz
respondent who skips the name/email fields - intentionally to bypass the gate,
or accidentally on mobile autofill failures - sees their score and (on
`pricing.html`) sees pricing, while the business gets zero. There is no
visible error state to tell the user the submission failed, so even
well-intentioned users with autofill mishaps will not retry.

The other lead-capture forms on the site (`protein-calculator.html`,
`hyrox-predictor.html`, `chs.html`) use `type="submit"` correctly; the quiz is
the lone outlier.

### Suggested fix

Either change `type="button"` to `type="submit"` on both forms and attach the
handler to the form's `submit` event (so HTML5 validation runs first), or
add explicit JS validation in `setupLeadCapture()` that checks
`nameInput.value.trim()` and a basic email regex before sending the fetch
and rendering results. The first option preserves the existing accessibility
hint of `required`. Either way, the results screen should not render until
the API call succeeds (or a clear inline error should be shown).

## [P1] Engagement-check cron sends a reminder email every single day to inactive clients

**ID**: bug-2026-06-09-02
**Status**: new
**File(s)**: `api/cron/engagement-check.js:18-94`, `vercel.json:23-26`
**Category**: functional
**Confidence**: high

### What's wrong

The engagement-check cron runs **daily** (`vercel.json` schedule
`0 15 * * *`) and emails every active client whose most recent
`client_dailylog:` entry is 3+ days old, or who has no log in the last 5
days. It never records that a reminder was sent, and never gates re-sending
by recipient. The client record has no `lastEngagementEmailSentAt` field
(verified by grep: no key like that exists anywhere in the repo). So once a
client crosses the 3-day inactive threshold, they receive the same
"We miss you at Telos" email every 24 hours until they log a check-in.

### How to reproduce

Trace through `api/cron/engagement-check.js` for a hypothetical active,
portal-enabled client whose last `client_dailylog:` is 4 days old:

1. Day 4 of inactivity, cron runs at 15:00 UTC. `lastLogDaysAgo === 4`,
   condition `lastLogDaysAgo >= 3` is true, email sent (lines 61-93).
   Nothing is written back to the client record or any tracking key.
2. Day 5 of inactivity, cron runs again. Same client, same condition
   (`lastLogDaysAgo === 5` or hits the `=== -1` branch once past the 5-day
   scan window). Email sent again.
3. Day 6, day 7, ... emails continue daily.

There is no de-duplication anywhere in the file - the `for (var i ...)` loop
processes every client every day, and the only skip conditions are
`status !== 'active'`, `!portalEnabled`, `emailEnabled === false`, and
`!email`.

### Why it matters

This is the kind of bug that quietly damages sender reputation. A client who
goes on vacation for two weeks will receive ~11 identical reminder emails to
the address Telos uses for transactional mail (`noreply@telosathleticclub.com`).
That triggers spam-folder placement, "report as spam" clicks, and Resend
deliverability hits that affect *all* outbound mail including password
resets. It also reads as harassment to the client. The fact that the email
copy ("It's been N+ days since your last check-in") includes a count makes
the repetition more glaring - the same number doesn't update on subsequent
sends because the scan window is only 5 days, so day 6 and later all read
"5+ days".

Note: clients can mute by setting `emailEnabled = false`, but there is no
admin UI surface for that field (the dashboard `clients` PUT in
`api/dashboard/clients.js:107-119` does not list `emailEnabled` among the
fields it updates), so in practice no one can turn it off.

### Suggested fix

Add a recipient-side gate. The lightest change is to write a Redis key like
`client_engagement_sent:{clientId}` with a 6- or 7-day TTL right after the
Resend POST succeeds, and skip the send at the top of the loop if that key
exists. That makes the cron at most one reminder per week per client, which
matches the intuitive expectation of a "we miss you" nudge. The weekly
summary cron already runs Mondays, so a 7-day TTL also avoids same-week
overlap with the weekly summary email.

A heavier but cleaner alternative is to track `lastEngagementEmailSentAt` on
the client record itself and gate on it - but that requires a small
extension to the client schema and the admin clients PUT to surface the
field.
