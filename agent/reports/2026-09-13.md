## P1 - No rate limiting on admin login endpoint

- **File:** `api/dashboard/login.js`
- **Category:** security / functional
- **Reproduce:** Send unlimited POSTs to `POST /api/dashboard/login` with guessed passwords. There is no `ratelimit:*:{ip}` guard, no lockout, no CAPTCHA. `verifyPassword` uses `crypto.timingSafeEqual` but that only prevents timing side-channels, not brute-force.
- **Impact:** A single `DASHBOARD_PASSWORD` protects the entire business dashboard (client PII, revenue, pipeline, ad spend, Charleston applications). If the password is short or reused, an attacker can brute-force it. Every other public POST endpoint (`submit-quiz`, `submit-email`, `submit-chs-application`) already implements the `INCR + EXPIRE` rate-limit pattern - login is the outlier.
- **Suggested fix:** Copy the pattern from `submit-chs-application.js` (5/hr per IP). For admin login, also consider a stricter cap (e.g. 5 attempts / 15 min per IP) and a global counter that alerts if breached.

## P1 - No rate limiting on client login endpoint

- **File:** `api/client/login.js`
- **Category:** security / functional
- **Reproduce:** Enumerate emails from a leaked list, POST `{email, password}` to `/api/client/login` in a loop. Nothing throttles the requests.
- **Impact:** Client accounts hold personal check-ins, nutrition logs, training data, and (per the client-portal schema) potentially payment tier. Combined with the enumeration finding below, an attacker can (1) confirm a valid email, then (2) brute-force its password.
- **Suggested fix:** Add rate limiting on `(ip, normalizedEmail)` composite so distributed guesses can't ride under a per-IP cap. Also consider a global per-IP cap for enumeration attempts.

## P2 - Client login error messages enable account enumeration

- **File:** `api/client/login.js` (lines 25-48)
- **Category:** security
- **Reproduce:**
  1. `POST /api/client/login` with a random email + any password → `401 "Invalid email or password"`.
  2. `POST /api/client/login` with a real client email whose portal is not enabled → `401 "Portal access not enabled"`.
  3. Real client email whose status isn't active → `401 "Account is not active"`.
  4. Real client email who never set a password → `401 "Password not set - contact your coach"`.
- **Impact:** An attacker can distinguish "email does not exist" from "email exists but is disabled / inactive / passwordless". Combined with the missing rate limit above, this makes it trivial to build a targeting list of real client emails.
- **Suggested fix:** Collapse all failure branches into the generic `"Invalid email or password"` response. If Thomas wants users who hit these states to see a helpful message, do that only after a valid password match, or via an out-of-band flow (email link the user requests).

## P3 - `chs.html` loads `js/main.js` without cache-busting version query

- **File:** `chs.html:1050`
- **Category:** functional / caching
- **Reproduce:** `grep 'main\.js' chs.html` returns `<script src="js/main.js"></script>`. Every other page in the repo uses `<script src="js/main.js?v=2"></script>` (see 27 other files listed in `js/main.js?v=` grep).
- **Impact:** When `main.js` is updated and the version bumps to `?v=3`, every page except `chs.html` will pull the new bundle; chs will serve the browser's cached copy indefinitely (Vercel's default cache headers for JS are long-lived). Charleston nav / hamburger behavior will drift out of sync with the rest of the site until the file is force-refreshed.
- **Suggested fix:** Change to `<script src="js/main.js?v=2"></script>` and remember to bump chs when the version bumps elsewhere.
