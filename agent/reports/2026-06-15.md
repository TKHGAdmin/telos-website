## P1-2026-06-15-001 — Deleting a client leaves a stale email lookup, blocking re-onboarding

**Severity:** P1 — Breaks a routine admin workflow (re-onboarding former clients).

**Files:**
- `api/dashboard/clients.js:142-154` (DELETE handler — missing cleanup)
- `api/dashboard/clients.js:59-97` (POST handler — the gate that ends up blocking)
- `api/dashboard/client-portal.js:114-124` (where the `client_email:` lookup is set/cleared today)

**Repro:**
1. From `/thomas` → **Clients**, create a client (e.g., `alice@example.com`).
2. In **Client Portal**, enable Alice's portal. This writes `client_email:alice@example.com → {aliceId}`.
3. Back in **Clients**, delete Alice.
4. Try to create a new client (Alice returning, or anyone) with `alice@example.com`.
5. **Observed:** `POST /api/dashboard/clients` returns `400 { error: "Email already in use by another client" }`.
6. **Expected:** The new client is created — Alice no longer exists.

**Root cause:** the DELETE handler only does

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

…but the `client_email:{normalizedEmail}` lookup that `client-portal.js` writes on portal-enable is never removed. The POST handler at `clients.js:70-73` reads that stale key and rejects:

```js
var existingEmailOwner = await redis('GET', 'client_email:' + normalized);
if (existingEmailOwner) {
  return res.status(400).json({ error: 'Email already in use by another client' });
}
```

There is no in-app recovery — the admin would have to delete the Redis key directly.

**Fix sketch:** before the `DEL` + `ZREM`, fetch the client, and if `portalEnabled` was true, also `DEL client_email:{normalizeEmail(client.email)}`. While you're there, consider cascading deletes for the per-client child keys (`client_dailylog:*`, `client_training_program:`, `client_nutrition_plan:`, `client_545_*`, `client_supplement_*`, `client_activity_log:*`, `client_resources:`, `client_mindset:`, `client_sidemenu:`) so deleted clients don't leak storage forever — secondary to the lookup cleanup which is the actual user-visible bug.

**Why this matters:** churn-and-return is a normal motion in coaching (someone pauses, restarts a quarter later). Today that pattern silently fails for any admin who has previously enabled the client's portal.

## P3-2026-06-15-002 — `/product` page hangs on "Loading product" if the Shopify Buy SDK fails to load

**Severity:** P3 — Low probability (sdks.shopifycdn.com is reliable), but the failure mode is a dead page with no error UI.

**Files:**
- `js/shop.js:23-35` (init: SDK-undefined branch)
- `js/shop.js:502-507` (`showEmpty()` — only targets shop-page IDs)
- `product.html:751-762` (product-page IDs are `productLoading` / `productNotFound`)

**Repro:**
1. Visit `/product?p=<any-handle>` with `https://sdks.shopifycdn.com` blocked (uBlock with one of the common privacy filter lists, corporate firewall, or a transient CDN outage).
2. **Observed:** the spinner with the text "Loading product" stays forever. No error message; no fallback CTA.
3. **Expected:** "Product Not Found" panel (or a more specific "Couldn't load — try again") with the Back-to-Shop button.

**Root cause:** the init handler in `shop.js` covers the SDK-missing case by calling `showEmpty()`:

```js
if (typeof ShopifyBuy === 'undefined') {
  console.error('[Telos Shop] Shopify Buy SDK not loaded');
  showEmpty();
  return;
}
```

`showEmpty()` only knows about the shop-page IDs:

```js
function showEmpty() {
  var loading = document.getElementById('shopLoading');
  var empty = document.getElementById('shopEmpty');
  if (loading) loading.style.display = 'none';
  if (empty) empty.style.display = 'block';
}
```

`product.html` uses `#productLoading` and `#productNotFound` — the `if (loading)` and `if (empty)` guards make `showEmpty()` a silent no-op on that page.

**Fix sketch:** either (a) extend `showEmpty()` to also hide `#productLoading` and show `#productNotFound` when present, or (b) introduce a shared `bailOut()` that handles both layouts and call it from both the SDK-missing branch (line 26) and the init-catch (line 71).

**Why this matters:** the only signal a user sees is a never-resolving spinner. Even a 1-in-1000 SDK-load failure burns trust on a paid-product page.
