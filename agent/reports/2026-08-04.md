## Findings

### F1 - [P1] Pricing gate bypassed by clicking "See Your Score" with empty inputs

- **File:** `js/quiz.js:225`
- **Category:** functional
- **Severity:** P1
- **Confidence:** high

**What breaks**

The lead-capture step of the Execution Score Quiz uses `<button type="button" class="quiz-see-score-btn">` (`pricing.html:594`, `index.html:580`) and attaches a `click` handler in `js/quiz.js:225`. Because the button is `type="button"`, the browser never runs HTML5 form validation on the `required` `name` / `email` inputs, and the handler itself does no validation before continuing.

On the `pricing.html` overlay this defeats the entire pricing gate: a visitor can click "See Your Score" with the fields empty, the client-side then unconditionally hides `.quiz-lead-capture`, shows `.quiz-results`, sets `localStorage.telosQuizCompleted = 'true'`, and (on the "View Pricing" button) reveals the four tier prices. The `fetch('/api/submit-quiz', ...)` call correctly returns 400 for the blank submission — server-side data stays clean — but the client ignores the response (`.catch(function(){})`, no `.then`) so the UX flow is unaffected. Thomas loses the lead **and** the visitor sees pricing without ever handing over an email.

The homepage inline quiz has the same bug but with lower impact (it doesn't gate anything, it just skips lead capture).

**Reproduction**

1. Open `https://www.telosathleticclub.com/pricing` in a fresh browser (or clear `localStorage.telosQuizCompleted`).
2. Click "Start" and answer any 8 questions.
3. When the lead-capture form appears, leave name / email / phone all blank.
4. Click **See Your Score**.
5. Observe: score animation runs, then "View Pricing" reveals all four tiers with actual dollar prices — no email captured, no lead recorded in Redis.

**Fix suggestion**

Either switch `quiz-see-score-btn` to `type="submit"` and bind on the `<form>`'s `submit` event (browser-native `required` validation kicks in), or add an explicit guard at the top of the click handler:

```js
if (!nameInput.value.trim() || !emailInput.value.trim() || !/@/.test(emailInput.value)) {
  emailInput.reportValidity();
  nameInput.reportValidity();
  return;
}
```

### F2 - [P2] Admin session token HMAC compared with `!==` (not timing-safe)

- **File:** `api/lib/auth.js:27`
- **Category:** security
- **Severity:** P2
- **Confidence:** high

**What breaks**

`verifyToken()` in the admin auth helper compares the HMAC signature from the cookie against the expected value with a plain string `!==`:

```js
// api/lib/auth.js:23-27
const expected = crypto
  .createHmac('sha256', SESSION_SECRET)
  .update(payload)
  .digest('hex');
if (signature !== expected) return false;
```

The sibling `verifyClientToken()` in `api/lib/client-auth.js:47-49` — written by the same author for the same purpose — correctly uses `crypto.timingSafeEqual` after a length check. And the admin's own `verifyPassword()` (auth.js:58) uses `timingSafeEqual`. So the admin token check is the odd one out.

String `!==` in V8 short-circuits on the first differing character; over enough requests an attacker measuring response-time deltas could recover the signature byte-by-byte and forge an admin session cookie for arbitrary expiry values (the signed payload is just a number). Exploitation is slow and noisy in practice, but it's a real deviation from the pattern the rest of the codebase already follows.

**Reproduction**

Code review only — I did not attempt to time-attack production.

1. Open `api/lib/auth.js:18-31`.
2. Compare to `api/lib/client-auth.js:34-52` — same shape, but the client version uses `crypto.timingSafeEqual(a, b)` after a `.length` guard.
3. The admin variant's `signature !== expected` is not constant-time.

**Fix suggestion**

Mirror the client-auth pattern:

```js
const a = Buffer.from(signature, 'hex');
const b = Buffer.from(expected, 'hex');
if (a.length !== b.length) return false;
if (!crypto.timingSafeEqual(a, b)) return false;
```

### F3 - [P3] `shop.js` cache-buster out of sync between `shop.html` (v=1) and `product.html` (v=2)

- **File:** `shop.html:841`
- **Category:** tech-debt
- **Severity:** P3
- **Confidence:** high

**What breaks**

`shop.html:841` loads `<script src="js/shop.js?v=1">` while `product.html:822` loads `<script src="js/shop.js?v=2">`. Commit `f5cb8c4` ("feat: add image gallery with thumbnails on product page") edited `js/shop.js` and bumped the cache-buster on `product.html` but not on `shop.html`.

Concrete impact today is small — the gallery edit only affects the product-detail branch of `shop.js` and nothing on the shop grid was changed — but the effect of the desync is that returning visitors who cached `shop.js?v=1` from an earlier `/shop` visit will serve the old file from cache when they hit `/shop` again, and only re-fetch when navigating into a product detail. Any future `shop.js` change that DOES touch the grid path (add-to-cart button, product card render) will silently ship broken to those users until `shop.html`'s buster is bumped.

CLAUDE.md's own convention is explicit: *"CSS cache busting: Stylesheet references use `?v=N` query param. Bump the version on all pages when changing style.css."* The same rule applies to `shop.js`.

**Reproduction**

1. `grep -rn "shop.js?v=" .` → `shop.html:841: shop.js?v=1`, `product.html:822: shop.js?v=2`.
2. `git log --oneline -- js/shop.js` shows the last edit is `f5cb8c4`.
3. `git show f5cb8c4 -- shop.html product.html` → only `product.html`'s cache-buster was bumped in that commit.

**Fix suggestion**

Bump `shop.html:841` to `js/shop.js?v=2`. Going forward, when editing `js/shop.js`, bump every HTML file that references it in the same commit (currently just `shop.html` and `product.html`).
