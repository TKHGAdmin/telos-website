## Summary

First run of the autonomous bug hunter. Today's focus was functional bugs in the
serverless API and core front-end JS. Two reproducible issues found:

1. **P1** — Duplicate-email check in `api/dashboard/clients.js` and
   `api/dashboard/client-portal.js` is incomplete; two clients can be created

   double-tap on mobile inflates the pillar score and skips the next question,
   corrupting every lead's pillar breakdown sent to `/api/submit-quiz`.

## Bug 1: Duplicate-email check leaks across clients, can lock portal users out

- **ID:** `2026-06-24-1`
- **Severity:** P1
- **Confidence:** high
- **Area:** Client portal auth integrity
- **File(s):** `api/dashboard/clients.js:65-71`, `api/dashboard/clients.js:113-125`, `api/dashboard/client-portal.js:108-118`
- **Status:** new

### What's wrong

The system treats `client_email:<email>` as the source of truth for email
uniqueness, but that lookup is only written when a client's portal is enabled
(`api/dashboard/client-portal.js:108-112`). Client creation
(`api/dashboard/clients.js:65-71`) only *reads* that lookup; it never writes
it. `clients.js` PUT (line 113) only consults the lookup when
`client.portalEnabled === true`. The combined effect: two clients can hold the
same email in their record, and enabling the portal on the second one
overwrites the lookup without warning — the first client's login then routes
to the second client's record, fails password verification, and the first
client is silently locked out.

### Reproduce

1. Coach calls `POST /api/dashboard/clients` with
   `{ name: "Alice", email: "alice@x.com", tier: "growth" }` — succeeds. No
   `client_email:alice@x.com` lookup is written (POST never writes it).
2. Coach calls `POST /api/dashboard/clients` with
   `{ name: "Bob", email: "alice@x.com", tier: "growth" }` — the duplicate
   check at `clients.js:67` reads `client_email:alice@x.com`, finds nothing,
   and lets the create succeed. Alice's and Bob's records both have
   `email: "alice@x.com"`.
3. Coach calls `POST /api/dashboard/client-portal` with
   `{ clientId: Alice.id, enabled: true, password: "..." }`. `client-portal.js`
   line 110 unconditionally `SET client_email:alice@x.com → Alice.id`.
4. Coach calls the same on Bob with `enabled: true`. Line 110 overwrites the
   lookup to point at Bob (no collision check). No 4xx response.
5. Alice tries `POST /api/client/login` with her real password. `login.js`
   resolves `alice@x.com` → Bob's id → Bob's `passwordHash`/`passwordSalt`.
   `verifyPassword` mismatches → `401 Invalid email or password`. Alice can
   never log in. Same outcome if the order is reversed (whoever the lookup
   last pointed at "wins" the email).

A second path to the same broken state: enable A → disable A
(`client-portal.js:115-118` DEL the lookup) → coach creates B with the same
email → enable A and B in any order. Same lockout.

### Fix sketch

Make `client_email:` ownership atomic and consistent:
- On `clients.js` POST, after the existence check, also write
  `client_email:<email> → newId` so the namespace is reserved at create-time
  regardless of `portalEnabled`. Mirror the existing-owner check in PUT for
  every email change (not just when `portalEnabled` is true).
- In `client-portal.js` POST, before the `SET`, read the lookup and reject
  with 400 if it already points to a different `clientId`.
- One-time migration: scan `clients_index`, normalize emails, and reject /
  flag any pre-existing duplicates.

## Bug 2: Quiz answers not debounced - double-tap inflates score and skips a question

- **ID:** `2026-06-24-2`
- **Severity:** P2
- **Confidence:** high
- **Area:** Lead-capture quiz on `/` and `/pricing`
- **File(s):** `js/quiz.js:181-201`
- **Status:** new

### What's wrong

`handleAnswerSelect` accumulates points and schedules a 400 ms `setTimeout` to
advance the question every time an option is clicked — there is no
`disabled` flag, no `pointer-events: none`, and no guard variable. A user who
clicks two options inside 400 ms (or double-taps the same option on mobile)
adds the points twice **and** queues two advance callbacks. When both fire,
the quiz skips the next question entirely and stores an inflated total in
Redis via `/api/submit-quiz`.

### Reproduce

1. Open the homepage or `/pricing` and start the quiz.
2. On any question, click any answer twice in quick succession (or, more
   realistically, double-tap on a phone).
3. Observe: `quiz.scores[pillar]` is incremented twice (e.g. a "5-point"
   option becomes 10), the next question briefly renders, and then a second
   `currentQuestion++` fires and advances past it without the user ever
   seeing or answering it.
4. Complete the quiz. `getTotalScore()` returns an inflated number → the
   tier shown on the results screen is wrong (e.g. `Almost Dialed` for a
   user who would be `Running on Fumes`), and the same inflated `scores` +
   `totalScore` are POSTed to `/api/submit-quiz` and persisted as a
   `quiz_submissions` ZSET member. The dashboard `/thomas` then triages this
   lead off the wrong tier.

### Fix sketch

Inside `handleAnswerSelect`, guard with a per-question "answered" flag and
either remove the click listeners from the option buttons or set them to
`disabled` / `pointer-events: none` once an answer has been recorded. The
simplest change: at the top of the function, `if (quiz.answered) return;
quiz.answered = true;` — reset it to `false` inside `renderQuestion()`.
