## Findings

### F-2026-11-06-01 — Quiz endpoint accepts malformed emails; lead table collects garbage

- **Severity:** P2
- **Category:** Functional / data quality
- **Focus bucket:** Functional

**Where**

- Server: `api/submit-quiz.js`, lines 15-20
- Client: `js/quiz.js`, lines 221-275 (`setupLeadCapture`)
- Form markup: `index.html` line 576-581 and `pricing.html` line ~590 (quiz lead-capture form)

**What is wrong**

The quiz lead-capture form uses a `<button type="button">` ("See Your Score") with a JS `click` handler that calls `e.preventDefault()` and reads field values directly:

```js
// js/quiz.js:225
submitBtn.addEventListener('click', function(e) {
  e.preventDefault();
  var nameInput = form.querySelector('input[name="name"]');
  var emailInput = form.querySelector('input[name="email"]');
  ...
  quiz.userEmail = emailInput.value;   // no format check
  ...
  fetch('/api/submit-quiz', { body: JSON.stringify({ name, email, phone, ... }) });
});
```

Because the button is `type="button"` (not `submit`), the browser's native HTML5 form validation (`required`, `type="email"`) never fires. The client then sends whatever the user typed to the server.

The server only guards against missing values, not malformed ones:

```js
// api/submit-quiz.js:18
if (!email || !name) {
  return res.status(400).json({ error: 'Name and email required' });
}
// No regex / format check. Any non-empty string is accepted.
```

**Reproduction**

1. Open `https://www.telosathleticclub.com/` and scroll to the quiz.
2. Complete the 8 questions.
3. In the lead-capture form, enter `Name: x`, `Email: x`, no phone.
4. Click "See Your Score".
5. The results screen appears normally and the submission is written to Redis (`quiz_submissions` ZSET).
6. In `/thomas → Leads`, the garbage row shows up as a real lead with email `x`.

Same path exists on `pricing.html` (same `quiz.js` module, same button pattern).

**Why this matters**

- Every quiz submission is a lead in Thomas's dashboard. A broken email means a lead that cannot be contacted.
- Bots and distracted fat-finger entries both land directly in the lead table today. The rate limiter (10/hr/IP) does not block low-volume garbage.
- Peer endpoints already do the right thing: `api/submit-chs-application.js` runs `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, and `api/submit-email.js` at least checks `email.includes('@')`. The quiz endpoint is the outlier.

**Suggested fix (approval-level only - agent does not modify app code)**

- Server (`api/submit-quiz.js`): reuse the CHS regex. One line below the existing `!email || !name` guard.
- Client (`js/quiz.js`): either change the button to `type="submit"` and listen on `form.submit`, or add an explicit `/.+@.+\..+/` check before `fetch(...)` and surface an inline error (the form has no error UI today, so the server guard alone is the smaller change).
