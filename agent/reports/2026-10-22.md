## Summary

First run of the Terminex Bug Detector. Focus: Security review of the auth plumbing, session handling, password reset flow, and admin dashboard headers. Reviewed all 16 admin endpoints, 24 client endpoints, both auth libraries, the client dashboard HTML sinks, and the Vercel header config.

Overall: the auth design is reasonable (HMAC-signed cookies, PBKDF2 for client passwords, timing-safe compare in the client-auth library, email enumeration mitigation attempted on reset) but there are five concrete security gaps worth fixing. None are a live breach - they are hardening gaps that a motivated attacker could chain. Nothing was fabricated and no secrets were discovered in the repo.

## Findings

### BUG-20261022-01 - No rate limiting on any auth endpoint

- **Severity**: P1
- **Category**: Security
- **File(s)**: `api/dashboard/login.js:3-17`, `api/client/login.js:9-60`, `api/client/reset-password.js:8-103`
- **Reproduce**: `curl -X POST https://www.telosathleticclub.com/api/dashboard/login -d '{"password":"guess1"}' -H 'content-type: application/json'` can be repeated unlimited times with no 429. Same for `/api/client/login` (per-email credential stuffing) and `/api/client/reset-password` (unlimited reset-email dispatch).
- **Impact**: (a) Admin dashboard is one password away from full business data exposure (clients, revenue, pipeline) and is defended only by `DASHBOARD_PASSWORD` strength. (b) Client logins are open to online credential stuffing. (c) An attacker can mass-trigger `reset-password` to spam clients and burn through the Resend quota.
- **Suggested fix**: Add the same Upstash INCR+EXPIRE rate-limit pattern already used in `api/submit-chs-application.js:40-46` to all three endpoints. Suggested budgets: admin login 10/hr/IP, client login 20/hr/IP (also key by lowercased email), reset-password 3/hr/IP and 5/day/email.

### BUG-20261022-02 - Password reset does not invalidate active client sessions

- **Severity**: P1
- **Category**: Security
- **File(s)**: `api/lib/client-auth.js:34-52`, `api/client/reset-password.js:70-96`
- **Reproduce**: 1) Log in as client A, capture the `telos_client_session` cookie. 2) As client A, request a password reset and set a brand-new password. 3) Replay the captured cookie against `GET /api/client/me` - it still returns 200 with client A's data until the 7-day expiry.
- **Impact**: Password reset is advertised as "take back your account" but does not revoke stolen sessions. If a laptop was lost, a shared browser left logged in, or a session cookie leaked (XSS in a side-menu custom panel, iframe cookie leak, log scraping), rotating the password does nothing for up to 7 days.
- **Suggested fix**: Stamp `passwordSetAt` (already stored on the client record) into the token payload: `clientId.passwordSetAt.expires.signature`. In `verifyClientToken`, fetch the client record and reject tokens whose embedded `passwordSetAt` is older than the stored one. (One extra Redis GET per authed request; acceptable for a small roster.)

### BUG-20261022-03 - Timing-side-channel email enumeration on reset-password

- **Severity**: P1
- **Category**: Security
- **File(s)**: `api/client/reset-password.js:20-67`
- **Reproduce**: Measure response latency of `POST /api/client/reset-password` with `{"email":"x"}`. For a non-client email the handler short-circuits at line 25 (one Redis GET, ~10-30 ms). For a real portal-enabled client it also calls `fetch('https://api.resend.com/emails', ...)` and awaits the response (~200-800 ms). The intentional "always return 200" protection (line 26) is defeated by this latency gap.
- **Impact**: An attacker who scrapes a list of candidate emails (LinkedIn, breach dumps) can distinguish real Telos clients from non-clients purely by timing, bypassing the enumeration-prevention design.
- **Suggested fix**: Either (a) send the Resend request without awaiting it (fire-and-forget - acceptable because the handler already returns 200 either way), or (b) always `await` an equivalent-cost no-op (e.g. a dummy `redis('SETEX', ...)` with a throwaway key) in the "no client" branch, or (c) do the Resend call behind a queue so both branches return immediately.

### BUG-20261022-04 - Admin HMAC signature compared with `!==` (not timing-safe)

- **Severity**: P2
- **Category**: Security
- **File(s)**: `api/lib/auth.js:22-27`
- **Reproduce**: Code inspection - line 27 does `if (signature !== expected) return false;`. The client-auth equivalent at `api/lib/client-auth.js:46-49` correctly uses `crypto.timingSafeEqual`. The admin path was written first and never backported.
- **Impact**: Theoretically allows a timing oracle against the HMAC signature. HMAC-SHA256 is resistant and the attacker would need to guess an entire 64-char hex string, so practical risk is low - but it is an inconsistency with the sibling library and a trivial one-line fix.
- **Suggested fix**: Mirror the client-auth pattern:
  ```js
  const a = Buffer.from(signature, 'hex');
  const b = Buffer.from(expected, 'hex');
  if (a.length !== b.length) return false;
  if (!crypto.timingSafeEqual(a, b)) return false;
  ```

### BUG-20261022-05 - No clickjacking protection on /thomas admin dashboard

- **Severity**: P2
- **Category**: Security
- **File(s)**: `vercel.json:3-12`, `thomas.html:1-30`
- **Reproduce**: `curl -I https://www.telosathleticclub.com/thomas` returns no `X-Frame-Options` and no `Content-Security-Policy: frame-ancestors`. A page under attacker control can embed `/thomas` in a transparent iframe over a decoy UI and capture clicks on the already-logged-in admin session (session cookie is `SameSite=Strict` which prevents cross-site navigation posts, but it is still sent to iframes of the same origin that are embedded cross-site, and browsers vary).
- **Impact**: An admin who follows a malicious link while logged in could be tricked into deleting a client, firing an email blast, or changing a password through overlayed clicks.
- **Suggested fix**: In `vercel.json`, add a header block scoped to the admin surface:
  ```json
  {
    "source": "/thomas",
    "headers": [
      { "key": "X-Frame-Options", "value": "DENY" },
      { "key": "Content-Security-Policy", "value": "frame-ancestors 'none'" }
    ]
  }
  ```
  Do NOT apply this to `/client-dashboard` - it must remain iframe-embeddable in Whop (see CLAUDE.md "Known Limitations").

## Methodology

- Read `api/lib/auth.js`, `api/lib/client-auth.js`, `api/lib/redis.js`-adjacent callers.
- Enumerated all `api/dashboard/*.js` and `api/client/*.js` and grep-confirmed every endpoint calls the correct `verifySession` or `verifyClientSession` gate (only `login.js`, `logout.js`, `reset-password.js`, and the admin-authed `notify.js`/`send-email.js` are exceptions, all intentional).
- Audited `api/client/reset-password.js` for enumeration, token lifetime, password strength, and session invalidation.
- Audited `api/submit-chs-application.js`, `api/submit-quiz.js`, `api/submit-email.js` for rate limiting, input validation, CORS.
- Grepped `client-dashboard.html` for `innerHTML` sinks and confirmed the `esc()` helper is defined and used on client-controlled data; the only coach-controlled HTML sink (`drawerCustomContent`, line 2749) is admin-only input.
- Checked `vercel.json` for security headers: HSTS, X-Frame-Options, CSP, Referrer-Policy, Permissions-Policy. None present on admin surface.
- Verified both dashboards carry `<meta name="robots" content="noindex, nofollow">`.

## Open questions
