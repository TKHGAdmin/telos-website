## P1-1 — `escapeHtml()` doesn't escape double quotes; breaks alt attributes when product titles contain `"`

**File**: `js/shop.js:509-514` (definition) — used at `js/shop.js:166`, `js/shop.js:276`, `js/shop.js:432`
**Severity**: P1
**Category**: Functional / Accessibility / Attribute injection

### The bug

`escapeHtml()` is implemented via DOM text-node serialization:

```js
function escapeHtml(str) {
  if (!str) return '';
  var div = document.createElement('div');
  div.appendChild(document.createTextNode(str));
  return div.innerHTML;
}
```

DOM serializers only escape `&`, `<`, and `>` in text nodes. **Double quotes and single quotes pass through untouched**. That's fine for text content, but the function is used inside `alt="..."` attribute contexts in three places:

- **Line 166** (product detail image): `imageEl.innerHTML = '<img src="' + allImages[0].src + '" alt="' + escapeHtml(product.title) + '">'`
- **Line 276** (product card in grid): `<img src="${image}" alt="${escapeHtml(product.title)}" loading="lazy">`
- **Line 432** (cart drawer item image): `<img src="${image}" alt="${escapeHtml(item.title)}">`

### Failure scenario

Concrete Shopify product titles that contain `"` are common in fitness gear (`The 8" Shorts`, `Men's 12" Compression Sleeve`, `The "Rebuild" Program`). For a product titled `The 8" Guide`:

- Input to `escapeHtml`: `The 8" Guide`
- Output: `The 8" Guide` (unchanged — `"` is not escaped)
- Injected: `<img src="..." alt="The 8" Guide">`
- Browser parses: `alt="The 8"` + a bogus attribute `Guide"` — the alt text is truncated to `The 8`, screen readers announce garbage, and the markup is invalid.

Also a mild attribute-injection surface: if a product title ever contained ` " onerror="…"`, the fragment executes. Requires Shopify admin compromise — but escapeHtml's job is to prevent exactly this class of failure.

### Verification

Reproduced locally with a stubbed `escapeHtml` (same behavior as the DOM implementation):

```
input:    Men's 8" Shorts
output:   Men's 8" Shorts
rendered: <img src="x.jpg" alt="Men's 8" Shorts">   ← broken
```

### Suggested fix

Replace the DOM implementation with an explicit-escape function that covers attribute contexts:

```js
function escapeHtml(str) {
  if (!str) return '';
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}
```

No callers need to change.

## P2-1 — Deleting a client leaves the `client_email:*` index orphaned, blocking re-creation with the same email

**File**: `api/dashboard/clients.js:143-154` (DELETE handler)
**Severity**: P2
**Category**: Functional / Data integrity

### The bug

The DELETE handler removes only two Redis keys:

```js
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

Per `CLAUDE.md`, the login lookup key `client_email:{normalizedEmail}` is set by `client-portal.js:117` when the client's portal is enabled and only removed by `client-portal.js:123` when the portal is explicitly disabled.

If admin deletes a client whose portal is enabled — without first disabling the portal — the `client_email:*` entry survives, pointing to a client id that no longer exists.

### Failure scenario

1. Admin creates client `foo@bar.com` and enables portal → `client_email:foo@bar.com → 42`.
2. Client cancels. Admin clicks Delete in the Clients tab → `client:42` and index entry are removed, but `client_email:foo@bar.com` still exists.
3. Weeks later the client returns. Admin tries to re-add `foo@bar.com` → POST `clients.js:70-72` sees `client_email:foo@bar.com` still exists and rejects with `"Email already in use by another client"`.
4. There's no admin-facing way to clear the orphaned entry — requires manual Redis surgery.

### Suggested fix

Before deleting the client record, look it up, normalize the email, and delete the index entry. Skeleton:

```js
var existing = await redis('GET', 'client:' + id);
if (existing) {
  try {
    var c = JSON.parse(existing);
    if (c.email) {
      var { normalizeEmail } = require('../lib/client-auth');
      await redis('DEL', 'client_email:' + normalizeEmail(c.email));
    }
  } catch (e) {}
}
await redis('DEL', 'client:' + id);
await redis('ZREM', 'clients_index', String(id));
```

Optional follow-up (not part of this bug): the DELETE also leaves orphaned `client_dailylog:*`, `client_nutrition_log:*`, `client_training_log:*` etc. That's a broader data-hygiene concern — not blocking, but worth a sweep later.

## P1-2 — `POST /api/client/reset-password` has no rate limiting; enables inbox-spam and Resend-quota drain

**File**: `api/client/reset-password.js` (whole file — no gate)
**Severity**: P1
**Category**: Functional / Abuse / Cost

### The bug

Every other public POST endpoint on the site rate-limits by IP: `submit-quiz.js`, `submit-email.js`, `submit-chs-application.js` all use `ratelimit:*:{ip}` counters. `reset-password.js` does not. An attacker can hit `POST /api/client/reset-password` with `{ email: "<real-client>@…" }` in a tight loop.

### Failure scenario

1. Attacker knows or guesses one active client's email (e.g., from an Instagram DM, a coach mention, or by scraping the coaching testimonials).
2. Attacker runs `while true; do curl -X POST .../api/client/reset-password -d '{"email":"victim@x.com"}'; done`.
3. Each request that matches a portal-enabled client triggers a Resend send (`reset-password.js:43-64`) with no throttle — the victim gets flooded with legitimate-looking reset emails, and each send bills against Thomas's Resend account.
4. Even for non-matching emails the code path is short and cheap for the attacker, so email-existence enumeration by response timing is also possible (though `email` responses are constant-body, the Resend network call adds measurable latency for real accounts vs the immediate no-op for fake ones).

### Suggested fix

Mirror the pattern used by `submit-chs-application.js` (5 requests / hour / IP):

```js
var ip = (req.headers['x-forwarded-for'] || '').split(',')[0].trim() || req.socket.remoteAddress;
var key = 'ratelimit:reset:' + ip;
var count = await redis('INCR', key);
if (count === 1) await redis('EXPIRE', key, 3600);
if (count > 5) return res.status(429).json({ error: 'Too many requests. Try again later.' });
```

Additionally consider a per-email rate limit (`ratelimit:reset-email:{normalizedEmail}`) at ~3/hour to prevent spamming a known victim from multiple IPs.

## P1-3 — `POST /api/client/login` has no rate limit; unlimited password guesses per account

**File**: `api/client/login.js` (whole file — no gate)
**Severity**: P1
**Category**: Security / Auth

### The bug

Same shape as P1-2: the login endpoint accepts unlimited attempts per IP and per email. PBKDF2 (via `client-auth.js`) is slow enough to make raw brute-force impractical, but:

- Dictionary attacks against a specific known-email client are still feasible over hours/days.
- The site has a small, known user base (paid coaching clients), so target enumeration is trivial — anyone who's ever appeared as a testimonial is a candidate.
- Every other public POST endpoint enforces IP-based limits; the omission here is inconsistent posture.

### Suggested fix

Same pattern as P1-2, but also introduce a per-email failure counter that increments only on `verifyPassword` mismatch (line 46) and locks the account for N minutes after M failures:

```js
var emailKey = 'ratelimit:login-email:' + email;
var failures = parseInt(await redis('GET', emailKey) || '0', 10);
if (failures >= 10) return res.status(429).json({ error: 'Too many failed attempts. Try again in 15 minutes.' });
// … after failed verifyPassword():
await redis('INCR', emailKey);
await redis('EXPIRE', emailKey, 900);
// … after successful verifyPassword():
await redis('DEL', emailKey);
```

## P1-4 — `GET /api/dashboard/clients` returns `passwordHash` and `passwordSalt` to the browser

**File**: `api/dashboard/clients.js:17-56` (GET handler)
**Severity**: P1
**Category**: Security / Data exposure

### The bug

`api/dashboard/client-portal.js:104-105` writes `passwordHash` and `passwordSalt` onto the `client:{id}` record. `api/dashboard/clients.js:23-30` reads the entire record with `JSON.parse(existing)` and returns the whole object in the JSON response — hashes included.

### Failure scenario

- Thomas is the only admin, so the direct-access risk is low.
- However, any XSS on `/thomas` (or a compromised extension, or someone shoulder-surfing devtools) exposes PBKDF2 hashes for every client with portal enabled.
- Hashes are one-way, but the leak is unnecessary: no code path on `thomas.html` actually consumes `passwordHash` — it's dead payload.
- Compare with `api/client/me.js`, which correctly strips sensitive fields before responding.

### Suggested fix

Strip the sensitive fields server-side before returning:

```js
results.forEach(function(r) {
  if (r.result) {
    try {
      var c = JSON.parse(r.result);
      delete c.passwordHash;
      delete c.passwordSalt;
      clients.push(c);
    } catch(e) {}
  }
});
```

Apply the same strip to POST/PUT response bodies (`clients.js:92`, `:135`) for consistency.
