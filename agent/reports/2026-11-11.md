# Bug Report 2026-11-11

- **Focus:** functional
- **Bugs found:** 12
- **Zero-bug day:** no

## Summary

First run of the Terminex Bug Hunter. Focus was functional defects — broken links, missing refs, and API contract mismatches. Scanned every top-level HTML file, the 23 blog articles, every endpoint under `/api/`, and every `fetch()` call across the client code.

The marketing surface and blog are clean (every internal link resolves, every script/CSS/image reference exists, CSS cache-bust is uniform at `?v=16`). But two public-facing problems do stand out:

1. The **product detail page** — introduced by the recent image-gallery commit (`f5cb8c4`) — renders with the Add-to-Cart button misplaced below the image on every desktop viewport, because a new `#productThumbs` strip was added as a third child of a two-column grid.
2. The **admin dashboard at `/thomas`** has a cluster of API contract mismatches that silently break major workflows for Thomas — course video uploads, client edits, lead pipeline edits, ad-spend logging, and content publishing all fail in different ways.

Every finding below was verified independently (not just trusted from the scan) by reading both sides of the contract or inspecting the rendered DOM/CSS. Three JS cache-busting version drifts were also found — stale JS will be served on at least one page of each pair after a bump.

## Findings

### [P1] BUG-2026-11-11-00 — Product detail: Add-to-Cart column pushed below the image on every desktop viewport

- **File:** `product.html:105-108, 120-124, 765-780` (also `js/shop.js:161-174`)
- **Category:** layout / grid-misplacement
- **Description:** `#productDetail` is `display: grid; grid-template-columns: 1fr 1fr;` with **three** direct children — `#productImage`, `#productImage`'s new sibling `#productThumbs`, and `#productDetail-info`. Grid auto-flow places them: row 1 col 1 = image, row 1 col 2 = thumbs strip, row 2 col 1 = title / price / **Add-to-Cart**. Even for single-image products (where `shop.js:168` leaves `#productThumbs` empty), the element still occupies the top-right cell because it has `display: flex; margin-top: 12px;`. Introduced by commit `f5cb8c4` ("feat: add image gallery with thumbnails on product page"). On ≤768px the media query collapses to one column and the order is accidentally correct.
- **Failure scenario:** Open `/product?p=<any-handle>` on a desktop viewport. The product image fills the left side; the top-right of the layout is either an empty strip (one-image products) or a row of thumbnails (multi-image). The title, price and primary **Add to Cart** button render *below* the image, pushed to the bottom-left of a half-blank layout — nowhere a desktop buyer expects to find them, and for tall product images the CTA sits below the fold.
- **Suggested fix:** Wrap `#productImage` and `#productThumbs` in a single `.product-detail-media` div so the two together occupy one grid column, or set `.product-detail-image` to `display: flex; flex-direction: column;` and move `#productThumbs` inside it.

### [P1] BUG-2026-11-11-01 — Course video upload: client PUTs, server only accepts POST

- **File:** `thomas.html:2314` vs `api/dashboard/upload-video.js:8-10`
- **Category:** api-method-mismatch
- **Description:** The video uploader uses `xhr.open('PUT', '/api/dashboard/upload-video?filename=...')`. The handler early-returns `405 Method not allowed` for any method other than `POST`.
- **Failure scenario:** From the Content → Modules tab, click **Upload video** on any lesson. The upload spinner runs to 100% then surfaces `Upload failed: Method not allowed`. No course lesson video can ever be attached via the dashboard.
- **Suggested fix:** Change `xhr.open('PUT', ...)` → `xhr.open('POST', ...)` on line 2314.

### [P1] BUG-2026-11-11-02 — Editing a client silently 400s ("ID required")

- **File:** `thomas.html:1380-1393` vs `api/dashboard/clients.js:100-103`
- **Category:** api-contract-mismatch (missing body.id)
- **Description:** `saveClient` on edit sends `PUT /api/dashboard/clients?id=5` with a body that contains name/email/tier/etc. but **no `id`**. The PUT handler at line 103 rejects `!body.id` with 400 "ID required". Unlike DELETE (line 145), the PUT branch has no `req.query.id` fallback.
- **Failure scenario:** On the Clients tab click **Edit** on any client, change the tier or notes, click Save. Toast: `Error: ID required`. Every edit fails. (New-client POST works — this only hits the edit path.)
- **Suggested fix:** In `clients.js:103`, mirror the DELETE line and use `var updateId = req.query.id || body.id;` (then use `updateId` for the GET/SET keys). Alternatively include `id: id` in the saveClient body.

### [P1] BUG-2026-11-11-03 — saveClient sends snake_case fields the server ignores

- **File:** `thomas.html:1386-1387` vs `api/dashboard/clients.js:83-84, 113-118`
- **Category:** field-name-mismatch
- **Description:** Client sends `monthly_rate` and `start_date`. Server only reads `monthlyRate` and `startDate` on both POST and PUT. On new-client creation (POST) the custom rate and start date are silently dropped — the server falls back to the tier default rate (e.g. $1,497 for rebuild) and today's date. When Thomas types a different rate for a one-off deal, it is discarded.
- **Failure scenario:** Add a new Rebuild-tier client, type `2000` in the monthly rate field, Save. Reopen the client — the rate shows `1497`.
- **Suggested fix:** Rename the client-side keys to `monthlyRate` / `startDate` (lines 1386-1387). Also fixes finding #4 below.

### [P1] BUG-2026-11-11-04 — Clients table, CSV, and Revenue-by-Tier read snake_case keys the server never returns

- **File:** `thomas.html:1094, 1096, 1288, 1289, 1330, 1331, 1429, 2450` vs `api/dashboard/clients.js:83-88, 118`
- **Category:** field-name-mismatch (read side)
- **Description:** The server returns `monthlyRate`, `startDate`, `createdAt`. The client reads `c.monthly_rate`, `c.start_date`, `c.created_at` across the Clients table rendering, the edit-modal pre-fill, the CSV export, and the Overview "Revenue by Tier" bars (`tierRevenue[c.tier] += c.monthly_rate`).
- **Failure scenario:** Open the Clients tab. The "Monthly Rate" and "Start Date" columns are empty for every client. Export CSV — those columns are blank. On the Overview tab, the "Revenue by Tier" bars render as all-zero even when clients exist.
- **Suggested fix:** Rename the eight read sites to the camelCase keys.

### [P1] BUG-2026-11-11-05 — Pipeline lead edit silently 400s + fields dropped

- **File:** `thomas.html:1198-1212` vs `api/dashboard/pipeline.js:53-55, 73, 80, 82`
- **Category:** api-contract-mismatch (missing body.id, enum + field drift)
- **Description:** `savePipeline` PUTs to `/api/dashboard/pipeline?id=5` with no `id` in the body — `pipeline.js:73` returns 400 "ID required". On top of that:
  - Client writes `score`, server reads `quizScore` (line 53) — dropped.
  - Client writes `follow_up_date`, server reads `followUpDate` (lines 55, 82) — dropped.
  - Client stage enum uses `'won'`/`'lost'` (thomas.html:1121), server whitelist uses `'closed_won'`/`'closed_lost'` (line 4). Even on POST, selecting "Won" or "Lost" writes `stage: 'won'` which the GET filter will no longer surface; on PUT, line 80's `STAGES.indexOf(body.stage) > -1` silently drops the stage change.
- **Failure scenario:** Open the Pipeline tab, click Edit on a lead, change the stage to Won and set a follow-up date. Save → `Error: ID required`. Fix that, and the follow-up date and score still never persist.
- **Suggested fix:** Add `req.query.id` fallback in `pipeline.js:73`. Rename client fields to `quizScore`/`followUpDate`. Replace `PIPELINE_STAGES` at `thomas.html:1121` with `['new','contacted','consultation','proposal','closed_won','closed_lost']` to match CLAUDE.md and the server.

### [P1] BUG-2026-11-11-06 — Pipeline table reads snake_case keys the server doesn't return

- **File:** `thomas.html:1147, 1152, 1155, 1179, 1185` vs `api/dashboard/pipeline.js:53, 55, 57`
- **Category:** field-name-mismatch (read side)
- **Description:** The lead card renders `lead.score`, `lead.follow_up_date`, `lead.created_at`. Server emits `quizScore`, `followUpDate`, `createdAt`.
- **Failure scenario:** Open Pipeline. Every lead card shows a blank score badge, no follow-up warning even for stale leads, and a broken "days ago" timestamp.

### [P1] BUG-2026-11-11-07 — "Convert to Client" shortcut never moves the lead to closed_won

- **File:** `thomas.html:1236-1244` vs `api/dashboard/pipeline.js:73, 80`
- **Category:** api-contract-mismatch (silent)
- **Description:** `convertToClient` calls `PUT pipeline?id=X` with `body: { stage: 'won' }` and `.catch(function(){})` — so the 400 from the missing-`body.id` check is swallowed, and even once that is fixed the stage `'won'` fails the whitelist at line 80. The downstream `openClientModal(null, lead)` still runs, so Thomas thinks the lead was converted, but the lead stays open in the pipeline forever.
- **Failure scenario:** On a lead card click **Convert to Client**, fill the client modal, Save. The client is created, but the original lead keeps showing in the "New" / "Contacted" / "Consultation" column. No visible error.
- **Suggested fix:** Change body to `{ id: id, stage: 'closed_won' }` and remove the silent `.catch(function(){})`.

### [P1] BUG-2026-11-11-08 — Content editor save/publish always 400s + date field lost

- **File:** `thomas.html:2904, 2947, 2963, 2967, 2990` vs `api/dashboard/content.js:58, 62, 78, 86`
- **Category:** api-contract-mismatch (missing body.id, field drift)
- **Description:** Save/publish/update calls build the path as `content?id=X` and omit `id` from the body — `content.js:78` returns 400 "ID required". Additionally the client reads/writes `scheduled_date` and `created_at` while the server stores `scheduledDate` / `createdAt` (lines 58, 62, 86), so the date input loses its value on save.
- **Failure scenario:** On the Content tab, edit any scheduled post → Save. Alert: `Error: ID required`. Clicking **Publish** does the same.
- **Suggested fix:** Add `req.query.id` fallback in `content.js:78`. Rename client-side `scheduled_date`/`created_at` to `scheduledDate`/`createdAt`.

### [P1] BUG-2026-11-11-09 — Ad spend logging always 400s; totals and table show blank/$0

- **File:** `thomas.html:3013-3138, 3109-3110` vs `api/dashboard/adspend.js:57-66, 93-94`
- **Category:** api-contract-mismatch (validation + field drift)
- **Description:** The form POSTs `{ campaign, amount, ... }`. The server's POST validator at line 57 reads `body.spend` and returns 400 "Date and spend required" when `spend` is undefined — which it always is. Even if that were fixed, the server would store `campaign` as `undefined` (it only reads `body.campaignName`) and `spend` as `0`. On the read side the client reads `e.amount` and `e.campaign` in the summary totals, the entries table, and the CSV export, while the server returns `spend` and `campaignName`.
- **Failure scenario:** On the Ad Spend tab click **Log Ad Spend**, fill in all fields, Save. Alert: `Error: Date and spend required`. Even for any rows that pre-date this bug, the "Total Spend" tile and the Entries table show `$0.00` and `-`.
- **Suggested fix:** Rename the client-side keys to `campaignName` / `spend` (lines 3109-3110) and the eight read sites that reference `e.campaign` / `e.amount`.

### [P2] BUG-2026-11-11-10 — Shared JS files loaded with mismatched `?v=` across pages

- **File:** `index.html:845`, `pricing.html:895`, `shop.html:841`, `product.html:822`, `chs.html:1050`
- **Category:** cache-busting drift
- **Description:** The same JS file is loaded with different cache-busting versions on different pages:
  - `js/quiz.js` — `index.html?v=2` vs `pricing.html?v=3`
  - `js/shop.js` — `shop.html?v=1` vs `product.html?v=2`
  - `js/main.js` — every public page uses `?v=2` **except `chs.html`**, which omits the query entirely.
- **Failure scenario:** After the quiz logic is next updated, a visitor who first loads `/pricing` and then navigates to `/` (or vice versa) will keep running the stale cached copy until a hard-refresh. The chs page will keep serving the stale `main.js` indefinitely.
- **Suggested fix:** Unify on one version per file across all pages, and bump when editing the file.

### [P2] BUG-2026-11-11-11 — Swallowed error on Convert to Client hides real failures

- **File:** `thomas.html:1242`
- **Category:** silent-failure
- **Description:** `.catch(function() {})` on the pipeline PUT inside `convertToClient` swallows every error without a toast or console log. This masks BUG-07 and will also mask future regressions on the same path.
- **Failure scenario:** Already covered by BUG-07 — listed separately because it's a distinct quality issue (silent failure vs. the underlying contract mismatch) and should be fixed alongside the real bug, not instead of it.
- **Suggested fix:** Replace `.catch(function(){})` with the same `alert('Error: ' + err.message)` pattern used by `saveClient`/`savePipeline`.
